# RFC 8455 — Terminology for Benchmarking SDN Controller Performance

Source read in full: `rfc/rfc8455.txt` (October 2018, Informational, BMWG). Companion of
RFC 8456 (methodology; see `rfc8456.md` for the procedures and formulas). Extends the
vocabulary of RFC 7426 (SDN layers and architecture terminology).

## 1. Purpose

Defines, protocol-independently, the terms used to benchmark an SDN controller as a black
box: the SDN terms (flow, northbound/southbound interface, controller forwarding table,
proactive vs reactive flow provisioning, path, standalone vs cluster mode, asynchronous
message, test traffic generator, leaf-spine topology), the test-setup terms (number of network
devices, trial repetition, trial duration, number of cluster nodes), and the benchmarks
themselves grouped into performance (8), scalability (3), security (2) and reliability (2),
each with definition, discussion and measurement units. It also fixes the two reference test
setups (controller standalone or in a cluster, between an application-plane test emulator on
interface I2 and a forwarding-plane test emulator on I1) and the coverage table that places
each benchmark in the setup, operational or teardown phase of a controller's lifecycle.
For Arcana it supplies the names and definitions under which the console (the controller),
its JSON API (northbound) and cblink (southbound) should be measured and reported.

## 2. Content

### 2.1 SDN terms (§2.1)
- **Flow (2.1.1)**: as "microflow" in RFC 4689 §3.1.5 — packets sharing source/destination
  address, source/destination port, or any combination.
- **Northbound Interface (2.1.2)**: RFC 7426's "service interface"; lets applications and
  orchestration program and retrieve network information through the controller.
- **Southbound Interface (2.1.3)**: the API the controller provides to interact with SDN
  nodes to define forwarding behaviour dynamically.
- **Controller Forwarding Table (2.1.4)**: flow entries learned from data-plane traffic or
  provisioned statically and distributed southbound; aging applies only to learned entries.
- **Proactive Flow Provisioning Mode (2.1.5)**: flows programmed into devices from entries
  provisioned through the northbound interface.
- **Reactive Flow Provisioning Mode (2.1.6)**: flows programmed in response to traffic
  received from devices via the southbound interface.
- **Path (2.1.7)**: RFC 2330 §5.
- **Standalone Mode (2.1.8)**: one controller, no redundancy/HA/failover; may manage several
  domains.
- **Cluster/Redundancy Mode (2.1.9)**: two or more controllers for load sharing and/or HA,
  active/standby or active/active.
- **Asynchronous Message (2.1.10)**: any message from a network device generated for a
  network event (flow setup request, link down…) to which the controller must respond; the
  device is non-blocking meanwhile.
- **Test Traffic Generator (2.1.11)**: generates/receives network traffic, attached to
  network devices.
- **Leaf-Spine Topology (2.1.12)**: two layers, every leaf connected to every spine.

### 2.2 Test configuration/setup terms (§2.2)
- **Number of Network Devices (2.2.1)**: devices in the test topology (real or emulated).
  Unit: count.
- **Trial Repetition (2.2.2)**: iterations; SHOULD be at least 10. Unit: trials.
- **Trial Duration (2.2.3)**: stop criterion per iteration; trials not completed in it are
  incomplete. Unit: seconds.
- **Number of Cluster Nodes (2.2.4)**: controllers in the cluster, MUST be > 1 for cluster
  tests. Unit: nodes.

### 2.3 Benchmarking terms (§2.3)

**Performance (2.3.1)** — all in milliseconds unless noted:
1. **Network Topology Discovery Time (2.3.1.1)**: interval from the first discovery message
   sent by the controller at its southbound interface until all features of the static
   topology are determined; a topology (tree/mesh/linear) of N nodes is presented and the
   discovery is awaited; assumes the controller discovers by protocol messages.
2. **Asynchronous Message Processing Time (2.3.1.2)**: from an asynchronous message sent by a
   device (after discovery completed) until the controller's response at the southbound
   interface; one message at a time from every device for the trial duration; assumes the
   controller responds.
3. **Asynchronous Message Processing Rate (2.3.1.3)**: responses per second to asynchronous
   messages that are valid and productive (non-trivial); measured by sending at the rate the
   controller can process without drops. Qualified as **Loss-Free** rate (incoming count ==
   response count) and **Maximum** rate (highest response rate regardless of loss); found by
   starting at the maximum sending rate and decreasing by STEP, or starting low and
   increasing. Unit: messages/s.
4. **Reactive Path Provisioning Time (2.3.1.4)**: from the first flow provisioning request
   received by the controller until the last flow provisioning response sent, southbound, for
   a path set up because traffic arrived.
5. **Proactive Path Provisioning Time (2.3.1.5)**: from the first proactive flow provisioned
   at the northbound interface until the last flow provisioning command sent southbound.
6. **Reactive Path Provisioning Rate (2.3.1.6)**: maximum number of independent paths
   established per second reactively, counted southbound, for requests received in the
   trial; obtained by unique src/dst flows and frames received at the destination device.
   Unit: paths/s.
7. **Proactive Path Provisioning Rate (2.3.1.7)**: same, for paths provisioned northbound.
   Unit: paths/s.
8. **Network Topology Change Detection Time (2.3.1.8)**: from a topology change notification
   received southbound until the first topology rediscovery message sent southbound.

**Scalability (2.3.2)**:
1. **Control Sessions Capacity (2.3.2.1)**: maximum number of control sessions the
   controller accepts from devices before it fails. Unit: sessions.
2. **Network Discovery Size (2.3.2.2)**: largest network (nodes and links) the controller can
   discover, found by growing/shrinking the offered topology. Unit: nodes and links.
3. **Forwarding Table Capacity (2.3.2.3)**: maximum flow entries managed in the controller's
   forwarding table, filled reactively or proactively until full. Unit: entries.

**Security (2.3.3)** — units: deviation from baseline:
1. **Exception Handling (2.3.3.1)**: deviation of the performance benchmarks when devices send
   error/failure messages; performed after baselines.
2. **Handling Denial-of-Service Attacks (2.3.3.2)**: deviation of performance and scalability
   benchmarks under DoS against the controller; after baselines.

**Reliability (2.3.4)**:
1. **Controller Failover Time (2.3.4.1)**: in redundancy mode, from bringing down the active
   controller until the first rediscovery message from the new controller at its southbound
   interface. ms.
2. **Network Re-provisioning Time (2.3.4.2)**: from the first failure notification received
   until the last flow re-provisioning message sent southbound; assumes a redundant path
   exists and the controller did not pre-provision it. ms.

### 2.4 Test setups (§3)
- Standalone (Figure 1): Application-Plane Test Emulator (Application, Service) —(I2,
  northbound)— SDN Controller (DUT) —(I1, southbound)— Forwarding-Plane Test Emulator with
  Network Devices 1..n (meshed, links l0..ln) and Test Traffic Generators TP1, TP2 attached to
  devices 1 and n.
- Cluster (Figure 2): same, DUT = SDN Controller 1 …n joined by an E/W interface.

### 2.5 Test coverage (§4)
| Lifecycle | Speed | Scalability | Reliability |
|---|---|---|---|
| Setup | Topology Discovery Time; Reactive/Proactive Path Provisioning Time; Reactive/Proactive Path Provisioning Rate | Network Discovery Size | — |
| Operational | Maximum and Loss-Free Asynchronous Message Processing Rate; Asynchronous Message Processing Time | Control Sessions Capacity; Forwarding Table Capacity | Topology Change Detection Time; Exception Handling; DoS Handling; Network Re-provisioning Time |
| Teardown | — | — | Controller Failover Time |

### 2.6 Security considerations (§6)
Lab only, isolated; the benchmark network MUST NOT connect to production or misroute into the
management network; black-box measurement only; no benchmarking-specific capabilities in the
controller; security implications identical in lab and production.

## 3. How the terms map to Arcana

| RFC 8455 term | Arcana |
|---|---|
| SDN Controller (DUT) | the console: Kore + `arcana-console.so` (plus the PWA as an application) |
| Northbound interface (I2) | the console's JSON API (`docs/openapi.yaml`): `/api/servers/*`, SD-WAN documents, apply/plan, jobs |
| Southbound interface (I1) | cblink: the `arcana` family over TCP+mTLS (or AF_UNIX) to `arcana-agent`; do/dump/notification/stream |
| Network Device | a FreeBSD host (or vnet jail) running `arcana-agent`; an SD-WAN edge |
| Flow | an SD-WAN application flow (ipfw classification rule + policy table entry); a flowspec rule |
| Controller Forwarding Table | the SD-WAN document's compiled rules and steering tables the console keeps per edge (`sdwan-rules`, `sdwan-steer`), plus route/ipfw state read back |
| Proactive flow provisioning | the only mode Arcana has: the console compiles and applies rules/steering from the document |
| Reactive flow provisioning | none in the controller; the edge's local failover (sdwan-steer candidates re-evaluated on probe/BFD state) is edge-local, not a controller action |
| Asynchronous message | cblink `event` notifications and streams from agents: `sdwan-tunnel` (probe/BFD up/down), `sdwan-tca`, faults, `sdwan-ids`, interface/route changes |
| Path | a tunnel (gre/gif/geneve/wg/uswe) in a service FIB, or the UNI→edge→tunnel→edge→UNI chain |
| Standalone mode | today's console (one process, one host) |
| Cluster mode | not available (open decision: console HA) |
| Test traffic generator | a jail with `ping`/`iperf3`/a small UDP sequence generator; the STAMP sender |
| Leaf-spine topology | hub-and-spoke or full-mesh SD-WAN services over vnet jails + epairs/bridges |
| Topology discovery | enrolment + `hello`/`network`/`l2`/`interfaces` reads until the map (USING.md "The network map") is complete |
| Topology change detection | route-socket/interface events from the agent → console marks the map/path |
| Network re-provisioning | tunnel fault → steering recompute → `sdwan-steer` table swap on the edges |
| Controller failover | N/A until a second console exists |

Measurement points: the RFC wants observations at the test emulator's interfaces, not inside
the DUT. Arcana's trace model (every reply carries timed steps; `events` carry `t`) is an
inside view; cblink is mTLS so a wire tap at I1 sees only TLS records. A harness should
therefore (a) time at the *agents* (their own cblink server logs with timestamps, which are
the "forwarding-plane emulator" side) and at the *API client*, and (b) use data-plane
observation (sequence-numbered frames at TP2) wherever the RFC does. Report the measurement
points as §4.5 of RFC 8456 requires.

## 4. Cannot be mapped / not applicable
- **Reactive provisioning (time and rate)**: Arcana devices do not send "flow miss" to the
  controller; there is no packet-in. The closest analogue is edge-local failover, which is not
  a controller benchmark. Report "not applicable" rather than inventing one — or define the
  controller's reaction to a `sdwan-tunnel` event (recompute + push steering) as an
  asynchronous-message benchmark instead.
- **Controller Failover Time**: no cluster mode.
- **Control Sessions Capacity**: the console is the cblink *client* (it dials agents), so the
  "sessions a controller accepts" becomes "sessions the console keeps open"; same unit,
  inverted direction; the agent side (sessions an agent accepts) is a device benchmark, not a
  controller one.
- **Forwarding table aging**: no learned entries, so no aging.
- **Leaf-spine** is a data-centre topology; use it for the lab layout only loosely.

## 5. Checklist (terms Arcana's benchmark reports must define exactly as RFC 8455)
1. State the DUT (console version), northbound (API version), southbound (cblink + family
   version), mode (standalone), connection setup (mTLS).
2. Define the network devices used (hosts vs vnet jails, agent version) and their count.
3. Trial repetition ≥ 10; trial duration stated per test.
4. Use the RFC's exact names and units for each reported benchmark (ms, messages/s, paths/s,
   sessions, nodes+links, entries, deviation from baseline).
5. Define what an "asynchronous message" is in Arcana (which cblink notifications) and what
   counts as a "valid and productive" response from the console.
6. Define "path" and "flow" for each test (tunnel, UNI-to-UNI chain, application flow).
7. Define topology discovery completion (map equals deployed topology: hosts, interfaces,
   tunnels, L2 links).
8. Mark the not-applicable benchmarks explicitly (reactive provisioning, failover) with the
   reason.
9. Report measurement points (agent side, API client, data plane) per test.
10. Keep the benchmark lab isolated (jails on one host, no production interface in the
    bridge).

## 6. Open decisions and trade-offs
- Whether to treat the edge-local failover as a **device** benchmark (Arcana-specific,
  outside this RFC) or to add a console-driven re-steer as the "reactive" path so RFC 8455's
  reactive benchmarks apply. The latter adds a controller round trip the design deliberately
  avoided.
- Whether "topology" for discovery includes L2 (bridges, LLDP-less epair links the agent
  cannot see) or only what agents report (interfaces, routes, tunnels, BFD neighbours).
- Whether the console's *job* model (changes queued and polled once a second) is part of the
  measured provisioning time (it is, from the API client's point of view; the 1 s poll
  granularity dominates small numbers — consider an event-driven job completion for
  benchmarking honesty).
- Cluster mode: if console HA is ever built (two Kore processes sharing the data directory /
  CA), the cluster terms and failover benchmark become applicable.
