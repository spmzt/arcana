# RFC 9732 — A Framework for NRP-Based Enhanced Virtual Private Networks

Read in full: 2065 lines, fetched from https://www.rfc-editor.org/rfc/rfc9732.txt (HTTP 200).
Informational, March 2025. Dong, Bryant, Li, Miyasaka, Lee. Normative reference: RFC 9543.
Local copy: `scratchpad/rfc/rfc9732.txt`.

## 1. Purpose

RFC 9732 is the realisation-side companion of RFC 9543. It defines the *enhanced VPN*: a
conventional overlay VPN (L2VPN, L3VPN, EVPN, pseudowire) integrated with a Network
Resource Partition (NRP) in the underlay so that the service gets guaranteed resources,
bounded latency/jitter, low loss and limited interaction with other services, beyond what
overlays alone give. It lists the requirements (performance guarantees, isolation/limited
interaction, integration with resources and service functions, dynamic change, customised
control, overlay applicability, inter-domain/inter-layer), the layered architecture
(physical infrastructure → NRPs → enhanced VPNs under a centralised controller), the
candidate technologies per plane (FlexE, dedicated queues, TSN; DetNet, MPLS-TE, SR, new
encapsulations; RSVP-TE/SR control; service YANG models), how NRP-based enhanced VPNs
realise RFC 9543 slices (NRP planning, creation, service provisioning, steering), the
scalability trade-offs (state in packets vs in network vs hybrid), resiliency, OAM,
telemetry and security. It also names areas for new work (NRP identifiers, NRP YANG,
scalability).

## 2. Architecture and terminology (complete)

### 2.1 Terminology (§2)
- **VPN**: overlay providing connectivity and traffic separation between customers (IP VPN RFC 2764/4364, L2VPN RFC 4664, EVPN RFC 7432).
- **Enhanced VPN**: a VPN that makes additional service-specific commitments; **NRP-based enhanced VPN** = a VPN integrated with an NRP.
- **NRP** (from RFC 9543): subset of buffer/queuing/scheduling resources and policies on each of a connected set of links; associated with a dedicated or shared topology.
- **Network slice service**: may be delivered by one or more NRP-based enhanced VPNs.
- **Tenant**: the enhanced VPN customer. Also SLA/SLO/SLE (RFC 9543), ACTN, DetNet, FlexE, TSN, VN.

### 2.2 Requirements (§3)
- **Performance guarantees (§3.1)**: guaranteed max loss (priorities, queue sizes, discard policies; zero congestion loss is DetNet/TSN's goal; media/interface failures need duplication over diverse paths), guaranteed max delay (DetNet plus underlay enhancements), guaranteed max delay variation (RFC 8578 cases; time transfer). Apply to conformant traffic; out-of-profile per RFC 7297 §3.6. Four illustrative service types: **best effort**, **assured bandwidth** (over-provisioning or TE-LSP reservations; per-VPN TE-LSPs not widely deployed for scale reasons; aggregation reduces assurance), **guaranteed latency** (upper bound matters more than minimum; TSN, FlexE, DetNet help), **enhanced delivery** (eliminate loss on equipment/media failure by sending copies over multiple paths).
- **Interaction between services (§3.2)**: *traffic isolation* (SLE per RFC 9543 §8.1; no delivery to other customers; RFC 4176, RFC 7297 §3.8; encryption at access and between PEs may be requested; exact behaviour to be specified in the request); *limited interaction* = controlled-load service (RFC 2211): either explicit SLOs or an SLE "behave like a lightly loaded best-effort network"; does not cover link errors. *Realisation*: VPN/multi-tenant techniques for separation; QoS/TE/security/planning for limited interaction; reserving data-plane resources per service or per group raises scalability concerns, so trade-offs; a dedicated physical network for the strictest cases vs packet-layer sharing with temporary dedication.
- **Integration with resources and service functions (§3.3)**: flexible, scalable overlay↔underlay integration; SFC (RFC 7665) functions may be part of the NRP; **abstraction** (RFC 7926, ACTN RFC 8453) may sit between overlay and underlay.
- **Dynamic changes (§3.4)**: create/modify/remove on demand including scheduled; changes to one enhanced VPN must not disrupt another; closed-loop optimisation over the lifetime; changes to the underlay managed without disruption.
- **Customised control (§3.5)**: optionally expose filtered/aggregated NRP info to the customer, let them specify paths/constraints inside the NRP, or give their controller an interface; bounded to their own enhanced VPN.
- **Overlay applicability (§3.6)**: pseudowires (RFC 3985), L2VPN, EVPN, L3VPN.
- **Inter-domain / inter-layer (§3.7)**: multi-AS and packet-over-optical coordination; reuse RFC 4364 multi-domain mechanisms with enhancements.

### 2.3 Architecture (§4)
Each enhanced VPN = overlay VPN + mapping to one NRP; one NRP may serve several enhanced VPNs. Design considerations:
- **Enhanced data plane**: latency/jitter, loss, resource isolation (bandwidth guarantee), and *a mechanism to associate a packet with the NRP's resources*.
- **Control plane**: collect topology and resources (to nodes and/or controller); create NRPs; distribute NRP attributes; compute and set up paths in each NRP; map services to NRPs; detect SLA-violation risk and act; balance per-packet vs per-node state.
- **Management plane**: provider↔customer interface for operations without awareness of other customers; capability exposure; lifecycle (create, modify, assure/monitor, decommission); OAM for NRPs and for services; telemetry for planning and for SLA fulfilment.
- **Layered architecture (§4.1, Fig. 1)**: physical infrastructure partitions link/node resources (each subset a virtual link/node) → NRPs (dedicated or shared resources; customised logical topology; per node/link a set of local resources; integration of topology and resources) → enhanced VPNs mapped to NRPs. NRP is the essential scaling construct (eliminates per-service per-path state). Controller creates NRPs, instructs nodes to allocate, provisions services; a distributed control plane may distribute NRP attributes. Holistic planning across customers; dynamic control within an NRP.
- **Connectivity types (§4.2)**: MP2MP VPNs need MP2MP NRP connectivity; some guarantees apply to specific endpoint pairs needing engineered P2P paths.
- **Application-specific data (§4.3)**: Ethernet via PW over MPLS (RFC 4448) or L2TPv3 (RFC 3931/4719).
- **Scalable service mapping (§4.4)**: no per-service state in the core; enhanced VPN state must be constrained; expect few enhanced VPNs; aggregate services with the same behaviour onto the same NRP ([NRP-SCALABILITY]).

### 2.4 Candidate technologies (§5)
- **§5.1 Underlay forwarding resource partitioning**: **FlexE** (fixed-bandwidth channels on Ethernet, bonding; link-level only; no sharing between channels; downstream queuing must preserve separation); **Dedicated queues** (Diffserv RFC 2475/4594 insufficient: too few markers (8 MPLS TCs), per-hop priority only, no quantitative reservation; steer to dedicated input/output queues per enhanced VPN or group; depends on router queue counts); **TSN** (time slots; TSN payload opaque over L3 PW, so carry TSN via DetNet).
- **§5.2 Network-layer encapsulation and forwarding**: **DetNet** (RFC 8655; copies over paths, upper-bound latency; IP RFC 8939 or MPLS RFC 8964 data planes); **MPLS-TE** (RFC 2702/3209 per-LSP bandwidth; scalability/management concerns); **SR** (RFC 8402; state in packet; TC bits only for priority; needs resource-aware segments [RESOURCE-AWARE-SEGMENTS] to steer to queues; "queue" as an abstraction for any underlay mechanism; SID groups can represent MP2MP); **New encapsulation extensions** (dedicated NRP identifiers, e.g. IPv6 option [IPv6-NRP-OPTION]).
- **§5.3 Non-packet data plane**: optical: bandwidth, physical isolation, predictable latency, measurable loss, easy flow identification; long-term end-to-end allocation; cost shared when an NRP hosts several services.
- **§5.4 Control plane**: hybrid of centralised controller (on-demand provisioning, global optimisation) and distributed protocols (scale, reliability, fast reaction, recovery). Functions: topology/resource collection (IGP, BGP-LS RFC 9552), NRP creation and attribute distribution (needs protocol extensions), service→NRP mapping, path computation (headend or PCE RFC 4655). Path setup candidates: RSVP-TE (reservations; scaling concerns) and SR (no signalling of reservations; controller plans and instructs nodes; SR Policy RFC 9256 to headends). Service→NRP mapping by packet characteristics or by VPN route attributes.
- **§5.5 Management plane**: lifecycle; 5G TN example (3GPP management system gives parameters, needs capability/status exposure); in-place modification (add/remove endpoints, change characteristics) with feasibility assessment and non-disruptive execution, no disruption to other services; delegation to the customer as a virtual network (cannot exceed virtual link capacities; may set metrics; management of the VN may request changes when near capacity or under-used).
- **§5.6 Service data models**: L3SM RFC 8299, L2SM RFC 8466, ACTN VN RFC 9731 (customer view); L3NM RFC 9182, L2NM RFC 9291 (operator view); SAP RFC 9408; PM RFC 9375; NRP YANG [NRP-YANG] (controller and device); augmentation expected.

### 2.5 Applicability to slice realisation (§6)
Technology-agnostic slice service model [NETWORK-SLICE-YANG] carries SDPs, connectivity, SLOs, SLEs; SDP maps to CE, PE, CE port or PE customer port = enhanced VPN endpoint. **NRP planning (§6.1)**: dedicated resources to avoid interference; topology, bandwidth, latency, reliability; controller computes a logical topology and the resources per node/link considering existing NRPs. **NRP creation (§6.2)**: nodes/links allocate resources (§5.1 mechanisms); data-plane identifiers for the NRP's resources provisioned (resource-aware SR segments, SR-for-enhanced-VPN, or a dedicated Resource ID in an IPv6 option); nodes may distribute logical topology, resource info and Resource ID in the control plane; TE or shortest paths computed within the NRP and NRP-specific forwarding entries installed. **Service provisioning (§6.3)**: overlay VPN created, then mapped to an NRP as virtual underlay. **Steering (§6.4)**: classify at the edge by operator policy; forward on TE paths or shortest paths of the NRP's topology using the NRP's resources.

### 2.6 Scalability (§7)
Three ways to hold the extra state: in the packet (SR: bigger headers, "latent state" of NRP-specific segments), in the network (RSVP-TE or SDN-installed per-path state incl. queuing policy), hybrid (binding SIDs; loose source routing; SRv6 compression). Aggregation (NRP) is the main lever; §7.1 SR maximum SID depth (RFC 8491); §7.2 RSVP-TE scaling (RFC 8370, RFC 8577); §7.3 SDN: per-node control channel to controller (fewer channels than neighbours) but processing burden and single point of failure at the controller.

### 2.7 Enhanced resiliency (§8)
Lifecycle modification and garbage collection of fragmented resources; imposed-path systems allow atomic headend transition but must verify the new path meets the SLA first; deadlocks from fragmentation (global concurrent optimisation RFC 5557/7399 helps; partly commercial); open issues: packets overtaking when latency drops during a transition, transient latency variation; failures: fast reroute (~50 ms RFC 5654) vs N+1 delivery vs DetNet replication/culling; micro-loops of best-effort traffic during reconvergence must be shielded from or prevented.

### 2.8 Manageability (§9), operations (§10), security (§11)
OAM: instrument the NRP so the operator knows committed resources perform; **OAM packets must follow the same path and resources as the service packets**; customer overlay OAM transparent to the operator; provider overlay OAM non-intrusive (RFC 8403 for SR). Telemetry (RFC 9232): NRP data for planning; per-service data for SLA analytics. Operations: coexistence with conventional VPNs; decision info on the management interface; models of §5.6 for lifecycle. Security: same as VPNs plus delay attacks by bursty tenants; operator monitoring may detect attacks early; customers should encrypt; privacy as for VPNs; no extra privacy guarantee.

## 3. How Arcana could realise each element on FreeBSD

Arcana's SD-WAN service is already an "assured bandwidth" NRP-based enhanced VPN in this RFC's terms: overlay = per-service FIB + tunnels between edges (L3VPN-like, A2A); NRP = the dummynet objects the console emits in `sdwan-rules` ("objects": `pipe N config …`, `queue N config …`, `sched N config …`) on each edge plus the tunnel set; control = console (centralised) + BIRD (distributed); management = console API, OpenAPI, events.

| RFC 9732 element | Arcana realisation on FreeBSD |
|---|---|
| Overlay VPN (L3) | Service FIB per edge (`setfib`, `net.fibs` tunable), routes from UNIs (static/BGP/OSPF via the service's BIRD instance, `kernel table N`), tunnels gre/gif/wg (IP) between edges. |
| Overlay VPN (L2, PW/EVPN) | geneve(4)/vxlan(4) tunnels bridged with `if_bridge` (+`if_vlan`) to UNI ports: an L2 service. No EVPN control plane in BIRD on FreeBSD worth relying on (BIRD lacks EVPN); MAC learning is the bridge's; static flood lists. L2TPv3/PW over MPLS: no. |
| NRP: link resource partition | Per Arcana-controlled link (WAN interface, tunnel interface, UNI): one `sched` (WF2Q+ or QFQ) with `bw` = link rate, one `queue` per NRP with `weight` for its share, `slots`/`bytes` for its buffer; `prio` scheduler for a latency tier. Ingress policing per NRP: `pipe` or `ng_car`. The NRP's "resource" is the queue number; its "identifier" on the wire is DSCP and/or the tunnel (see below). |
| NRP: logical topology | Console graph: which edges, which WAN interfaces, which tunnels belong to the NRP (dedicated tunnel set = dedicated topology; shared tunnels with distinct queues = shared topology). |
| Packet↔NRP association (data plane) | At the ingress edge: ipfw classification (`sdwan-rules`: tables, `lookup`, `dscp`, 5-tuple) → `setdscp` (NRP class) + `setfib` (service) + `queue N` (NRP queue on this hop) + steering via table/`fwd`/route to the NRP's tunnel. On transit Arcana hops: `dscp` match → `queue N`; inner DSCP copied to outer by gre/gif (tos copy); wg: DSCP of outer settable per interface policy only (wg(4) copies ECN, DSCP handling limited — to verify). |
| FlexE | Not available (hardware). Nearest: dedicated physical WAN interface per NRP tier. |
| Dedicated queues | Yes: dummynet queues (up to 65535 per host) on every link, but like Diffserv the *wire marker* is DSCP (64) unless a tunnel per NRP is used; the RFC's "queue as an abstraction" (§5.2.3) is exactly dummynet's queue object. |
| TSN | No. |
| DetNet | Only the DetNet IP data plane (RFC 8939) flow identification with resource allocation, no PREOF — see rfc8655.md/rfc9938.md. |
| MPLS-TE, SR-MPLS, SRv6, resource-aware segments, IPv6 NRP option | No kernel support; cannot be used or processed. Explicit paths are expressed as tunnels + per-FIB static routes on Arcana hops. |
| Non-packet (optical) | Out of scope; an underlay Arcana rides on. |
| Control plane: topology/resource collection | Agents report interfaces, link rates, neighbours (netlink), routes, nexthop groups, BIRD protocols/BFD, dummynet objects; the console assembles the topology. No IGP-TE/BGP-LS (BIRD does not speak BGP-LS). |
| NRP creation and attribute distribution | Console → agents over cblink (`sdwan-rules` objects, tunnel jobs); should become an explicit `nrp` object in the contract (planned YANG: the NRP YANG draft's device part — queues, link partitions — maps well). |
| Path computation in each NRP | Console: constrained selection of tunnels/edges per service using measured delay/loss (probes) and committed bandwidth (admission ledger); the RFC's "PCE" role. Headend-local: the agent's `sdwan-steer` candidate ordering with failover is a tiny headend path selector. |
| Service → NRP mapping by packet characteristics | ipfw rules at the UNI (`sdwan-rules`). |
| Service → NRP mapping by route attributes | BIRD filters: routes carrying a BGP community/extended community exported to a given kernel table (`protocol kernel { table T; kernel table N; export where (C, x) ~ bgp_community }`) → the FIB (and thereby the tunnel set) of the NRP. Distributed mapping without new protocols. |
| Path setup: RSVP-TE / SR Policy | Not available. Equivalent: tunnels pinned per NRP, static routes per FIB, ECMP with weights (`route add -weight`, nexthop groups) for load spread. |
| SLA-violation risk detection and correction | Probe TCAs and BFD (119-1) → console re-steers (`sdwan-steer` rewrite) or agent fails over locally; closed loop already present for up/down, to be extended to delay/loss thresholds. |
| Management plane interface, lifecycle | Console API; in-place modification: the agent applies `sdwan-rules` by filling a disabled ipfw set then enabling it (atomic swap), dummynet objects re-`config`ed in place (dummynet keeps queue state across reconfig), BIRD `configure` reload; non-disruptive by construction for most changes. |
| Capability exposure to the customer | Console per-tenant view: SLO/SLE catalogue, measured performance, not the topology. |
| Delegated virtual network (customer sets metrics) | Possible: per-service BIRD instance config exposed in part (metrics/preferences per UNI route); bandwidth caps enforced by the NRP queues regardless. |
| Service data models | Northbound: L3SM (RFC 8299)/L2SM (RFC 8466) for customers, L3NM (RFC 9182)/L2NM (RFC 9291) for the operator view of each edge, SAP (RFC 9408) for UNIs, PM (RFC 9375) for probes/counters, slice service YANG, NRP YANG. Device-level (cblink redesign): ietf-interfaces, ietf-ip, ietf-routing (+FIB as routing-instance), an Arcana ipfw/dummynet module, tunnel modules, a BIRD-config module. |
| NRP planning considering existing NRPs | Console ledger per link: committed rates of all queues ≤ `sched bw`; refuse or suggest. |
| Steering and forwarding within NRP | Shortest path = FIB lookup in the service table; "TE path" = the chosen tunnel. |
| Scalability | State per edge per service: 1 FIB, 1 BIRD process, 1 ipfw table set, N dummynet queues, M tunnels. Aggregation lever: NRP tiers shared by many services (one queue set per tier per link), one BIRD instance per *tier* instead of per service is impossible (routes must stay per FIB) but a route reflector (119-5) removes the full mesh. |
| Enhanced resiliency: atomic transition | ipfw set swap and table replacement are atomic; verifying the new path before moving traffic = probing the candidate tunnel first (probes run on all tunnels, not only the active one). Overtaking/reordering on switch: unavoidable; document it as a transient. Micro-loops: BIRD/OSPF behaviour; keep best-effort in FIB 0 away from service FIBs. |
| Enhanced delivery (copies over paths) | Not in kernel for IP (no PREOF). Partial: 1+1 at L2 via `ng_hub`/`ng_one2many(all)` replication into two tunnels, but no elimination; a user-space eliminator (divert socket) is possible, slow. Otherwise fast local failover (BFD 100–300 ms ×3). |
| OAM on the same path/resources | Probes already use the tunnel's FIB and a `dscp`; set the probe DSCP to the construct's DSCP and classify probes into the same dummynet queue so OAM shares path *and* resources. Customer overlay OAM passes transparently. |
| Telemetry | Events stream, `sdwan` samples/history, ipfw counters, dummynet queue statistics (`ipfw queue show`: length, drops), `ng_netflow` → IPFIX (NetFlow v5/v9/IPFIX export via netgraph) for per-service flow records. |
| Security: delay attacks by other tenants | Per-tenant policing at the UNI (pipe/ng_car), WF2Q+ isolation of shares, monitoring. Same limits as RFC 9543 notes §4. |

## 4. Cannot be mapped (and why)

1. **FlexE, TSN, time-gated or credit-based shapers** — hardware/link-layer features absent from FreeBSD; no kernel work allowed.
2. **MPLS-TE, SR-MPLS, SRv6, resource-aware SR segments, binding SIDs, SRv6 compression** — no MPLS/SR data plane; BIRD can carry MPLS/VPN AFI routes but the kernel cannot forward labels (119-4 decision).
3. **IPv6 NRP/VTN-ID option, any "new encapsulation extension" (§5.2.4)** — ipfw and the IPv6 stack do not act on such options; would be a kernel module.
4. **RSVP-TE signalling, PCEP, BGP-LS, IGP-TE** — none in BIRD on FreeBSD/not implemented; topology must come from agents (Arcana-own), which is fine inside our domain but gives no view of the carrier underlay.
5. **DetNet "enhanced delivery" (replication + elimination) at L3** — no PREOF in kernel; the DetNet IP data plane itself has none.
6. **Quantitative guaranteed latency / jitter (§3.1 "guaranteed latency" service)** — only on Arcana-owned hops and only as engineering estimates (queue bytes / rate), not guarantees; nothing across a third-party underlay.
7. **L2TPv3/PW-over-MPLS pseudowires (§4.3)** — kernel has no L2TPv3 or MPLS PW; L2 is geneve/vxlan + bridge instead.
8. **EVPN control plane** — BIRD lacks EVPN; FRR could (ports) but is not Arcana's chosen daemon; static L2 flood lists otherwise.
9. **Per-enhanced-VPN dedicated hardware queues** (§5.1.2 "some routers have a large number of queues") — dummynet queues are software; NIC TX rings are not assignable per class from user space.
10. **Multi-domain enhanced VPN (§3.7)** — no inter-console protocol; RFC 4364 option B/C style interconnect needs MPLS.
11. **Global concurrent optimisation / defragmentation (§8)** — no path state fragmentation problem exists because there is no per-path reservation in transit; only the console's bandwidth ledger per link, which it can re-pack. Not a gap, but the RFC's mechanism does not apply.
12. **Optical/non-packet NRP** — out of scope.

## 5. Requirements and recommendations checklist

1. Guarantees apply to conformant traffic; define out-of-profile handling separately (§3.1, RFC 7297 §3.6).
2. Support the service spectrum: best effort, assured bandwidth, guaranteed latency (upper bound), enhanced delivery; mixtures allowed (§3.1).
3. Treat traffic isolation as an SLE: no delivery to other customers; optional encryption at access and PE–PE; the request must spell out expected behaviour so assurance feedback is meaningful (§3.2.1).
4. Offer limited interaction either as explicit SLOs or as a controlled-load SLE (RFC 2211) (§3.2.2).
5. Realise isolation with routing/authorisation configuration, and limited interaction with QoS/TE/planning tools; reserve data-plane resources per service or per group; balance against scalability (§3.2.3).
6. Integrate overlay with underlay resources and service functions flexibly and scalably; allow abstraction (RFC 7926/ACTN) between them (§3.3).
7. Create/modify/remove on demand and on schedule; a change must not disrupt other enhanced VPNs; run closed-loop optimisation so delivered service matches the SLA (§3.4).
8. Optionally expose filtered NRP information and bounded control to the customer or its controller (§3.5).
9. Apply to PW, L2VPN, EVPN, L3VPN overlays (§3.6); support multi-domain/multi-layer coordination where needed (§3.7).
10. Data plane must provide latency/jitter, loss, bandwidth isolation, and a packet↔NRP association mechanism (§4).
11. Control plane must collect topology/resources, create NRPs, distribute NRP attributes, compute/set up paths per NRP, map services to NRPs, detect SLA-violation risk and act, and balance per-packet vs per-node state (§4, §5.4).
12. Management plane must provide customer-isolated operation interfaces, capability exposure, lifecycle management, NRP OAM, service OAM, planning telemetry and SLA telemetry (§4).
13. Plan NRPs holistically across customers; allow dynamic control within an NRP (§4.1).
14. Keep per-service state out of the core; aggregate services with the same needs onto one NRP; expect and constrain a small number of enhanced VPNs (§4.4, §7).
15. Diffserv alone is insufficient (markers, per-hop priority only); steer to dedicated queues per enhanced VPN or group (§5.1.2).
16. Hybrid control: centralised controller for provisioning/optimisation, distributed protocols for scale/reaction (§5.4).
17. Service→NRP mapping by packet characteristics or by VPN route attributes (§5.4).
18. Support in-place modification with feasibility assessment, reject when NRP changes are impossible, execute non-disruptively (§5.5).
19. If delegating a virtual network to the customer, prevent exceeding virtual link capacities while letting them set metrics (§5.5).
20. Use/augment L3SM, L2SM, VN, L3NM, L2NM, SAP, PM and NRP YANG models (§5.6).
21. Classify slice traffic at the edge by operator policy and forward on TE or shortest paths within the NRP using its resources (§6.4).
22. Choose consciously where state lives (packet, network, hybrid); mind header size and controller load/single point of failure (§7).
23. Before moving traffic to a new path, verify it is operational and meets the SLA; handle overtaking and transient latency variation; shield high-priority traffic from micro-loops (§8).
24. OAM packets must follow the same path and resources as service packets; provider overlay OAM must be non-intrusive (§9.1).
25. Collect NRP telemetry (planning) and per-service telemetry (SLA) (§9.2).
26. Supply decision information (VPN vs enhanced VPN) on the management interface (§10).
27. Security: guard against delay/burst attacks by other tenants; monitor to detect them; advise customers to encrypt; preserve customer privacy (§11).

## 6. Open decisions and trade-offs for Arcana

1. **What is an NRP in the Arcana contract?** Make it a first-class object (name, member links/tunnels per host, scheduler type, per-link share, buffer, DSCP class) that services reference, instead of the console inlining dummynet commands into `sdwan-rules`. This is what the NRP YANG draft models and what the YANG redesign of the agent needs.
2. **NRP identifier on the wire**: DSCP only (64 classes, survives tunnels if copied, may be rewritten by carriers), tunnel-per-NRP (unbounded count, costs tunnels/SAs/BFD sessions), VLAN per NRP on L2 links, or combination. Recommendation: `(tunnel set, DSCP)`; DSCP for tiers, tunnel for hard separation.
3. **Scheduler choice per link**: WF2Q+ (weights, work-conserving, well understood) vs QFQ (cheaper at high rates) vs `prio` for a latency tier on top; FQ-CoDel/FQ-PIE inside a tier for intra-tier fairness and low queueing delay. Decide a default tier template (e.g. prio tier for control/voice, WF2Q+ tiers for assured, best effort residual).
4. **Where the "guaranteed latency" class ends**: declare it as *queueing-delay bounded on Arcana hops* only, and compute an engineering bound (queue bytes / rate + serialisation) to show, never promise end to end.
5. **Service→NRP mapping method**: ipfw classification (today) vs BGP-community-driven FIB export (distributed, elegant for route-based mapping, new BIRD templates). Both can coexist; the contract should allow either.
6. **Centralised vs distributed metric/steering loop**: console re-steer on TCA (global view, slower) vs agent-local failover (fast, local view). Current split (agent: up/down; console: policy) seems right; decide thresholds for delay/loss-based local switching to avoid flapping (damping).
7. **Admission control strictness and overbooking factor** per NRP tier.
8. **Route reflector (119-5) vs full mesh**: scale vs an extra component on the console host.
9. **L2 services**: whether to offer L2 enhanced VPN (geneve/vxlan + bridge) with the same NRP treatment; flooding and MAC scale without EVPN.
10. **OAM in-queue**: classify probe packets into the construct's queue (true "same resources") at the cost of probes being affected by congestion — which is the point; versus a control queue for faster fault detection (BFD). Likely: BFD in a control class, probes in the service class.
11. **Telemetry export**: adopt IPFIX via `ng_netflow` per service FIB for SLA analytics, or stay with counters/events; data volume vs insight.
12. **YANG strategy**: implement L3NM/L2NM/SAP/PM as console views over the service document, and the slice service model as the customer-facing one; keep MEF 70.2 as internal vocabulary or migrate.
