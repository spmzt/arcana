# RFC 8568 — Network Virtualization Research Challenges

Source read in full: `rfc/rfc8568.txt` (April 2019, Informational, IRTF NFVRG consensus).

## 1. Purpose

Documents the research and engineering challenges of network virtualisation (NFV together
with SDN) and the current approaches, to expose requirements for future research and
standards work. It first gives background: the ETSI NFV framework (VNF, NFVI, NFV-MANO with
NFVO/VNFM/VIM, EM, OSS/BSS), the ONF SDN architecture (data/control/application planes,
management across all), RFC 7426's SDN layer model (forwarding, operational, control,
management, application planes; DAL/CAL/MAL/NSAL), ITU-T Y.3300–Y.3302's SDN functional
architecture (SDN-AL/CL/RL with multi-layer management functions), MEC, IEEE 802.1CF, DMTF
(OVF, CIMI, NETMAN, VMAN) and open-source projects (OpenStack, Kubernetes, ODL, ONOS,
OpenContrail, OPNFV, OSM, OpenBaton, ONAP, SONA). It then lists ten challenge areas —
guaranteeing QoS, performance improvement, multiple domains, 5G and network slicing, service
composition, end-user device virtualisation, security and privacy, separation of control
concerns, network function placement, testing — and maps them to IETF/IRTF groups and NFVRG
focus areas. For Arcana (jails as lightweight NFVI, per-service BIRD/Unbound/Squid/Suricata
instances as VNFs, the console as a small MANO+SDN controller) it is a checklist of the
properties a "complete SDN solution" is expected to address or explicitly exclude.

## 2. Content

### 2.1 Terminology (§2)
Application Plane; Control Plane (instructs devices how to process/forward); Forwarding
Plane; Management Plane (monitoring, configuring, maintaining; mostly operational-plane
related); NFVI; NFV-MANO = NFVO + VNFM + VIM; NFVO (network service life cycle, coordinates
VNF life cycle and NFVI resources); Operational Plane; PNF; SFC (abstract ordered functions;
= ETSI NF-FG) and SFP (concrete instances); VIM; VNF; VNFM.

### 2.2 Background (§3)
- ETSI NFV (3.1): three domains (VNFs; NFVI = virtual compute/storage/network over a
  virtualisation layer over hardware; MANO). Functional blocks: VNF, EM, NFVI, VIM(s), NFVO,
  VNFM(s), descriptors (service, VNF, infrastructure), OSS/BSS.
- SDN (3.2): logically centralised control; OpenFlow as one southbound protocol among
  NETCONF, RESTCONF, ForCES; ONF architecture with management spanning all planes; RFC 7426
  layers and abstraction layers (DAL, CAL, MAL, NSAL).
- ITU-T Y.3302 (3.3): SDN-AL, SDN-CL, SDN-RL plus MMF with MMFA/MMFC/MMFR reference points,
  ACI and RCI interfaces.
- MEC (3.4), IEEE 802.1CF OmniRAN (3.5), DMTF (3.6), open source (3.7) with highlighted
  areas: policy-based resource management, analytics for visibility/orchestration, service
  verification for security and resilience.

### 2.3 Challenges (§4)
1. **Guaranteeing QoS (4.2)**: stable forwarding rate on COTS is hard; cloud tools (EPA,
   SR-IOV, NUMA, DPDK) are not enough; lightweight virtualisation (containers, unikernels,
   minimal OSes) as alternatives to VMs (4.2.1). **Metrics for NFV characterisation (4.2.2)**:
   need metrics and protocols (IPPM had no NFV items; BMWG RFC 8172 on benchmarking VNFs on
   general-purpose hardware, compare PNF and VNF the same way; ETSI NFV-PER 001; VNF
   benchmarking as a service). **Predictive analysis (4.2.3)**: diagnose and react before
   anomalies (migrate, scale). **Portability (4.2.4)**: run a VNF on multiple NFVIs with
   predictable performance; hypervisor differences, EPA hardware dependencies, state sync;
   VM descriptor/compute host descriptor requirements.
2. **Performance improvement (4.3)**: energy efficiency (energy-aware scaling and placement,
   scheduling/chaining to minimise cost; trade-off with performance); improved link usage (SDN
   raised utilisation — Google B4; SFC/forwarding graphs add complexity; DC topology design).
3. **Multiple domains (4.4)**: cross-operator/cross-domain orchestration (5GEx), network as a
   service with hierarchies of networks/tunnels/overlays, harmonising management domains
   (MEC has its own MANO).
4. **5G and network slicing (4.5)**: slices combine RAN/core components per use case; the
   definition of a slice is debated (YANG models to stitch slices vs fundamental timing/sync
   research). **Virtual Network Operators (4.5.1)**: VNOs need finer control; platforms lack
   common functions; need a common set of functions across network (ODL, ONOS, Ryu) and
   compute (OpenStack…) controllers, **PUSH notifications instead of polling** (WEBPUSH RFC
   8030), and a common ontology. **IoT (4.5.2)**: slices for massive IoT; location-based
   placement of VNFs at the far edge ("fog"), understanding IoT location references, linking
   APs to compute nodes.
5. **Service composition (4.6)**: SFC/SFP; composition algorithms for load balancing and
   reliability; context-aware selection using monitoring of instances, links and chain-level
   metrics (end-to-end delay); re-selection on degradation; ILP, ML, co-flows; SFC WG lacks
   management/configuration of SFC components and redundancy/reliability mechanisms (VNFpool).
6. **Device virtualisation for end users (4.7)**: cloning end devices into the cloud.
7. **Security and privacy (4.8)**: attestation among functions, external monitoring, slice
   isolation (minimum security = that of the most critical slice), continuous threat
   modelling and DevOps; privacy by data minimisation and opt-in; the orchestrator as the
   security-policy orchestrator (placement on more secure hardware); multiple administrative
   domains (who holds keys, replicate private keys for redundancy?); NFV may better resist
   DoS (distributed, traffic steering) and isolate faults per DC; SDN for AAA management.
8. **Separation of control concerns (4.9)**: two SDN control levels — NFVI connectivity among
   VNFs/PNFs vs configuration of the VNFs themselves; need clear interaction mechanisms
   (ETSI NFV-EVE 005, CLAS layered SDN).
9. **Network function placement (4.10)**: resource allocation considering resiliency,
   (anti-)affinity, security, privacy, energy; harder with chains and multi-domain.
10. **Testing (4.11)**: (a) methodology changes — a VNF cannot be tested alone, the NFVI and
    MANO become the test environment and must be held constant (CPU pinning, NUMA,
    hypervisor/vSwitch/NIC versions); NFVI testing depends on workload type (forwarding,
    control, encryption, auth — e.g. jitter irrelevant for control plane, drops critical);
    test system deployable with the system (CI/CD) and **not sharing resources with the
    SUT**; (b) new functionality — VNF forwarding graphs realised by vSwitch/SDN/tunnels
    (VXLAN) become a test variable; scaling (policy-driven resource change) puts all of MANO
    into the SUT; (c) opportunities — test tools as VNFs deployed with the service, tests on
    every deployment, CI/CD to production.

### 2.4 Gaps to IETF groups (§5, Table 1) and NFVRG focus (§6, Table 2)
QoS → IPPM (NFVI measurement); performance → SFC WG, NFVRG (energy-driven orchestration);
multiple domains → NFVRG; slicing → NVO3, NETSLICES; service composition → SFC WG (management
and configuration); device virtualisation → none; security → none; separation of control →
NFVRG; testing → NFVRG (testing of scaling); placement → NFVRG, SFC WG. NFVRG focus points:
re-architecting functions (containerisation, statelessness, serverless, control/data
separation, SDN integration, programmability); new management frameworks (new OAM, hybrid
descriptors, lightweight MANO); low latency and resource isolation (HW acceleration, NIC
offload); measurement and benchmarking.

## 3. How Arcana relates on FreeBSD

Arcana already is a small NFV/SDN system: NFVI = FreeBSD hosts and jails (lightweight
virtualisation of §4.2.1 — jails are the FreeBSD "container"); VNFs = per-service BIRD,
Unbound, dnsmasq, rtadvd, Squid, c-icap/ClamAV, Suricata instances started by the agent as
plugins; VIM/VNFM/NFVO = the console's document → plan → apply → jobs with the agent executing
(jail create/start, service start, plugin lifecycle); SDN controller = the console over cblink;
descriptors = the SD-WAN/SASE document; EM = the agent's reads. Mapping of the challenges:

1. **QoS guarantees and metrics**: dummynet pipes/weighted queues give shares, not guarantees
   (TODO notes this); STAMP (rfc8972.md) and alternate marking (rfc9342.md) are the IPPM
   answer to §4.2.2 for the data plane; for NFVI/VNF characterisation adopt RFC 8172's advice
   (benchmark PNF and VNF alike) with the RFC 8456 harness (rfc8456.md) plus per-plugin
   throughput tests (Suricata/Squid in a jail under iperf3). Predictive analysis (§4.2.3):
   TCAs with damping exist; add trend-based pre-alerts (e.g. delay percentile rising over N
   windows) as a later item. Portability (§4.2.4): jails + base-system services make Arcana's
   VNFs portable across FreeBSD hosts by construction; record host capabilities
   (`hw.model`, NICs, offload features, `kern.hz`, `cpuset` layout) in `hello` as the
   "compute host descriptor" and let the plan check plugin requirements against them.
2. **Performance improvement**: energy — `powerd`/`hw.acpi` and CPU frequency are host facts
   the agent can read and set; low value for Arcana now. Link usage — the SD-WAN steering by
   performance criteria is the SDN-style utilisation improvement; alternate-marking per-cluster
   rates feed it.
3. **Multiple domains**: Arcana is single-administration (one user, one CA); multi-operator
   orchestration is out of scope; Mplify 119's "edge of one vendor with a service of another"
   is the only cross-domain seam (iBGP to a foreign vendor control plane) — keep the contract
   RFC 4364-compatible there and stop.
4. **Slicing and VNOs**: a service = a slice (FIB, routing domains with RD/RT, BIRD instance,
   DNS filter instance, bandwidth); the RFC's VNO requirements map to the console's per-service
   API: allocate/deallocate resources dynamically and get monitoring data; **PUSH over
   polling** → the console should consume the agents' `events` stream (cblink notifications)
   rather than poll `sdwan` once a second, and the API should offer server-sent events/WebPush
   (RFC 8030) to the PWA; a common ontology → the YANG-model redesign (ietf-network, RFC 8345;
   ietf-network-slice-service, RFC 9543 is already in the scratchpad RFC set).
5. **Service composition (SFC)**: SASE chains (ipfw divert → Suricata; fwd → Squid; DNS →
   Unbound) are an SFP; model the chain explicitly (RFC 7665 terms) with health per function
   (plugin fail-closed with a Critical fault exists) and re-selection on degradation; chain-
   level end-to-end delay from STAMP across the chain.
6. **Device virtualisation for end users**: not applicable.
7. **Security and privacy**: attestation — mTLS with the console CA, host keys never leave the
   host (WireGuard, IPsec DH pairs, STAMP keys); slice isolation — FIBs, ipfw sets, jails;
   DevOps — the repo's test-per-commit practice; privacy — the record/captures hold packet
   data: data minimisation (capture only on request, bounded, root-only /tmp, no payload in
   events by default); key replication for redundancy — currently none (console CA key on one
   host), an HA decision; security-policy orchestration by the console is the SASE design.
8. **Separation of control concerns**: Arcana's agent does both NFVI connectivity (FIBs,
   tunnels, ipfw) and VNF configuration (BIRD templates, Squid config); keep them as separate
   model subtrees (infrastructure vs network-service/VNF config) so a future split (another
   controller configuring the VNFs) is possible; today's single agent is acceptable but the
   contract should not entangle them.
9. **Placement**: which edge runs the control-plane host (route reflector), the IDS, the proxy
   per service is a placement choice the console makes manually today; candidates for policy:
   affinity (plugin near the UNI), anti-affinity (RR not on an edge in the same failure
   domain), resources (`racct`/`rctl` figures in `hello`/`stats`).
10. **Testing**: the two-jail lab and the RFC 8456 harness must hold the environment constant
    (pin the console and generators with `cpuset`, fixed `kern.hz`, same kernel/`ipfw`
    module versions) and keep the test system off the SUT's CPUs; tests deployable with the
    system (ATF/kyua already in base; a `bench` target); scaling tests include the console's
    plan/apply loop as part of the SUT; "test tools as VNFs" → a probe/reflector/generator
    jail image shipped with Arcana (STAMP reflector doubles as a test tool).

## 4. Cannot be mapped / not applicable
- Multi-operator/multi-domain orchestration (5GEx-style), VNO marketplaces, InP/VNO split.
- 5G RAN/core slicing, massive IoT slices, fog placement by IoT location references.
- End-user device cloning.
- Energy-aware orchestration across data centres (single-host `powerd` at most).
- Hardware acceleration/NIC offload for VNFs (SR-IOV passthrough to jails is not a FreeBSD
  jail feature; bhyve VMs would be, which Arcana does not manage).
- Hypervisor portability (Arcana's unit is a jail on FreeBSD; no VM descriptors/OVF).
- ETSI MANO interfaces (Or-Vi, Ve-Vnfm, SOL003/SOL005): Arcana's console is not an ETSI NFVO
  and should not pretend to be; the YANG contract is its own.

## 5. Checklist (requirements Arcana derives)
1. Record NFVI facts per host (CPU, memory, NICs and offloads, kernel, `cpuset` topology,
   `racct` state) as a host descriptor the plan checks against plugin requirements.
2. IPPM-based data-plane metrics (STAMP, alternate marking) and VNF/NFVI benchmarks (RFC 8172
   method, RFC 8456 harness) as part of CI.
3. Push, not poll: console consumes agent `events`; API offers push to the PWA.
4. Services modelled as slices with explicit resources (FIB, domains, bandwidth, plugin
   instances) and monitoring per slice.
5. SFC modelled explicitly with per-function health and chain-level metrics.
6. Security: keys never leave hosts; attestation via CA; data minimisation in captures/
   records; documented key-redundancy decision for the console CA.
7. Model separation: infrastructure connectivity vs VNF configuration in different subtrees.
8. Placement hints (affinity/anti-affinity/resources) in the document, honoured by the plan.
9. Test environment constancy (pinning, versions) and SUT/test-system resource separation in
   the lab scripts; test tools shipped as a jail image.
10. Out-of-scope list (multi-domain, 5G, device virtualisation, VM portability) stated in the
    docs.

## 6. Open decisions and trade-offs
- **How far to borrow ETSI vocabulary** (VNF/NFVI/MANO) in the docs and models: it eases
  comparison but overstates what a single-user fleet manager is. Use RFC 7426/8568 terms in
  the architecture doc, keep Arcana's own names (Archives, Agent, Orchestrator) in the UI.
- **Push vs poll**: converting the console to event-driven changes its concurrency model
  (Kore workers, one cblink session per agent with a long-lived stream); the gain is
  sub-second reaction and lower load; the cost is session management and reconnect logic.
- **Guarantees vs shares in QoS**: dummynet cannot guarantee against unmanaged UCS traffic;
  either document "weighted shares" honestly or add ALTQ/ipfw queue admission at the UNI (more
  rules, same limitation on the WAN side).
- **Console HA and key redundancy**: §4.8's question (replicate private keys for redundancy?)
  — a second console with the CA key replicated vs a single console with backups; relates to
  RFC 8456's failover benchmark being N/A.
- **Placement automation**: manual (today) vs policy-driven; policy needs resource telemetry
  the agent already has but a solver the console lacks — start with constraints checking at
  plan time, not optimisation.
