# RFC 9731 — A YANG Data Model for Virtual Network (VN) Operations

Source read in full: `scratchpad/rfc/rfc9731.txt` (2575 lines, March 2025,
Standards Track, TEAS WG). Supporting texts read for the references:
RFC 8453 §2–§7 (ACTN framework), RFC 8795 §2–§5 and the YANG groupings for
the connectivity matrix / LTP / te-node-info, Appendix A node subtree,
RFC 8776 typedefs/groupings imported by `ietf-vn`, RFC 8345 §4 and the trees
of `ietf-network` / `ietf-network-topology`, RFC 9522 §5.1.2.2.

A note on "RFC 9522 (ACTN applicability?)": RFC 9522 is *Overview and
Principles of Internet Traffic Engineering* (Farrel, Jan 2024, obsoletes
RFC 3272). Its only ACTN content is §5.1.2.2 (ACTN as a hierarchical SDN
architecture for multi-domain TE: abstraction, virtualization, presentation
of a VN to tenants over programmable interfaces) and §5.1.2.3 (IETF Network
Slices as "a VPN connectivity matrix with SLOs"). The document that explains
how YANG models fit ACTN, *Applicability of YANG models for ACTN*
(draft-ietf-teas-actn-yang, cited as [ACTN-YANG] in RFC 8453 §5.3.2),
**expired at -11 in 2023 and never became an RFC** (checked on the
datatracker). RFC 8453 remains the normative framework reference for the
VN/AP/VNAP vocabulary.

---

## 1. Purpose and where it sits

- Defines `ietf-vn`, a **customer service model** (RFC 8309 sense) for a
  *Virtual Network*: "a network provided by a service provider to a customer
  for the customer to use in any way it wants as though it were a physical
  network" (RFC 8453 §2.1).
- It lives on the **CNC–MDSC Interface (CMI)** of ACTN: the Customer Network
  Controller POSTs it, the Multi-Domain Service Coordinator serves it. It is
  *not* a device model; it never reaches a PNC or a network element.
- Its content is deliberately thin: identifiers for **Access Points** (the
  customer/operator shared name of an access link, RFC 8453 §6), **VN Access
  Points** (the binding of an AP to one VN), **VNs** and their **VN members**
  (edge-to-edge abstract links, one per src/dest pair), admin/oper status,
  a VN-level disjointness policy, and a `vn-compute` RPC for pre-instantiation
  path computation.
- Everything topological (bandwidth, constraints, explicit paths, metrics) is
  **delegated by leafref to RFC 8795 `ietf-te-topology`**: a VN is one
  abstract TE node (`abstract-node`) whose `connectivity-matrix` entries are
  the VN members; Type 2 VNs add an `underlay` with explicit paths inside the
  connectivity-matrix entry. The VN type (1 or 2) is not a leaf; it is
  implied by whether the referenced matrix entry has an underlay path.
- NMDA-style: config and state (`oper-status`, `if-selected`, VNAP
  `max-bandwidth`) in one tree.
- **In Arcana terms**: the console (arcana-console) is CNC+MDSC+PNC collapsed
  into one program; the PWA/operator (or a future external orchestrator) is
  the customer; `arcana-agent` is the device below the PNC's SBI. `ietf-vn`
  therefore describes the console's *northbound* view of an SD-WAN service
  (MEF 70.2 service = VN, UNI = AP/VNAP, tunnel between two edges = VN
  member). The cblink family would carry only the *per-edge projection* of
  it (this host's APs, this host's half of each VN member, their oper-status).

Types imported from RFC 8776 that ietf-vn uses directly:

| Type | Definition (RFC 8776) |
|---|---|
| `te-global-id` | `uint32` (provider-id / client-id; 0 = native topology, RFC 8795 §5.4) |
| `te-topology-id` | `union { string length 0; string pattern '([a-zA-Z0-9\-_.]+:)*/?([a-zA-Z0-9\-_.]+)(/[a-zA-Z0-9\-_.]+)*' }` |
| `te-node-id` | `yang:dotted-quad` (4 octets, maps to the TE Router ID) |
| `te-tp-id` | `union { uint32 (unnumbered); inet:ip-address }` |
| `te-bandwidth` | `string` with a long pattern: comma-separated decimal / hex / IEEE-754 hex-float (e.g. `0x1p10` = 1024 bytes/s) |
| `te-common-status` | `enumeration { up, down, testing, preparing-maintenance, maintenance, unknown }`; `te-oper-status` and `te-admin-status` are both this type |
| `te-path-disjointness` | `bits { node(0), link(1), srlg(2) }` (JSON `"node link srlg"`) |
| `te-ds-class` | `uint8 { range "0..7" }` (RFC 4124 Class-Type) |
| `te-topology-identifier` | grouping: container with the three leaves above, each `default "0"` / none |
| `generic-path-constraints` | grouping `path-constraints` = common-path-constraints-attributes (te-bandwidth container with `choice technology { default generic; case generic { leaf generic te-bandwidth } }`, link-protection identityref, setup-priority/hold-priority uint8, signaling-type identityref, path-metric-bounds list [metric-type] {metric-type identityref, upper-bound uint64}, path-affinities-values/-names, path-srlgs-lists/-names) + generic-path-disjointness (`disjointness? te-path-disjointness`) |
| `generic-path-optimization` | grouping `optimizations` with `choice algorithm { case metric {if-feature path-optimization-metric; list optimization-metric [metric-type]; container tiebreakers} case objective-function {if-feature path-optimization-objective-function; ...} }` |

## 3. Every container/list/significant leaf: meaning and candidate Arcana realisation

Vocabulary used below: *service* = an Arcana MEF 70.2 SD-WAN service
(`sdwan-*` operations today), *edge* = a FreeBSD host running
`arcana-agent`, *UNI* = an interface placed in the service's FIB on an edge,
*tunnel* = gre/gif/geneve/wg(/ipsec) interface between two edges in a given
FIB, *probe* = the ICMP echo measurement (`sdwan-probes`).

### 3.1 `access-point/ap*` [id]

| Node | Meaning (RFC) | Arcana realisation | Agent gap |
|---|---|---|---|
| `ap` list, key `id` (ap-id = `string {length 1..max}`) | The customer/operator *shared logical identifier of an access link* between CE and PE (RFC 8453 §6: "an AP is a common identifier for the link itself", distinct from the LTP which is a link *end*). Unique in the scope of the entity controlling the VN. | A **UNI** of the SD-WAN document: an interface on an edge host that faces the subscriber. AP id = the document's UNI id. On the agent: the interface name plus FIB (`if-set`/`if-create` with `fib`). | The agent has no first-class "UNI" object; UNIs exist only as interfaces + ipfw tables + BIRD config written by the console. A `uni` attribute set (id, ifname, fib, service) would make this a dumpable object. |
| `pe` leafref `-> /nw:networks/network/node/tet:te-node-id` | The PE node in the *native* TE topology where the access link lands. §3.2.1: an AP may be created with *only* the PE known, customer side filled later. | The edge host (`host` set: hostname; the console's server registry). te-node-id is a dotted quad → use the edge's router-id (BIRD `router id`) or the loopback in the SD-WAN Service domain (Mplify 119 routing domain). | Agent has no router-id attribute in `hello`; add `router-id` (dotted-quad) to host facts. |
| `max-bandwidth` te-bandwidth | Access link capacity (RFC 8453 fig. 12/14: MaxResBw of CE port / PE port). | `ifconfig <uni> media` link speed (ifm_active / `ifi_baudrate`), or the UNI's dummynet pipe bandwidth when configured. Encoded as `0x1p..` hex-float bytes/s. | `network` reply has no baudrate; expose `if_data.ifi_baudrate` and the dummynet limit. |
| `avl-bandwidth` te-bandwidth | Available bandwidth after VNAP reservations (fig. 15: 10 Gbps − 1 − 2 = 7). | Console arithmetic: max − Σ(service bandwidth reservations on this UNI). Not an agent quantity. | — |

### 3.2 `access-point/ap/vn-ap*` [id]

| Node | Meaning | Arcana realisation | Gap |
|---|---|---|---|
| `vn-ap` list, key `id` (ap-id) | VN Access Point: the **binding of an AP to one VN** so several VNs can share one AP and bandwidth is tracked per VN (RFC 8453 §6, fig. 15 "VNAP1.9", "VNAP1.5"). Also the anchor for dual-homing relationships (§6.1). | A UNI *in a service*: since Arcana puts the UNI interface itself into the service FIB, today one UNI belongs to exactly one service. A VNAP would be e.g. a VLAN subinterface (`vlan(4)`) of a physical UNI port placed in service X's FIB, or an ipfw table entry classifying the subscriber's prefixes to service X. | Supporting several services per physical UNI needs VLAN or prefix classification at the UNI (ipfw `sdwan-rules` already classifies per set; add per-VNAP accounting). |
| `vn` leafref `-> /virtual-network/vn/id` | Which VN this binding belongs to. | Service id. | — |
| `abstract-node` leafref `-> /nw:networks/network/node/nw:node-id` with `must` that the node has `tet:te-node-id` | The abstract TE node that *represents the VN* (one node per VN, RFC 9731 §2.1 fig. 3: "AN1"). | Console-level: the service viewed as one node. | `ltp` leafref `-> /nw:networks/network/node[node-id=current()/../abstract-node]/nt:termination-point/tet:te-tp-id` | The LTP *on the abstract node* (not on the real PE) where this VNAP enters the VN. te-tp-id is a uint32 or IP address. | The UNI interface's address or index as the TP id of the service's abstract node. Agent: `if_nametoindex` or the UNI IP. | — |
| `max-bandwidth` (ro) te-bandwidth | Bandwidth of this VNAP (operator view, fig. 15 "1 Gbps"). | The service's bandwidth on that UNI: the dummynet pipe/queue the console configures via `sdwan-rules` objects (`pipe N config bw ...`). Readable from `ipfw pipe show`. | Agent returns the configured objects but not a typed bandwidth figure; add a per-UNI `bandwidth` gauge. |

| Node | Meaning | Arcana realisation | Gap |
|---|---|---|---|
| `vn` list, key `id` (vn-id string) | One VN = one customer service instance (Type 1 or 2). | One SD-WAN **service** (the document the console applies; today the console compiles it into `sdwan-*` JSON blobs). | The agent has no service object; everything is "json". | `if-selected` (ro, feature) boolean default false | Whether this member is the one chosen among multi-src/dest candidates. | The steering outcome: `sdwan` reply's "steer" → which candidate is chosen per prefix. Per-member boolean = "this tunnel is the active candidate for at least one prefix" or better per (prefix, member). | Agent has the data in JSON; needs a typed per-member leaf. |
| `admin-status` te-admin-status default up | Customer-side enable/disable of the whole VN. | Service enabled/disabled in the document → agent brings tunnels/BIRD/rules down (`ifconfig down`, stop BIRD instance) without deleting. | Agent has no "disable service" verb; today the console deletes the config. |
| `oper-status` (ro) | VN-level state (aggregate). | Console aggregates member states (all up → up, some → testing/unknown?, none → down). | Console-only. |
| `vn-level-diversity` te-path-disjointness (bits node/link/srlg) | Required disjointness *across all members* of the VN (grouping vn-policy). | SD-WAN: "the two tunnels of a service must not share a WAN link / underlay provider" → Arcana's WAN-link concept (UCS UNIs). Node-disjoint is meaningless on a single-node abstract view; link-disjoint = different WAN uplinks; srlg = same ISP. | Console path selection; the agent could expose per-tunnel `srlg` (which WAN uplink/ISP) so the console can enforce. |

### 3.4 `rpc vn-compute`

| Node | Meaning | Arcana realisation |
|---|---|---|
| `input/te-topology-identifier`, `abstract-node` | Optional reference to a pre-made abstract topology. | Console-level only. |
| `input/path-constraints` (te-bandwidth, link-protection, setup/hold priority, signaling-type, path-metric-bounds, affinities, SRLGs, disjointness) | VN-level constraints; member-level overrides VN-level. | Arcana "Check" (dry run of a document): verify every tunnel pair can meet delay/loss bounds from the *current probe history* (the agent's 3600 samples) and that bandwidth fits the WAN links. `setup/hold-priority`, `signaling-type` (RSVP-TE/SR identities), affinities and label restrictions have no SD-WAN meaning. |
| `input/cos` te-ds-class 0..7 | Class-Type (DS-TE) of the traffic. | DSCP class of the tunnel / probe (`dscp` in sdwan-probes) — map class-type ⇄ a DSCP set; MEF 70.2 application flow's CoS. |
| `input/optimizations` (metric or objective-function) | What to minimise/maximise (te-types path-metric-* identities: te, igp, hop-count, delay-average, delay-minimum, residual-bandwidth, …; objective functions of-minimize-cost-path, of-maximize-residual-bandwidth …). | Steering policy: "lowest delay", "lowest loss", "prefer cheapest WAN" → the ordering of candidates the console computes into `sdwan-steer`. |
| `input/vn-member-list*` | Members with per-member constraints, cos, optimizations. | The tunnel pairs of a planned service. |
| `input/vn-level-diversity` | As above. | As above. |
| `output/vn-member-list*/compute-status` (vn-compute-status = te-common-status; "all statuses apart from up and down are considered unknown") | Per-member result. | up = feasible, down = infeasible. |
| `output/.../error-info` {error-description string 1..max, error-timestamp yang:date-and-time, error-reason identityref base vn-computation-error-reason} | Why computation failed. Identities: `vn-computation-error-not-ready`, `-no-cnc`, `-no-resource`, `-path-not-found`, `vn-computation-ap-unknown`. | Arcana Check diagnostics: edge unreachable (no-cnc ≈ "dependent controller unavailable" → agent down), no WAN link with capacity (no-resource), no probe history meeting bounds (path-not-found), UNI not on any edge (ap-unknown). |
| `output/.../if-selected`, `connectivity-matrix-id`, `underlay` | Which candidate was picked and where its properties are. | The console's chosen steering candidate and the tunnel details. |

Note the RPC does **not reserve** anything (§4.3.1): "it simply computes the
resulting VN". Arcana's "Check" vs "Apply" split matches this exactly.

### 3.5 What the model needs that the agent lacks (summary)

1. A typed **UNI / access-point object** per edge (id, ifname, FIB, service
   binding, bandwidth, available bandwidth, router-id of the edge).
2. A typed **tunnel/VN-member object** with service id, member id, far-end
   edge, encapsulation, outer addresses, FIB, DSCP, oper-status enum, and
   `selected` flag — instead of ids known only to the probe JSON.
3. **Oper-status as a 6-value enum** (te-common-status) and an
   admin-status that disables without deleting.
4. Edge **router-id** (dotted quad) and per-WAN-link **SRLG/affinity** tags
   so disjointness can be checked.
5. Timestamps as `yang:date-and-time` (RFC 3339 with offset) where today
   epoch seconds / ms are used in JSON (`since`, sample times).
6. Bandwidth as hex-float bytes/s string (te-bandwidth) or at least u64
   bytes/s with a documented conversion.

## 4. Cannot be mapped (with reasons)

| Node / concept | Why not |
|---|---|
| `abstract-node`, `te-topology-identifier`, `connectivity-matrix-id`, `vn-ap/ltp` leafrefs into `/nw:networks` | They point into an RFC 8795 TE-topology instance that exists only in the controller (MDSC). The agent is one node of the native topology and has no datastore of abstract topologies. In cblink these become opaque identifiers (text/u32) the console owns; referential integrity cannot be checked by the agent. |
| `vn-ap/abstract-node` `must` expression (`/nw:networks/nw:network/nw:node[nw:node-id=current()/../abstract-node]/tet:te-node-id`) | Cross-tree XPath over another module's data; cblink `checks` are per-attribute ranges only. Console-side validation. |
| `multi-src` / `multi-dest` *selection by the MDSC* | Selection among candidate *endpoints* (different APs = different sites/DCs, RFC 8453 §7) is a controller decision needing global knowledge. Arcana's local steering chooses among *paths to the same destination*, which is the degenerate case (same dest AP, different members). Multi-site DC selection is console-only. |
| Type 2 VN: `underlay/primary-path/path-element*` with strict/loose hops over an underlay TE topology | The SD-WAN underlay (the Internet / provider UCS) is not TE-visible; Arcana cannot pin hops. Only "which WAN uplink" (first hop) is controllable, via `tunnelfib`/source address. |
| `path-constraints/setup-priority`, `hold-priority`, `signaling-type`, `link-protection`, `path-affinities-*`, `path-srlgs-*`, `label-restrictions` | RSVP-TE / GMPLS notions (preemption priorities, admin groups/colours, label sets). FreeBSD has no MPLS data plane and Arcana's tunnels are not signalled. Affinities could be re-purposed as WAN-link colours, but that is an extension, not a mapping. |
| `te-bandwidth` as reservation | Arcana can *shape* (dummynet) but not *reserve* across the underlay; `avl-bandwidth` is bookkeeping only. |
| `vn-level-diversity` node-disjointness | A single-node abstract topology has no intermediate nodes; only link/srlg disjointness has a realisation (different WAN uplinks/ISPs). |
| `vn-compute` as an agent RPC | Path computation needs all edges' probe histories and WAN capacities; it is a console function. The agent can only answer "feasibility from *my* history" (a sub-RPC). |
| `vn-computation-error-no-cnc` | Refers to dependent *CNCs* in hierarchical ACTN; Arcana has one controller. Reusable only loosely as "edge unreachable". |
| Customized topologies (`client-id` ≠ 0), MDSC hierarchy (RFC 8453 §4.1), grey/black abstraction (§5.2) | Single-operator, single-controller deployment. Only "native/white" exists. |

## 5. Features, and which Arcana could advertise

Features **defined** in ietf-vn:

- `multi-src-dest` — "Support for selection of one source or destination
  among multiple." Gates `multi-src`, `multi-dest`, `if-selected`.
  **Arcana could advertise it** in the restricted sense of
  multi-*path* selection (same AP pair, several members = tunnels over
  different WAN links; `if-selected` = steering outcome). True multi-site
  endpoint selection would be a console feature only.

Features **referenced through imported groupings** (appear in the tree):

- `te-types:path-optimization-metric` — optimise by a metric list
  (delay-average, delay-minimum, residual-bandwidth, hop-count, te, igp…).
  Arcana could advertise: steering by measured delay/loss/ipdv is exactly
  this. Needs metric identities (RFC 8776 defines path-metric-te, -igp,
  -hop, -delay-average, -delay-minimum, -residual-bandwidth,
  -optimize-includes/excludes; a delay-variation/loss metric would need an
  Arcana identity derived from `te-types:path-metric-type`).
- `te-types:path-optimization-objective-function` — OF identities
  (minimise cost, maximise residual bandwidth, …). Partially: "cheapest WAN"
  / "most headroom".
- `tet:te-topology-hierarchy` — the `underlay` container of connectivity
  matrix entries (Type 2). **Not** advertisable (no TE-visible underlay).
- `tet:template` — node/link templates. Not needed.

Arcana-specific additions that would *not* be features of ietf-vn but of an
augmenting module: encapsulation types, IPsec keying, BFD, probes.

## 6. YANG constructs used, with examples, and what the YAML/CBOR schema must express

The cblink spec format today (SPEC-FORMAT.md) has: typed attributes
(u8..u64, s8..s64, bool, flag, text, bytes, float, nest), `multi-attr`,
`enum`/`flags` definitions, `checks` (min/max, min-len/max-len, exact-len,
min-count/max-count), `required` per op, `do`/`dump`/`event`/stream. Below,
each YANG construct found in ietf-vn and its imports, with the example from
the module and what a strict YANG-following schema language needs.

| Construct | Example in RFC 9731 (or its imports) | What the schema language must add |
|---|---|---|
| **module / namespace / prefix / revision** | `module ietf-vn { yang-version 1.1; namespace "urn:ietf:params:xml:ns:yang:ietf-vn"; prefix vn; revision 2025-03-27 }` | Family = module; add `namespace` and `revision` (date) fields; `version` today is a single integer. Prefix ⇄ `c-prefix`. |
| **import** | `import ietf-te-types { prefix te-types; }` | Cross-family type/grouping reuse: today one file = one family with no imports. Need `imports:` and qualified names (`te-types:te-bandwidth`). |
| **typedef** (derived types with restrictions) | `typedef vn-id { type string { length "1..max"; } }`; `typedef vn-compute-status { type te-types:te-common-status; }` | Named reusable types (`definitions: - type: typedef`) with base type + restrictions; chained typedefs. |
| **feature / if-feature** | `feature multi-src-dest {...}`; `leaf multi-src { if-feature "multi-src-dest"; ... }` | `features:` list at top level; `if-feature:` on attributes/ops; the server advertises supported features in `ctrl getfamily` (cf. YANG library). |
| **identity / identityref** | `identity vn-computation-error-reason;` `identity vn-computation-error-path-not-found { base vn-computation-error-reason; }`; `leaf error-reason { type identityref { base vn-computation-error-reason; } }` | An *open, extensible* enumeration: entries can be added by other modules and have a base hierarchy. Encode on the wire as text `"module:identity"` (like RFC 7951 JSON) or as a registered (family, id) pair; schema: `type: identityref, base: <identity>`; `identities:` definitions with `base`. Closed `enum` is not enough. |
| **enumeration** | `te-common-status { enum up; enum down; enum testing; enum preparing-maintenance; enum maintenance; enum unknown; }` | Existing `enum` definition works (values 0..5); keep YANG names and the ability to assign explicit `value`. |
| **bits** | `te-path-disjointness { bits { bit node {position 0} bit link {position 1} bit srlg {position 2} } }` | Existing `flags` definition (bit numbers) matches; CBOR as uint mask; JSON form is a space-separated name list — document the canonical text form too. |
| **union** | `te-tp-id = union { uint32; inet:ip-address }`; `te-topology-id = union { string length 0; string pattern ... }` | A `union` type listing member types; CBOR naturally carries uint vs text so the kind disambiguates; the schema must allow one attribute with several accepted kinds and validate each alternative's restrictions. |
| **leafref** (absolute, and with XPath predicate) | `leaf ap { type leafref { path "/access-point/ap/id"; } }`; `leaf vn-ap-id { type leafref { path "/access-point/ap[id=current()/../ap]/vn-ap/id"; } }` | Reference types: `type: leafref, path: ...`. The agent can validate references *inside its own datastore* (e.g. a member's `ap` must be an existing UNI); references into another family (`/nw:networks/...`) must be declared `require-instance false` (RFC 8345 does so everywhere) → carry the target's key type and skip validation. Predicate form (`[id=current()/../ap]`) = *composite reference* (ap id + vn-ap id); realise as two attributes checked together. |
| **choice / case** | `te-bandwidth { choice technology { default "generic"; case generic { leaf generic { type te-bandwidth; } } } }`; `optimizations { choice algorithm { case metric {...} case objective-function {...} } }`; path-element `choice type` with 5 cases | Mutually exclusive attribute groups: `choice:` with `cases:` each listing attributes; validator rejects attributes from two cases; a `default` case. |
| **presence container** | `tet:te!`, `te-topology!` (RFC 8795), `nvp:service!` (RFC 9375) — ietf-vn itself has none, but every nw:network-types type is one | A `nest` whose *existence* carries meaning even when empty; today an empty nest is representable (CBOR empty map) but `flag`-like semantics should be explicit: `presence: true`. |
| **empty container as augmentation hook** | `container underlay { description "An empty container that can be augmented..." }` | `nest` referencing a set that other families may extend (`augment`). |
| **augment** | Not in ietf-vn itself, but its whole data lives by augmenting RFC 8345 (`augment /nw:networks/nw:network/nw:node { leaf te-node-id ... }` in 8795). ietf-vn's `underlay` and the §4.4 text expect future augments. | `augments:` section: a family adds attributes to another family's set at a path; attribute ids must come from a per-augmenting-family range to avoid collisions; the wire needs qualified attribute keys (e.g. (family-id, attr-id) pairs or text keys `"tet:te-node-id"`). |
| **must** (XPath constraint) | `leaf abstract-node { must '/nw:networks/nw:network/nw:node[nw:node-id=current()/../abstract-node]/tet:te-node-id' }` | Arbitrary cross-node constraints; a strict schema would need a small expression language or named C check hooks (`checks: must: <name>` implemented in the server). Cross-family musts: console-side only. |
| **when** | Not in ietf-vn; heavy in RFC 9375/8346 (`when '../nw:network-types/nvp:service'`). | Conditional presence of attributes on another attribute's presence/value: `when: <attr> present` / `when: <attr> == value`. |
| **default** | `leaf multi-src { default "false"; }`, `admin-status { default "up"; }`, `provider-id { default "0"; }`, `choice technology { default "generic"; }` | `default:` per attribute; generated parsers fill `has_x=false` + default; dumps may omit defaults (JSON "explicit"/"trim" modes). |
| **mandatory** | none in ietf-vn (all leaves optional, `?`); RFC 9375 has `service-type { mandatory true; }` | Existing `required` ≈ mandatory; keep both op-level and attribute-level. |
| **config false** (state) | `oper-status`, `if-selected`, `vn-ap/max-bandwidth` (`config false;`) | Mark attributes `config: false`; they appear only in replies/dumps/events, never accepted in requests; generator can emit separate struct views (intended vs operational). |
| **list with key** | `list ap { key "id"; }`, `list vn-member { key "id"; }` | `multi-attr` of `nest` plus a `key:` declaration naming the key attribute(s); keys are `required` and unique within the list; dumps can filter by key. |
| **composite keys** | Not in ietf-vn; RFC 8345 `supporting-node* [network-ref node-ref]`, `supporting-termination-point* [network-ref node-ref tp-ref]`; RFC 8795 `information-source-entry* [information-source information-source-instance]` | `key:` as a list of attribute names. |
| **ordered-by user** | Not in ietf-vn; RFC 8776 `path-route-object { ordered-by user }`, RFC 8795 `path-element* [path-element-id]` is effectively ordered | `ordered-by: user` on a list → CBOR array order is significant (today multi-attr order is preserved by generated structs; make it a declared property). |
| **leaf-list** | RFC 8795 `leaf-list signaling-address { type inet:ip-address; }`; RFC 8346 `leaf-list router-id`, `leaf-list flag` | = `multi-attr` on a scalar. Already present. |
| **grouping / uses** | `grouping vn-member {...}` used in `vn-member` list and twice in the RPC; `uses te-types:generic-path-constraints` | Reusable attribute groups (`groupings:`) that expand into sets, including from imported families; today `nested-attributes` can share a set but cannot *inline* it. |
| **rpc / input / output** | `rpc vn-compute { input {...} output {...} }` | = cblink `do` with request/reply. Already present. |
| **action** (per-instance operation, YANG 1.1) | none in these RFCs | Would be `do` with the list key(s) as required request attributes. |
| **notification** | none in ietf-vn (RFC 8346/8795 have `l3-node-event`, `te-node-event` etc.) | = cblink `event` + `mcgrp`. Present. |
| **decimal64 / fraction-digits** | not in ietf-vn (RFC 9375 `percentile`, `percentage`) | see RFC 9375 notes. |
| **string pattern / length** | `vn-id { length "1..max" }`, `te-bandwidth` pattern (hex-float list), `te-topology-id` pattern | `checks: pattern: <regex>` (POSIX ERE or XSD regex semantics — YANG uses XSD regexes, anchored implicitly), beside min-len/max-len. |
| **yang:date-and-time** | `error-timestamp { type yang:date-and-time; }` | Typed timestamp: text RFC 3339 pattern, or CBOR tag 0/1 (RFC 8949) — decide one canonical encoding (tag 1 epoch float is compact; RFC 7951 JSON parity wants text). |
| **yang:dotted-quad** | `te-node-id` | 4-octet text pattern or `bytes exact-len 4`. |
| **inet:\*** | `inet:ip-address` (in te-tp-id union; signaling-address), `inet:as-number` (path-element), `inet:uri` (nw:node-id, network-id, link-id, tp-id in RFC 8345!) | Typed address attributes (`type: ip-address` → CBOR bytes 4/16 or text), `as-number` = u32, `uri` = text with pattern. |
| **uint8 range** | `te-ds-class { range "0..7" }`, `setup-priority uint8` | existing min/max. |
| **boolean** | `multi-src`, `if-selected`, `is-allowed` | existing `bool`. |
| **empty** | `is-abstract { type empty; }` (RFC 8795) | existing `flag`. |
| **binary** | `tunnel-tp-id binary` (RFC 8795) | existing `bytes`. |
| **counter32/counter64/gauge64** | RFC 8795 statistics (`creates yang:counter32`), RFC 9375 | u32/u64 with semantic tag (monotonic vs gauge) for the UI. |
| **description / reference** | everywhere | `doc:` exists; add `reference:`. |

## 7. Open decisions and trade-offs

1. **Where the VN model lives.** Two options: (a) the console implements
   `ietf-vn` northbound (RESTCONF/JSON over its existing API) and the cblink
   family stays an *edge* model that only borrows types/semantics (status
   enum, te-bandwidth, date-and-time, identities); (b) the cblink family
   itself carries a per-edge projection of `access-point` and
   `virtual-network` (this edge's APs/VNAPs, the members this edge
   terminates). (b) gives the agent a typed service object (replacing the
   `json` blobs of `sdwan-*`) and lets `arcanactl` show a service; it costs
   duplicating controller data on every edge and keeping it consistent.
   Recommendation: (b) for AP/VNAP/member *instances* and their oper-state,
   (a) for abstract-node/topology/compute.
2. **Member = one tunnel or one bidirectional pair?** ietf-vn members are
   src→dest links of an abstract node and are not declared unidirectional
   (RFC 8345 links are). A tunnel is bidirectional but each edge sees one
   end. Decide whether the agent reports `vn-member` as "my end of member X"
   with role src|dest, or whether the console creates two members per
   tunnel. RFC 9375 (unidirectional links, two per tunnel) pushes toward the
   latter for PM; ietf-vn toward the former for service intent.
3. **Identifiers.** ietf-vn ids are free strings (`length 1..max`); RFC 8345
   ids are `inet:uri`; te-node-id is a dotted quad. Arcana today uses short
   names and integers. Decide canonical forms (`arcana:<host>/<svc>/<tunnel>`
   URIs?) and whether the agent validates them.
4. **te-bandwidth encoding.** Keep the RFC string (`"0x1p30"`) for fidelity,
   or a u64 bytes/s in CBOR with text conversion at the console. The pattern
   is complex to validate in C; a union {u64, text pattern} is a compromise.
5. **Status enums.** Adopt `te-common-status` (6 values) for every
   admin/oper status in the family, mapping Arcana's probe states
   (`unknown/up/down/ended/error`) onto it, or keep Arcana's and translate at
   the console. One vocabulary everywhere is the strict-YANG choice.
6. **Thresholds as path-metric-bounds.** Moving the `tca` thresholds
   (delay, ipdv, loss, damping) into RFC 8776 `path-metric-bounds`
   (metric-type identityref + `upper-bound uint64`) requires new metric
   identities for loss and delay-variation (RFC 8776 only has
   delay-average/minimum, te, igp, hop, residual-bandwidth) and loses the
   decimal loss fraction (uint64 → use ppm/1e-6 units). Trade: standard shape
   vs. precision/clarity.
7. **Features.** Advertise `multi-src-dest` in the narrowed multi-path
   sense? It is honest only if documented; alternatively define an Arcana
   feature `multi-path` in an augmenting module.
8. **Underlay augment.** Define `arcana-sdwan-underlay` augmenting
   `vn:vn-member/vn:underlay` with encapsulation (identityref base
   vpn-common:protocol-type: gre/gre-v4/gre-v6/ip-in-ip(gif)/geneve +
   Arcana identities for wg and ipsec), outer addresses, fib, dscp, bfd,
   IPsec SA parameters. This is the one place the RFC explicitly invites.
9. **Cross-family references.** How far does the cblink schema go in
   expressing leafrefs into `ietf-network`/`ietf-te-topology` trees the agent
   does not hold? Proposal: `leafref` with `require-instance: false` → typed
   opaque key, validated by the console; the generator emits only the key's
   type.
10. **RPC vs. intent.** `vn-compute` is a pure function; Arcana's "Check"
    today runs on the console with agent dry-runs. Decide whether to add a
    per-edge `feasibility` do-op (input: member constraints; output:
    compute-status + error-info from local probe history) so the console's
    compute is a fan-out of standard sub-calls.
