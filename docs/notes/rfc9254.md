# RFC 9254 — CBOR Encoding of Data Modeled with YANG ("YANG-CBOR")

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc9254.txt (July 2022, Standards Track, 2253 lines, read in full).

## Purpose

Defines the CBOR (RFC 8949) encoding of YANG 1.1 data trees and of their enclosing
"representation nodes" (notification contents, rpc/action input/output, yang-data /
sx:structure instances). It is the binary sibling of RFC 7951 (JSON). It is encoding-only:
it does not define a protocol (CORECONF does), nor how SIDs are assigned (RFC 9595 does).
Two key forms exist: **SIDs** (integers) and **names** (text strings). A protocol may mandate
one of them; the media type `application/yang-data+cbor` carries `id=sid` or `id=name`
(or no parameter: both may be present).

## Terminology that matters for cblink

- **SID**: 63-bit unsigned integer, range 0..2^63-1 (0 is reserved: "no SID", never on the wire).
  Identifies: identities, data nodes, rpcs (+ their input/output), actions (+ input/output),
  yang-data structures, notifications, modules, features. Submodules get no SID; their items
  are allocated as part of the including module.
- **delta**: current SID minus a reference SID. Signed (CBOR major type 0 or 1).
- **absolute SID**: a SID in a key position not encoded as a delta: must be tagged with
  CBOR tag 47.
- **representation tree / node**: a data tree possibly enclosed by the representation of
  a schema node (structure, notification, rpc, action).
- **container-like instance**: instance of a container, structure, notification contents,
  rpc/action input/output, a list entry, or an anydata node. All of them encode as a map.
- **parent** of a representation node: schema node of the closest enclosing representation
  node.

## Complete encoding rules

### Properties (section 3)
1. Every container-like instance is a CBOR map; each child schema node is one key/value pair.
2. Keys are either SIDs (major 0/1 bare integer = delta; or tag 47(uint) = absolute) or
   names (major 3 text).
3. CBOR tags are used ONLY for: absolute SIDs (47), anyxml content, union members that need
   disambiguation (43–46). Nothing else is tagged. (Note: decimal64 uses tag 4 — a generic
   CBOR tag, not a YANG-CBOR one.)
4. **Indefinite-length encoding SHALL be supported by decoders** "unless specified otherwise
   by the protocol or mechanism implementing this specification". cblink's wire profile
   forbids indefinite lengths and all tags; a cblink profile of YANG-CBOR may legitimately
   keep the indefinite-length ban (the RFC explicitly lets the protocol override), but it
   MUST allow tags 4, 43, 44, 45, 46 and 47 in body positions where YANG needs them.
5. Empty-but-present arrays, maps, byte strings, text strings are encoded with length 0.
6. The payload SHOULD carry enough to identify each node statelessly (SID, SID delta from
   another SID in the payload, qualified name, or instance-identifier).
7. The examples' outer map `{ SID: value }` is "a typical usage example and is not part of
   the encoding rules. Only the value within this CBOR map is compulsory". So a protocol may
   put the root SID in a header and send only the value.

### Delta computation (3.2 and 4.2.1)
- Reference SID of the outermost map is 0 unless the environment unambiguously confers one
  (e.g. a CoAP URI / a header field naming the resource).
- Reference SID of a map directly embedded in a map entry with a **name** key is 0.
- Otherwise the reference SID is the SID computed for the enclosing map entry, even when an
  array intervenes (list → entry maps).
- Container: delta = SID(child) − SID(container).
- List: delta = SID(child) − SID(list) (NOT entry-specific; the list node's SID).
- RPC input/output: delta = SID(child) − SID(rpc) (NOT the SID of the `input`/`output` node,
  although RFC 9595 does allocate SIDs to input and output nodes themselves).
- Action input/output: delta = SID(child) − SID(action).
- Notification content: delta = SID(child) − SID(notification).
- Deltas may be negative (a child's SID may be smaller than its parent's: augmentations from
  other modules; items allocated later; see 9595 example `error-tag` = SID 1028 in a
  container with SID 1024 → delta 4, but any ordering is legal).
- SIDs ↔ deltas is a stateless conversion given the outermost reference SID.

### Names (3.3, 4.2.2)
- `name = [identifier ":"] identifier`; namespace = module name (main module for submodule
  items).
- Namespace-qualified form is MANDATORY for every member of the top-level map and whenever
  the node's module differs from its parent's. Simple form is MANDATORY otherwise.
  (Same rule as RFC 7951 section 4.)
- Name keys are text strings (major 3).

### Representation nodes (section 4)
| YANG node | CBOR | Notes |
|---|---|---|
| leaf | per its type (section 6) | |
| container, structure, notification contents, rpc/action input/output | map (major 5) | keys = SID delta / absolute 47(SID) / name |
| leaf-list | array (major 4) of values encoded per type | ordered-by user preserves order |
| list | array (major 4) of maps — **also for a single entry** | each entry's keys use the list's SID as reference |
| anydata | map, same rules as container; children are regular YANG-modeled data | the RFC notes tag 47 absolute SIDs "might be simpler" at the anydata root, because the content's parent in the schema is not known |
| anyxml | any CBOR data item ("xml" is a misnomer); MAY contain items tagged 43–47, and those tags SHALL be supported | |
| yang-data (RFC 8040 ext.) / sx:structure | map containing a single pair: key = SID (or qualified name) of the structure container, value = container encoding (4.2) | e.g. `ietf-coreconf:error` |

### Types (section 6)
| YANG type | CBOR | Notes |
|---|---|---|
| uint8/16/32/64 | major 0 | |
| int8/16/32/64 | major 0 or 1 by sign | |
| decimal64 | **tag 4 decimal fraction** `4([exponent, mantissa])` e.g. 2.57 → `4([-2, 257])` = `C4 82 21 19 0101` | exponent is negative fraction-digits; this forces tag support in the decoder |
| string | major 3 (UTF-8) | |
| boolean | simple true (F5) / false (F4) | |
| enumeration | major 0/1 integer = the enum `value` (explicit or auto-assigned per 7950 §9.6.4.2) | **inside a union**: tag 44 + text string with the enum NAME, e.g. `44("unbounded")` |
| bits | byte string (major 2), or array alternating positive uint (skip count ×8 bits) and byte strings; LSB-first within a byte; trailing zero bytes never generated; single-bytestring array MUST collapse to the bare byte string; single-integer array is an error; adjacent same-kind elements are an error; receivers MAY accept trailing zero bytes | **inside a union**: tag 43 + text with space-separated bit names, e.g. `43("under-repair critical")` |
| binary | major 2 | |
| leafref | encoded as the referenced leaf's type | |
| identityref | SID form: major 0 = the identity's absolute SID (no delta — not a key position); name form: text, qualified when the identity's module ≠ the leaf's module, otherwise either form | **inside a union**: tag 45 wraps the uint or text |
| empty | simple null (F6) | |
| union | encoded per the member type actually used; bits, enumeration, identityref, instance-identifier members MUST be tagged (43, 44, 45, 46) to disambiguate major types; enumeration/bits members switch to text-name form | the only place where type-dependent tags appear |
| instance-identifier | SID form: single-instance node → major 0 = target SID; list entry → array `[SID, key1, key2, ...]` with keys in `key` statement order from the top-most list down through subordinate lists; name form: text string like 7950 §9.13.2 XPath but with 7951 namespace rules (`/ietf-interfaces:interfaces/interface[name='eth0']/ietf-ip:ipv4/ip`) | **inside a union**: tag 46 |

Important consequence of the instance-identifier SID form: a leaf-list entry or a node
under a keyed list is addressed by `[SID, keys…]` where the SID is of the *target* node, and
the key values are listed for *every* ancestor list — the encoding is NOT a path of SIDs but a
target SID plus the key tuple. Decoding needs schema knowledge (the SID → schema node → list
of ancestor key leaves and their types).

### Content types (section 7, 9.1, 9.2)
- `application/yang-data+cbor` (CoAP CF 340): both key kinds allowed.
- `application/yang-data+cbor; id=name` (CF 341).
- `application/yang-data+cbor; id=sid` (CF 140).
- An implementation MUST reject the other key kind when the id parameter is used (section 8).

### CBOR tags registry (9.3)
| Tag | Data item | Meaning |
|---|---|---|
| 43 | text | YANG bits (union member) |
| 44 | text | YANG enumeration (union member) |
| 45 | uint or text | YANG identityref (union member) |
| 46 | uint, text or array | YANG instance-identifier (union member) |
| 47 | uint | absolute YANG SID in a key position |

Plus generic tag 4 (decimal fraction) for decimal64.

### Security considerations
Receivers SHOULD reject anything non-conforming. SID mapping data must be managed as
carefully as the YANG modules themselves.

## Observations for cblink

1. A cblink body today is a map with keys 1..65535 (family attribute ids, per set) and
   −1..−64 (framework). YANG-CBOR keys are SID deltas, which are signed and unbounded
   (63-bit). A YANG-CBOR map legitimately contains negative small keys (an augmenting
   module's node allocated below the parent, e.g. delta −3). cblink's framework keys
   therefore collide with legitimate data keys. See cblink-yang-design.md section (a).
2. cblink forbids tags; YANG-CBOR needs tag 4 (decimal64), 43–46 (union members) and 47
   (absolute SIDs). The profile must allow at least these in value positions and tag 47 in
   key positions.
3. cblink forbids indefinite-length items; RFC 9254 lets the protocol forbid them.
4. cblink's `flag` kind (presence = true) does not exist; YANG `empty` is `null`. cblink's
   `null` simple value is accepted today, so `empty` fits.
5. cblink arrays = repeated attributes = YANG leaf-list / list. Exactly the same shape.
6. A YANG `list` with a single entry is still an array; cblink multi-attr is the same.
7. Floats: YANG has none (decimal64 instead). cblink's `float` kind has no YANG counterpart.
8. YANG `bits` on the wire (byte string with LSB-first positions, or the skip-array) is
   different from cblink's `flags` (uint bit mask). A 64-bit bit mask in cblink = one
   8-byte CBOR byte string in YANG-CBOR, same bit positions (position i → byte i/8, bit i%8).
9. The root: RFC 9254 lets the environment confer the outermost reference SID. cblink's
   header (`family`, `cmd`) can carry the root SID so the body is the *value* only; or the
   body is `{ SID: value }` with reference 0. Both are conformant.
10. Deltas are relative to the enclosing *schema* node — rpc children relative to the rpc
    SID, not the `input` node — so an rpc input map is keyed by `SID(leaf) − SID(rpc)`.
