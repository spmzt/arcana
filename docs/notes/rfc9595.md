# RFC 9595 — YANG Schema Item iDentifier (YANG SID)

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc9595.txt (July 2024, Standards Track, 2359 lines, read in full).

## Purpose

Defines what a SID is (a globally unique 63-bit unsigned integer naming one YANG item),
how SIDs are allocated (ranges, registries), how they survive module revisions, and the
`.sid` file format (JSON per RFC 7951 of module `ietf-sid-file`) that persists and publishes
assignments. It is the management companion of RFC 9254.

## What gets a SID

- identities
- data nodes (including nodes under `rc:yang-data` and `sx:structure`)
- RPCs **and their `input` and `output` nodes**
- actions **and their `input` and `output` nodes**
- notifications and their content nodes
- YANG modules and features
- NOT submodules (their items are allocated as part of the including module; `.sid` files
  exist only per module).
- "RPC or action 'input' and 'output' YANG items MUST always be assigned SIDs even if they
  don't contain further YANG items", because other modules may augment them (Appendix B).
  Note the tension with RFC 9254 §4.2.1 where rpc children's deltas are relative to the
  *rpc* SID, not the input/output SID; the input/output SIDs exist for augment targets and
  for instance-identifiers, not for delta computation.

## Objectives (section 2)
- Objective 1 (MUST): any 63-bit unsigned integer is either unassigned or immutably maps to
  exactly ONE YANG name. Only unassigned → assigned transitions exist. Hence a receiver can
  always translate SIDs back to YANG names (for JSON/XML encodings).
- Objective 2 (SHOULD): any YANG name in active use has one SID (no names without SIDs, no
  duplicates). Not fully attainable: autonomous assigners may collide "like ships in the
  night".
- Objective 3 (MUST): SID management is independent of module versioning. New revision
  items are added to the existing assignments; existing assignments are never changed.
- Keep short (2..4 byte) SIDs available; keep locality so deltas are small.
- SID 0 is reserved ("no SID") and never appears in interchange.
- Roles: module controller, SID assigner, SID range registry, SID repository, SID user.
  Type-1 (SID-guiding) module developers ship `.sid` files; type-2 designate an assigner;
  type-3 (SID-oblivious) rely on a repository to mediate.

## `.sid` file lifecycle (section 3, Appendix B, C)
- Obtain a SID range from a registry; assign (preferably by tool); store in `.sid`.
- Provisional assignments during development have status `unstable`; finalised ones
  `stable`; never-to-be-reused retired ones `obsolete`. A published `.sid` file MUST NOT
  contain `unstable` items. Transitions: unstable → stable → obsolete only.
- Two variants during development: "published" (stable only) and "unpublished" (also
  unstable).
- **All SIDs present in a previous version of the file that was in active use MUST be present
  in the new version.** If more SIDs are needed, a new `assignment-range` is appended.
- Recommended automatic assignment (Appendix B):
  1. extract all items;
  2. sort: `namespace` descending (data, feature, identity, module), `identifier` ascending;
  3. assign sequentially from `entry-point`;
  4. add a range when exhausted;
  5. record `dependency-revision` for each import.
  On update: keep existing assignments, assign only new items, bump `sid-file-version`
  (0 or absent for the first file of a module revision; versions are per module revision).
  A renamed node with same structure/semantics MAY keep its SID; an item whose meaning or
  CBOR encoding changes SHOULD get a new SID (author's discretion).
- The `.sid` file MUST NOT be published inside the RFC; IANA's registry is authoritative.

## `.sid` file format (section 4)
Tree:
```
module: ietf-sid-file
  structure sid-file:
    +-- module-name            yang:yang-identifier     (mandatory)
    +-- module-revision?       revision-identifier      YYYY-MM-DD; absent if the module has no revision
    +-- sid-file-version?      uint32                   default 0
    +-- sid-file-status?       enumeration              unpublished | published (default published)
    +-- description?           string
    +-- dependency-revision*   [module-name]
    |  +-- module-name         yang:yang-identifier
    |  +-- module-revision     revision-identifier      (mandatory)
    +-- assignment-range*      [entry-point]
    |  +-- entry-point         sid                      lowest SID of the range
    |  +-- size                uint64                   (mandatory); ranges MUST NOT overlap
    +-- item*                  [namespace identifier]   unique "sid"
       +-- status?             enumeration              stable(0) | unstable(1) | obsolete(2), default stable
       +-- namespace           enumeration              module(0) | identity(1) | feature(2) | data(3)
       +-- identifier          union { yang-identifier ; schema-node-path }
       +-- sid                 sid                      (mandatory)
```
- `typedef sid { type uint64 { range "0..9223372036854775807"; } }`.
- `schema-node-path`: absolute schema node id with **module names instead of prefixes**;
  leftmost name always qualified; subsequent names qualified only when the node's module
  differs from its parent's; no predicates. Pattern:
  `/[a-zA-Z_][a-zA-Z0-9\-_.]*:[a-zA-Z_][a-zA-Z0-9\-_.]*(/[a-zA-Z_][a-zA-Z0-9\-_.]*(:[a-zA-Z_][a-zA-Z0-9\-_.]*)?)*`
- For `namespace` module/feature/identity the identifier is a bare YANG identifier; for
  `data` it is a schema-node-path. The `item` list MUST include every item of the module.
- Encoded as JSON (RFC 7951): note that uint64 and the `sid` typedef are therefore JSON
  *strings* ("1700"), as 7951 requires for 64-bit integers. The example in Appendix A shows
  `"entry-point": "1700"`, `"size": "100"`, `"sid": "1700"`.
- Media type `application/yang-sid+json`, CoAP CF 260, extension `.sid`.
- Appendix D: a `.sid` file may be wrapped in an RFC 9195 instance-data-set.

Example items from Appendix A (ietf-system@2014-08-06, range 1700/100):
module ietf-system → 1700; identities 1701..1706; features 1707..1714; data nodes
1715..1776 in path-sorted order (`/ietf-system:set-current-datetime` 1715,
`.../input` 1775 (assigned later, outside the original sorted block: a revision added
input/output SIDs), `.../input/current-datetime` 1776, `/ietf-system:system` 1717, ...).

## Registries (section 6)
- **YANG-SID Mega-Ranges** (Expert Review): delegate blocks (normally 1,000,000 SIDs) to SDOs
  or registrars; policy Public/Private/both; initial entry 0..999,999 → IANA. Ranges above
  4,295,000,000 preferred for oversized allocations. Registry must run ≥5 years (10 for
  private).
- **IETF YANG-SID Ranges** (within IANA's first million):
  | Entry | Size | Policy |
  |---|---|---|
  | 0 | 1,000 | IESG Approval (0 reserved) |
  | 1,000 | 59,000 | RFC + Expert Review |
  | 60,000 | 40,000 | Experimental Use — MUST NOT be used in operational deployments |
  | 100,000 | 200,000 | RFC + Expert Review |
  | 300,000 | 700,000 | Reserved |
  Range size: multiple of 50, ≥33% headroom, SHOULD NOT exceed 1,000. Initial assignments:
  ietf-coreconf 1000/100, ietf-yang-types 1100/50, ietf-inet-types 1150/50, iana-crypt-hash
  1200/50, ietf-netconf-acm 1250/50, ietf-sid-file 1300/50, ietf-interfaces 1500/100,
  ietf-ip 1600/100, ietf-system 1700/100, iana-if-type 1800/400.
  **Not yet allocated by this RFC: ietf-routing, ietf-network-instance, ietf-logical-network-element,
  ietf-yang-library, ietf-subscribed-notifications, ietf-yang-push, ietf-datastores.** (Check
  the live IANA registry; otherwise Arcana must assign them in its own range.)
- **IETF YANG-SID Modules** (Expert Review): per-module `.sid` file URIs. Expert checks:
  valid JSON structure; all SIDs in the module's ranges; same SIDs as any older/newer `.sid`
  for the module; all old SIDs still present.
- Early allocation (BCP 100) expected for drafts; a module referencing SID-less modules
  triggers recursive allocation for its dependencies.

## Security
`.sid` files map semantics to integers; a tampered file changes meaning. Only import from
sources as authoritative as the YANG modules themselves. Dereferenceable identifiers caveat.

## Implications for Arcana / cblink

1. **Arcana needs its own SID space.** For IETF modules with IANA `.sid` files (interfaces,
   ip, system, iana-if-type, netconf-acm, yang-types, inet-types, coreconf, sid-file) use the
   published files. For IETF modules *without* allocations (routing, network-instance,
   logical-network-element, yang-library, yang-push, subscribed-notifications, datastores,
   ietf-yang-schema-mount, ietf-restconf's yang-errors, ...) and for Arcana's own modules
   (jails, services, packages, jobs, stats), Arcana must either (a) request a Mega-Range
   delegation (overkill), (b) use the experimental range 60,000..99,999 (forbidden in
   operational deployments by the RFC), or (c) pick a private block in the 63-bit space, e.g.
   above 2^32, "like ships in the night" — legitimate per section 2.1 as long as Arcana's
   agent and console are the only parties; the SIDs are then 5-byte CBOR integers at the top
   level only (deltas inside maps stay 1–2 bytes). Option (c) is the practical one; keep
   IANA SIDs for IANA modules so standard tooling (pyang, libyang) interoperates.
2. **The `.sid` file is the "numbers are forever" ledger.** Its rules (never remove, never
   reuse, append ranges, status stable/obsolete) are precisely cblink's FAMILIES.md rule
   generalised. cblink-gen can consume `.sid` files and refuse to emit code if an item lacks
   a stable SID or if a SID moved between revisions (the file's `sid-file-version` and the
   module revision give the check).
3. **Generating `.sid` files in C** is a sort + sequential assignment over the schema tree —
   trivial once the schema tree is available. The hard part is having the schema tree
   (YANG parser) in C. Alternatively pyang's `--sid-generate-file` does it.
4. The sorted-order recommendation means SIDs of siblings are *not* dense per container:
   siblings are interleaved with descendants of earlier siblings in alphabetical path
   order, so deltas inside one map are small but irregular, and can be negative for nodes
   added in later revisions (assigned after the parent's whole subtree). Any key in a
   YANG-CBOR map may therefore be a small negative integer — the cblink framework-key
   conflict is real, not theoretical.
5. The JSON encoding of `.sid` files requires a JSON parser in the generator (libucl in
   base, which Arcana already uses, parses JSON).
