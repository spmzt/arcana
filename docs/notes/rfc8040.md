# RFC 8040 — RESTCONF Protocol

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8040.txt (January 2017, Standards Track, 7675 lines, read in full).

## Purpose
HTTP(S)-based protocol giving CRUD access to YANG-modeled data using NETCONF datastore
concepts; payloads in XML (7950) or JSON (7951); rpc/action invocation via POST; event
notifications via Server-Sent Events (SSE). Data-model-driven: clients derive all URLs from
the YANG modules; the server advertises them with ietf-yang-library (RFC 7895, now 8525).
Editing model = `:writable-running` — each edit is applied on success (candidate is
auto-committed; startup auto-updated). This is the north-bound API the Arcana console
should expose to the browser.

## Transport (section 2)
TLS MUST (RESTCONF MUST NOT run over plain HTTP); https on 443; server presents X.509v3;
client MUST validate path or pin; server MUST authenticate clients — SHOULD be TLS client
certs, otherwise any HTTP auth scheme (e.g. cookies/sessions are *not* in the registry;
WebAuthn + session cookie as Arcana does today is "an HTTP authentication scheme" only
loosely — RFC 8040 says "MUST use one of the HTTP authentication schemes registry"; Arcana's
cookie session would be a deviation to note, or use `Authorization: Bearer` after WebAuthn).
The derived identity is the "RESTCONF username" subject to NACM (RFC 8341). TLS 1.3 0-RTT
RECOMMENDED off.

## Resources (section 3)
| Resource | Path | Notes |
|---|---|---|
| root discovery | `GET /.well-known/host-meta` (XRD, `<Link rel='restconf' href='/restconf'/>`) | exactly one `restconf` link; one RESTCONF server per host:port |
| API resource | `{+restconf}` | yang-data `yang-api`: `data`, `operations?`, `yang-library-version` (ro string, revision date of ietf-yang-library); JSON name `ietf-restconf:restconf` |
| datastore resource | `{+restconf}/data` | unified view of config + state; cannot be created/deleted by client; ETag MUST and Last-Modified SHOULD be maintained (only config changes update them); a locked datastore → 409 `in-use` |
| data resource | `{+restconf}/data/<api-path>` | any container, leaf, leaf-list entry, list entry, anydata, anyxml; methods affect the node and all descendants; per-resource ETag/Last-Modified MAY/SHOULD, config-only |
| operation resource | `{+restconf}/operations/<module>:<rpc>` (rpc) or `{+restconf}/data/<path>/<action>` (action) | invoked with POST; `GET /operations` lists rpcs as empty leaves `{"operations": {"example-jukebox:play": [null]}}` |
| schema resource | URL in `modules-state/module/schema`, media type `application/yang` | optional |
| event stream resource | URL in `restconf-state/streams/stream/access/location`, `text/event-stream` | SSE |
| errors | yang-data `yang-errors` (not retrievable) | section 7 |

### api-path (3.5.3) — the URI encoding of instance identifiers
```
api-path       = root *("/" (api-identifier / list-instance))
api-identifier = [module-name ":"] identifier
list-instance  = api-identifier "=" key-value *("," key-value)
```
- module name prefix MUST be present when the node's module differs from its parent's or the
  parent is the datastore (same rule as 7951 names).
- list entry: `list=key1,key2,key3` in `key` statement order, canonical string values,
  percent-encoded reserved characters, `,` in a value percent-encoded; all keys required
  (no partial identifiers); empty key value = empty string between commas (`list1=foo,,baz`).
- leaf-list entry: `name=value`.
- keyless (state) lists: single instances cannot be addressed.
- Example: `/restconf/data/example-top:top/list1=key1,key2,key3/list2=key4,key5/X`;
  `/restconf/data/example-top:top/list1=%2C%27"%3A"%20%2F,,foo`.

### Default handling (3.5.4, 4.8.9, 9.1.2)
Server MUST report its `basic-mode` (report-all | trim | explicit) in the `defaults`
capability URI. A GET whose target *is* a leaf with a default MUST return the in-use default
regardless of basic-mode. For containers/lists the server MAY return defaults per mode and
`with-defaults` (report-all, trim, explicit, report-all-tagged → `@mtu: {"ietf-netconf-with-defaults:default": true}` RFC 7952 metadata).

### Operation resources (3.6)
- rpc: `POST {+restconf}/operations/module:rpc`; action: `POST {+restconf}/data/<path>/action`.
- Input body: object named `input` in the rpc's module namespace: `{"example-ops:input": {...}}`.
  Body MUST be sent if input has mandatory nodes; MUST NOT be sent if there is no `input`.
- Output: `{"example-ops:output": {...}}`, 200 OK; no output → 204 No Content (no body).
- Errors → `errors` body with the appropriate status.

## Methods (section 4)
| Method | RESTCONF semantics | NETCONF equivalent | Status |
|---|---|---|---|
| OPTIONS | MUST; returns `Accept-Patch` | — | |
| HEAD | MUST; same as GET without body | get/get-config | |
| GET | MUST; data + metadata; not on operation resources (405 `operation-not-supported`); unauthorized → 401 `access-denied` or 404 `invalid-value`; partially authorized → prune; non-existent → 404 `invalid-value`; multiple instances in XML → 400 | get/get-config | 200 |
| POST | MUST; on datastore/data = **create** child (exactly one instance in body; `insert`/`point` allowed for ordered-by user); exists → 409 `resource-denied`; on operation = invoke | edit-config create / rpc | 201 Created + `Location` / 200 or 204 |
| PUT | MUST; create or **replace** target (body required, 400 otherwise); on datastore = replace whole datastore (copy-config); keys in body MUST equal keys in URI; MUST NOT change leaf-list values | edit-config create/replace, copy-config | 201 (created) / 204 (replaced) |
| PATCH | MUST plain patch (`application/yang-data+json|xml` = **merge**; create/update but not delete children; target MUST exist); MAY YANG Patch (RFC 8072) and others; keys MUST match | edit-config merge | 200/204 |
| DELETE | MUST; target MUST exist (no `remove` semantics); single list/leaf-list instance only | edit-config delete | 204 |
Access control: server MUST NOT allow operations the client is not authorised for; RESTCONF
path → YANG instance identifier → NACM rules.

### Query parameters (4.8) — case-sensitive, at most once, unknown → 400 `invalid-value`
| Name | Methods | Values | Mandatory? | Capability URI |
|---|---|---|---|---|
| content | GET/HEAD on datastore/data | config, nonconfig, all (default) | MUST | — |
| depth | GET/HEAD on api/datastore/data | 1..65535 or unbounded (default); target = depth 1; nodes selected by `fields` and their ancestors count as depth 1 | optional | `:depth` |
| fields | GET/HEAD on api/datastore/data | `fields-expr = path "(" fields-expr ")" / path ";" fields-expr / path`; e.g. `fields=admin(label;catalogue-number)`, `modules-state/module(name;revision)` | optional | `:fields` |
| filter | GET/HEAD on event stream | XPath 1.0 over the conceptual `notification` document; prefixes = module names; e.g. `/event/event-class='fault'`, `(/m1:* or /m2:*)` | optional | `:filter` |
| insert | POST/PUT on ordered-by user list/leaf-list | first, last (default), before, after (need `point`) | MUST | — |
| point | POST/PUT | api-path of the insertion point | MUST | — |
| start-time | GET on event stream | date-and-time; replay (RFC 5277); stream must have `replay-support` | optional | `:replay` |
| stop-time | GET on event stream | date-and-time, after start-time; future allowed | optional (with start-time) | `:replay` |
| with-defaults | GET/HEAD on data | report-all, trim, explicit, report-all-tagged; unsupported value → 400 | optional | `:with-defaults` |

## Messages (section 5)
- `<OP> /<restconf>/<path>?<query>`; fragment unused; `Location` on create.
- UTF-8; server MUST support XML or JSON (MAY both); client needs both for full interop;
  `Content-Type` MUST be present with a body; `Accept` MUST be supported (406 if none
  acceptable; 415 for unsupported request encoding); without Accept the request encoding is
  used.
- Metadata: XML attributes / RFC 7952 `@name` members in JSON.
- Status: 4xx SHOULD carry `errors`; 5xx MAY; 1xx/2xx/3xx MUST NOT.
- `Cache-Control` MUST be present in every response (SHOULD NOT cache; use ETag/If-None-Match,
  If-Match, If-Unmodified-Since, 304, 412).

## Notifications (section 6)
- Optional. Streams listed in `ietf-restconf-monitoring:restconf-state/streams/stream`
  (name, description, replay-support, replay-log-creation-time, access[encoding]{location}).
- Subscribe: `GET <location>` with `Accept: text/event-stream` (SSE); server MAY accept
  `filter`, `start-time`, `stop-time`; MAY compress; SHOULD support the "NETCONF" stream.
- Event data: RFC 5277 `<notification>` with `eventTime` + payload; JSON module name for
  `notification` and `eventTime` is **`ietf-restconf`**:
  `data: {"ietf-restconf:notification": {"eventTime": "2013-12-21T00:01:00Z", "example-mod:event": {...}}}`
- SSE `retry` MAY be sent (clients SHOULD honour); `event`/`id` SHOULD NOT be sent; servers
  sending `id` SHOULD support `start-time` instead of `Last-Event-ID`.

## Error reporting (section 7)
error-tag → HTTP status: in-use 409; invalid-value 400/404/406; request too-big 413;
response too-big 400; missing-attribute, bad-attribute, unknown-attribute, bad-element,
unknown-element, unknown-namespace, malformed-message 400; access-denied 401/403;
lock-denied, resource-denied, data-exists, data-missing 409; rollback-failed 500;
operation-not-supported 405/501; operation-failed 412/500; partial-operation 500.
Body (SHOULD for 4xx except 403): yang-data `yang-errors`:
```
+---- errors
      +---- error*
         +---- error-type       enumeration  transport | rpc | protocol | application  (mandatory)
         +---- error-tag        string                                             (mandatory)
         +---- error-app-tag?   string
         +---- error-path?      instance-identifier
         +---- error-message?   string
         +---- error-info?      anydata (a container of extra nodes)
```
JSON: `{"ietf-restconf:errors": {"error": [{"error-type": "protocol", "error-tag": "invalid-value", "error-path": "/example-ops:input/delay", "error-message": "Invalid input parameter"}]}}`.

## Modules (sections 8–10)
- `ietf-restconf@2017-01-26` (prefix rc): extension `yang-data` (argument `name`, yin-element
  true; ignored unless top-level; MUST produce exactly one container; XPath root = the
  extension itself; lists need no key; if-feature and config ignored; identityref values
  limited to the module + its imports); `rc:yang-data yang-errors { uses errors; }`;
  `rc:yang-data yang-api { uses restconf; }` with `restconf { data; operations; yang-library-version }`.
- `ietf-restconf-monitoring@2017-01-26` (prefix rcmon): `restconf-state` (config false) →
  `capabilities/capability*` (inet:uri) and `streams/stream*[name]` as above.
  Capability URIs: `urn:ietf:params:restconf:capability:{defaults,depth,fields,filter,replay,with-defaults}:1.0`;
  `defaults` MUST be present with `?basic-mode=report-all|trim|explicit`.
- `ietf-yang-library` (7895 → superseded by 8525) MUST be implemented and list all modules.

## Security (12)
TLS mandatory; NACM for authorization; clients can detect changes to unauthorised data via
ETag changes; servers SHOULD limit resource consumption of edits.

## What the Arcana console (arcana-console) needs to be RESTCONF-conformant
1. `/.well-known/host-meta` → `/restconf`; `/restconf` → yang-api; `/restconf/data[/path]`
   with GET/HEAD/OPTIONS/POST/PUT/PATCH/DELETE; `/restconf/operations/<mod>:<rpc>`;
   `/restconf/yang-library-version`.
2. An api-path parser (module-qualified identifiers, `=`-separated keys, percent-decoding)
   that maps to the schema tree and produces the YANG-CBOR instance-identifier for the
   agent.
3. JSON (7951) ⇄ YANG-CBOR (9254) translation with the schema.
4. Mandatory: `content`, `insert`, `point`, `defaults` capability; optional `depth`, `fields`,
   `with-defaults`, `filter`, `replay`.
5. ETag/Last-Modified on the datastore (config only), `If-Match`, `If-Unmodified-Since`
   → 412.
6. `ietf-restconf-monitoring` and `ietf-yang-library` (8525) as data under `/restconf/data`.
7. SSE event stream with `{"ietf-restconf:notification": {"eventTime": ..., "<mod>:<notif>": {...}}}`;
   YANG-Push (8641) subscriptions ride on the same SSE stream (see rfc8639/8641 notes).
8. Error bodies per `yang-errors`; status mapping table above.
9. A multi-host fleet does not fit RESTCONF's "one server per host:port" unless hosts are
   modelled as data: use `ietf-network-instance`/`ietf-logical-network-element`-style mount
   points, or a top-level Arcana list `hosts/host[name]` with `yangmnt:mount-point` (RFC 8528)
   under which each host's full datastore appears — i.e. `/restconf/data/arcana:hosts/host=web1/ietf-interfaces:interfaces`.
   This is exactly the schema-mount use case and keeps a single RESTCONF root.
