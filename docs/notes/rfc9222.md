# RFC 9222 — Guidelines for Autonomic Service Agents

IRTF/IETF ANIMA, Informational, March 2022. Source: `scratchpad/rfc/rfc9222.txt` (read in
full including Appendix A). Depends on RFC 8990 (GRASP), RFC 8991 (GRASP API), RFC 8993
(reference model), RFC 8994 (ACP), RFC 8995 (BRSKI); see rfc8994.md for those.

## 1. Purpose

RFC 9222 tells the designer of an Autonomic Service Agent (ASA) how to build one that
survives in an Autonomic Network built on the ANI (ACP + GRASP + BRSKI). An ASA is "an
agent implemented on an autonomic node that implements an autonomic function, either in
part or whole" (RFC 7575); it is a component of network or service management, not a
service to end users. The document covers the ASA's internal structure (threads, main
loop, self-monitoring), how it interacts with the security bootstrap, the ACP, the GRASP
API and (undefined) policy mechanisms, how it coexists with non-autonomic management
(NETCONF, CLI, DHCP), how to design GRASP objectives (idempotence, dry run, CBOR, size,
YANG-CBOR), the ASA life cycle (installation, instantiation, operation, removal) with its
inputs and outputs, coordination between autonomic functions, robustness rules and
security rules, and ends with a worked resource-delegation example. For Arcana it is the
blueprint for turning the agent's device-resident control loops (failover, rekeying,
thresholds) into peer-to-peer autonomic functions once an ACP and GRASP exist.

## 2. Concepts and definitions, completely

### 2.1 Terminology (Section 2)

Autonomic (self-managing: self-configuring, self-protecting, self-healing,
self-optimizing, with high-level guidance from a central entity such as a NOC);
Autonomic Function (adapts on its own); Autonomic Node; ACP (RFC 8994); AN (network of
autonomic nodes interacting directly); ANI (Autonomic Network Infrastructure: ACP, BRSKI,
GRASP); ASA; BRSKI (RFC 8995); CBOR (RFC 8949); GRASP (RFC 8990); GRASP API (RFC 8991);
NOC (RFC 8368); Objective (a GRASP technical objective: a data structure whose main
contents are a name and a value; the value is one configurable parameter or a set).

RFC 8993's addition: an ASA "is a process that makes use of the features provided by the
ANI to achieve its own goals, usually including interaction with other ASAs via GRASP or
otherwise ... it also interacts with the specific targets of its function, using any
suitable mechanism. Unless its function is very simple, the ASA will need to handle
overlapping asynchronous operations ... forming part of the application layer above the
ANI." Simple ASAs exist (one objective, no asynchrony); constrained nodes get limited
ASAs; an ASA may control tens or hundreds of simple devices (a device controller holding
one ASA). Existing scripts in routers could be upgraded to ASAs (configure an IGP on
neighbours, exchange IGP keys securely).

### 2.2 Logical structure (Section 3)

Main thread housekeeping: obtain authorization credentials; register the ASA with
GRASP; acquire policy parameters; declare data structures for its objectives; register
the objectives it actively manages; launch a self-monitoring thread; enter its main loop.
Extra threads: repeatedly flood an objective; accept synchronization requests; accept
negotiation requests and conduct negotiations; manage subsidiary non-autonomic devices.
Threads exit or wait when done; multiple negotiating threads need queues and
synchronization. The main loop may initiate synchronization or negotiation, must watch
for policy changes, refresh credentials occasionally, and limit its own execution
frequency. The self-monitoring thread detects failure, fixes it, or restarts the ASA.
Event-loop models are an acceptable alternative to threads (GRASP API must then be
non-blocking with callbacks).

### 2.3 Interaction with the ANI (Section 4)

- **Security (4.1)**: the node is bootstrapped into the key infrastructure (BRSKI)
  before normal ASAs start; the key material secures the ACP and may secure additional
  peer interactions; bootstrap itself uses special-purpose ASAs with restricted (DULL)
  GRASP.
- **ACP (4.2)**: ASAs run as clients of the ACP, which provides a fully secured network
  for ASA-to-ASA communication, usually mediated by GRASP; ACP formation uses
  restricted-GRASP ASAs too.
- **GRASP and its API (4.3)**: GRASP likely runs as a separate process with a user-space
  API, so ASAs need no privilege unless their function requires it. Objectives are the
  ASA's view; the value's format and size are unconstrained except CBOR serializability
  and GRASP's maximum message size. API features: registration (ASA and objectives);
  discovery of ASAs supporting an objective; negotiation request + listen + stepping
  functions (symmetric, successive values until agreement or failure); synchronization
  request + listen (asymmetric: one value from listener to requester); flood (value
  flooded AN-wide). Extra communication may go directly over the ACP, using GRASP as a
  rendezvous (pass a TCP port via GRASP), preferably TLS over the ACP (RFC 8994 §6.9.2).
- **Policy (4.4)**: ANI policy mechanisms undefined at the time; declarative policies
  ("Intents") a research topic (RFC 9315); ETSI ZSM009-1 goal statements may apply to
  closed-loop ASAs; dissemination expected via GRASP to every ASA; **every ASA must
  work out of the box with carefully chosen defaults** for all policy parameters.

### 2.4 Non-autonomic components (Section 5)

An ASA must interact with the resource it manages and with local software managing the
same entity: if that is NETCONF, the ASA acts as an independent NETCONF client in the
same node to avoid inconsistency. In virtualized/sliced environments decide whether an
ASA runs per physical node or per virtual context, and whether one ANI or several
virtual ANIs exist.

### 2.5 Design of GRASP objectives (Section 6)

Format, names and IANA registration per RFC 8990. GRASP has no transactional
integrity; negotiation steps are not idempotent; design idempotent objectives when
possible; when allocating shared resources ensure no double allocation (easiest: one
negotiation at a time; overlapping negotiations must not interfere). Negotiations always
end (success, failure, timeout, loop count); specify the negotiation policy. **Dry run**
mode: a negotiation not committed until a later live negotiation; the specification must
say what state is saved, for how long, what happens if the live run comes after deletion,
and the requester must expect a successful dry run followed by a failed live run; support
dry run only where the benefit is significant. Values: any CBOR; simple items or tuples;
JSON-like structures easy; API may hand raw CBOR to the ASA. Size limited by
GRASP_DEF_MAX_SIZE (2048 bytes) unless the objective specifies larger for unicast and
multicast. YANG may be transported as YANG-CBOR. CBOR flexibility means values will be
extended in service, so ASAs must tolerate unknown components.

### 2.6 Life cycle (Section 7, Figure 1)

```
                  +--------------+
Undeployed ------>|  Installed   |------> Undeployed
              +-->|              |---+
  Mandate     |   +--------------+   | Receives a Mandate
  is revoked  |   +--------------+   |
              +---| Instantiated |<--+
              +-->|              |---+
  set down    |   +--------------+   | set up
              +---| Operational  |<--+
                  +--------------+
```

Seamless replacement of a running ASA by a new version must be designed in (service
continuity).

- **Installation (7.1)**: software loaded with libraries, not activated; checked for
  integrity and authenticity; properties: *dynamic installation* (on demand on any
  compatible host), *decoupling* (an ASA on one machine controls resources on another:
  "decoupled mode"), *multiplicity* (one ASA controls multiple resource sets). Inputs:
  ASA_type, Installation_target_infrastructure (candidate hosts),
  ASA_placement_function (decoupled mode only: explicit host list or criteria). Output:
  List_of_ASAs on List_of_hosts (a static interaction map for coordination). Primitives:
  install(...) and uninstall(...).
- **Instantiation (7.2)**: create an instance from installed software; start the code
  and determine which resources to control (straightforward when coupled; discovered or
  communicated when decoupled). Operator's goal: which resources are managed by which
  autonomic function (and which release), how ASAs are organized across nodes, and the
  goals (GRASP objectives). Instruction format: "[Instances_of_ASA_type] ready to control
  [Instantiation_target_infrastructure] with [Instantiation_target_parameters]". Inputs
  as named; output Set_of_ASA_resources_relations (a configuration log). Instructions
  are sent to a targeted ASA or broadcast to all; grouped as an **ASA Instance Mandate**
  (out of scope). The result is described by an **ASA Instance Manifest** (resources
  managed, metrics monitored, actions executable), needed for coordination and
  knowledge exchange.
- **Operation (7.3)**: operator can activate/deactivate loops, modify targets
  (objectives), modify managed resources (decoupled only); ASAs exchange knowledge
  (traffic predictions to a load balancer) and collaborate (link metrics by neighbour
  load); apply coordination schemes.
- **Removal (7.4)**: reverse the steps; purge data, especially key material.

### 2.7 Coordination and data models (Section 8)

Independent autonomic functions vs interfering ones (two optimizers on one parameter):
a method to identify and coordinate them is needed in a complete system. Coordination
with traditional management (CLI, DHCP, DHCPv6, SNMP, NETCONF, RESTCONF): avoid clashes
per deployment; RFC 8368 for OAM, RFC 8992 for prefix delegation vs DHCPv6; each objective
and ASA description should discuss such interactions. Data models: management functions
share a formal model (YANG); design the ASA and its objectives to match it; YANG as CBOR
may be the objective value directly.

### 2.8 Robustness (Section 9)

1. Fatal error: restart automatically after a pause (randomization, exponential backoff).
2. Out-of-bounds value: leave the parameter unchanged or restore a known-safe value.
3. Failed session: repeat after a pause with backoff.
4. Repeated failures: consider the peer failed, flush GRASP's discovery cache, rediscover.
5. Repeat discovery periodically anyway.
6. Check every received message; ignore malformed; M_INVALID may be sent in unicast
   sessions (GRASP itself may do this).
7. Check every received objective's syntax and semantics; ignore wrong ones; in a
   negotiation send M_END with O_DECLINE; log.
8. Tolerate unknown components in objective values; the objective's specification says
   whether to ignore, log and ignore, or reject.
9. On M_INVALID or M_END+O_DECLINE, the peer may lack a new feature: retry without it.
10. No unhandled exceptions.

Principle: an ASA moving the system from state (1) to a better state (2) must on error
return to (1), never to a worse state (3): "make-before-break" as in routing
reconfiguration; GRASP dry run supports "test-before-make".

### 2.9 Security (Section 10)

ASAs run inside the ACP (admission via BRSKI); the ACP provides keying material for
mutual authentication and confidential channels; a secure L2 partition might substitute.
ASAs remain responsible: when configuring elements outside the ACP they must not become
loopholes (no passing executable code, no proxying unverified commands), should run
unprivileged, validate all input, avoid privilege elevation, especially when talking to
a NETCONF server. Gateway ASAs between two ACPs must validate both sides. GRASP has no
transactional integrity. Privacy per RFC 6973. Initial trust model: every node admitted
to the ACP is trusted to manipulate any objective; fine-grained authorization of nodes
and ASAs for specific objectives is future work; interfaces between ASAs and the node's
configuration services can carry their own authentication, with parameters passed at
instantiation.

### 2.10 Appendix A example

A distributed resource (e.g. IPv6 prefixes, RFC 8992): one *origin* ASA gets the initial
pool and policy parameters from the NOC, floods and serves `EX1.Params`, listens for
negotiation of `EX1.Resource`; *delegators* start empty, learn parameters by flood or
synchronization, negotiate quantities from peers when low, hand out to subsidiary
consumers, garbage-collect returned pieces. Threads: MAIN (discover with M_DISCOVERY,
request_negotiate, M_END+O_ACCEPT/O_DECLINE, remember a good peer), MAIN_NEGOTIATOR
(listen_negotiate, spawn NEGOTIATOR), NEGOTIATOR (offer A or less, handle accept/decline),
DELEGATOR, GARBAGE_COLLECTOR. Pools must be in stable storage; GRASP is not idempotent so
integrity under failure is the designer's job; dry run would require reserving resources
until the live run or a timeout.

## 3. How Arcana maps onto each element, and what it would need

### 3.1 Arcana today in ASA terms

| 9222 element | Arcana today | Assessment |
|---|---|---|
| Autonomic node / ANI | a FreeBSD host with `arcana-agent`; no ACP, no GRASP, no BRSKI; the console is the only peer every host talks to | the agent is a *managed device agent* (RFC 7426 device with DAL), not an ASA: it has no peer-to-peer interaction; the Orchestrator does all coordination (`docs/NAMING.md`: "Orchestrator: what should happen? -> Agent: do it here") |
| Autonomic functions already present | steering failover (`invidia/sdwan.c`: the first tunnel not down is taken when a probe or BFD state changes, "without the console"); threshold rules with hysteresis (`gula/history.c`); record log rotation when a rule nears `logamount` (`gula/record.c`); SA rekey at the half-life with both ends installing inbound before outbound (119-3 task 3.4, orchestrated by the console); jobs queue surviving disconnection (`ira/jobs.c`) | device-local closed loops; the only cross-node loop (rekey) is coordinated centrally, which 9222 would do by GRASP negotiation |
| Managing subsidiary non-autonomic components (§3, §5) | plugins: BIRD via birdc, strongSwan via swanctl, Squid, dnsmasq, Suricata, c-icap, unbound, wg(8) (`luxuria/plugins.c`); the agent writes its own files beside hand-written ones (`arcana-<name>.conf` in swanctl conf.d, markers in ntp.conf, rc.conf via sysrc, jail.conf in place and read back with `jail -e`) | exactly §8.2's coexistence pattern: own namespace in shared configuration, read-back to detect clashes |
| GRASP API functions | none; the console pushes `sdwan-steer`, `sdwan-probes`, peers' public keys (`peer:ID` jobs) | synchronization and flooding are emulated by the console fanning out documents |
| Objectives / data model (§6, §8.3) | `share/arcana/jobs.yaml` declares, per job kind, what it needs, uses and destroys; `arcana.yaml` declares attribute policies with bounds (min/max, enums) | a manifest-like declaration exists for jobs; typed bounds checking exists on the wire |
| Dry run / test-before-make / make-before-break (§6, §9) | `ipfw -n` syntax check from a file beside the kept one; `GET /api/sdwan/plan` before apply; ipfw `apply` safe mode (old rules kept in a disabled set and swapped back unless confirmed within the time allowed); `job-confirm`; libjailconf write then `jail -e` read-back and restore on disagreement; new SAs installed beside old ones at the activation time | strong local implementation of the robustness principle; not generalized to all jobs |
| Life cycle: installation | pkg/port `sysutils/arcana`, `agent-update` and `agent-build` operations (dynamic installation from the console), integrity by pkg signatures | installed state exists; integrity check of console-driven builds should be explicit |
| Life cycle: instantiation | `arcana-enrol(8)` with a one-time token = the mandate carrier (certificate for the host name, console adds `tcp://host:port`); the SD-WAN document says which edges run which services = Instantiation_target_infrastructure; probe/BFD/TCA parameters = Instantiation_target_parameters | an implicit Instance Mandate spread over certificate, server list and document; no Instance Manifest the agent publishes back beyond `hello`/`plugins` |
| Life cycle: operation | jobs, `sdwan-steer`, settings; workflows activate/deactivate automation | activate/deactivate exists for workflows, not for the agent's own loops (probes can be removed, which is deactivation) |

| Security (§10) | agent runs as root ("the only privileged component"); console unprivileged; mTLS; CRL support in cblink; keys never leave hosts and never appear in traces (`exec_set_secret`) | 9222 wants ASAs unprivileged where possible: the privileged executor and the autonomic logic are one process today |
| Coordination between autonomic functions (§8.1) | implicit: one job queue serialized under one lock; steering tables swapped atomically; the console is the single writer | sufficient while there is one orchestrator; breaks when peer ASAs also write |

### 3.2 Proposal: ASAs for Arcana on FreeBSD

Prerequisite: an ACP and a GRASP daemon as in rfc8994.md. Then:

1. **A GRASP core process (`arcana-grasp`, unprivileged)** exposing an RFC 8991-style C
   API over the local AF_UNIX socket (or as a libcblink family `grasp`: `register-asa`,
   `register-objective`, `discover`, `request-negotiate`, `listen-negotiate`,
   `negotiate-step`, `end-negotiate`, `request-synchronize`, `listen-synchronize`,
   `flood`, `get-flood` with callbacks as cblink notifications). Two instances per RFC
   8990: DULL per interface (insecure, link-local, for ACP neighbour discovery) and the
   ACP instance (TCP 7017 link-local flooding, TLS unicast on the ACP address).
2. **Split the agent along the privilege line**: keep `arcana-agent` as the privileged
   executor (DAL + jobs + readers) and move autonomic logic into unprivileged ASA
   processes (or threads of an unprivileged `arcana-asa` daemon) that talk to the agent
   over the 0600 AF_UNIX socket with the same cblink family the console uses. This
   satisfies §10 and §4.3 ("ASAs may operate without special privilege") and reuses the
   existing authorization boundary.
3. **Candidate ASAs and their objectives** (private names need a colon and a globally
   unique prefix: use `freebsd.org/arcana:` or the project's FQDN; values YANG-CBOR of
   the corresponding Arcana YANG modules):
   - `arcana:steer` (synchronization, flooded per service): each edge floods the state
     of its tunnels (up/down, last probe metrics) so both ends of a tunnel and the
     console learn it consistently and the far edge can switch its own tables in step
     (today each edge decides alone, which can create asymmetric paths).
   - `arcana:sa-rekey` (negotiation, with dry run): the two ends of a `uswe` tunnel
     negotiate the activation time and new public halves peer-to-peer, honouring the
     manager's lifetime policy; dry run reserves the new SPIs and keys until the live run
     or a timeout; one negotiation per tunnel at a time (shared resource rule).
   - `arcana:tunnel` (negotiation): inner /127 and MTU of a tunnel pair, replacing
     central allocation when two edges are told to connect but the console is
     unreachable (CAP availability).
   - `arcana:fault` (flood): faults with Mplify 119 attributes, so neighbours and the
     console hear them even when the data plane to the console is down (over the ACP).
   - `arcana:params` (flood + synchronization, origin = console host): probe, TCA,
     BFD and history parameters as policy parameters, with built-in defaults so an ASA
     works "out of the box" (§4.4).
   - `arcana:console` (flood, origin = console host): the console's ACP locator for
     agents, replacing the static server list direction (agents find the console; the
     console still finds agents by the certificate's ACP address).
   Each objective's specification states: idempotence, loop count and timeout, dry-run
   state and its lifetime, maximum size (keep under 2048 bytes or specify), handling of
   unknown value members (ignore and log), negotiation policy and tie-breaking.
4. **Life cycle made explicit**: *Installed* = package present; *Instantiated* = enrolled
   (the ACP certificate is the mandate carrier: roles and the ACP address in the
   certificate per RFC 8994 A.9.5) and the console's document names the ASA's resources
   (services, tunnels); the agent publishes an **Instance Manifest** (a YANG `asa`
   list: name, version, objectives, resources managed, metrics, actions) readable by the
   console and flooded on the ACP; *Operational* = loops enabled per ASA (an
   `enable`/`disable` leaf per ASA, which the console sets); *Removal* = an `unenrol`
   operation that revokes the certificate, purges keys (host key, WireGuard keys, uswe
   pairs, SAs), removes kept files and leaves the host clean.
5. **Self-monitoring and restart**: a watchdog thread in the agent (checks reader threads
   are alive, probe sockets open, lock not held too long), `arcana_agent` rc script with
   supervision (restart with randomized exponential backoff), and the console's
   `host-down` as the outer supervision.
6. **Robustness rules applied**: validate every received objective against the YANG
   model (cblink policies already enforce attribute bounds); out-of-range values leave
   the running configuration untouched (point 2); failed negotiations retry with backoff
   and after N failures flush the discovery cache (point 4); periodic rediscovery (point
   5); tolerate unknown members (point 8); generalize make-before-break: every
   connectivity-affecting job gets the ipfw-style confirm-or-revert.
7. **Coordination (§8.1)**: extend `jobs.yaml` with the resource each job and each ASA
   touches (table, FIB, interface, rule set) and let the agent refuse or serialize
   overlapping writers (steer ASA vs console `sdwan-steer`; BIRD config by console vs by
   an IGP ASA); record the owner of each kept file. §8.2: keep writing only Arcana-owned
   files/sections (already the practice) and read back.
8. **Virtual context decision (§5)**: one ANI per fleet; one ASA set per host; vnet
   jails that are SD-WAN edges are controlled by the host's ASAs (decoupled mode within
   the host), consistent with the agent's `-Q jid` helper model.

## 4. Cannot be mapped / not applicable

- **BRSKI bootstrap of ASAs' nodes**: no manufacturer IDevID/MASA for general-purpose
  FreeBSD hosts; the token enrolment stands in (rfc8994.md §3).
- **Constrained devices**: all Arcana nodes are full hosts.
- **Gateway ASAs between two ACPs / inter-domain GRASP**: single administrative domain
  today; Mplify 119 interop with other vendors' edges is by BGP/IPsec, not GRASP.
- **ETSI ZSM closed-loop goal statements**: not used.
- **Resource delegation example as such**: Arcana allocates tunnel addresses and FIBs
  centrally from reserved prefixes; distributed delegation only matters if several
  consoles or offline operation are wanted (then the `arcana:tunnel` objective is the
  minimal form).

## 5. Checklist Arcana could be measured against

1. Autonomic logic runs unprivileged and reaches the privileged executor through an
   authenticated local interface.
2. Each autonomic function is an identifiable ASA with a name, version, the objectives it
   manages, the resources it controls and the actions it may take (Instance Manifest).
3. ASAs communicate peer-to-peer only inside the ACP, authenticated by the domain
   certificate, with TLS for unicast beyond GRASP.
4. Every GRASP objective Arcana defines has a published specification: unique name with
   a globally unique prefix, CBOR (YANG-CBOR) value schema, flags, loop count, timeout,
   size limit, idempotence statement, dry-run semantics, unknown-member policy,
   negotiation policy and failure handling.
5. ASAs work with built-in defaults when no policy parameters are received.
6. ASAs tolerate GRASP core restarts, discovery cache loss, peer failure and malformed
   input without crashing; failures restart with randomized exponential backoff.
7. Discovery is repeated periodically and after repeated session failures.
8. Changes are make-before-break or test-before-make with automatic reversion to the
   previous state on failure or missing confirmation.
9. Shared resources (SPIs, addresses, table slots) are never double-allocated: one
   negotiation at a time per resource or equivalent locking.
10. ASAs that share configuration with other tools write only their own sections/files
    and read back the effective configuration.
11. Interfering ASAs are identified (declared resources) and coordinated.
12. Installation, instantiation, operation and removal are explicit operations; removal
    purges keys and kept state.
13. A self-monitoring component exists on the node and a supervising one in the console.
14. ASAs never pass executable code or unverified commands to the executor; all input is
    validated against the model.
15. Objectives match the YANG data model used by management so that the console and ASAs
    see the same data.

## 6. Open decisions and trade-offs

- **How much autonomy to move out of the console**: peer-to-peer steering and rekey
  reduce dependence on the console and fix asymmetric failover, but the console's trace
  tree currently explains every change; ASA decisions need their own audit (flood them to
  the console as events).
- **Threads in the agent vs separate ASA processes**: processes give the privilege
  split and crash isolation 9222 asks for; threads are simpler and share the agent's
  readers. A single unprivileged `arcana-asa` process with threads per ASA is the middle
  path.
- **GRASP API shape**: a C library mirroring RFC 8991 (blocking calls, threads) vs a
  cblink family (asynchronous, fits the event-loop model the agent already uses for
  streams). The RFC allows either.
- **Idempotence vs expressiveness** of objectives: idempotent "desired state" values
  (like the SD-WAN document) are safer than imperative steps; negotiation then converges
  on a state, not on an action.
- **Dry run only where it pays**: rekey and address allocation; not for steering.
- **Trust granularity**: 9222's initial model trusts every ACP member for every
  objective; Arcana can be stricter from the start by putting roles (edge, control-plane
  host, console) in the certificate (RFC 8994 A.9.5) and letting the GRASP core filter
  objectives by role.
