# RFC 7426 — Software-Defined Networking (SDN): Layers and Architecture Terminology

IRTF SDNRG, Informational, January 2015. Source: `scratchpad/rfc/rfc7426.txt` (read in full).

## 1. Purpose

RFC 7426 is a vocabulary, not a protocol. It consolidates what "SDN" means in the
peer-reviewed literature and the RFC series into one layered reference model so that
people stop calling both OpenFlow (a control interface) and NETCONF (a management
interface) "the SDN interface" without qualification. It defines planes (forwarding,
operational, control, management, application), abstraction layers (DAL, CAL, MAL,
NSAL) and the interfaces between them (CP and MP southbound interfaces, service
interface), discusses what separates control from management (timescale, persistence,
locality, CAP theorem) and then shows where ForCES, NETCONF/YANG, OpenFlow, I2RS, SNMP,
PCEP and BFD sit in that model. It explicitly does not standardise any layer, does not
cover orchestration or resource allocation, and treats physical and virtual resources
alike. For Arcana it is the yardstick for saying precisely which program is the
controller, which interface is the SBI, which the NBI, and what is missing.

## 2. Terminology and architecture, completely

### 2.1 Terms (Section 2)

| Term | Definition (RFC wording condensed) |
|---|---|
| SDN | A programmable-networks approach that separates control and forwarding planes via standardized interfaces. |
| Resource | A physical or virtual component in a system; fine-grained (port, queue) or complex (a whole device). |
| Network Device | A device performing packet manipulation/forwarding; physical or virtual; a container of resources and a resource itself. |
| Interface | A point of interaction between two entities; a network protocol when remote; an API, IPC or protocol when collocated. |
| Application (App) | Software that uses underlying services to perform a function and offers no interface to other apps/services. |
| Service | Software performing functions that provides one or more APIs to applications or other services; composable. |
| Forwarding Plane (FP) | The collection of resources across all devices responsible for forwarding traffic ("data plane", "data path"). |
| Operational Plane (OP) | The resources responsible for managing the overall operation of individual devices (active/inactive, ports, their status). |
| Control Plane (CP) | Functions that control one or more devices: instructs the FP how to process and forward packets; interacts primarily with FP, less with OP. |
| Management Plane (MP) | Functions that monitor, configure and maintain devices; mostly related to OP, less to FP. |
| Application Plane | The collection of applications and services that program network behaviour. |
| DAL | Device and resource Abstraction Layer: the device's resource abstraction based on one or more models (HAL when physical); a uniform point of reference for FP and OP resources. |
| CAL | Control Abstraction Layer: gives control-plane apps/services access to the CP Southbound Interface (CPSI). |
| MAL | Management Abstraction Layer: gives management-plane apps/services access to the MP Southbound Interface (MPSI). |
| NSAL | Network Services Abstraction Layer: service abstractions usable by applications and services. |

Notes the RFC attaches to the figure: planes may be collocated or separated; when
separated the interface can only be a protocol, when collocated it may be a protocol,
an IPC API or kernel system calls. Apps and services may span planes (an app using both
OpenFlow and OF-CONFIG uses CPSI and MPSI); services spanning several planes belong to
the application plane. Layers can be stacked recursively (hierarchical controllers,
virtual resources on physical ones). Historically the MP sat on top of the CP (CP as a
service to the MP); with SDN that distinction blurs. Apps may also reside *in the
device* (event monitoring, topology discovery or ARP offloaded into the device).

### 2.3 The planes in detail (Sections 3.1 to 3.7)

- **Forwarding plane**: handles packets in the data path on CP instructions; forward,
  drop, change; termination point of CP services; resources include filters, meters,
  markers, classifiers.
- **Operational plane**: operational state of the device (active, port count, port
  status); termination point of MP services; resources: memory, CPU, ports, interfaces,
  queues. Some SDNRG participants consider it not a plane but functions of the FP; the
  RFC keeps it as a plane.
- **Control plane**: decides how packets are forwarded and pushes decisions down;
  usually distributed; functions: topology discovery and maintenance, route selection
  and instantiation, path failover. East-west interface between CP entities (BGP, PCEP),
  in-band, redirected by the FP to the CP. CPSI characteristics: time-critical (low
  latency, sometimes high bandwidth), wire-efficient and device-oriented rather than
  human-readable; fast, high-frequency table updates, robustness for packet handling
  and events; a protocol when not collocated (ForCES, OpenFlow). Control *apps*: OSPF,
  IS-IS, BGP. Control *services*: VPLS, service tunnels, topology services.
- **Management plane**: usually centralized; ensures the network as a whole runs
  optimally; functions per FCAPS: fault and monitoring management, configuration
  management; may include orchestrators, VNF managers, VIMs (NFV); configures the FP
  only infrequently and "wholesale". MPSI: not time-critical, usability first (RFC 3535:
  ease of use over performance; UTF-8 strings, case-insensitive ASCII protocol
  elements), less frequent messages; examples ForCES, NETCONF, IPFIX, syslog, OVSDB,
  SNMP. Management apps: monitoring, fault detection, recovery.
- **Section 3.5 control vs management**: *timescale* (CP milliseconds, MP minutes to
  days), *persistence* (CP ephemeral state e.g. routing; MP persistent state surviving
  reboots), *locality* (CP local and distributed, MP remote and central; SDN muddles
  this), *CAP theorem* (consistency, availability, partition tolerance; CP operations
  local and fast = available, MP central = consistent; a centralized SDN controller is a
  consistent global database; a switch cut from its controller has unavailable flows;
  multiple controllers improve partition tolerance at the cost of consistency).
- **NSAL (3.6)**: access from CP/MP/application services to other services; service
  interfaces: RESTful (resource identification by URI, representation manipulation,
  self-descriptive messages, hypermedia) or RPC (procedure identifier, client knows
  name and parameters); also NETCONF, IPC, CORBA.
- **Application plane (3.7)**: apps and services using CP and/or MP services; examples
  topology discovery, provisioning, path reservation.

### 2.4 The model view (Section 4)

"The SDN southbound interface should encompass both CPSI and MPSI." Controllers (NOX,
Beacon) are collections of CP apps/services implementing a CPSI and offering a
*northbound interface implemented in the NSAL*.

| Technology | DAL | CPSI | MPSI | Other |
|---|---|---|---|---|
| ForCES (RFC 3746/5810/5812) | ForCES model (LFBs) for FP and OP | ForCES protocol | could be MPSI too | Set/Get/Del, high throughput |
| NETCONF/YANG | YANG models for FP and OP | not designed for fast CP updates | NETCONF | RPC-based, XML |
| OpenFlow | OpenFlow switch spec (FP) | OpenFlow protocol | OF-CONFIG = YANG DAL (FP+OP) + NETCONF | |
| I2RS | any available DAL | any CPSI | SNMP/NETCONF for agent management | agent = CP service; spans CP and application planes; info model in NSAL |
| SNMP | MIBs for FP and OP | — | SNMP | |
| PCEP | — | active PCE for (G)MPLS LSPs | — | PCE = CP service; PCEP east-west between PCEs |
| BFD | — | a BFD agent could use CPSI | — | usually an app *on the device* using the FP, updating OP resources; CP/MP subscribers learn through their interfaces |

Security (Section 6): none of its own; refers to SDN security literature and the
interface specs.

## 3. How Arcana maps onto each element, and what it would need

### 3.1 Mapping of today's Arcana

| RFC 7426 element | Arcana today | Where |

| DAL | `share/arcana/arcana.yaml`: the cblink family (attribute sets, 60-odd `do`/`dump` ops, one mcast group `events`, four streams) plus the C structures cblink-gen generates. | MAL | the console's connection pool and trace stacking (`hosts.c`), the SD-WAN compiler from service document to per-edge jobs (`sdwan_edge.c`), the jobs vocabulary (`jobs.yaml`) | `www/arcana-console/hosts.c`, `sdwan_edge.c`, `share/arcana/jobs.yaml` |
| CAL | not a distinct layer. Control decisions (tunnel ordering by performance criteria, which tunnel a prefix uses, BFD parameters) are computed in the console's SD-WAN manager and shipped through the MAL as jobs/`sdwan-steer`. | `sdwan.c`, `sdwan_edge.c`, agent `invidia/sdwan.c` |

So: *controller* = console; *SBI* = cblink `arcana` family (acting as both CPSI and
MPSI); *NBI* = the console's REST/WebSocket API; *management plane* = console + the
agent's management ops; *control plane* = console steering manager + BIRD + agent-local
failover; *DAL* = `arcana.yaml`.

### 3.2 What is missing, measured against the RFC

1. **No model-based DAL.** `arcana.yaml` is a transport contract, not a device model;
   half of the payloads are opaque JSON. The RFC's DAL examples are all models (YANG,
   ForCES, MIBs). This is exactly what the planned "strictly YANG" redesign fixes.
2. **CPSI and MPSI are the same channel with the same priority.** The RFC wants the
   CPSI time-critical and wire-efficient; a slow dump or a `pkg upgrade` trace on the
   same cblink connection can delay a steering update. SCTP transport already
   multiplexes cblink streams on SCTP streams (`cblink/docs/TRANSPORTS.md`), which is
   the hook for separation.
3. **No CAL.** Control logic is spread between `sdwan.c`/`sdwan_edge.c` in the console
   and `invidia/sdwan.c` in the agent with no named interface between "decide" and
   "program". A CAL would be the place where a future GRASP/ACP-based distributed
   control plane (see rfc8994.md, rfc9222.md) plugs in beside the central manager.
4. **One controller, CAP ignored.** A host that loses the console keeps forwarding and
   failing over locally (good: "available"), but no second console can take over and
   agents accept exactly one CA/one server list. The RFC's discussion of multiple
   non-collocated controllers applies.
5. **NBI is read-mostly for machines.** API tokens open GETs only; writes require a
   WebAuthn session. There is no standard NBI (RESTCONF) and no machine subscription
   other than the page-oriented WebSocket.
6. **`arcanactl` bypasses the NSAL**: it is an application talking the SBI, acceptable
   for admins and tests, but it means the SBI must carry authorization on its own
   (it does: mTLS or the 0600 socket).

### 3.3 Concrete proposal for Arcana on FreeBSD

1. **Name the planes in `docs/ARCHITECTURE.md`** with RFC 7426's words: FP = kernel,
   OP = what the agent reads, DAL = YANG modules, CPSI/MPSI = cblink profiles, CAL/MAL =
   console modules, NSAL = REST + RESTCONF + WebSocket, application plane = PWA,
   workflows, SD-WAN manager, SASE.
2. **DAL as YANG, carried by cblink.** Replace per-feature attribute sets with a
   generic datastore family (`get`, `get-config`, `edit-config`, `action`/`rpc`,
   `subscribe`, following NETCONF/RESTCONF semantics and NMDA datastores, RFC 8342:
   running/intended/applied/operational) whose payload is YANG data encoded as
   YANG-CBOR (RFC 9254, with YANG SIDs RFC 9595 so that identifiers stay small on the
   wire). Reuse standard modules where FreeBSD has the feature: `ietf-interfaces`
   (RFC 8343), `ietf-ip` (RFC 8344), `ietf-routing`/`ietf-ipv4/6-unicast-routing`
   (RFC 8349, with a FIB-index augmentation; netlink(4) is already the agent's native
   route interface), `ietf-access-control-list` (RFC 8519, as far as ipfw can be
   expressed; the rest in an `arcana-ipfw` module including dummynet and tables),
   `ietf-system` (RFC 7317: hostname, NTP, users), `ietf-hardware`/`ietf-system`
   state, the I2NSF IPsec models of RFC 9061 (IKE and "ikeless" cases: the ikeless
   case is precisely manually keyed SAs on an interface, i.e. Mplify 119-3 and
   setkey(8)), `ietf-syslog`, plus Arcana modules for jails, services, pkg, ZFS,
   WireGuard, BIRD, netgraph, SD-WAN (MEF 70.2 attributes) and faults. cblink-gen
   would then generate from YANG (or from a YANG-to-cblink-spec step) instead of a
   bespoke YAML.
3. **CPSI profile.** Define which operations are control-plane (`sdwan-steer` table
   swaps, probe and BFD state notifications, route programming) and give them their own
   cblink stream/SCTP stream with a latency budget and a small CBOR encoding; keep
   dumps and traces on the management stream. Over TCP, use a second connection for
   control.
4. **CAL.** Factor the steering manager into a module with a defined interface
   (inputs: topology, probe/BFD samples, policy criteria; output: ordered candidate
   lists per prefix) so that an on-device ASA (rfc9222.md) and the console can share
   it; the edge's local failover is the device-resident part of the CAL.
5. **NBI.** Serve the same YANG at the console as RESTCONF (RFC 8040) with
   YANG-Push over HTTPS (RFC 8650) for subscriptions; keep the JSON API for the PWA;
   add role-bearing API tokens (read, operate, administer) so machines can write.
6. **Multiple controllers.** Let an agent trust a CA, not a single console, and keep a
   server list of several consoles; define ownership/leases for the SD-WAN document
   (the document's version counter is already optimistic concurrency) and an east-west
   console sync (or make the BIRD route reflector plus GRASP flooding the distributed
   control plane and the console purely MP, which is the RFC's classical layout).
7. **Legacy MPSI, optional.** bsnmpd(8) in base can expose standard MIBs to an existing
   NMS without new code; syslog export already exists via syslogd; IPFIX via ng_netflow
   (see rfc9232.md).

## 4. Cannot be mapped / not applicable

- **ForCES LFB model and protocol**: no FreeBSD implementation and FreeBSD's forwarding
  path is not an LFB graph; netgraph(4) is the closest in spirit (nodes and hooks) but
  only for the netgraph subsystem. Not worth a mapping beyond the DAL idea.
- **OpenFlow / OF-CONFIG**: FreeBSD has no OpenFlow switch in base; ipfw tables with
  `fwd`/`skipto tablearg` resemble match-action but are not a flow-table pipeline. Not
  pursued.
- **PCEP / active PCE**: requires MPLS or GMPLS LSPs. Arcana declined kernel MPLS
  (PLAN-119 phase 4). Not applicable.
- **I2RS protocol**: never completed as a protocol; FreeBSD's netlink(4) is the local
  equivalent of a programmable RIB interface and is already used.
- **Hardware abstraction (HAL)**: software-only devices; the HAL note is moot.
- **CAP for forwarding consistency across many switches**: Arcana's forwarding decisions
  are per host (ipfw rules per edge); cross-host consistency is a routing-protocol
  matter handled by BIRD, not by the controller's flow pushes.

## 5. Checklist Arcana could be measured against

1. The architecture document names, for every component, its RFC 7426 plane and layer.
2. The device abstraction (DAL) is a formal data model (YANG), covering both forwarding
   and operational resources, from which the wire contract is generated.
3. Forwarding-plane state (routes, ACLs, SAs, tunnels) and operational state
   (interfaces, counters, jails, services) are readable through the same DAL with
   consistent naming.
4. A control-plane southbound profile exists: identified operations, bounded latency,
   compact encoding, isolated from bulk management traffic.
5. A management-plane southbound profile exists: human-usable, UTF-8, persistent
   configuration semantics (survives reboot) separated from ephemeral state.
6. Control state is treated as ephemeral (steering tables rebuilt from policy and
   measurements), management state as persistent (documents, rc.conf, kept files).
7. The controller exposes a northbound service interface (REST and/or RESTCONF) for
   applications other than its own UI, with authorization suitable for machines.
8. Applications that span planes (SD-WAN manager, SASE) are identified as
   application-plane services and consume CP and MP through defined service interfaces,
   not by reaching into the SBI directly.
9. Device-resident control applications (probe/BFD-driven failover, threshold rules)
   are documented as such, with what they decide without the controller.
10. East-west control between devices (iBGP, OSPF, BFD, future GRASP) is documented and
    its security stated.
11. Loss of the controller is analysed per CAP: what stays available, what becomes
    stale, how a second controller can take over.
12. More than one controller instance can own the fleet (or the design states why not).
13. The CLI (`arcanactl`) is recognised as an application on the SBI and the SBI's
    own authorization is sufficient for it.
14. Security of each interface (SBI mTLS/DTLS, NBI WebAuthn/tokens, east-west TCP-MD5,
    IPsec) is written down per interface.

## 6. Open decisions and trade-offs

- **YANG over cblink vs NETCONF/RESTCONF on the agent.** Keeping cblink (CBOR, mTLS,
  streams, notifications, generated C) and carrying YANG-CBOR inside it keeps the
  agent small and FreeBSD-native but is a non-standard MPSI; adding a RESTCONF server
  on every agent would give standard tooling access but duplicate the auth/transport
  layer and add an HTTP server to the privileged daemon. Middle path: standard YANG,
  cblink transport on the SBI, RESTCONF only on the console (NBI).
- **How far to push CPSI/MPSI separation.** A separate SCTP/TCP stream costs little;
  a separate protocol costs a lot. The RFC only asks for the characteristics
  (latency, efficiency), not a second protocol.
- **Centralized steering vs distributed control plane.** Today the console computes
  the tunnel order; a GRASP/ACP-based ASA could do it edge-to-edge. More autonomy means
  less single-point-of-failure but harder explainability (the trace model is a strength
  of the central design).
- **Multiple controllers**: true consistency (consensus between consoles) is heavy for
  a one-user project; a primary/standby with a shared document store and agents
  trusting the CA rather than one console may be enough.
- **How much of ipfw fits `ietf-access-control-list`**: tables, dummynet, NAT, divert,
  skipto/fwd tablearg have no standard model; expect an Arcana augmentation that is
  larger than the standard part.
- **Operational plane as a plane**: the RFC admits the SDNRG split on this; for Arcana
  it is useful because the agent's OP reads (history, stats, jails) are its bulk.
