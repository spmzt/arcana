# RFC 8955 — Dissemination of Flow Specification Rules (BGP FlowSpec), with RFC 8956 (IPv6)

Sources read in full: `rfc/rfc8955.txt` (December 2020, Standards Track, obsoletes RFC 5575
and RFC 7674) and `rfc/rfc8956.txt` (IPv6 FlowSpec, December 2020). BIRD 3.x documentation
(bird.network.cz, v=30, chapters 5 and 6) checked online for flowspec support and syntax.
RFC 9117 (revised validation, referenced by BIRD) not read; BIRD implements it.

## 1. Purpose

FlowSpec carries n-tuple traffic filters ("Flow Specifications") as BGP NLRI (AFI 1 SAFI 133
for IPv4 unicast, SAFI 134 for VPNv4; RFC 8956 adds AFI 2 for IPv6) together with traffic
filtering actions encoded as transitive BGP extended communities (rate limit in bytes or
packets, sample/terminal action bits, redirect to a VRF by route target, DSCP remarking).
Its applications are inter-domain DDoS mitigation, filtering inside BGP/MPLS VPNs, and
centralised traffic control in SDN/NFV. A received Flow Specification is validated against
unicast routing (the originator of the best unicast route for the destination prefix may
filter traffic to it) and ordered deterministically so every router applies the same
precedence. For Arcana it is the standard way to push ACL-like policy (drop, rate limit,
mark, steer into a FIB) across the fleet through BIRD instead of only through the console's
own cblink ops; the catch is that FreeBSD has no kernel consumer of flowspec routes, so the
agent must translate BIRD's flowspec table into ipfw rules.

## 2. Content

### 2.1 NLRI (RFC 8955 §4)
- Carried in MP_REACH_NLRI / MP_UNREACH_NLRI (RFC 4760); Next-Hop length MUST be 0 and the
  next-hop ignored. Capability (AFI=1, SAFI=133) or (1,134) MUST be negotiated; for IPv6
  (2,133)/(2,134).
- NLRI = `<length, value>`; length 1 octet if < 240, else 2 octets `0xfnnn` (max 4095).
- Value = sequence of components in **strictly increasing type order, each type at most
  once**; a packet matches if it matches **all** components (AND). Unknown component type or
  bad encoding → malformed → RFC 7606 error handling (§10). Impossible combinations (ICMP type
  AND port) SHOULD NOT be propagated.
- VPNv4 (SAFI 134, §8): 8-octet Route Distinguisher precedes the components; propagation by
  Route Targets as RFC 4364; rules apply only to traffic of the importing VRF; accepted by
  default from remote PEs (no validation step); MPLS-switched traffic not filtered by default.

**Operators**
- `numeric_op` (1 octet): `e a len(2) 0 lt gt eq`. `e` end-of-list; `a` AND with the previous
  pair (OR when unset; AND binds tighter than OR; first operator's `a` MUST be 0); `len`
  encodes value size 1/2/4/8 octets (1<<len). lt/gt/eq combinations: 000 false, 001 ==,
  010 >, 011 >=, 100 <, 101 <=, 110 !=, 111 true.
- `bitmask_op` (1 octet): `e a len(2) 0 0 not m`. `m`=1: match if (data AND value) == value;
  `m`=0: match if any bit of value is set in data; `not` negates.

**Components (IPv4 names / IPv6 names per RFC 8956, same type numbers)**

| Type | IPv4 (8955) | IPv6 (8956) | Encoding |
|---|---|---|---|
| 1 | Destination Prefix | Destination IPv6 Prefix | v4: `<len, prefix>` as BGP UPDATE; v6: `<length, offset, pattern, padding>` — offset = most-significant bits to skip, pattern = length−offset bits; length=0,offset=0 matches all, else offset < length < 129 |
| 2 | Source Prefix | Source IPv6 Prefix | same |
| 3 | IP Protocol | Upper-Layer Protocol (first non-extension Next Header) | numeric_op list, SHOULD be 1-octet values |
| 4 | Port | Port | numeric_op; matches **source OR destination** TCP/UDP port; 1–2 octet |
| 5 | Destination Port | Destination Port | numeric_op |
| 6 | Source Port | Source Port | numeric_op |
| 7 | ICMP Type | ICMPv6 Type | numeric_op, 1 octet |
| 8 | ICMP Code | ICMPv6 Code | numeric_op, 1 octet |
| 9 | TCP Flags | TCP Flags | bitmask_op, 1 octet = TCP octet 14 (control bits), 2 octets = octets 13–14 with data offset treated as 0 |
| 10 | Packet Length | Packet Length | numeric_op, total IP length incl. header, excl. L2; 1–2 octets |
| 11 | DSCP | DSCP | numeric_op, MUST be 1 octet, 6 LSBs |
| 12 | Fragment | Fragment | bitmask_op, MUST be 1 octet: v4 bits `0000 LF FF IsF DF`; v6 `0000 LF FF IsF 0` (no DF) |
| 13 | — (unassigned) | Flow Label (new in 8956) | numeric_op, SHOULD be 4-octet values, 20-bit label |

Component rules: port/ICMP/TCP-flags components never match when the IP protocol is not
TCP/UDP (6/17) resp. ICMP (1) / ICMPv6 (58) / TCP, when the packet is a non-first fragment, or
when the transport header cannot be located (IP options, ESP-NULL, oversized IPv6 header
chains — RFC 7112/8883). DF: IPv4 flags bit 1; IsF: fragment offset ≠ 0; FF: offset 0 AND
MF; LF: offset ≠ 0 AND MF=0 (IPv6: from the Fragment header).

Examples (§4.3): "to 192.0.2.0/24 and TCP port 25" = `0b 01 18 c0 00 02 03 81 06 04 81 19`;
port range [137,139] or 8080 = `04 03 89 45 8b 91 1f 90` (`03` = >=, `45` = AND <=, `91` =
end, 2 octets, ==); fragment {DF or FF} = `0c 80 05`. IPv6 (RFC 8956 §3.8): source
`::1234:5678:9a00:0/64-104` = `02 68 40 12 34 56 78 9a` (length 104, offset 64, 40-bit
pattern); with offset 65 the pattern is shifted and padded to an octet.

### 2.2 Ordering (§5.1, RFC 8956 §4)
Compare component by component from the lowest type: the spec that has the lower-numbered
component type has precedence over one lacking it; equal types → type-specific comparison;
equal → next component. Prefixes: if one is more specific it wins, else the lower IP value
wins. IPv6: if offsets differ the lower offset wins, else as IPv4 on the pattern (longest
prefix, then lowest). Other components: `memcmp` on the encoded (op, value) string; equal
length → lowest wins; different lengths → compare the common prefix, lowest wins, if equal the
**longer** string wins. Appendix A (8955) and Appendix A (8956) give Python reference code
(`flow_rule_cmp`, `flow_rule_cmp_v6`). Order is independent of arrival order.

### 2.3 Validation (§6, RFC 8956 §5)
A Flow Specification (SAFI 133 validated against SAFI 1 routes, 134 against 128) is feasible
iff: (a) it contains a destination prefix component (IPv6: with offset = 0); (b) the
originator (ORIGINATOR_ID or peer address) equals the originator of the best-match unicast
route (longest prefix covering the destination); (c) no more-specific unicast route for that
destination was received from a *different* neighbouring AS. Rule (a) MAY be relaxed by
configuration, then (b)/(c) are moot. eBGP: the left-most AS_PATH element MUST be the
neighbour AS. Re-validate whenever unicast routes change. Rationale: the AS that is the
destination of the traffic may ask that it be dropped. (RFC 9117 refines this for iBGP/route
servers; BIRD implements both.)

### 2.4 Traffic Filtering Actions (§7) — transitive extended communities
Default action for a match: accept (normal forwarding). Multiple actions SHOULD all be applied;
interfering ones are an implementation decision that SHOULD be documented (§7.7).

| Community | Action | Encoding |
|---|---|---|
| 0x8006 | traffic-rate-bytes | 2-octet AS (informational) + IEEE 754 float, bytes/s; 0 = discard; negative → 0 |
| 0x800c | traffic-rate-packets (new vs 5575) | same, packets/s |
| 0x8007 | traffic-action | 6 octets; bit 47 **T** Terminal: when set, evaluation *continues* with subsequent specs (when unset it stops); bit 46 **S** Sample: enable sampling/logging; other bits 0 |
| 0x8008 | rt-redirect AS-2octet | RT as RFC 4360 §3.1 (2-octet AS, 4-octet value), sub-type 0x08 |
| 0x8108 | rt-redirect IPv4 | 4-octet IPv4 + 2-octet value |
| 0x8208 | rt-redirect AS-4octet | 4-octet AS + 2-octet value (RFC 5668) |
| 0x8009 | traffic-marking | 6 octets, DSCP in the 6 LSBs of the last octet |
| 0x000d (IPv6-address-specific) | rt-redirect-ipv6 (RFC 8956 §6.1) | IPv6 RT as RFC 5701, type 0x000d |

Redirect = send matching traffic to the VRF whose import policy lists that RT (several match →
local choice, e.g. lowest RD). Interference: the two rate limits may conflict unless policy
allows both; all redirects interfere with each other; T-bit multiplicity means several specs
may match and all their actions are collected. §7.6: implementations should let arbitrary
communities map to local actions (e.g. worse-than-best-effort PHB).

### 2.5 Monitoring, errors, IANA, security
- §9: SHOULD log headers of filtered traffic and count matches per rule.
- §10: RFC 7606 treat-as-withdraw style handling; malformed action communities = undecodable
  per §7.
- §11: SAFI 133/134 renamed; YANG enums `flow-spec-safi`/`l3vpn-flow-spec-safi` in
  `iana-routing-types` (RFC 8294) updated; component type registry 1–127 Specification
  Required, 128–254 Expert Review; "Traffic Action Fields" registry (bits 46, 47).
- §12 security: equivalent to BGP unicast security as long as validation holds; relaxation
  must be accompanied by filtering; IXP route servers do not extend AS_PATH → strict inbound
  policy; firewall-like state in routers complicates diagnosis; rogue automated controllers
  may flood specs → cap number/rate; screen action communities from third parties (only expose
  a subset, map user communities to actions); device capacity limits.

### 2.6 BIRD 3 (FreeBSD port net/bird3) flowspec support — from the online docs
- Channels/tables `flow4` (AFI 1 SAFI 133) and `flow6` (AFI 2 SAFI 133). **No VPN flowspec
  (SAFI 134) channel** in the channel table.
- BGP channel option `validate switch` implements RFC 8955 §6 + RFC 9117; `base table name`
  selects the unicast table (must have `trie` enabled; ipv4 for flow4, ipv6 for flow6);
  default off; does not work reliably with `import table`.
- Static flowspec routes: `route flow4 { dst 10.0.0.0/8; src …; proto 6; port 1..1023,1194;
  dport 49151; sport = 0; icmp type 3; icmp code 1; tcp flags 0x03/0x0f; length > 1500;
  dscp 8..15; fragment dont_fragment, is_fragment || !first_fragment; }` — numeric matches
  as lists/ranges or `=,!=,<,<=,>,>=,true,false` chained with `&&`/`||`; bitmask matches
  `value/mask` or `!value/mask`. `dst` mandatory for flow4; flow6 adds `offset num` on
  prefixes, `next header`, `label bitmask`, and has no `dont_fragment` and no mandatory
  component.
- Filters: `NET_FLOW4/NET_FLOW6` types; "filters currently do not support much flowspec
  parsing, only `.src` and `.dst`". Actions are plain `bgp_ext_community` values; unknown
  types print/parse as `(generic, 0x80060000, 0x…)`, route targets as `(rt, AS, N)`.
- No kernel protocol for flow tables (the `kernel` protocol handles ipv4/ipv6/mpls only); the
  only way out of BIRD is `show route table <flow4> all` on the CLI socket (birdc) or export
  to another BGP/pipe.

## 3. How Arcana could realise it on FreeBSD

FreeBSD's kernel has no flowspec consumer; ipfw is the enforcement engine Arcana already
drives. Design: **BIRD receives and validates, the agent translates into an ipfw set, the
console originates**.

1. **Receive**: each per-service BIRD instance (luxuria/sdbird.c already renders templates and
   runs `birdc` on the instance's socket) gets `flow4`/`flow6` channels on the iBGP session to
   the route reflector (Mplify 119-5's control-plane host) with `validate on` and
   `base table` = the service's unicast table (which must be declared with `trie`); for eBGP
   at a UNI (a subscriber's router sending flowspec) `validate on` is mandatory and the
   accepted action communities are filtered in the import filter (only `(generic,0x8006…)`,
   `0x800c`, `0x8007`, `0x8009`; redirects only from trusted peers).
2. **Read**: the agent polls `birdc -s <sock> show route table <svc>_flow4 all` (and flow6)
   on a timer and after `show protocols` reports a route count change (BIRD has no push on its
   CLI; polling every 1–5 s is fine), parses the `flow4 { … }` text and `BGP.ext_community`
   into a canonical component list (keep BIRD's text grammar as the parser input; it is the
   same grammar the console would write for static routes). Keep the parsed set in the
   `sdwan` read (`flowspec: [{net, components, actions, from, valid}]`) and raise an event on
   change.
3. **Order**: sort with the RFC 8955 §5.1 / 8956 §4 algorithm (port Appendix A's Python to C
   in the agent; unit-test against the examples) and assign ipfw rule numbers in that order in
   a reserved ipfw set (e.g. set 28, below the SD-WAN set so flowspec is evaluated first when
   the operator says so, or after — a knob), flushed and refilled atomically with `ipfw set
   disable`, `-f delete set`, add, `set enable` (the pattern sdwan.c uses), or via two sets
   and `set swap`.
4. **Match translation** (component → ipfw words, IPv4 `ip4`/IPv6 `ip6` and `proto`):
   - 1 dst prefix → `to A.B.C.D/len`; 2 src → `from …`; IPv6 with offset ≠ 0 → not
     expressible (ipfw matches prefixes from the top bit) → reject the spec (U-flag-like
     "unsupported", logged); offset 0 → `to prefix/len`.
   - 3 proto → `proto { 6 or 17 }` (ipfw or-blocks) for lists; `!=`/ranges expanded to lists
     (0–255 is small); IPv6 upper-layer protocol: ipfw's `proto` on IPv6 matches the last
     next header, same as BIRD's `next header`.
   - 4 port (either) → `{ src-port L or dst-port L }`; 5/6 → `dst-port L`/`src-port L` with
     L = the numeric expression normalised to a disjunction of ranges (`lt/gt/eq` with AND/OR
     → interval arithmetic → `80,137-139,1024-65535`); empty set → spec cannot match → skip.
   - 7 ICMP type → `icmptypes L` / `icmp6types L`; 8 ICMP code → **no ipfw match** → the spec
     is rejected as unsupported (document); 9 TCP flags: 1-octet mask with m=1 → `tcpflags
     syn,!fin,…` (listed = set, `!` = clear, for the bits in the mask; m=0 "any of" → or-block
     of single-flag rules); 2-octet (NS/reserved bits) → unsupported.
   - 10 length → `iplen L` (ranges supported); 11 DSCP → `dscp L` (list, ipfw takes numbers
     or names); 12 fragment: DF → `frag df`, IsF → `frag offset`, FF → `frag mf,!offset`,
     LF → `frag !mf,offset`, negation with `!`; IPv6 fragments → `ext6hdr frag` only (IsF/FF/
     LF distinctions not expressible → partial, document); 13 flow label → `flow-id L` (exact
     labels only, ranges expanded if small, else unsupported).
   - Components that never match without TCP/UDP/ICMP (§4.2.2.4) are naturally respected by
     ipfw's own semantics (port options imply TCP/UDP; `icmptypes` implies ICMP); add
     `frag !offset`-style guard so non-first fragments do not match port rules (ipfw already
     does not match ports on non-first fragments).
5. **Action translation** (all actions of one spec applied; the T bit decides whether to end):
   - traffic-rate-bytes 0 or traffic-rate-packets 0 → `deny` (optionally `deny log`);
   - traffic-rate-bytes > 0 → a dummynet pipe `pipe N config bw <bytes*8>bit/s` per spec
     (objects are already managed by sdwan.c) and `pipe N ip from … to …`; with
     `net.inet.ip.fw.one_pass=1` the pipe terminates; if the T bit says continue, use
     `one_pass=0` (global!) or `ngtee`→`ng_car` — see trade-offs;
   - traffic-rate-packets > 0 → dummynet has no pps mode; use `ngtee`/`netgraph` to an
     `ng_car` node in packet-count mode (`NG_CAR_COUNT_PACKETS`), or approximate as bytes with
     the spec's average size (configurable), or reject as unsupported;
   - traffic-action S (sample) → `log logamount N` or `log logdst bpf` (FreeBSD 16; the agent's
     capture/sampler reads it) and `count`; T (terminal; "continue") → non-terminal ipfw
     actions only (`count`, `setdscp`, `setfib`, `ngtee`, `tag` all continue; `deny`, `fwd`,
     `pipe` under one_pass, `netgraph` terminate) — a spec whose actions require a terminating
     primitive while T asks to continue is reported as interfering;
   - rt-redirect (any encoding) and rt-redirect-ipv6 → `setfib N` where N is the FIB of the
     Arcana routing domain whose route target list contains the RT (Mplify 119-2 gives every
     domain its RTs); several match → lowest RD (the RFC's example rule); none → unsupported;
   - traffic-marking → `setdscp N` (continues, so pair with a terminating `allow`/`skipto`
     when T=0).
   - Default (no action community) → `allow`? No: default is "accept, normal forwarding", i.e.
     `count` only (so the match counter of §9 exists) and continue.
6. **Monitoring** (§9): per-spec `count` rule counters in the `sdwan` read (`ipfw -S show`),
   `log` lines to the record (gula/record.c already reads ipfw logs), `events` on install/
   withdraw.
7. **Originate from the console**: the console writes flowspec as `protocol static { flow4;
   route flow4 { dst …; dport 25; } { bgp_ext_community.add((generic, 0x80060000, 0)); }; }`
   into the control-plane host's BIRD (the route reflector) — BIRD's static flowspec grammar
   is exactly RFC 8955's expressiveness, including IPv6 offsets and flow labels. That makes
   DDoS mitigation / SASE ip-block policies a BGP-distributed object; the per-edge translation
   above enforces it. Also accept flowspec from a subscriber router at a UNI (eBGP, validated)
   so a customer can blackhole their own prefixes.
8. **YANG/contract**: BGP flowspec has no IETF YANG model yet (draft-ietf-idr-flowspec-yang is
   not an RFC); model it in Arcana's agent contract as `flowspec { rules* [afi, nlri-text]
   {components…, actions…, origin, validated, ipfw-rule-number, counters} }` mirroring RFC
   8955's component types 1–13 and action communities one to one, plus `unsupported-reason`.

## 4. Cannot be mapped / not applicable
- **Kernel enforcement of flowspec**: none on FreeBSD; nothing in BIRD exports flow tables to
  the kernel → agent translation only (polling birdc).
- **VPNv4/VPNv6 flowspec (SAFI 134)**: BIRD 3 has no such channel; RDs/VRF-scoped flowspec
  cannot be received; use per-service BIRD instances (one flow4 table per service) instead.
- **ICMP code (type 8)**: ipfw has no ICMP code match; `icmp6types` likewise type only.
- **IPv6 prefix with non-zero offset (8956 types 1/2)**: ipfw cannot skip leading bits.
- **TCP flags 2-octet form** (NS bit, reserved bits) and bitmask "any-of" with multiple bits in
  one or-block are awkward; exact-match form only.
- **traffic-rate-packets**: no pps limiter in dummynet; only via ng_car (netgraph) or
  approximation.
- **Non-first-fragment semantics for IPv6 LF/FF**: ipfw sees only "has a fragment header".
- **Terminal-bit semantics with terminating ipfw actions** (pipe/nat under one_pass=1):
  continuing after a pipe needs `net.inet.ip.fw.one_pass=0` globally, which changes the
  SD-WAN rules' behaviour too.
- **Redirect to an arbitrary RT**: only RTs that name an Arcana routing domain (FIB) are
  resolvable; MPLS/L3VPN redirect to a remote VRF is not (FreeBSD has no MPLS forwarding).
- **Interference resolution** beyond "apply all, document conflicts": implementation-defined
  by the RFC; Arcana must document its choice (proposal: rate-bytes wins over rate-packets;
  redirect + marking both applied; conflicting redirects → first in RT order).

## 5. Checklist of requirements / tests
1. BIRD per-service instances with `flow4`/`flow6` channels, `validate on`, `base table`
   with `trie`; import filter restricting action communities by peer trust.
2. Agent parser for `show route table … all` flowspec output, incl. ext communities
   `(generic, …)`/`(rt, …)`; unit tests with the RFC §4.3 and RFC 8956 §3.8 examples rendered
   by BIRD static routes.
3. NLRI canonicalisation: strict type order, one component per type; numeric_op semantics
   (e, a, len, lt/gt/eq table) and bitmask_op (not, m) reduced to interval lists / flag sets.
4. Ordering per §5.1/8956 §4 implemented in C with the Python reference as test oracle
   (prefix specificity, lowest value, offsets, memcmp rules, longer-string-wins).
5. ipfw translation table for all 13 component types with the exact unsupported cases listed
   above; unsupported specs are skipped, counted and reported, never silently dropped.
6. Actions: rate 0 → deny; rate bytes → dummynet pipe; rate packets → ng_car or documented
   approximation; S → log + count; T → non-terminating composition or reported interference;
   redirect → `setfib` by RT→domain lookup (lowest RD on ties); marking → `setdscp`;
   default → `count`.
7. Atomic install: dedicated ipfw set, rebuilt on every change with disable/delete/add/enable
   (or set swap); rule numbers in precedence order; set position relative to the SD-WAN set
   configurable.
8. Revalidation: BIRD revalidates on unicast change; the agent re-reads on any flowspec table
   change (poll ≤ 5 s) and reinstalls only on diff.
9. Per-rule match counters and sampled logs in the `sdwan`/flowspec read; events on
   install/withdraw/unsupported.
10. Caps: maximum rules per service, maximum update rate; exceeding → fault, not silent drop
    (§12).
11. Console origination: static flowspec routes with ext communities on the control-plane
    BIRD; round trip test: console → RR → edge BIRD → agent → ipfw rule present → traffic
    dropped/limited/marked/refibbed as asked.
12. eBGP at a UNI: a stand-in router announcing flowspec for its own prefix is accepted
    (validation b/c), for a foreign prefix rejected; AS_PATH left-most check.
13. Lab: two vnet jails; `traffic-rate-bytes 0` for TCP/25 to a prefix → `nc` to port 25
    fails, port 80 works; withdraw → restored within one poll interval; `traffic-marking 46`
    → `tcpdump` shows EF on the far side; redirect RT → packet leaves via the breakout FIB.

## 6. Open decisions and trade-offs
- **Poll birdc vs a BIRD-side export**: polling is simple and uses what sdbird.c has; a BIRD
  `pipe` to a dedicated table plus `show route` on a short interval is the same thing. A BIRD
  patch to export flowspec via a Unix socket is more work than Arcana takes on. Decide: poll,
  1 s default when flowspec channels exist.
- **Evaluate flowspec before or after the SD-WAN classification set**: before = DDoS filters
  protect the edge's steering/NAT; after = the SD-WAN policy keeps precedence over customer
  flowspec. Default before for rate-0 (drop) and after for marking/redirect? Simpler: one
  knob per service, default before.
- **`one_pass`**: keep 1 (today's behaviour) and treat "continue after pipe" as interference,
  or set 0 and audit every SD-WAN rule for fall-through. Keep 1.
- **pps limits**: ng_car via `ngtee`/`netgraph` is exact but adds a netgraph graph per rule;
  approximation (bytes = pps × 1500) is cheap but wrong on small-packet floods (the exact DDoS
  case). Offer ng_car when `ng_car` loads, else reject.
- **Which actions to trust from which peer**: default accept only drop/rate from eBGP UNIs
  (RFC 8955 §12), everything from the console's RR.
- **Validation relaxation (rule a)**: allow specs without a destination prefix from the
  console only (BIRD: `validate off` on that session) for "all traffic with dport X" filters.
- **Contract shape**: expose flowspec in the YANG-shaped contract as its own list, or fold it
  into a generic ACL model (ietf-access-control-list, RFC 8519) with a `bgp-flowspec` origin —
  the ACL model has prefix/port/DSCP/TCP flags/fragment matches and `drop/accept/reject` plus
  augmentations for rate and marking; mapping both flowspec and the SASE ip-block policies to
  RFC 8519 would give one ipfw translator.
