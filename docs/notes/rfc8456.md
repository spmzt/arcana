# RFC 8456 — Benchmarking Methodology for SDN Controller Performance

Source read in full: `rfc/rfc8456.txt` (October 2018, Informational, BMWG), including
Appendix A (OpenFlow illustration). Terminology in `rfc8455.md`.

## 1. Purpose

Gives generic, protocol-independent procedures to benchmark an SDN controller (black box, VM
or bare metal, standalone or cluster of homogeneous controllers; federations out of scope)
for performance, scalability, security and reliability. For each of 15 tests it states the
objective, reference setup, prerequisites, procedure, measurement formulas (per trial,
average and variance over trials) and a mandatory reporting format. It fixes test
considerations: leaf-spine topology with ≥ 2 devices, frame sizes 128/512/1508, the emulator
timestamps control messages, four connection-setup variants (encrypted or not, same or
different protocol versions), measurement points at the emulator interfaces and reported,
direct connectivity, ≥ 10 repetitions, and a report template of 11 configuration parameters
and 3 controller settings. Appendix A shows every test as an OpenFlow message sequence
(LLDP packet-out/in for discovery, packet-in/flow-mod for provisioning, port-status for
change detection). For Arcana it is the recipe for a self-benchmark harness of the console
over cblink on a one-host jail lab.

## 2. Content

### 2.1 Test considerations (§4)
- §4.1 topology: SHOULD be leaf-spine, ≥ 2 devices; TP1 on leaf 1, TP2 on leaf n; benchmark
  many topologies and sizes; enable loop prevention when redundant paths exist.
- §4.2 traffic: used to signal new flows; frame sizes 128, 512, 1508 bytes (jumbo optional).
- §4.3 emulator SHOULD timestamp transmitted/received control messages; those timestamps give
  processing time.
- §4.4 connection setup: (1) unencrypted same version, (2) unencrypted different versions
  (controller newer / switch newer), (3) encrypted same, (4) encrypted different; key
  management/exchange MUST happen before measurement.
- §4.5 measurement points: at the test emulator interfaces unless a test says otherwise;
  locations MUST be reported.
- §4.6 connect the controller directly to the emulators; report physical/logical connectivity
  for VMs.
- §4.7 repeat each test ≥ 10 times.
- §4.8 report: controller name/version; northbound protocols/versions; southbound
  protocols/versions; redundancy mode; connection setup; device type (physical/virtual/
  emulated); number of nodes; number of links; data-plane traffic type; controller system
  configuration (CPU, memory, caches, OS, interface speed, storage); reference setup.
  Controller settings: topology rediscovery timeout; redundancy mode; state persistence
  on/off. Emulator capabilities: max devices emulated; control message processing time.

Common statistics for every "time" test: per-trial value Xi, average = ΣXi / trials,
variance = Σ(Xi − mean)² / (trials − 1); results in a table with a row per iteration, the
average in the penultimate row and the variance in the last; when repeated for varying N
nodes, a graph with X = N.

### 2.2 Performance tests (§5.1)

**5.1.1 Network Topology Discovery Time** — prerequisites: discovery supported; the tester can
read the discovered topology via NB/management interface; rediscovery timeout set to maximum.
Procedure: controller operational; connect devices; record Tm1 = first discovery message
from the controller at I1; query the controller every t s (RECOMMENDED t = 3) and compare to
the deployed topology; stop when they match or when three consecutive queries return the
same; record Tmn = last discovery message to the controller at I1. DT = Tmn − Tm1; average
and variance; graph vs N. (OpenFlow: Tm1 = first OFPT_PACKET_OUT with LLDP, Tmn = last
OFPT_PACKET_IN with LLDP.)

**5.1.2 Asynchronous Message Processing Time** — prerequisite: discovery completed.
Procedure: every device sends asynchronous messages one at a time in series for Td; record
each request transmit time Ti and response receive time Ri at I1. APT = (ΣRi − ΣTi) / Nrx
(Nrx = successful exchanges); average/variance; also report Nrx and the unsuccessful
percentage (1 − Nrx/Ntx)·100; graph vs N. (OpenFlow: PACKET_IN with one match header →
PACKET_OUT with one action header.)

**5.1.3 Asynchronous Message Processing Rate** — prerequisites: discovery done; choose Td,
STEP, tolerance P%, maximum sending rate Ntx1/Td. Procedure: send continuously at the maximum
rate from all devices for Td; record Nrx1 and Ntx1; compute APR1 = Nrx1/Td and loss ratio
Lr1 = 1 − Nrx1/Ntx1; ensure the controller recovered; repeat with the rate reduced by STEP;
continue until both the maximum Nrx and the Nrx with zero loss are found; trials at the
benchmark levels MUST be repeated until responses are equal ±P% for two consecutive trials.
Maximum APR = MAX(APRn); Loss-Free APR = MAX(APRn | Lrn = 0). Table columns: offered rate
Ntxn/Td, APRn, Lr, benchmark reached; optional graph with dual Y axes; graph vs N with both
rates.

**5.1.4 Reactive Path Provisioning Time** — prerequisites: topology known; destination
location known (learned or static); flow-miss = send to controller; every device on the path
needs a controller decision. Procedure: send one stream TP1→TP2; record Tsf1 = first flow
provisioning request sent to the controller at I1; wait for the first frame at TP2 or Td;
record Tdf1 = last flow provisioning response received from the controller at I1.
RPT = Tdf1 − Tsf1; average/variance; report the number of devices in the path. (OpenFlow:
G-ARP from TP2, PACKET_IN(D1), traffic, PACKET_IN(S1,D1), FLOW_MOD(D1), traffic at TP2.)

**5.1.5 Proactive Path Provisioning Time** — prerequisites: topology known; destination
known; flow-miss = drop. Procedure: send one stream TP1→TP2; install the flow entries for the
path through the NB/management interface; wait for the first frame at TP2 or Td; record Tsf1
= time the proactive flow is provisioned at I2; Tdf1 = last flow provisioning message
received from the controller at I1. PPT = Tdf1 − Tsf1; average/variance; devices in path.

**5.1.6 Reactive Path Provisioning Rate** — prerequisites as 5.1.4 (send-to-controller).
Procedure: traffic with unique src/dst pairs from TP1; record Ndf = unique frames received at
TP2 within Td. RPR = Ndf / Td; average/variance; report devices in path and offered rate.

**5.1.7 Proactive Path Provisioning Rate** — prerequisites as 5.1.5 (drop). Procedure:
continuous traffic with unique src/dst from TP1; install the corresponding flows through the
NB interface; record Ndf at TP2 within Td. PPR = Ndf / Td; average/variance; devices in path;
offered rate. "Measurement is based on data-plane observations of successful path activation."

**5.1.8 Network Topology Change Detection Time** — prerequisites: discovery done; periodic
discovery interval = 2·Td. Procedure: bring down an active device; record Tcn = first topology
change notification sent to the controller at I1; stop when the controller sends the first
rediscovery message or at Td; record Tcd = first rediscovery message from the controller at
I1. TDT = Tcd − Tcn; average/variance. (OpenFlow: PORT_STATUS link down → first PACKET_OUT
with LLDP.)

### 2.3 Scalability tests (§5.2)

**5.2.1 Control Sessions Capacity** — establish control connections from every emulated
device; stop when the controller starts dropping connections; CCn = successful connections.
Capacity = CCn (OpenFlow: HELLO exchange per switch until one fails; n − 1).

**5.2.2 Network Discovery Size** — prerequisites: automatic discovery; tester can read the
topology. Procedure: connect; query every t s (RECOMMENDED 30) until the topology is the same
in the last two responses; compare with the deployed topology; if equal, add one node and
repeat; if not, remove one and repeat; continue until the comparison succeeds; Ns = nodes of
the last successful trial. Size = Ns. Td = the time within which the user expects discovery.

**5.2.3 Forwarding Table Capacity** — prerequisites: empty forwarding table; flow idle time
high/infinite; discovery done; tester can read the forwarding table. Reactive: bidirectional
traffic with unique addresses from TP1 and TP2 at the controller's asynchronous message
processing rate; query the learned-entry count every ~5 s; stop when constant for three
consecutive queries; Nrp. Proactive: install unique flows via the NB interface until a
failure response; Nrp = successful responses (some designs need traffic to elicit responses).
Capacity = Nrp; report the provisioning type.

### 2.4 Security tests (§5.3)

**5.3.1 Exception Handling** — impact MUST be measured on Path Provisioning Rate, Path
Provisioning Time and Topology Change Detection Time, after baselines; invalid messages must
not be dropped by intermediate devices. Procedure: run those tests while 1 %, then 2 %, of the
messages of the 5.1.3 rate test are invalid (wrong protocol fields or failure notifications).
Report a table: rows = the three tests, columns = without / 1 % / 2 % exceptions. (OpenFlow:
PACKET_INs with a wrong version number; traffic 1 % above the path programming rate.)

**5.3.2 Handling Denial-of-Service Attacks** — impact on Path Provisioning Rate, Path
Provisioning Time, Topology Change Detection Time and Network Discovery Size, after baselines.
Launch a DoS during the trial on one of: northbound (continuous flow-entry queries),
management (ping flood), southbound (TCP SYN flood). Report rows per test, columns without /
with attack, with the attack's nature and interface. (OpenFlow: TCP SYN attack from a switch.)

### 2.5 Reliability tests (§5.4)

**5.4.1 Controller Failover Time** — cluster setup; master election done; nodes connected per
redundancy mode; discovery done; devices send all new flows to the controller; destination D1
known. Procedure: unidirectional traffic from TP1 with incrementing sequence numbers and
source addresses at a rate the controller handles without drops; verify no drops at TP2;
bring down the active controller; stop when the first frame after failover arrives at TP2;
record T1 = last valid frame before the sequence error, T2 = first valid frame after it.
Failover Time = T2 − T1; Packet Loss = missing sequences. Report: cluster nodes, redundancy
mode, failover time, loss, cluster keep-alive interval. No loss → failover time negligible.

**5.4.2 Network Re-provisioning Time** — prerequisites: redundant paths; controller knows TP1
and TP2; the alternate path is NOT pre-provisioned. Procedure: bidirectional traffic with
unique sequence numbers from TP1 and TP2; bring down a link or switch on the path; stop after
the first frame after reconvergence; record TP2-Tlfr/TP2-Tffr (last before / first after the
loss at TP2) and TP1-Tlfr/TP1-Tffr. FDRT = TP2-Tffr − TP2-Tlfr; RDRT = TP1-Tffr − TP1-Tlfr;
Network Re-provisioning Time = (FDRT + RDRT)/2; forward/reverse packet loss = missing
sequences. Report nodes in primary and alternate paths, time, both losses. Trial valid only
if the controller provisioned the alternate path.

### 2.6 Appendix A (OpenFlow) — the message-level mapping
Controller-to-switch (features, config, read-state, PACKET_OUT, FLOW_MOD, role),
asynchronous (PACKET_IN, flow-removed, PORT_STATUS, error), symmetric (HELLO, ECHO,
experimenter); channel over TCP or TLS; auxiliary connections. Sequences per test as noted
above; discovery via LLDP in PACKET_OUT/PACKET_IN; path provisioning via FLOW_MOD after
PACKET_IN; change detection via PORT_STATUS → LLDP; sessions capacity via HELLO; forwarding
table via G-ARP for H1..Hn and repeated FWD-table queries until F1==F2==F3.

## 3. How Arcana could realise it on FreeBSD

### 3.1 The DUT and its interfaces
- DUT: `kore` + `arcana-console.so` (one process). Northbound I2 = the JSON API; a harness
  client (`curl`/a small C or Python client with the session cookie and `X-Arcana: 1`) is the
  "application-plane test emulator" and timestamps every request/response.
- Southbound I1 = cblink over TCP+mTLS to each `arcana-agent`. The "forwarding-plane test
  emulator" is the set of agents themselves (real devices, "emulated in hardware" per RFC
  8455 §2.2.1 is allowed) running in **vnet jails** on one FreeBSD host, each with its own
  epair into a bridge per "link"; TP1/TP2 are two more jails attached to edge jails. The
  agents log each received request and sent reply with a monotonic timestamp (add a
  `benchmark-log` option or use the existing trace steps' times and the `events` `t`), which
  gives the I1 timestamps without decrypting TLS; a `ktrace`/`dtrace` on the agent's
  `recv`/`send` syscalls is the black-box alternative.
- Connection setup variants (§4.4): mTLS is the only southbound transport; "unencrypted"
  = AF_UNIX (only local). Protocol version variants = different `arcana` family versions
  (cblink's family version negotiation) — test a newer console against an older agent and
  vice versa.
- System configuration for the report: `sysctl hw.model hw.ncpu hw.physmem`, `uname`,
  interface speeds (epair: software), storage (ZFS pool for the console's data directory).

### 3.2 Test-by-test mapping
1. **Topology Discovery Time**: Tm1 = the console's first cblink request after the harness
   adds N hosts (enrolment tokens pre-issued; `POST /api/enrol/tokens` + `arcana-enrol` in
   each jail; or servers pre-registered and the console restarted); Tmn = the last reply
   (`hello`/`network`/`interfaces`/`l2`) that completes the map; the harness polls
   `GET /api/map` (or the servers' interfaces endpoints) every 3 s and stops when the map
   equals the deployed topology (N jails, their epairs, the bridges). Graph vs N (1, 5, 10,
   20, 50 jails).
2. **Asynchronous Message Processing Time**: asynchronous message = a cblink `event` from an
   agent (`sdwan-tunnel` down/up is the productive one: the console must recompute steering
   and push `sdwan-steer`; `sdwan-tca`, faults and `sdwan-ids` produce a UI record only — not
   "productive"). Trigger: the harness flips a probe target (dummynet `plr 1` on the tunnel
   epair, or a `sdwan-probes` change) in one agent at a time; Ti = event emitted by the
   agent, Ri = the console's `sdwan-steer` request arriving at that agent. APT = mean
   (Ri − Ti). If the console reads `sdwan` by polling (once a second) rather than by the
   event stream, APT is dominated by the poll interval — report both and consider making the
   console subscribe to `events`.
3. **Asynchronous Message Processing Rate**: generate `sdwan-tunnel` events at increasing
   rates from all agents (a benchmark-only knob in the agent to emit synthetic events, which
   RFC 8455 §6 discourages — alternative: many probe targets with dummynet toggling), count
   `sdwan-steer` pushes; find the loss-free and maximum rates; STEP e.g. 10 % of the maximum.
4. **Reactive Path Provisioning Time/Rate**: **not applicable** (no flow-miss to controller).
   Closest Arcana analogue, reported separately and named differently: *local failover time*
   (edge-only; probe/BFD down → `sdwan-steer` candidates re-evaluated → ipfw table swap →
   first frame on the alternate tunnel at TP2), measured by data-plane sequence numbers like
   5.4.2.
5. **Proactive Path Provisioning Time**: Tsf1 = the API request that applies an SD-WAN
   document (a new application flow steered over a tunnel; the console compiles `sdwan-rules`
   and `sdwan-steer` for each edge and submits them as jobs); Tdf1 = the last agent's `ok`
   for the last job (I1), and, data-plane, the first frame at TP2 (flow-miss = drop holds
   because the SD-WAN set denies what is not classified). Report devices in the path (2 edges
   + transit jails if the underlay has them). The console's 1 s job poll inflates the API view;
   measure at I1 (agent logs) for the RFC number and at I2 for the user-visible number.
6. **Proactive Path Provisioning Rate**: apply a document with n flows (unique src/dst pairs
   from TP1) in one request; count unique frames received at TP2 in Td (a UDP generator with
   distinct src/dst per flow and a receiver that counts distinct 4-tuples). PPR = Ndf/Td;
   vary n and the number of edges.
7. **Network Topology Change Detection Time**: Tcn = the agent's event for an interface down
   (route socket `RTM_IFINFO` → `events`) or the BFD/probe `sdwan-tunnel` event; Tcd = the
   console's first "rediscovery" request to any agent (a `network`/`interfaces` read of the
   affected host or the `sdwan` read). Bring the link down with `ifconfig epairXb down` in
   the jail. Periodic rediscovery (the console's refresh interval) set to 2·Td.
8. **Control Sessions Capacity**: number of agents the console keeps connected (one cblink
   session each, mTLS state, keepalives) before it fails to open new ones or drops old ones:
   grow the number of agent jails (or many agent processes on distinct ports in one jail —
   `arcana-agent` with different sockets) until `GET /api/servers` shows an unreachable one.
   Also measure the agent-side capacity (clients per agent) as a device figure.
9. **Network Discovery Size**: largest N (jails, epairs, bridges, tunnels) the map renders
   completely within Td; grow/shrink by one as in §5.2.2 with t = 30 s.
10. **Forwarding Table Capacity** (proactive): install unique flows / table entries through
    the API until a failure response (`sdwan-rules` size limits, ipfw table limits,
    `max-batch`), Nrp = successes; also the largest `sdwan-rules` JSON one apply can carry
    (SASE-2's "large tables, chunks of atomic adds").
11. **Exception Handling**: 1 %/2 % of the asynchronous messages malformed: cblink messages
    with bad CBOR/attributes from a modified agent or the cblink fuzz harness
    (`cblink/fuzz`) injected on the agent side, or agents replying `error` to 1 % of jobs;
    rerun 5, 6, 7 and tabulate.
12. **DoS Handling**: northbound flood (`GET /api/servers/*/network` in a loop), management
    ping flood of the console host, southbound TCP SYN flood at the console's outbound
    connections is meaningless (console is the client) → instead SYN-flood the agents' cblink
    ports and the console's HTTPS port; rerun 5, 6, 7, 9; `pf`/ipfw `limit` on the console
    host as the mitigation to document.
13. **Controller Failover Time**: not applicable (standalone).
14. **Network Re-provisioning Time**: service with two tunnels (primary, alternate) between
    two edges, policy preferring the primary; bidirectional sequence-numbered UDP TP1↔TP2;
    bring the primary tunnel's underlay epair down (or dummynet `plr 1`); the *controller*
    path is: agent event → console orders candidates by the performance criteria → pushes
    `sdwan-steer`; but Arcana's local failover will re-steer first (the edge takes the first
    tunnel not down) — to measure the controller as the RFC wants, disable local failover in
    the test (a knob) or report both "local" and "controller" re-provisioning times.
    FDRT/RDRT from the receivers' sequence gaps; (FDRT + RDRT)/2.

### 3.3 Harness on one FreeBSD host
- `bench/` (new) with `rc`-style shell/ATF scripts (the repo already has `tests/` with
  kyua/atf and a two-jail SD-WAN lab): create N vnet jails (`jail -c vnet persist`), epairs
  and bridges per topology (linear, tree, hub-and-spoke, leaf-spine 2×n), `arcana-agent` in
  each with its certificate (the console's CA), the console in its own jail (unprivileged
  user), TP1/TP2 jails running a UDP sequence generator/receiver (a 100-line C program;
  `iperf3` for throughput only). Resource isolation per RFC 8568 §4.11: `cpuset -l` the
  console jail apart from the agent jails and the generators; `rctl` limits; same host clock
  so timestamps across jails are directly comparable (A = 0 — a benchmark advantage).
- Timestamps: agents and console log `CLOCK_MONOTONIC`/`CLOCK_REALTIME` per request/reply/
  event when `-b benchlog` is set (or via dtrace `syscall::sendto`/`recvfrom` on the agent
  pids); the harness joins logs by request id (cblink sequence numbers) and computes the
  formulas; output: per-test CSV + the RFC's table (rows per trial, average, variance) and
  the §4.8 header.
- Repeat ≥ 10; frame sizes 128/512/1508 for the data-plane tests.

## 4. Cannot be mapped / not applicable
- Reactive Path Provisioning Time and Rate (no flow-miss/packet-in; Arcana is proactive).
- Controller Failover Time (standalone only).
- Southbound SYN flood against the *controller* (it is the TCP client); replaced by flooding
  the agents and the northbound.
- "Unencrypted" southbound over the network (mTLS is mandatory; AF_UNIX only locally).
- OpenFlow-specific message mapping (LLDP, FLOW_MOD): Arcana's discovery is "ask each host",
  there is no in-band LLDP topology; links between hosts are inferred from addresses/tunnels/
  BFD, so "all links discovered" must be defined as what the map can know.
- Measurement at a wire tap of I1: TLS; replaced by agent-side timestamps (reported as the
  measurement point).

## 5. Checklist of requirements / tests
1. Report header per §4.8 (11 configuration parameters, 3 controller settings, 2 emulator
   capabilities) and the measurement points per §4.5.
2. ≥ 10 trials per test; average and variance formulas as given; tabular format with the
   average and variance rows.
3. Topology Discovery Time vs N with t = 3 s polling and the 3-identical-queries stop rule.
4. Asynchronous Message Processing Time with Nrx and the unsuccessful percentage; define
   the productive response (`sdwan-steer` push).
5. Asynchronous Message Processing Rate: STEP, P%, Td recorded; Maximum and Loss-Free rates;
   table with offered rate, APR, loss ratio, benchmark flag.
6. Proactive Path Provisioning Time at I2 and I1, devices in path reported.
7. Proactive Path Provisioning Rate with unique src/dst frames counted at TP2; offered rate.
8. Topology Change Detection Time with rediscovery period = 2·Td.
9. Control Sessions Capacity (console side) and, as a device figure, agent-side sessions.
10. Network Discovery Size with the ±1 node search and t = 30 s.
11. Forwarding Table Capacity, proactive, with the limiting resource named (JSON size, ipfw
    table, rule numbers).
12. Exception Handling at 1 % and 2 % malformed cblink messages / error replies; table
    without/1 %/2 %.
13. DoS Handling on northbound, management and (adapted) southbound; table without/with,
    attack nature stated.
14. Network Re-provisioning Time: FDRT, RDRT, mean, both losses, nodes in both paths; local
    failover disabled or reported separately.
15. Not-applicable tests listed with reasons; frame sizes 128/512/1508; lab isolated;
    cpuset separation of DUT and emulators; no benchmark-only code paths in the console (the
    agent's synthetic-event knob, if added, documented as a test-only option of the device
    emulator, not of the DUT).

## 6. Open decisions and trade-offs
- **Event-driven vs polling console**: most "time" benchmarks collapse to the console's 1 s
  poll of `sdwan`/jobs. Subscribing to the agents' `events` stream (cblink `mcgrp: events`)
  would make the console reactive in milliseconds — a design change the benchmarks would
  expose. Decide before benchmarking what the console *should* be.
- **Local failover vs controller re-provisioning**: Arcana's edge-local failover is a
  feature; the RFC measures the controller. Keep both numbers: "Local Failover Time" (device)
  and "Network Re-provisioning Time" (controller, local failover disabled).
- **Where to timestamp I1**: agent logs (needs a benchmark flag in the device, acceptable per
  RFC 8455 §2.2.1 "emulated") vs dtrace on syscalls (no code change, root on the host).
- **Jails vs hosts**: one host with vnet jails shares CPU and the scheduler; numbers are
  relative, not absolute; good for regression tracking across console versions (CI), not for
  comparing with other controllers. Note RFC 8568 §4.11's "test system must not share
  resources with the SUT".
- **Discovery definition**: with no LLDP, "links" = tunnels + BFD/probe adjacency + same-subnet
  inference; decide what the map must show to count as complete.
- **Scale targets**: pick N for CI (e.g. 10 agents, 20 flows) and a nightly larger run
  (100 agent processes, 1000 flows) — agent processes on distinct ports in few jails scale
  further than one jail per agent.
