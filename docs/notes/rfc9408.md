# RFC 9408 — A YANG Network Data Model for Service Attachment Points (SAPs) (Standards Track, June 2023)

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc9408.txt (read in full, incl. module and appendices); RFC 8345 skimmed for the ietf-network / ietf-network-topology base.

## 1. Purpose and place in the layered picture

- A **network model** (RFC 8969 sense) that is really *inventory*: an abstract view of the provider network exposing the points where services (L3VPN, L2VPN, slices, SD-WAN, basic IP) *can* be attached and *are* delivered. Flows from the **network controller up to the service orchestrator** (Fig. 1), alongside L3NM/L2NM which flow down.
- Augments `ietf-network` (RFC 8345) — not `ietf-network-topology` — with a `sap-network` network type and a per-node list of services, each with a list of SAPs. It *imports* ietf-network-topology only to reference a parent termination point (`nt:tp-id`).
- Both **UNI** (customer-facing, PE side of an attachment circuit, or CE side for provider-managed CE) and **NNI** (ASBR-to-ASBR, Inter-AS Option A, App. C) SAPs. A SAP is bound to one or more ACs; it is neither a TTP nor a link. One AC can terminate on several SAPs (unlike RFC 8345 links, which end in one TP).
- Use: service feasibility checks, "free SAP" discovery (admin-down + no anomaly), choosing `sap-id` = L3NM `vpn-network-access/id`, mapping slice endpoints to underlay TPs, exposing NNIs between domains.
- Two statuses: `sap-status` (ro, the interface regardless of service) and per-service `service-status` (admin rw / oper ro); anomaly detection by comparing them (admin-up + sap-down => oper must be down; admin-down + oper-up => stale provisioning).
- For Arcana: this is the natural *fleet inventory* family — the console's topology view (www/arcana-ui/src/topo.c, netview.c) already draws hosts and interfaces; SAP gives it an IETF shape and makes "which interface on which host can host VPN X" a query.

RFC 8345 typedefs relevant: `node-id`, `network-id`, `link-id`, `tp-id` are all `inet:uri`; all leafrefs there carry `require-instance false`. Network types are presence containers under `network-types` (hierarchies of subtypes nest presence containers). A network may be system-controlled (learned, operational datastore) or client-configured (overlay referencing a supporting network).

### 2.1 Identities defined by RFC 9408

- base `vpn-common:service-type` additions: `virtual-network` (ACTN), `enhanced-vpn` (VPN+), `network-slice`, `sdwan` (PE-based SD-WAN, draft-ietf-bess-bgp-sdwan-usage), `basic-connectivity` (plain IP connectivity).
- `interface-role`: `uni`, `nni`.
- `interface-type`: `phy`, `loopback`, `lag`, `irb` (connects IP-VRF to a bridge domain), `local-bridge`, `logical` (sub-interface, only when nothing more specific fits).

### 2.2 Groupings

- `sap-entry`: sap-id, description, parent-termination-point (nt:tp-id), attachment-interface (string), interface-type, encapsulation-type (vpn-common base), role, allows-child-saps, leaf-list peer-sap-id.
- `sap-list`: `list sap [sap-id]` { uses sap-entry; ro container sap-status {uses vpn-common:oper-status-timestamp}; container service-status { admin-status {status identityref administrative-status, last-change}, ro oper-status {uses oper-status-timestamp} } }.

Augments: `/nw:networks/nw:network/nw:network-types` += presence container `sap-network { leaf-list service-type }`; `/nw:networks/nw:network/nw:node` += `list service [service-type] { uses sap-list }` with `when '../nw:network-types/sap:sap-network'`.

## 3. Node-by-node meaning and Arcana/FreeBSD realisation

| Node | Meaning | Arcana / FreeBSD realisation |
|---|---|---|
| nw:networks/network [network-id] | one topology; SAP network is one of them | One "SAP network" per fleet (or per domain/site group). `network-id` is a URI: `arcana:fleet/<name>/sap`. A second, system-controlled "physical" network holds hosts + interfaces + discovered links as the *supporting network* |
| network-types/sap-network! | presence: this network is a SAP inventory | a constant in the Arcana topology family; `service-type*` = the union of service types any host advertises (`l3vpn`, `sdwan`, `basic-connectivity`; maybe `arcana:l2-bridge`) |
| supporting-network / supporting-node | layering onto an underlay network/node | SAP node -> supporting physical node (the host) in the physical network; both are the same FreeBSD host. `node-id` URI = `arcana:host/<hostname>` (matches L3NM `ne-id`) |
| node [node-id] | a PE | an arcana-agent host; vnet jails on a host that act as PEs could be their own nodes (`arcana:host/<h>/jail/<j>`), supported by the host node |
| nt:termination-point [tp-id] (base) | port/interface | every interface of the host (em0, lagg0, vlan10, epair0b, bridge0, lo0, wg0, ipsec0, gif0 ...) as `tp-id` = `arcana:host/<h>/if/<ifname>`; supporting-tp for vlan->parent, lagg->members, epair-b->jail side |
| nt:link (base) | unidirectional p2p link | discovered links: LLDP (net-mgmt/lldpd, not base) between hosts; Arcana tunnels (wg/ipsec/gre/vxlan peers) as links in an overlay network; epair pairs between host and jail; `supporting-link` tunnel -> physical uplink |
| service* [service-type] | per node, which service types it can attach | per host: derived from features present (BIRD installed => l3vpn; SD-WAN configured => sdwan; always basic-connectivity) |
| sap* [sap-id] | an attachment point | an interface (or sub-interface) designated customer-facing. `sap-id` SHOULD equal the L3NM `vpn-network-access/id` (RFC §5) — pick `<host>:<ifname>` or a UUID allocated by console; same id reused under multiple service-types for shared SAP |
| description | text | free |
| parent-termination-point | tp the SAP is bound to; links SAP to physical topology; parent of sub-interfaces | the TP of the physical/parent ifname (vlan's `vlandev`, lagg for lagg ports; bridge for IRB) |
| attachment-interface | the interface hosting the SAP; may be any of L3NM l2-termination-point / local-bridge-reference / bearer-reference / lag-interface-id / l3-termination-point | FreeBSD ifname (vlan10, em0.10 not valid on FreeBSD — note names are `vlan10`/`em0.10` both allowed by ifconfig since 12.x: `em0.10` creates vlan on em0 with tag 10) |
| interface-type | phy / loopback / lag / irb / local-bridge / logical | phy: physical NIC (`ifconfig -g` ? no: detect via `sysctl dev.<drv>` or absence of `vlan:`/`groups: ...`); loopback: lo(4); lag: lagg(4); irb: if_bridge(4) with an inet/inet6 address; local-bridge: if_bridge without address; logical: vlan(4), epair, tun/tap, gif/gre/wg/vxlan |
| encapsulation-type | from vpn-common | untagged-int/ethernet-type: plain; vlan-type/dot1q: vlan(4) (`vlan: N vlanproto: 802.1q`); qinq: stacked vlan w/ 802.1ad; vxlan: vxlan(4); lag-int: lagg; priority-tagged/qinany: none |
| role | uni / nni | console/operator-assigned per interface; uplinks to another fleet/AS = nni (App. C: ASBR with per-VPN sub-interfaces; FreeBSD can do Option A: a vlan per VPN into the VPN's FIB and a BIRD BGP session per FIB to the peer ASBR) |
| allows-child-saps | parent can host per-service sub-interfaces | true for physical/lagg interfaces that can take vlan(4) children; false for vlan/epair/loopback |
| peer-sap-id* | remote end of the AC (CE id, site id, SDP id, peer ASBR address) | Arcana SD-WAN UNI id / CE name / jail name (for epair-attached jails) / peer ASBR IP; for Arcana-managed CEs (a jail or another host), the peer's own sap-id |
| sap-status (ro) | interface oper status independent of service | ifconfig `status: active|no carrier` + UP flag -> op-up/op-down; `op-unknown` for interfaces without link state (gif, lo); last-change: `if_lastchange` via getifaddrs/ifmib or Arcana event timestamp |
| service-status/admin-status | whether the service is enabled at this SAP (MUST NOT be influenced by sap-status) | console intent; agent stores per (ifname, service) |
| service-status/oper-status (ro) | service as observed *at this SAP only* | agent: address configured and interface up and (for l3vpn) BIRD protocol on that interface up / routes installed in the FIB; last-change from events |

### 3.1 Anomaly rules (RFC §5) as Arcana checks

- admin-up at SAP and sap-status down => oper-status must be down (else report inconsistency).
- admin-down but oper-up => stale provisioning: agent should raise an event (gula/faults.c).
- Parent interface disabled => child SAPs report parent's status (precedence rule).

### 3.2 Appendix D flow in Arcana terms

1. Console asks every agent (or the fleet inventory) for SAPs with `service-type=l3vpn`, filters `service-status/admin-status=admin-down` and no anomaly => free SAPs.
2. Check `interface-type`/`encapsulation-type` compatibility; if the SAP is `phy` with `allows-child-saps`, create a logical child SAP (vlan) via the SAP model first.
3. Use the chosen `sap-id` as L3NM `vpn-network-access/id` and `attachment-interface` as `interface-id`.
4. Inter-AS Option A: pick free NNI SAPs on both ASBRs, provision an L3NM in each domain.

## 4. Cannot be mapped

| Node | Why |
|---|---|
| service-type vpls / vpws / *-evpn under `sap-network` | no such data plane on FreeBSD (see rfc9181.md) — never listed |
| service-type virtual-network / enhanced-vpn / network-slice | no ACTN / VPN+ / slice controller; could be listed only as opaque |
| encapsulation-type priority-tagged / qinany | vlan(4) limitations |
| interface-type irb in the EVPN sense (RFC 9135 IP-VRF <-> MAC-VRF) | FreeBSD if_bridge with an address is a local IRB, but there is no MAC-VRF/EVPN; semantics are local only |
| nt:link discovery | no LLDP in base (lldpd is a port); without it, physical links are operator-entered or inferred from Arcana tunnels/epairs |
| `supporting-termination-point` auto-inference | RFC 8345 says the system infers it from link dependencies; Arcana would have to compute from vlan/lagg/epair parentage explicitly |
| ro `last-change` persistence | needs agent-side state across restarts |

## 5. Features

RFC 9408 defines no features. It depends on vpn-common identities only (`service-type`, `encapsulation-type`, statuses), so the vpn-common feature advertisement (rfc9181.md §5) governs which encapsulation identities are legal (e.g. `qinq` only if feature `qinq`).

## 6. YANG constructs used

| Construct | Example | Needed in cblink |
|---|---|---|
| augment (of another module's data tree) | `augment "/nw:networks/nw:network/nw:network-types" { container sap-network { presence ...; } }`; `augment "/nw:networks/nw:network/nw:node" { list service ... }` | cross-family augmentation: a family must be able to add attributes to another family's attribute-set (ietf-network node) — or Arcana folds ietf-network + topology + sap into one `topology` family and loses the modularity |
| when on augment | `when '../nw:network-types/sap:sap-network'` | conditional presence of a subtree based on a sibling presence container; cblink needs `when:` (XPath subset) or documents it |
| presence container | `container sap-network { presence "Indicates the SAP network type."; }`; RFC 8345 network types SHOULD be presence containers, nested for subtypes | `nest` presence is natural (empty map); need `presence: true` so an empty nest is not dropped by encoders |
| identityref with cross-module base and identities added in another module | `identity sdwan { base vpn-common:service-type; }`; `leaf service-type { type identityref { base vpn-common:service-type; } }` | identity registry spanning families (see rfc9181.md §6) |
| leafref via typedef from another module, require-instance false | `leaf parent-termination-point { type nt:tp-id; }` (nt:tp-id is inet:uri, not a leafref here); RFC 8345 base uses `leafref { path ...; require-instance false; }` everywhere | `ref:`/leafref checks with a `require-instance` flag so inventory can reference not-yet-present nodes (ephemeral/learned data) |
| list keyed by identityref | `list service { key "service-type"; }` | identityref keys |
| leaf-list of identityref / string | `leaf-list service-type`, `leaf-list peer-sap-id` | multi-attr — OK |
| config false containers | `container sap-status { config false; }`, `oper-status` | `config: false` marker |
| inet:uri typedef keys | node-id/network-id/link-id/tp-id | text with URI pattern (or no pattern) |
| grouping reuse across modules | `uses vpn-common:oper-status-timestamp;` | imports of groupings |
| boolean | `allows-child-saps` | cblink `bool` — OK |
| yang:date-and-time | last-change | typedef (text RFC 3339 pattern, or CBOR tag 0/1) |
| JSON encoding specifics (RFC 7951) in the examples | `"ietf-sap-ntw:service"`, `"ietf-vpn-common:op-up"` module-qualified names at augment boundaries and identity values | decide the CBOR counterpart (RFC 9254 YANG-CBOR uses SIDs or names) |
| rpc / action / notification | none | n/a; Arcana would add `event`s for sap-status changes (RFC 8345 has none either) |

## 7. Open questions / decisions

1. **One topology family or three?** Model ietf-network, ietf-network-topology and ietf-sap-ntw as three cblink families with augmentation (faithful, needs the augment construct) vs one Arcana `topology` family whose node set carries tp/link/sap nests (simple, no augment needed, but a single opinionated schema).
2. **Who owns the SAP network?** (a) each agent dumps its own node + TPs + SAPs (`network-id` per host, console merges), or (b) the console/fleet daemon holds the `networks` tree and agents only report interface facts. (a) keeps agents authoritative for oper status; (b) matches the RFC's "network controller exposes to orchestrator" reading and allows `supporting-network` layering and NNIs between fleets.
3. **sap-id scheme.** Operator-visible stable strings (`pe1:vlan10`) vs UUIDs. RFC wants the same id reused across service types and equal to L3NM access id; stable derived names break on interface rename, UUIDs need a mapping table.
4. **Jails as nodes or as peer-sap-ids?** A vnet jail used as a CE (customer workload) is best a `peer-sap-id`; a vnet jail used as a PE/VRF instance (one jail per VPN instead of FIBs) would be its own node supported by the host. This decision is coupled to the FIB-vs-vnet choice in rfc9182.md §7.
5. **Link discovery:** adopt lldpd (port) as an Arcana plugin to populate `nt:link`, or treat physical links as operator-entered and only auto-derive overlay links from Arcana tunnels/epairs.
6. **Learned vs configured networks (NMDA origin).** RFC 8345 distinguishes system-controlled networks (operational datastore) from client-configured overlays. Arcana must mark which parts of the topology are discovered (interfaces, link state) vs intended (SAP roles, admin status), which again needs the datastore/`config false` discriminator.
