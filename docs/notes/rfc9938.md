# RFC 9938 — A Framework for the Deterministic Networking (DetNet) Controller Plane

Read in full: 832 lines, fetched from https://www.rfc-editor.org/rfc/rfc9938.txt (HTTP 200).
Informational, March 2026. Malis, Geng (ed.), Chen, Varga, Bernardos. Normative: RFC 8655, RFC 8938, RFC 9016, RFC 9055, RFC 9551.
Local copy: `scratchpad/rfc/rfc9938.txt`. (The number resolves at rfc-editor.org; it is a published RFC, not a draft.)

## 1. Purpose

RFC 9938 collects into one document the requirements and considerations for the DetNet
*Controller Plane* (RFC 8655's merger of control and management planes) that are scattered
across RFC 8655, RFC 8938 (data plane framework), RFC 9551 (OAM framework) and RFC 9055
(security), and discusses how three architectures — fully distributed signalling, fully
centralised SDN, and hybrid — could satisfy them. It details what the control plane must do
for each DetNet mechanism (explicit paths: computation and establishment; resource
reservation: allocation per RFC 9016 traffic specification, device configuration with or
without flow discrimination; PREOF: multi-path "LSP graph" computation and establishment),
data-plane-specific points (legacy MPLS label distribution, DetNet IP without PREOF, SR),
encapsulation/metadata capability discovery, the management plane (OAM: active PM
discouraged in operation, passive PM/IOAM preferred, CFM per RFC 9551/9634/9546), and
multi-domain CPF cooperation. It specifies no protocol; it is the reference for future
controller-plane protocol work. It cites RFC 9633 (DetNet YANG) and PCE-CC (RFC 8283) as
centralised tools.

## 2. Architecture and terminology (complete)

### 2.1 Scope and planes (§1)
- Controller plane = control plane (instantiation/maintenance of flows, MPLS label allocation/distribution, in-band/out-of-band signalling) + management plane (fault, configuration, performance management; accounting and security management out of scope) per RFC 8655 §4.4.2 and RFC 7426.
- Data plane references: RFC 8938 (framework), RFC 8964 (MPLS), RFC 8939 (IP), RFC 9023/9024/9025/9037/9056 (IP over TSN, TSN over MPLS, MPLS over UDP/IP, MPLS over TSN, IP over MPLS).

### 2.2 Requirements (§2)
**Control plane (§2.1)**:
1. Dynamic instantiation, modification, deletion of DetNet flows: explicit path determination, link bandwidth reservations, restriction to specific links (e.g. TSN links), node buffer and other resource reservations, required queuing disciplines along the path, bidirectional flows (RFC 8938).
2. Flow aggregation/de-aggregation: create/delete flow aggregates (FAs), add/remove member flows (RFC 8938).
3. Flow requests may originate from an end application (API, static provisioning, SDN controller, or distributed signalling).
4. For MPLS: manage S-Label, F-Label, A-Label allocation and distribution (RFC 8964/8938).
5. For MPLS: support the service sub-layer (PREOF) (RFC 8655).
6. Support queue control techniques of RFC 8655 §4.5 and RFC 9320 requiring time synchronisation among data-plane nodes.
7. Advertise static and dynamic node/link characteristics (capabilities, adjacencies) to nodes or controllers (RFC 8938).
8. Scale to the number of flows of a domain (possibly per-flow signalling/provisioning) (RFC 8938).
9. Provision flow identification at each node along the path; identification may differ by location/role (transit vs relay) (RFC 8938).

**Management plane (§2.2)** (RFC 9551): monitor flow and node performance proactively and on demand; continuity check and connectivity verification; test/monitor replication, elimination and ordering.

**Both planes (§2.3)**: operate in a converged domain with DetNet and non-DetNet flows; adapt to topology changes (failures, additions, removals: recovery/restoration) (RFC 8655). Security (RFC 9055): integrity/authenticity of control and signalling packets (no modification/injection, anti-spoofing, anti-segmentation); protection against controller compromise (verify controller legitimacy, prevent impersonation); system-wide design resilient to a compromised node/controller; timely delivery of control messages without resource leakage.

### 2.3 Control plane architectures (§3)
- **Distributed (§3.1)**: UNI info over a DetNet UNI protocol (not needed if end systems are DetNet-capable) then propagated by signalling. RSVP-TE example: IGP collects topology and DetNet capabilities; ingress computes paths; PATH with explicit route, RESV with label and reservation. IGP and RSVP-TE need DetNet extensions.
- **Fully centralised (§3.2)**: flow and UNI info to a centralised controller via API/northbound; node configuration via NETCONF (RFC 6241), YANG (RFC 6020/7950), **DetNet YANG (RFC 9633)**, or PCE-CC (RFC 8283). Steps: controller collects topology/capabilities via NETCONF/YANG; receives flow request; computes paths; configures devices along the optimal path via PCE-CC. Extensions may be needed.
- **Hybrid (§3.3)**: e.g. controller collects topology via IGP/BGP-LS (RFC 9552), receives requests via API, computes, distributes path to ingress and configures DetNet info (replication/elimination) on nodes; RSVP-TE then signals the explicit route. Many variations; extensions for future work.

### 2.4 Control plane per DetNet mechanism (§4)
- **Explicit paths (§4.1)**: *path computation* meeting SLA (bandwidth, max e2e delay, max delay variation, max loss, …) — distributed: IGP with CSPF; centralised: controller from collected information; *path establishment*: send/configure/signal the path to devices.
- **Resource reservation (§4.2)**: resources = packet processing, buffers, output port bandwidth; determined by SLA and capability. *Allocation*: bandwidth is the easy, usual TE resource; a DetNet flow is characterised by the RFC 9016 traffic specification (Interval, MaxPacketsPerInterval, MaxPayloadSize) describing the worst case; DetNet also needs buffer allocation, queuing disciplines, and resources for service sub-layer functions (PREOF). *Device configuration with or without flow discrimination*: output-port bandwidth reservation as a queue-management/port-scheduling parameter; aggregated flows share allocated resources; independently treated flows need a per-flow↔resource mapping on the device.
- **PREOF (§4.3)**: existing P2P/P2MP path mechanisms are insufficient; need to compute and establish a *set* of paths from replication point(s) to merge/ordering point(s), map flows/member flows to path segments; protocol extensions and new terminology ("LSP graph") required.
- **Data-plane specifics (§4.4)**: legacy MPLS: LDP (RFC 5036), RSVP-TE (RFC 4875), BGP (RFC 8277) could distribute S-/A-Labels like PW/VPN labels but need DetNet extensions (PREOF, aggregation, node resources, queue placement); **legacy IP: DetNet IP (RFC 8939) is simpler, does not support PREOF, so only one path per flow or aggregate; protocol extensions expected to be limited to existing IP routing protocols**; SR: explicit routing in headers with centralised computation, less signalling and core state; DetNet MPLS/IP data planes are compatible with SR-MPLS and SRv6.
- **Encapsulation and metadata (§4.5)**: controller must discover per node the supported encapsulations (MPLS, IP) and metadata schemes (sequencing, timestamping), then instruct nodes which to apply per flow (e.g. MPLS header + sequence number).

### 2.5 Management plane (§5)
Static provisioning plus OAM. **Active PM** (injected packets) affects delay/throughput — not recommended in operational DetNet domains, useful for commissioning/troubleshooting. **Passive PM** (IOAM RFC 9197) monitors real traffic — preferred. **CFM**: RFC 9551 (framework), RFC 9634 (IP), RFC 9546 (MPLS).

### 2.6 Multi-domain (§6)
Multiple CPFs collaborate to implement FME requests as per-flow per-hop behaviours; CPFs (e.g. PCEs) must discover, authenticate and negotiate per-hop behaviours; RAW (wireless) adds Point of Local Repair functions; the application plane may split per-domain responsibilities.

### 2.7 Security (§8)
No protocol → no new considerations; future solutions must include them; see RFC 8655 and RFC 9055.

## 3. How Arcana could realise each element on FreeBSD

Arcana is, by construction, the **fully centralised model (§3.2)**: the console is the controller, cblink is the NETCONF-equivalent southbound, agents are the devices. The intended redesign toward YANG makes RFC 9633 (DetNet YANG) a natural candidate for the DetNet part of the northbound and, in part, the southbound. BIRD gives a distributed flavour only for the underlay (hybrid, §3.3), never for DetNet flow signalling.

| RFC 9938 element | Arcana realisation on FreeBSD |
|---|---|
| Controller Plane Function (CPF) | The console: path computation, reservation ledger, flow provisioning (cblink), fault/performance management (events, probes, BFD). |
| Flow Management Entity / northbound | Console API; adopt the RFC 9633 `ietf-detnet` structure: `app-flows` (ingress/egress, traffic-specification per RFC 9016, traffic-requirements: min/max latency, max loss, max consecutive loss, max misordering), `service` sub-layer (we would expose only "none"/aggregation), `forwarding` sub-layer (explicit path, resource reservation). |
| Topology and capability collection (§3.2 step 1) | Agents' `network` (interfaces, link media/rate, neighbours via netlink, routes, nexthop groups, ipfw/dummynet `qos` objects, bird/BFD) and `kernel` (modules: dummynet, netgraph nodes, wg, ipsec). cblink replaces NETCONF `get`. |
| Path computation (§4.1) | Console CSPF over Arcana's own graph: links with rate, committed bandwidth, measured delay/ipdv/loss (probes, ms), administrative colours; constraint: sum of committed ≤ rate, hop-count × tick ≤ delay budget. |
| Path establishment (§4.1) | Per hop via cblink: static route in the flow's FIB (`route … -fib`), ipfw classification into that FIB and its dummynet queue, tunnel to the next hop. Replaces PCE-CC/RSVP-TE. |
| Resource allocation (§4.2) | Per hop: `queue Q config sched S weight W slots N [codel|pie]` from the TSpec (`bw = MaxPacketsPerInterval × MaxPayloadSize / Interval`; `slots ≥ MaxPacketsPerInterval × k`); port bandwidth as `sched S config bw R`; ingress `pipe`/`ng_car` policing to the TSpec. Buffer allocation = `slots`/`bytes`. Queuing discipline = scheduler type (`wf2q+`, `qfq`, `prio`, `fq_codel`, `fq_pie`). |
| Device configuration with/without flow discrimination (§4.2) | Aggregated: one DSCP class → one queue (`dscp` match). Independent: 6-tuple ipfw rule per flow → own queue; the device keeps the flow↔resource mapping as rule→queue number. |
| Flow aggregation / FAs (§2.1 req 2) | Console-managed DSCP class or shared tunnel; add/remove member flows = add/remove ipfw table entries (`table T add …`) under the same `queue`. |
| Bidirectional flows | Two unidirectional provisionings along the same hops (console enforces symmetry if requested). |
| Restriction to specific links | Explicit path selects only tagged links (console colours); no TSN links exist. |
| PREOF support (§4.3) | Not provisionable: no PEF/POF in kernel. The console should refuse flows requesting service protection other than "failover" (BFD/probe-driven re-steer) and L2 1+1 replication without elimination. No "LSP graph". |
| Label management (§4.4.1) | Not applicable (no MPLS). |
| DetNet IP (§4.4.2) | The matching data plane: one path per flow/aggregate, 6-tuple identification — exactly what ipfw + FIB + dummynet give. |
| SR (§4.4.3) | Not applicable. |
| Encapsulation and metadata discovery (§4.5) | Agent reports tunnel kinds available (gre/gif/geneve/vxlan/wg/ipsec), DSCP marking (`setdscp`), no sequencing/timestamping metadata; console instructs the encapsulation per flow (tunnel kind, outer DSCP). |
| Queue control needing time sync (§2.1 req 6) | Not supported (no time-gated queues); time sync (PTP ports) only for measurement. |
| Advertise static/dynamic characteristics (req 7) | Agent `network` reads + events (`interface up/down`, BFD state); periodic probe samples. |
| Scale (req 8) | Per-flow ipfw rules/queues per host up to 65535 queues; tables scale to many entries; console ledger. |
| Flow identification at each node (req 9) | ipfw rules per hop, generated per node role (edge: 6-tuple+setfib+queue; transit: dscp+queue). |
| Management: proactive/on-demand PM (§2.2) | Probes with per-flow DSCP and FIB (active; use for commissioning and low-rate background), ipfw per-rule counters and dummynet queue/drop statistics (passive), TCA events; on-demand `traceroute`/`capture` operations exist. |
| Continuity check / connectivity verification | BFD per tunnel (BIRD, 119-1); ICMP probes. |
| PREOF test/monitor | Not applicable. |
| Converged DetNet + non-DetNet (§2.3) | Yes: WF2Q+ work-conserving shares, best effort in its own queue; FIB 0 for non-DetNet. |
| Topology change adaptation (§2.3) | Events → console re-computation and re-provisioning; agent-local failover among pre-provisioned candidate tunnels (`sdwan-steer`). |
| Security (§2.3): integrity/authenticity of control | cblink over mTLS with per-host certificates (console CA); console WebAuthn; BIRD sessions with TCP MD5/BFD auth. Controller compromise: hosts trust only the console CA; no mutual verification of console *behaviour* — see open decisions. Timely delivery: cblink is TCP/SCTP; prioritise control traffic with a `prio` queue on WAN links. |
| Passive PM / IOAM (§5.1.1.2) | IOAM not in kernel; passive = counters, queue stats, `ng_netflow`/IPFIX records, pcap samples. |
| CFM per RFC 9634 (DetNet IP OAM) | Not implemented; BFD and ICMP cover continuity; no DetNet-specific OAM encapsulation. |
| Multi-domain (§6) | One console per domain; no CPF–CPF protocol; a future Coordinator (RFC 9543 A.6) would stitch at NNIs. |

## 4. Cannot be mapped (and why)

1. **PREOF provisioning and "LSP graph" computation (§4.3, req 5)** — no replication/elimination/ordering functions in the FreeBSD kernel; no kernel work allowed; the IP data plane does not carry sequence numbers anyway.
2. **MPLS S-/F-/A-Label allocation and distribution (§4.4.1, req 4)** — no MPLS forwarding.
3. **Queue control techniques requiring time synchronisation (req 6; RFC 9320 schedulers, 802.1Qbv/Qch)** — no gated queues; no sub-µs sync.
4. **Distributed DetNet signalling (RSVP-TE with DetNet extensions, IGP DetNet capability advertisement, BGP-LS)** — none available in BIRD/FreeBSD; only the centralised model applies.
5. **SR-based explicit routing** — no SR.
6. **IOAM-based passive PM, DetNet-specific CFM (RFC 9634/9546)** — not in kernel/user space; passive PM limited to counters/flow export.
7. **Metadata schemes (sequencing, timestamping) in encapsulation (§4.5)** — none of our tunnels add DetNet metadata; discovery will always report "none".
8. **Worst-case SLA path computation** — inputs (per-hop worst-case delay) do not exist; computation can only use measured averages/percentiles and engineering estimates.
9. **Timely control delivery guarantees (§2.3)** — cblink over TCP across the same WAN; can be prioritised, not guaranteed.
10. **Multi-domain CPF discovery/authentication/negotiation (§6)** — no protocol; out of scope for now.

## 5. Requirements and recommendations checklist

1. Support dynamic instantiation, modification and deletion of flows including explicit path, bandwidth, link restriction, buffers/resources, queuing disciplines, bidirectionality (§2.1).
2. Support flow aggregates: create/delete FAs, add/remove members (§2.1).
3. Accept flow requests from applications via API, static provisioning or a dynamic control plane (§2.1).
4. (MPLS) Manage S/F/A-Labels (§2.1) — N/A.
5. (MPLS) Support the service sub-layer/PREOF (§2.1) — N/A.
6. Support time-synchronised queue control (§2.1) — N/A.
7. Advertise static and dynamic node/link characteristics to nodes or controllers (§2.1).
8. Scale to the expected number of flows (§2.1).
9. Provision flow identification at every node, role-dependent (§2.1).
10. Monitor flow and node performance proactively and on demand (§2.2).
11. Support continuity check and connectivity verification (§2.2).
12. Test and monitor PREOF (§2.2) — N/A.
13. Operate in a converged DetNet/non-DetNet domain (§2.3).
14. Adapt to topology changes: failures, additions, removals (§2.3).
15. Ensure integrity and authenticity of control/signalling messages; prevent spoofing and segmentation attacks (§2.3).
16. Protect against controller compromise; verify controller legitimacy; prevent impersonation (§2.3).
17. Design system-wide resilience so one compromised node/controller is not catastrophic (§2.3).
18. Deliver control messages without undue delay and without resource leakage (§2.3).
19. Choose distributed, centralised or hybrid architecture consciously; centralised uses NETCONF/YANG/RFC 9633/PCE-CC (§3).
20. Path computation must meet SLA (bandwidth, max delay, max delay variation, max loss); path establishment must install the path on devices (§4.1).
21. Reserve resources from the RFC 9016 traffic specification (worst case): bandwidth, buffers, queuing disciplines, and service-sub-layer resources (§4.2).
22. Configure devices with or without flow discrimination; keep flow↔resource mapping when flows are independent (§4.2).
23. For PREOF compute and establish a set of paths from replication to merge points and map member flows to segments (§4.3) — N/A.
24. Discover encapsulation and metadata capabilities per node; instruct nodes per flow (§4.5).
25. Prefer passive PM in operation; use active PM for commissioning/troubleshooting (§5.1.1).
26. Follow RFC 9551/9634/9546 for CFM (§5.1.2).
27. Multi-domain: CPFs discover, authenticate and negotiate per-hop behaviours (§6).

## 6. Open decisions and trade-offs for Arcana

1. **Adopt RFC 9633 (ietf-detnet) for the northbound?** It models exactly the three roles (app-flow, service, forwarding) and traffic-spec/requirements; we would implement a profile: service sub-layer "none", forwarding "explicit path + reservation", requirements accepted only within declared capability. Trade-off: standards fidelity vs implementing a large model for a partial feature.
2. **Southbound granularity**: should the agent expose DetNet-style per-flow objects (flow → queue → route), or stay at generic device objects (ipfw rule, dummynet queue, route) that the console composes? The latter keeps the agent generic and YANG-device-like (RFC 8309 device model); the former eases consistency. Recommendation: generic device modules + a console-side compiler, matching how `sdwan-rules` works today.
3. **Active probing policy in DetNet classes**: RFC 9938 discourages active PM in operation; our probes are the only delay/loss source. Compromise: low-rate probes (interval ≥ 1 s) in the flow's class, BFD in a control class, counters for the rest.
4. **Controller legitimacy (§2.3)**: agents trust the console CA; add certificate pinning/short-lived certs, signed configuration bundles, or two-person approval (`job-confirm`) for DetNet-class changes.
5. **Control traffic class**: a `prio` queue for cblink/BFD/BIRD on every WAN link to approximate "timely delivery".
6. **Reservation ledger durability**: where committed resources are recorded (console DB) and how agents re-derive state after restart (they keep rules/objects "for the next start" already).
7. **Refusal semantics**: when a request's traffic-spec/requirements cannot be met (PREOF, latency below hop×tick, bandwidth), return RFC 8578 §11.3.1-style rejection with the nearest feasible alternative.
8. **Hybrid with BIRD**: let BIRD/OSPF compute the underlay (FIB 0) and keep DetNet FIBs static; or allow BIRD to populate DetNet FIBs with filtered, stable routes. Static is more deterministic; BIRD reacts faster to failures.
9. **Multi-domain**: ignore now; keep flow identifiers (DSCP class plan, tunnel ids) globally unique per console to allow stitching later.
