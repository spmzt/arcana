## 1. Purpose and place in the layered picture

- Defines **ietf-vpn-common** (prefix `vpn-common`, ns `urn:ietf:params:xml:ns:yang:ietf-vpn-common`, revision 2022-02-11): a library module of features, identities, one typedef and ten groupings reused by L3NM (RFC 9182), L2NM (RFC 9291), SAP (RFC 9408) and future L3SM/L2SM revisions.
- It is *layer-neutral* (L2/L3) and *model-type-neutral* (service model or network model): it sits across the customer-service and network layers of RFC 8309 Fig. 3. It exposes no data nodes of its own (no config, no state, no RPC) — security considerations are inherited by the users of the groupings.
- Imports: ietf-netconf-acm (`nacm:default-deny-write` on provider profiles), ietf-routing-types (RD, RT, RT type), ietf-yang-types (date-and-time), ietf-packet-fields (ACL header-field groupings, RFC 8519).
- Appendix A explains why L3NM no longer reuses L3SM groupings: reuse looked like a deployment dependency. For Arcana: keep a `vpn-common`-equivalent attribute library in cblink and have every VPN-ish family depend on it, never on each other.
- For Arcana the main value is: (a) the **identity hierarchies** are the vocabulary (service types, encapsulations, underlay protocols, routing protocols, statuses, roles, topology types, multicast types, applications), (b) the **status/RD/RT/placement/QoS groupings** are the building blocks every family will repeat.

### 2.2 Identities (every one, one line)

Address family (`address-family`): `ipv4`, `ipv6`, `dual-stack`.

VPN topology (`vpn-topology`): `any-to-any`; `hub-spoke` (spokes talk to hubs only, hubs to each other); `hub-spoke-disjoint` (hubs cannot talk to each other); `custom` (import/export policies decide).

Site network access type (`site-network-access-type`): `point-to-point`; `multipoint`; `irb` (integrated routing and bridging / pseudowire connection); `loopback`.

Operational status (`operational-status`): `op-up`, `op-down`, `op-unknown`.

Administrative status (`administrative-status`): `admin-up`, `admin-down`, `admin-testing`, `admin-pre-deployment`.

Role (`role`): `any-to-any-role`, `spoke-role`, `hub-role`, `custom-role`.

Placement diversity (`placement-diversity`): `bearer-diverse`, `pe-diverse`, `pop-diverse`, `linecard-diverse`, `same-pe`, `same-bearer`.

Service type (`service-type`): `l3vpn` (RFC 4364); `vpls` (RFC 4761/4762); `vpws` (RFC 4664 §3.1.1); `vpws-evpn` (RFC 8214); `pbb-evpn` (RFC 7623); `mpls-evpn` (RFC 7432); `vxlan-evpn` (RFC 8365).

VPN signaling type (`vpn-signaling-type`): `bgp-signaling` (RFC 6624/7432); `ldp-signaling` (RFC 5036 targeted LDP); `l2tp-signaling` (RFC 3931 L2TPv3).

IS-IS level (`isis-level` {rtg-isis}): `level-1`, `level-2`, `level-1-2`.

BFD session type (`bfd-session-type` {bfd}): `classic-bfd` (RFC 5880), `s-bfd` (RFC 7880).

Import/export (`ie-type`): `import`, `export`, `import-export`.

Bandwidth direction (`bw-direction`): `inbound-bw` {inbound-bw}, `outbound-bw` {outbound-bw}.

Bandwidth type (`bw-type`): `bw-per-cos` {qos}, `bw-per-port`, `bw-per-site`, `bw-per-service`.

QoS profile direction (`qos-profile-direction` {qos}): `site-to-wan` (CE->PE), `wan-to-site` (PE->CE), `both`.

Transport instance type (`transport-instance-type`): `virtual-network` (ACTN RFC 8453), `enhanced-vpn` (VPN+), `ietf-network-slice`.

Protocol type (`protocol-type`, underlay transport): `ip-in-ip` -> `ip-in-ipv4` (RFC 2003), `ip-in-ipv6` (RFC 2473); `gre` -> `gre-v4` (RFC 1702), `gre-v6` (RFC 7676); `vxlan-trans` (RFC 7348); `geneve` (RFC 8926); `ldp`; `mpls-in-udp` (RFC 7510); `sr` -> `sr-mpls` (RFC 8660), `srv6` (RFC 8754), `sr-mpls-over-ip` (RFC 8663); `rsvp-te` (RFC 3209); `bgp-lu` (RFC 8277); `unknown`.

Encapsulation type (`encapsulation-type`): `priority-tagged`; `dot1q` {dot1q}; `qinq` {qinq}; `qinany` {qinany}; `vxlan` {vxlan}; `ethernet-type`; `vlan-type`; `untagged-int`; `tagged-int`; `lag-int` {lag-interface}.

VXLAN peer mode (`vxlan-peer-mode` {vxlan}): `static-mode`, `bgp-mode` (EVPN learning).

Multicast group address mapping (`multicast-gp-address-mapping` {multicast}): `static-mapping`, `dynamic-mapping` (snooping).

Multicast tree type (`multicast-tree-type` {multicast}): `ssm-tree-type`, `asm-tree-type`, `bidir-tree-type`.

### 3.1 Groupings

## 5. Features Arcana would advertise

Advertise: `dot1q`, `qinq`, `vxlan`, `lag-interface`, `ipv4`, `ipv6`, `rtg-bgp`, `rtg-ospf`, `rtg-rip`, `bfd`, `bearer-reference`, `placement-diversity` (console-side), `qos`, `inbound-bw`, `outbound-bw`, `encryption`, `external-connectivity`.

Conditional (only if the plugin is installed on that host, so per-agent): `multicast`, `igmp`, `pim` (net/pimd), `rtg-vrrp` (carp semantics; consider an Arcana `carp` identity instead), `extranet-vpn` (if BGP vpn4 tables adopted).

Do not advertise: `qinany`, `mld` (no router-side MLD/PIMv6), `rtg-isis`, `rtg-ospf-sham-link`, `fast-reroute`, `carriers-carrier`.

## 6. YANG constructs used and what a strict YAML/CBOR schema language needs

| Construct | Example in RFC 9181 | cblink today / needed |
|---|---|---|
| feature / if-feature | `feature vxlan`; `identity vxlan { if-feature "vxlan"; ... }`; `list external-connectivity-identifier { if-feature "external-connectivity"; }` | none. Need `features:` at top level, `if-feature:` on attributes/ops/enum entries (and-expressions like `"vpn-common:igmp and vpn-common:ipv4"` appear in 9182), advertised through `ctrl getfamily` |
| identity / identityref with base and derived-from-or-self | `identity gre-v4 { base gre; }`; `leaf protocol { type identityref { base protocol-type; } }` | cblink `enum` is flat, closed, unnamed on the wire, single-module. Need: `identities:` definition kind with `base`, cross-family references (`vpn-common:gre`), open extensibility (Arcana adds `wireguard`), and wire encoding (text `module:name`, or a registered u32 SID per RFC 9595) plus `derived-from-or-self` validation |
| typedef | `typedef vpn-id { type string; }`; imported `rt-types:route-target`, `rt-types:route-distinguisher`, `rt-types:route-target-type`, `inet:dscp`, `inet:port-number`, `inet:ipv4-prefix`, `inet:ipv6-flow-label`, `yang:date-and-time` | cblink has only const/enum/flags. Need `typedef` with base type + checks, and a shared types family (ietf-inet-types/ietf-yang-types/ietf-routing-types equivalents) |
| pattern | inherited: `rt-types:route-target` (`(0:(6553[0-5]|...)` ...), `inet:ipv4-prefix`, `date-and-time` pattern | none. Need `pattern:` (POSIX ERE or XSD regex subset) in `checks`, or binary encodings that make patterns unnecessary (RD/RT as 8-byte `bytes exact-len: 8`, prefixes as bytes+len) |
| grouping / uses | ten groupings; `uses packet-fields:port-range-or-operator;` `uses oper-status-timestamp;` inside service-status | attribute-set + `nest` gives *nested* reuse only; YANG `uses` flattens. Need either `uses:` (inline expansion of another set's attributes with id renumbering) or accept one extra nesting level per grouping |
| choice / case (incl. nested, empty-leaf cases) | `choice type { case abstract {...} case protocol {...} }`; `choice rd-choice` with five cases; `choice target-flavor` with `empty` leaves; `choice match-type { default "match-flow"; ... }`; `choice l3 { container ipv4 ...; container ipv6 ... }` (shorthand cases) | none. Need `choice:` groups listing mutually exclusive attributes (at most one present), optional `default` case, `mandatory` choice |
| default | `choice match-type { default "match-flow"; }` | none. Need `default:` on attributes and choices; generated structs must distinguish absent-with-default from explicit |
| mandatory | `leaf route-target-type { mandatory true; }` | `required` (per op) — OK, but YANG `mandatory` inside a list entry is per-instance, i.e. required inside a nested set, which cblink's op-level `required` cannot express. Need `required` honoured inside `nest` policies |
| list with key / keyed by non-string / nested keyed lists | `list vpn-target { key "id"; }` (uint8), `list route-targets { key "route-target"; }`, `list constraint { key "constraint-type"; }` (identityref key) | `multi-attr` + `nest` has no key. Need `key:` on nested-attributes lists, uniqueness validation, identityref/uint keys |
| leaf-list, ordered-by user | `leaf-list protocol { type identityref; ordered-by user; }`; `list rule { key "id"; ordered-by user; }` | multi-attr arrays preserve order; need an explicit `ordered: user|system` flag so the server knows order is semantic (classification rules!) |
| config false (ro) | `leaf status { config false; }` in oper-status-timestamp; `auto-assigned-rd`; whole `oper-status` container | none. Need `config: false` on attributes so generators split request (rw) from reply (rw+ro) policies |
| empty type | `leaf auto { type empty; }`, `no-rd`, `all-other-accesses` | cblink `flag` — OK |
| bits | `flags? bits` (ipv4 header flags, tcp flags, from RFC 8519) | cblink `flags` definition on uint — OK (names not on wire; YANG-JSON sends names) |
| binary | `options? binary` (tcp options) | cblink `bytes` — OK |
| enumeration | none in 9181 itself (operator enum via packet-fields: lte/gte/eq/neq) | cblink `enum` — OK |
| union | none in 9181 (but in 9182: `next-hop`, `local-address`, `far-end`) | none in cblink |
| decimal64 | none in 9181 (9182: `warning-threshold`, rate limits) | cblink `float` is binary double; need `decimal64` with `fraction-digits` (CBOR tag 4 decimal fraction, or scaled integer) |
| nacm extension | `nacm:default-deny-write` on valid-provider-identifiers | cblink `auth: true` per op; need per-attribute/per-subtree write protection or accept op granularity |
| presence container | none in 9181 (9182: `authentication!`) | nest presence = map present; OK |
| when / must | none in 9181 (many in 9182) | none |
| augment | none defined; the module is *designed* to be augmented (new identities derive from its bases from other modules, e.g. 9408 adds `sdwan` to `service-type`) | none. Need cross-family identity derivation at minimum |
| import with prefix / namespaced identifiers | `vpn-common:ipv4`, `rt-types:route-target` | cblink has one file per family with no imports; need `imports:` of definition-only families (types, identities, groupings) |
| reference / description / units / contact | throughout | `doc:` covers description; `units` could be a doc convention or a `units:` key |
| rpc / action / notification | none in 9181 | n/a |

## 7. Open questions / decisions

1. **Identity encoding on the wire.** (a) text `"module:name"` as RFC 7951 JSON does — self-describing, bigger, needs string tables in C; (b) per-family uint with a registry (like cblink enums) — compact but cross-module derivation needs a global registry (RFC 9595 YANG SIDs is the IETF answer); (c) CBOR tag + uint. Trade-off: interop/readability vs. size and the C generator's complexity.
2. **RD/RT: real or bookkeeping?** Without MPLS the only reason to carry RD/RT is to run BGP vpn4/vpn6 between Arcana PEs in BIRD and derive per-FIB membership from RTs. Alternative: ignore RD/RT (`no-rd`, empty vpn-targets) and let the orchestrator compute tunnel meshes + per-FIB BIRD sessions. The first is standards-faithful and scales (one BGP session per PE pair carrying all VPNs), the second is simpler but O(VPNs x PEs) sessions.
3. **Profiles: resolved at console or templated in agent?** vpn-profile-cfg only has ids. Pushing ids requires the agent to hold the profile bodies (new families for qos/bfd/encryption/routing/forwarding profiles); pushing resolved values keeps agents dumb but loses the "glue" semantics and makes diffs bigger.
4. **Which bases to extend with Arcana identities.** Candidates: protocol-type += `wireguard`, `ipsec`; routing-protocol-type += `carp` (instead of mis-mapping vrrp), `babel` (BIRD supports it); service-type += `arcana:l2-bridge` (vxlan+if_bridge), `arcana:sdwan` already exists in 9408; encryption profile choices += wg vs ikev2. Extending keeps the IETF vocabulary intact; mis-mapping (vrrp=carp) would be simpler for the UI but lies to third parties.
5. **How much of qos-classification-policy to accept.** The packet-fields reuse brings ~30 match leaves, several of which ipfw cannot match (ihl, offset flags, tcp data-offset/urgent/seq/ack ranges, udp length). Options: advertise the full grouping and reject unsupported leaves at apply time with a structured error; or define an Arcana-trimmed grouping. The former is what YANG servers do (`must`/deviation); the latter needs a `deviation` concept in cblink.
6. **Status timestamps:** `last-change` requires the agent to persist state transitions across restarts (or re-derive from kernel timestamps like `ifconfig`'s `if_lastchange`/`birdc show protocols` since). Decide whether the agent or console owns the clock.
7. **Multicast**: it is a feature-gated subtree. Is PIM in scope at all for Arcana's SDN? If not, do not advertise `multicast` and drop the subtree from the family; if yes, net/pimd must become a first-class managed plugin with a config generator (like BIRD).
