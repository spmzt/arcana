# RFC 8763 — Deployment Considerations for Information-Centric Networking (ICN)

Source read in full: `rfc/rfc8763.txt` (April 2020, Informational, IRTF ICNRG). Research
Group consensus document; not a protocol specification.

## 1. Purpose

Fills a gap the ICNRG charter names: concrete migration paths and interworking configurations
for ICN (name-based data retrieval replacing host-based addressing) in the live Internet. It
classifies possible deployments into five configurations — Clean-slate ICN, ICN-as-an-Overlay,
ICN-as-an-Underlay, ICN-as-a-Slice and Composite-ICN — describes migration paths per
stakeholder (applications/services, CDNs, edge networks, core networks), summarises real
trials (PURSUIT, SAIL/NetInf, NDN testbed, ICN2020, UMOBILE, POINT/RIFE, FLAME, CableLabs,
NDN IoT, NREN, DOCTOR, Hybrid ICN) and lists nine protocol gaps where IETF standardisation
would help (REST APIs, naming, routing interaction, multicast, caching, NFV/SDN/SFC
integration, protocol mapping with security preservation, QoS via Diffserv/flow
classification, OAM via YANG/NETCONF/RESTCONF and performance measurement). For Arcana — an
IP/SDN fleet manager — it is background: it does not describe anything Arcana must implement,
but its vocabulary (overlay/underlay/slice), its NFV/SDN and OAM gap analysis, and its
deployment-scaling advice are transferable to the SD-WAN/SASE design.

## 2. Content

### 2.1 Terminology (§2–3)
Deployment = an ICN network ready for useful work in a live environment and interoperable
with the Internet (access, service-edge, transport, CDN, core and back-end networks; the
document limits itself to edge, core and CDN). ICN per RFC 7927/ICN-TERM; NFV per RFC 8568;
SDN per RFC 7426. A long abbreviation list (NAP = Network Attachment Point, NFD = NDN
Forwarding Daemon, TCL = Transport Convergence Layer, …).

### 2.2 Deployment configurations (§4)
1. **Clean-slate ICN (4.1)**: replace IP routers with ICN forwarders (NFD, CCNx, PURSUIT);
   some ICN approaches (POINT) instead rely on SDN switch upgrades; never trialled, "no longer
   considered a viable alternative" (§6.4).
2. **ICN-as-an-Overlay (4.2)**: ICN islands tunnelled over IP (ICN-over-UDP, ICN-in-L2-in-IP,
   NetInf convergence layer to HTTP, SDN-friendly overlays separating user and control
   planes); needs interworking between IP routing (OSPF/RIP/IS-IS) and ICN routing; edge or
   core; easiest for experimentation.
3. **ICN-as-an-Underlay (4.3)**: native ICN islands integrated via application-layer gateways/
   proxies that translate message semantics (HTTP/CoAP ↔ ICN); routing domains strictly
   separated. Edge (4.3.1): greenfield IoT, CoAP↔ICN proxies, VSER edge service gateway with
   its own compute/network virtualisation controllers and service discovery, mobility as a
   service. Core (4.3.2): POINT maps HTTP/CoAP onto ICN at the NAP (access points/CPE) so the
   core looks like IP from outside; CableLabs uses ICN inside CDN server farms.
4. **ICN-as-a-Slice (4.4)**: network slicing (NGMN; NFV+SDN functional decomposition) hosting
   an ICN slice with its own control and forwarding plane; in 5G (TS 23.501/23.502) either as
   an edge service via the local data network with UPF classification, or natively via non-IP
   PDU sessions to ICN UPFs at the gNB; ICN as SFC; orchestration by ONAP; "the slice is
   created to run a 5G-ICN instance".
5. **Composite-ICN (4.5)**: mixtures, e.g. Hybrid ICN (hICN) carries ICN names in IPv6
   addresses and other ICN data in the payload so ICN-unaware IPv6 routers forward normally
   and ICN-aware ones apply ICN semantics.

### 2.3 Migration paths (§5)
Stakeholders: application providers, ISPs/service providers (core, access, ICN providers),
CDN providers, device makers/users; economics and regulation excluded.
- Applications/services (5.1): HTTP is the convergence point (even video moved to DASH/HLS);
  underlay + proxy mapping gives compatibility (HTTP/TCP/IP ↔ HTTP/ICN, TCP/ICN, HTTP/NDN
  gateways with caching-friendly mapping); overlay and slice let new ICN-native apps use
  multicast/caching; dual-stack devices with a TCL middleware choosing ICN or IP per
  transaction.
- CDN (5.2): underlay for existing CDNs; BIER multicast overlay use case; reduce origin load.
- Edge (5.3): IoT via underlay + CoAP/oneM2M proxies; 5G access networks via slices; campus/
  AR-VR islands.
- Core (5.4): slices on SDN-based optical transport isolate ICN traffic; underlay with IP
  preserved at the edge.

### 2.4 Trials (§6)
Overlay: PURSUIT (70+ nodes, L2 VPN overlay across continents), SAIL NetInf (UDP/HTTP
overlays, stadium, routing hints), NDN testbed (~100 nodes, videoconferencing, geolocation),
ICN2020 (37 nodes USA/EU/Japan, ~70 Mbps per node for video), UMOBILE (NDN+DTN, DABBER
routing, PiCasso edge platform on 10 Raspberry Pis in Guifi.net, post-disaster and emergency
trials). Underlay: POINT/RIFE (80+ nodes, HTTP streaming multicast, PrimeTel IPTV/HLS trial,
40 Guifi.net households, ETSI MEC PoC), FLAME (Bristol and Barcelona city-scale SDN,
location-based game with video multicast to six surrogates, latency bounded by one hop; 23
media experiments planned), CableLabs (CDN farm, untested, 3–5 years), NDN IoT (60 nodes over
6LoWPAN; ROM −60 %, RAM −80 % vs IP stack), NREN (Cisco/Internet2 CICN, ~15 nodes, VPN L2),
DOCTOR (NDN over Docker NFV with HTTP/NDN gateway for top-1000 websites; ML-based attack
detection — content poisoning detected > 95 % with < 0.01 % false positives — and
MANO-orchestrated countermeasures). Composite: hICN (150 DASH clients). Summary: all trials
< 1k users and few applications; Huawei/China Unicom starting ICN-as-a-Slice over wired and
5G-NR; recommendation to scale users linearly and monitor at every multiple of 1k.

### 2.5 Protocol gaps (§7, Table 1)
| Gap | Potential effort |
|---|---|
| 1 REST APIs | HTTP/CoAP support of ICN semantics |
| 2 Naming | dynamic naming of data objects (hash names — RFC 6920 — do not fit dynamic data; CCNx names RFC 8569/8609) |
| 3 Routing | interaction between IP and ICN routing protocols |
| 4 Multicast | multicast enhancements (ICN has implicit multicast retrieval) |
| 5 In-network caching | cache placement and sharing; interplay with managed CDNs |
| 6 NFV/SDN support | integration with NFV/SDN incl. SFC impacts |
| 7 Protocol mapping | HTTP and other protocols ↔ ICN while preserving message security (cf. RFC 8075 HTTP↔CoAP, RFC 8613 OSCORE) |
| 8 QoS | Diffserv DSCP for ICN data paths, flow classification for rate/cache control |
| 9 OAM | YANG models, NETCONF/RESTCONF, performance measurement/benchmarking comparable to IP (CCNinfo/Contrace traceroute exists) |

Security (§10): ICN's intrinsic content authentication/encryption; access control, privacy,
cache security and DoS protection immature (RFC 7945); gateways/proxies must preserve
end-to-end security across translation; interest flooding and content poisoning attacks and
MANO-orchestrated countermeasures (DOCTOR).

## 3. How it relates to Arcana on FreeBSD

Arcana is not an ICN system and the RFC does not ask it to become one. What transfers:
1. **Deployment configuration vocabulary**: Arcana's SD-WAN is "overlay" (tunnels in service
   FIBs over the UCS underlay) with "slices" (a FIB and routing domains per service, Mplify
   119 §7.3). Using the RFC's overlay/underlay/slice/composite taxonomy in the SD-WAN/SASE
   docs and in the YANG redesign (e.g. an `overlay`/`underlay` role on every link in the
   RFC 8345 network topology model) keeps the naming aligned with IRTF/IETF usage.
2. **ICN island as a plugin (hypothetical)**: the plugin mechanism (luxuria/plugins.c runs
   Squid, Suricata, c-icap/ClamAV, Unbound per service) could in principle run an NDN
   forwarder (NFD, `net/ndn-cxx`/`nfd` ports) or hICN in a jail as an *ICN-as-an-Overlay*
   island over the SD-WAN, steered by ipfw (UDP 6363) like any application flow. Nothing in
   the plan needs it; list as "possible, not planned".
3. **Gap 6/7/8/9 are Arcana's own concerns**: SFC via ipfw `divert`/`fwd` to plugins is how
   SASE chains functions; DSCP-based QoS (gap 8) is the SD-WAN policy; OAM via YANG models +
   NETCONF/RESTCONF-shaped contract and IPPM-style measurement (gap 9) is exactly the agent
   redesign — the RFC's observation that ICN lacks these is a reminder that an SDN solution
   is judged on them.
4. **Edge gateway pattern**: the underlay's NAP/proxy that terminates one protocol and maps
   it to another while preserving security (RFC 8613-style) is the same shape as Arcana's
   Squid TLS proxy with its own CA (SASE-4): the RFC's security warning (translation must
   preserve end-to-end security) applies verbatim.
5. **Scaling advice**: trials never exceeded 1k users; "increase users linearly and monitor
   at every multiple of 1k" — adopt as a rollout rule for SASE remote endpoints (SASE-3's wg
   identities) and tie it to the RFC 8456-style benchmarks.
6. **MANO-driven countermeasures (DOCTOR)**: ML detection + orchestrated remediation (scale
   a bottleneck, deploy a firewall/signature-verification function) is a pattern for Arcana's
   faults → actions loop (IDS alert → ipfw rule / plugin scale) in the SASE phases.

## 4. Cannot be mapped / not applicable
- Clean-slate ICN, ICN naming, ICN routing (NLSR, DABBER), in-network caching, interest/data
  forwarding (NFD/CCNx), hICN, ICN-as-a-Slice in 5G cores, ATSSS/UPF integration — none has a
  FreeBSD kernel or Arcana counterpart; FreeBSD has no ICN forwarder in base.
- ICN multicast retrieval and BIER overlays: FreeBSD has no BIER; Arcana's SD-WAN is unicast.
- CDN migration, DTN (UMOBILE), 6LoWPAN IoT stacks: outside a fleet manager's scope.
- ICN-specific security (content poisoning, interest flooding) and ICN OAM tools
  (CCNinfo/Contrace).

## 5. Checklist (what Arcana takes from the RFC)
1. Use overlay/underlay/slice terminology consistently in docs, API and YANG models.
2. Keep SFC (gap 6) explicit in the model: a function chain per policy (ipfw divert/fwd order)
   rather than ad hoc rule ordering.
3. QoS by Diffserv (gap 8) remains the classification primitive; document DSCP preservation
   across tunnels (`dscpinherit`) and proxies.
4. OAM (gap 9): YANG models + RESTCONF-like API + IPPM-based measurement (STAMP, alternate
   marking) — the redesign's core.
5. Security of protocol-translating proxies (Squid TLS bump, DNS filter): preserve or clearly
   terminate end-to-end security, state it in the model.
6. Rollout rule: scale SASE users linearly, review metrics at every 1k.
7. Optional: an "ICN island" example as a plugin/jail in the docs, marked not planned.

## 6. Open decisions and trade-offs
- Whether to model overlay/underlay roles in the topology model now (small cost, future-proof
  for RFC 8345/8346 exports) or leave them implicit in "service FIB vs FIB 0".
- Whether SASE's function chaining should be a first-class SFC object (RFC 7665 vocabulary:
  SFC, SFP, classifier) or stay as compiled ipfw rule order; the RFC's gap list suggests
  operators expect the former.
- Whether to spend any effort on ICN interop (an NDN plugin) — recommendation: none.
