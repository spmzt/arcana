# RFC 8342 — Network Management Datastore Architecture (NMDA)

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8342.txt (March 2018, Standards Track, updates 7950, 2467 lines, read in full).

## Purpose
Replaces the original NETCONF model (running/candidate/startup + a separate "operational
state" that was not a datastore and forced duplicated `config false` branches such as
`interfaces` / `interfaces-state`) by a set of named datastores sharing one schema: data
nodes are defined once and instantiated per datastore. Updates 7950's XPath accessible-tree
rules and action invocation context.

## Terminology (section 3)
datastore (an instantiated YANG data tree); datastore schema (the modules a datastore
supports, with deviations/features); configuration (`config true`); running; candidate;
startup; **intended** configuration (running after transformations, what the system tries
to apply); conventional configuration datastores (running, startup, candidate, intended —
same schema, copyable); dynamic configuration datastore (ephemeral, obtained via other
systems/protocols); learned configuration (from protocols); system configuration (supplied
by the device); default configuration; applied configuration (actually in use);
system state (`config false`); **operational state** = applied configuration + system state;
origin (metadata annotation); remnant configuration (still applied after removal from
intended until resources are released).

## The datastores (section 5)
```
 <candidate> (ct,rw) --\        /-- <startup> (ct,rw)
                      <running> (ct,rw)
                          | transformations (inactive removal, templates)
                      <intended> (ct,ro)  -- subject to validation
                          | applied, subject to missing resources, delays
 dynamic datastores --\   |   /-- learned, system, default configuration
                    <operational> (ct+cf, ro) <-- system state
```
- `<running>` MUST be supported if conventional configuration is possible; MUST always be
  valid (7950 §8.1).
- `<startup>` only where startup is separate; persists; `<candidate>` not persistent.
- `<intended>` read-only; MUST be updated and validated immediately when running changes;
  for simple servers running == intended; does not persist. No standard transformation
  mechanisms exist yet.
- Dynamic datastores: ephemeral, MAY have a different schema; feed `<operational>`.
- `<operational>` read-only; contains ALL config true + config false nodes; schema MUST be a
  superset of all configuration datastores' schemas (config nodes MAY be omitted if the
  server cannot report them accurately). Returns the value **in use**, regardless of defaults
  (absent = not in use). SHOULD conform to constraints, but **semantic constraints MAY be
  violated** (when, must, mandatory, unique, min/max-elements, key uniqueness) because of
  remnants, abnormal values, list restructuring; **syntactic constraints MUST NOT be
  violated** (hierarchy, identifiers, types) — a syntactically invalid node MUST NOT be
  returned. Does not persist.
- Remnant configuration (5.3.1), missing resources (5.3.2: config for a non-present interface
  stays in running/intended, is absent in operational; validity MUST NOT depend on resource
  presence), system-controlled resources (5.3.3: appear/disappear dynamically; matching
  intended config gets applied when they appear).

## Origin annotation (5.3.4, module ietf-origin)
`md:annotation origin { type origin-ref; }` on any config node in `<operational>` (inherited
from the parent when absent; MUST be present on top-level config nodes; not on non-presence
containers). Identities under `or:origin`: `intended`, `dynamic`, `system`, `learned`,
`default`, `unknown`. In JSON this is RFC 7952 metadata: `"@hostname": {"ietf-origin:origin": "ietf-origin:learned"}`.
In YANG-CBOR there is no standard metadata encoding yet (RFC 9254 has none) — a cblink
profile would need to carry origin either not at all, or as a framework-level annotation.

## Implications on YANG (section 6) — updates to 7950
- XPath accessible tree: for state-data nodes = all operational state (root has all top
  nodes); for notifications = the notification instance + all operational state; for
  rpc/action input and output = the operation instance + all operational state.
- Actions are always invoked in the context of `<operational>`; the target node MUST exist
  in `<operational>`.

## Module ietf-datastores@2018-02-14 (prefix ds)
Identities: `datastore` (base) → `conventional` → `running`, `candidate`, `startup`,
`intended`; `dynamic` (base for dynamic datastores); `operational`. `typedef datastore-ref
{ type identityref { base datastore; } }`. (CORECONF adds `coreconf:unified` with base
`ds:datastore`.)

## Appendix A: guidelines to define a new datastore
Which modules; which subset of nodes (e.g. only config true); how data is actualised (into
operational); which protocols; a `ds:datastore`-derived identity and optionally an
`or:origin`-derived identity. Example: `ds-ephemeral` with base `ds:dynamic` and
`or-ephemeral` with base `or:dynamic`.

## Appendix C examples (what operational looks like)
System example: intended has hostname foo + eth0 + eth1; operational shows `hostname`
origin learned (DHCP), `eth0` origin intended with `enabled` origin default, a learned
extra address, `lo0` origin system, and eth1 absent (hardware missing). BGP example: peer
local-as/peer-as filled from parents with origin default, local-port origin system,
`state` cf leaf; a removed peer remains with `state closing` until resources are released.
Interface example: pre-provisioned et-0/0/0 absent from operational until the FRU is
inserted; system-provided lo0 with addresses origin system unless configured.

## Relevance to Arcana
1. **Which datastores should arcana-agent expose?** The agent today applies changes
   immediately (jail(8), ifconfig, sysrc, route) and *also* edits persistent files
   (jail.conf, rc.conf) — i.e. it already distinguishes "live" from "persistent", which is
   exactly `<operational>` (what the kernel has: ifconfig/sysctl/netstat/jls) versus
   `<running>`/`<startup>` (rc.conf, jail.conf, /etc/*). FreeBSD has no `<candidate>`
   natively. A faithful mapping:
   - `ds:running` = the configuration files as parsed (rc.conf, jail.conf, pf.conf, …);
     `ds:startup` = same files (FreeBSD does not separate them), so startup == running;
   - `ds:intended` = running (no transformations);
   - `ds:operational` = kernel state via ifconfig/ioctl/sysctl/netstat/jls/libprocstat,
     with `origin` = `intended` when the live value matches rc.conf, `system` for kernel-
     created things (lo0, default FIB, system jails?), `learned` for DHCP/RA addresses and
     routes, `default` for YANG defaults in use.
   Current arcana `address` op's "live and/or persistent" flag is precisely "edit operational
   (dynamic datastore) and/or running". Modelling the live-only change as a dynamic
   datastore `arcana:ds-live` (base ds:dynamic) is the NMDA-conformant way to say "apply now,
   do not persist".
2. CORECONF uses a single `unified` datastore; RESTCONF 8040 exposes only the unified
   `{+restconf}/data`. NMDA-aware RESTCONF (RFC 8527, not in scope here) adds
   `{+restconf}/ds/ietf-datastores:operational` etc. Choosing NMDA on the cblink side
   means a datastore identity (SID) parameter in the datastore operations; it costs one
   integer per request and buys the running/operational distinction Arcana already has.
3. The "semantic constraints MAY be violated in operational" rule means the agent's
   validator must be able to run in a lenient mode for state reporting (type checks only)
   and a strict mode for edits — two validation entry points in the generated code.
4. The origin annotation needs a metadata channel; RFC 9254 has no YANG-CBOR metadata
   encoding. Options: a cblink framework attribute carrying `{instance-identifier → origin SID}`
   sidecar map, or omit origin in CBOR and let the console synthesise it. See design doc.
