## 1. Purpose

RFC 8655 is the architecture for Deterministic Networking (DetNet): carrying specified
unicast or multicast flows for real-time applications with extremely low loss and bounded
end-to-end latency within one administrative domain (campus, private WAN; not the
Internet). It defines the DetNet QoS (worst-case latency bounds, loss ratio, misordering
bound; averages are irrelevant), the three techniques (resource allocation, service
protection, explicit routes), the two data-plane sub-layers (service: sequencing,
replication, elimination, ordering, encoding; forwarding: resource allocation, explicit
routes), the node roles (end system, edge, relay, transit), flow types, the three planes
(application, controller, network) with the Flow Management Entity and Controller Plane
Functions, queuing/shaping mechanisms (TSN shapers, gates, CQF, preemption, AQM), service
instances, flow identification across technology borders, resource advertisement, scaling
by aggregation, L2 compatibility, and security/privacy. It assumes time synchronisation is
provided by other means (PTP). DetNet operates at the IP layer over MPLS and TSN sub-nets.

## 2. Architecture and terminology (complete)

### 2.1 Terms (§2.1)
allocation; App-flow (payload carried over a DetNet service); DetNet compound flow / member flow (a flow split into duplicate member flows for protection, merged back without duplicates; relative terms, recursive); DetNet destination/source (end systems); DetNet domain (the DetNet-aware portion); **DetNet edge node** (a relay node acting as source/destination at the service sub-layer: service proxy for PREOF, starts/terminates resource allocation, aggregates; ≈ LER/PE); DetNet flow (packets matching a flow identifier, including DetNet headers); **forwarding sub-layer** (optional resource allocation over paths of the underlying network); intermediate node (relay or transit); **relay node** (service sub-layer function interconnecting forwarding paths for protection; usually also transit); **service sub-layer** (where protection is provided); service proxy (maps App-flows to DetNet flows); DetNet system; **transit node** (forwarding sub-layer only, link/network-layer switching across links/sub-networks; ≈ LSR); DetNet-UNI (packet reference point: encapsulation, status, synchronisation); end system (host/end station, aware or not); link (physical or sub-network); **PEF** (eliminates duplicates); **PRF** (replicates to one or more next hops; copy count is a per-flow parameter at that point); **PREOF** (replication, elimination, ordering collectively); **POF** (reorders); reservation. TSN dictionary (§2.2): Listener=destination, Relay system=intermediate node, Stream=flow, Talker=source.

### 2.2 DetNet QoS (§3)
- Expressed as: min and max end-to-end latency, timely delivery, bounded jitter derived from them; loss ratio under stated operational states; an upper bound on out-of-order delivery (zero allowed). **Worst case only**; a priority scheme gives better average latency but unacceptable worst case.
- **Resource allocation** (§3.2.1): assign buffer/bandwidth per flow or aggregate along the path; eliminates contention loss; requires sources limited to a max packet size and rate; no need for transport congestion control (but it must not hurt); finite buffers imply a max latency. Every node must regulate output not to exceed the flow's rate (except brief catch-up); policing and shaping at the domain ingress are mandatory, also to protect non-DetNet traffic; beware large buffers (bufferbloat). Reservation requires provisioning; other node resources may be over-subscribed and cause rejection. **Jitter reduction** (§3.2.1.2): emulate serial cables; use sub-µs synchronisation plus time-of-execution fields in packets; packet networks have practical limits.
- **Service protection** (§3.2.2): against equipment/media failures; methods of RFC 6372 (1+1); PREOF (1+n hitless); in-order delivery (misordering is a side effect; POF restores order; zero misordering is a valid constraint). PREOF capabilities: sequencing info (sequence number/timestamp, added once near the source, or inherent), PRF into member flows over different (SRLG-disjoint) paths, PEF based on sequence history (output is one packet; anywhere, usually near the receiver), POF. Order of PEF/POF/PRF is implementation-defined. Passive: does not react to failures. Merge point may need extra buffering to equalise path delays so the compound flow does not exceed its bandwidth after a path is restored. **Packet encoding/network coding** (§3.2.2.3) as an alternative.
- **Explicit routes** (§3.2.3): paths do not change immediately (or at all) with topology events; established via RSVP-TE, SR, SDN (RFC 8453), IS-IS PCR (RFC 7813); typically MPLS-TE LSPs; help in-order delivery because changes are planned between explicit routes.
- Eight combinations of the three techniques; typical: explicit routes + protection (seamless ring redundancy, IEC 62439-3, RFC 8227); resource allocation alone (AVB, MSRP + shapers); all three for max protection. Prioritisation + over-provisioning works only with little non-critical traffic and no misbehaviour.
- **Secondary goals** (§3.3): coexistence with normal traffic (unused DetNet bandwidth available to non-DetNet, not to other DetNet flows; DetNet flows shaped so the highest-priority non-DetNet packet also has a worst-case latency; schedules leave room; avoid starvation by policing/shaping); fault mitigation (filters and policers detect wrong interface/time/volume and discard or shut down; edge filtering and remarking so non-DetNet packets are not mistaken for DetNet; sending DetNet into unprovisioned networks is a fault; egress filters strongly recommended; PRF-generated member flows count as non-congestion-controlled; techniques: policing, shaping, per-flow rate-limited queues, AQM RFC 7567).

### 2.3 Architecture (§4)
- **Stack model (§4.1.1, Fig. 2)**: Source/Destination; Service sub-layer: packet sequencing ↔ duplicate elimination, flow replication ↔ flow merging, packet encoding ↔ decoding; Forwarding sub-layer: resource allocation, explicit routes; lower layers. Not all sub-layers are needed. OAM (in-band/out-of-band, tagging to trace replicas, active/hybrid methods need bandwidth) may be in any layer. PREOF may be at the ends or in relay nodes.
- **Data-plane overview (§4.1.2, Fig. 3/4)**: end systems, edge nodes, relay nodes interconnected by transit nodes (e.g. LSRs, forwarding-aware only) over sub-networks (MPLS-TE, TSN, OTN, p2p links; or a lower DetNet). Service sub-layer technologies: PW, UDP, GRE; forwarding sub-layer: IPv6, IPv4, MPLS-TE LSPs, MPLS SR. Basic header choice (MPLS label vs IP header) drives the forwarding logic; IP addresses address DetNet nodes in both; flows must be mapped to the sub-network (e.g. TSN Streams).
- **Reference model (§4.1.3, Fig. 5)**: DetNet-UNIs may add encapsulation, provide reservation status, provide synchronisation, carry signalling for reservations without a controller; multidomain (DetNet-1, DetNet-2); internal end-system reference points expect in-order delivery.
- **End systems (§4.2.1, Fig. 6)**: App-flow CBR or VBR, L1/L2/L3 encapsulation, reserved at peak for VBR; categories: DetNet-unaware (needs service proxy), f-aware (forwarding/reservation only), s-aware (sequence numbers, no reservation), sf-aware (full).
- **Edge/relay/transit (§4.2.2)**: DetNet-unaware nodes between DetNet nodes threaten QoS; configure them to minimise loss/delay and over-provision downstream buffers.
- **Flow types (§4.3.1)**: App-flow, DetNet-f-flow, DetNet-s-flow, DetNet-sf-flow. **Source behaviour (§4.3.2)**: synchronous flows (nodes synchronised to <1 µs; repeating schedules share buffers/bandwidth over time) vs asynchronous (worst-case interference assumed; characterised by max packet size, observation interval, max transmissions per interval → bandwidth). Sources must not exceed limits; unused capacity goes to non-DetNet traffic; no congestion-control expectation; reservation before start is unavoidable; requirements translate into queuing/shaping/scheduling parameters delivered to nodes; non-aware nodes must be provisioned by neighbours (TSN streams, TE LSPs). **Incomplete networks (§4.3.3)**: extra buffering downstream of non-DetNet nodes increases latency/jitter.
- **TE planes (§4.4)**: DetNet is a branch of TE (TEAS). **Application Plane**: User Agent requests via the abstract **Flow Management Entity (FME)**; **TSpec** abstraction over the Northbound Service Interface with location (IP/DNS). **Controller Plane** = control + management (RFC 7426) (+ measurement per CCAMP); **CPF** = PCE, NME or distributed protocol; CPFs place flows along deterministic arrangements (possibly with replication/elimination points) respecting per-flow constraints and optimising aggregate cost; **Northbound Service Interface** and **Southbound Network Interface** (extends TEAS topology/resource description). **Network Plane**: NICs, routers, switches, data plane + OAM; nodes expose capabilities/resources and topology perception; CPFs install per-flow paths with a Flow Characterization tighter than a TSpec; nodes may exchange path state and perform drop/declassify as last resort.
- **Queuing, shaping, scheduling, preemption (§4.5)**: reservation alone is insufficient; standard algorithms needed so TE can compute each node's latency contribution, buffer need and translate flow spec → managed objects: credit-based shaper (802.1Qav), time-gated queues (802.1Qbv), cyclic queuing and forwarding (802.1Qch), frame preemption (802.1Qbu/802.3br); applicable beyond Ethernet except preemption; TSCH for wireless; IETF CoDel (RFC 8289) and PIE (RFC 8033) noted as further techniques DetNet may adopt.
- **Service instance (§4.6, Fig. 8)**: all functions on a node for the end-to-end service between UNIs; access filter (F1/F2) selects DetNet packets into a flow-specific service instance (SI-1/SI-2); a tunnel between SIs used *exclusively* for the DetNet flow (unlike RFC 6658 packet PWs); SI and tunnel may be shared by several flows if forwarding tables are populated.
- **Flow identification at technology borders (§4.7)**: export higher-layer flow identification to lower layers (TSN Stream id, distinct LSP label) rather than deep inspection; aggregates allowed; Flow-IDs per domain (Eth, MPLS, IP) added/removed at borders, unique per domain, created or derived; when flow id is exported, sequence-number encoding must be exported/altered likewise (Figures 9–11).
- **Advertising (§4.8)**: capabilities (queuing/shaping algorithms, DetNet buffers, worst-case forwarding delay and misordering), resource state, neighbours and link characteristics including latency in nanoseconds.
- **Scaling (§4.9)**: per-flow state is heavy; the data plane must support aggregation (MPLS hierarchy, DSCP).
- **L2 compatibility (§4.10)**: sub-networks (MPLS-TE, TSN, OTN) provide DetNet-compatible service; multilayer DetNet possible.

### 2.4 Security and privacy (§5–§6)
Single administrative domain; secure request/control of resources (authentication/authorisation, ACTN precedent RFC 8453 §9), confidentiality via IPsec (RFC 4301) or MACsec, per-flow identification increases exposure, DoS via admission control (§3.2.1) and fault mitigation (§3.3.2), delay attacks mitigated by authenticating domain devices, time-sync integrity critical (RFC 7384); privacy: markings allow correlation; per-node flow identification is an attack surface.

## 3. How Arcana could realise each element on FreeBSD

Honest framing first: FreeBSD has no DetNet data plane (no RFC 8964 MPLS d-CW/S-label, no PREOF, no TSN). What it has is exactly what the **DetNet IP data plane (RFC 8939)** needs for the *forwarding sub-layer*: 6-tuple flow identification (ipfw), per-flow or per-aggregate resource allocation (dummynet), explicit routes (per-FIB static routes, tunnels), ingress policing (pipe, ng_car), AQM (CoDel/PIE). RFC 9938 §4.4.2 confirms the IP data plane has no PREOF and needs one path per flow. So Arcana can be a **DetNet-f domain over IP** with soft bounds, never an sf domain. The Controller Plane maps well onto console+agents.

| RFC 8655 element | Arcana realisation on FreeBSD |
|---|---|
| DetNet domain | A set of Arcana hosts (edges and transit) under one console: single administrative control, as the RFC demands. |
| End system, DetNet-UNI | A UNI interface on an edge; unaware end systems get a service proxy = ipfw classification at the UNI (access filter F1). |
| Service proxy / edge node | Edge host: ipfw rule `… src-ip A dst-ip B proto P src-port/dst-port … dscp D` (RFC 8939 6-tuple) → `setfib S` (the flow's service instance) + `queue Q` (its reservation on this hop) + tunnel to the next DetNet node. No sequencing is added (IP data plane has none). |
| Relay node (service sub-layer) | **Not realisable** (no PEF/POF). |
| Transit node (forwarding sub-layer) | Any intermediate Arcana host: `dscp`/6-tuple match → `queue Q` on the egress link; explicit route = static route in the flow's FIB; no routing-protocol influence on that FIB. |
| Resource allocation (bandwidth) | dummynet `sched` WF2Q+ or `prio` per egress link; per DetNet flow (or aggregate) `queue Q config sched S weight W slots N` where W ≈ rate share and N = max packets per interval × safety factor (buffer dedicated to the flow). Bandwidth from the asynchronous TSpec: `bw = MaxPacketsPerInterval × MaxPayloadSize(+headers) / Interval`. |
| Ingress rate limiting / shaping | `pipe P config bw <bw> burst <B>` per flow at the UNI (shaper) or `ng_car` policer (CIR/CBS, drop red) for strict policing; both protect non-DetNet traffic from misbehaving sources (§3.2.1.1 mandatory). |
| Per-node regulation of output | Shaping queue per flow on each egress (dummynet is a shaper when `bw` is set); meets "do not exceed the rate except brief catch-up". |
| Explicit routes | Tunnels (gre/gif/wg/geneve) pinned between DetNet nodes + static routes per FIB on each hop (`route add -fib S …`); they do not move with OSPF/BGP convergence (BIRD does not export into that FIB). Planned changes = console rewrites. |
| Service protection (PREOF) | Not in kernel. Options with trade-offs: (a) L2 1+1 replication only: `ng_hub`/`ng_one2many` (`xmit_all`) duplicates Ethernet frames into two geneve/vxlan tunnels — no elimination, receiver gets duplicates (acceptable only if the application tolerates/dedups, e.g. PRP-aware IEDs); (b) user-space PEF: ipfw `divert` both member flows into an Arcana daemon that dedups by an application-visible sequence (RTP seq) and reinjects — adds scheduler latency and a copy, breaks "kernel-only" latency, but is pure user space and legal under the project rule; (c) 1:1 protection switching: BFD (100–300 ms ×3) + `sdwan-steer` failover — not hitless (hundreds of ms loss). |
| Packet encoding | No. |
| In-order delivery / POF | Single explicit path per flow gives order; no reorder buffer. |
| Coexistence (§3.3.1) | WF2Q+ is work-conserving: unused DetNet share is used by best effort automatically; give best effort a queue with its own weight so it is never starved; `prio` scheduler must be paired with policing to avoid starvation. |
| Fault mitigation (§3.3.2) | ipfw `recv ifX` match to drop DetNet-marked packets on the wrong interface; `limit`/pipes for volume; egress `deny dscp D out xmit wanX` where downstream is not provisioned; remark (`setdscp be`) non-DetNet traffic that arrives marked. |
| Queuing algorithms (§4.5) | CBS/Qbv/Qch/preemption: no. CoDel/PIE/FQ-CoDel/FQ-PIE: yes in dummynet (RFC 8289/8033 are the ones the RFC says DetNet may adopt). Strict priority: `prio` scheduler. |
| Service instance and exclusive tunnel (§4.6) | One tunnel per DetNet flow (gre keyed tunnels, wg peers, geneve VNI) is possible but costly; shared tunnel with per-flow dummynet queue and FIB is the practical SI; forwarding tables = FIB routes. |
| Flow identification / exporting Flow-ID (§4.7) | IP domain: 6-tuple + DSCP aggregate. Ethernet border: a VLAN per DetNet class with fixed PCP (`ifconfig vlanX vlanpcp P`) exports the class to bridges; per-packet PCP from ipfw is not available. MPLS border: none. |
| Aggregation (§4.9) | DSCP classes aggregating flows into one queue; tunnels aggregating many flows. |
| Application plane / FME / TSpec | Console API: a DetNet flow object with RFC 9016 traffic-spec (interval, max-pkts-per-interval, max-payload-size), min/max latency, max loss, endpoints (addresses/DNS). |
| Controller plane / CPF | Console: path computation over the Arcana topology (constraint: committed bandwidth per link, measured delay), reservation ledger, per-hop configuration via cblink; management (faults, performance) via events/probes. The agent-side `sdwan-steer` is a degenerate CPF for failover. |
| Northbound / Southbound interfaces | Northbound: RFC 9633 DetNet YANG subset (see rfc9938.md). Southbound: cblink → YANG-aligned device modules (interfaces, routing/FIB, ipfw+dummynet, tunnels). |
| Advertising (§4.8) | Agents report: link speed (`media`), scheduler types available (dummynet module present), queue counts, neighbours, measured link delay (probes, ms resolution). Worst-case forwarding delay: cannot be stated honestly; report an engineering estimate (queue bytes ÷ rate + serialisation) and label it so. |
| Time synchronisation | Not DetNet's job, but needed: `ntpd` (base) ~ms; `ptpd` or `linuxptp` from ports with kernel software timestamps (no general NIC hardware timestamping API in FreeBSD) ~10–100 µs; GPS/PPS refclock via the PPS API for a grandmaster. Sub-µs: not achievable. |
| Security | mTLS cblink, console WebAuthn, admission control at ingress, IPsec/WireGuard tunnels for confidentiality, BFD authentication/TCP MD5 for BIRD; time-sync integrity: NTS not in base ntpd (ports ntpsec/chrony offer NTS). |
| OAM | Probes (active; ok for commissioning), ipfw/dummynet counters and drop statistics (passive, per flow/queue), events on TCA. |

Engineering bound available (not a guarantee): for a flow with its own queue of `slots` packets under WF2Q+ at link rate R with total committed weight sum ≤ 100 %, worst queueing delay on that hop ≈ (slots × MTU)/R_share + MTU/R + scheduler overhead; interrupt moderation, `hz`/callout granularity of dummynet (`net.inet.ip.dummynet.hz`, default 1000 → 1 ms tick!) and tunnel crypto add jitter. **The dummynet tick (1 ms default, raise `hz` to 10000 for ~100 µs) is the floor of what bounded latency can mean on FreeBSD.**

## 4. Cannot be mapped (and why)

1. **PREOF (PRF/PEF/POF) in the network** — no kernel function; the DetNet IP data plane itself has no sequence numbers; MPLS data plane (d-CW) absent. Only L2 replication without elimination, or user-space elimination (slow), or protection switching (not hitless).
2. **Packet encoding / network coding** — no.
3. **Worst-case end-to-end latency guarantees** — dummynet is a software timer-driven shaper (1 ms default tick), general-purpose scheduler, no per-hop latency calculus standard; we can bound queue occupancy, not transmission timing. Across non-Arcana hops nothing.
4. **Bounded misordering / zero misordering as a *guarantee*** — only by single path; any failover reorders.
5. **Synchronous DetNet flows (time-scheduled, <1 µs sync, 802.1Qbv/Qch)** — no gating, no sub-µs sync.
6. **Credit-based shaper semantics (802.1Qav), frame preemption (802.1Qbu/802.3br)** — not in kernel/hardware.
7. **MPLS forwarding sub-layer (TE LSPs, SR-MPLS), DetNet MPLS service sub-layer (S-label, F-label, d-CW)** — no MPLS.
8. **TSN sub-network mapping (DetNet flows → TSN Streams, MSRP)** — no TSN; only VLAN/PCP per class.
9. **Link latency in nanoseconds (§4.8)** — probes give ms (ipdv in ms); software timestamps ~µs; no hardware timestamps.
10. **Per-flow exclusive hardware resources** — software queues share NIC rings/CPU; a DetNet-unaware kernel path (netisr, crypto) sits inside our own "node".
11. **Multicast DetNet flows with resource reservation** — no multicast reservation; IP multicast routing is add-on (pimd) without allocation.
12. **Time-of-execution / clock transport services at the UNI** — out of Arcana's scope; PTP accuracy limits as above.
13. **Hitless 1+n protection** — follows from 1.

## 5. Requirements and recommendations checklist

1. DetNet applies only within a single or closed group of administrative domains (§1).
2. Express QoS as worst-case min/max latency, bounded jitter, loss ratio under stated states, and a misordering bound (§3.1).
3. Reserve bandwidth and buffers per flow or aggregate along the path; source limited to max packet size and rate (§3.2.1).
4. Every node regulates its output to the flow's rate; police and shape at the domain ingress (mandatory), also protecting non-DetNet traffic (§3.2.1.1).
5. Avoid oversized buffers (bufferbloat) (§3.2.1.1).
6. For jitter-critical apps combine sub-µs sync with time-of-execution fields (§3.2.1.2).
7. Service protection via PREOF over SRLG-disjoint paths or encoding; include a max misordering constraint (possibly zero); equalise path delays at merge points (§3.2.2).
8. Use explicit routes that do not change with topology events (§3.2.3).
9. Unused DetNet bandwidth must be available to non-DetNet traffic, not to other DetNet flows; shape DetNet so the top non-DetNet class also has a worst-case; avoid starvation (§3.3.1).
10. Filters/policers detect wrong interface, time, volume and discard or shut down; edge filtering/remarking; egress filters so DetNet traffic never enters unprovisioned networks; treat non-congestion-controlled traffic into unprovisioned networks as a fault (§3.3.2).
11. Separate service and forwarding sub-layers conceptually; not all are required (§4.1).
12. End systems may be unaware, f-aware, s-aware or sf-aware; provide proxies for unaware ones (§4.2.1).
13. Reserve VBR flows at peak; asynchronous flows characterised by max packet size, interval, max transmissions per interval (§4.3.2).
14. Reservation before the application starts is unavoidable; translate requirements into node queuing/shaping/scheduling parameters (§4.3.2).
15. Provision DetNet-unaware nodes and add downstream buffering where they exist (§4.2.2, §4.3.3).
16. Structure as Application, Controller and Network planes with FME, TSpec, CPFs, Northbound and Southbound interfaces (§4.4).
17. Nodes expose capabilities, resources and topology to CPFs; CPFs install per-flow per-hop behaviour; nodes drop or declassify as last resort (§4.4.3).
18. Use standard queuing/shaping algorithms so TE can compute per-node latency and buffer contributions (§4.5).
19. Model a service instance with access filter, flow-specific SI and a tunnel exclusive to the DetNet flow (§4.6).
20. Export flow identification to lower layers at technology borders rather than deep inspection; keep Flow-IDs unique per domain; export sequence numbering alongside (§4.7).
21. Advertise capabilities (algorithms, buffers, worst-case delay and misordering), resource state, neighbours and link latencies (§4.8).
22. Support aggregation of flows (MPLS hierarchy, DSCP) to scale (§4.9).
23. Secure the request/control of resources; protect confidentiality (IPsec/MACsec); apply admission control against DoS; authenticate domain devices against delay attacks; protect time synchronisation (§5).

## 6. Open decisions and trade-offs for Arcana

1. **Scope statement**: declare Arcana a *DetNet-IP forwarding-sub-layer (f-aware) domain with engineering (not worst-case) bounds*, or not use the DetNet name at all and call it "assured latency class". Using the name invites expectations of PREOF and worst-case bounds we cannot meet; the RFC's own vocabulary (f-flow, incomplete networks) lets us be precise.
2. **dummynet tick**: raise `net.inet.ip.dummynet.hz` (default 1000) on DetNet-class hosts to 10000 or more for finer shaping; costs CPU; or use `io_fast` (`net.inet.ip.dummynet.io_fast=1`) to bypass the queue when not backlogged.
3. **Per-flow queue vs per-class aggregate**: RFC 8939 allows DSCP aggregation; per-flow queues give the cleanest buffer dedication but multiply state; decide a cap per host.
4. **Protection strategy**: offer only BFD-based failover (honest, ~300–900 ms) or add L2 1+1 replication for PRP-capable endpoints, or build the user-space PEF; each has a different latency/complexity/honesty profile.
5. **Exclusive tunnel per DetNet flow or shared tunnel + queue**: exclusive gives per-flow outer DSCP and SA; shared scales. Maybe exclusive only for the highest tier.
6. **Explicit route maintenance**: static routes per FIB per hop are brittle; the console must own them end to end and re-plan on topology events (never let BIRD into those FIBs), with a documented reconvergence policy.
7. **Time sync offering**: ship PTP (ptpd/linuxptp) configuration as an Arcana job or leave to the operator; document achievable accuracy.
8. **Capability honesty in the contract**: the agent should report `worst-case-delay: unknown` and an estimate field; the YANG model (RFC 9633) has places for capabilities; decide what we fill.
9. **Ethernet border handling**: VLAN+PCP per DetNet class on UNIs/bridges, or rely on IP DSCP only.
10. **Admission**: reject flows whose TSpec does not fit (RFC 8578 §11.3.1 demands rejection over silent acceptance); define the fit test (bandwidth sum, queue slots, hop count × tick).
11. **Multicast DetNet**: skip, or ingress replication to N unicast members (bandwidth ×N).
