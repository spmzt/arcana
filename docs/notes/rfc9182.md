## 1. Purpose and place in the layered picture

- **ietf-l3vpn-ntw** (prefix `l3nm`) is the *service delivery / network model* for BGP-PE-based L3VPNs (RFC 4364) and MVPNs (RFC 6513/6037). It sits between the **service orchestrator** (which talks L3SM to customers) and the **network controller/orchestrator** (which decomposes it into device models: routing RFC 8349, BGP, PIM, NAT RFC 8512, QoS, ACL RFC 8519). Fig. 1 refines RFC 8309 Fig. 3 into service orchestration -> network orchestration -> domain orchestration -> config manager. Fig. 2 places it in ACTN (CNC–MDSC–PNC): L3SM on CNC->MDSC, L3NM MDSC->MDSC(child)/PNC.
- It is **not** an augment of L3SM: "prune and extend" from RFC 8299 but restructured. Uses ietf-vpn-common for all identities/groupings. Not a device model; "how the L3NM is used to derive device-specific actions is implementation specific."
- Structure: `l3vpn-ntw` -> `vpn-profiles` (opaque provider profile ids) + `vpn-services` -> `vpn-service*[vpn-id]` -> `vpn-instance-profiles` (reusable RD/RT/AF/max-routes/multicast per role) + `underlay-transport` + `external-connectivity` + `vpn-nodes` -> `vpn-node*[vpn-node-id]` (≈ a VRF on a PE identified by `ne-id`; may be abstract) -> `vpn-network-accesses` -> `vpn-network-access*[id]` (the PE side of a CE-PE attachment: L2 `connection`, L3 `ip-connection`, `routing-protocols` static/bgp/ospf/isis/rip/vrrp, `oam` bfd, `security` encryption, `service` bw/mtu/qos/CsC/ntp/multicast).
- Inheritance: service-level `vpn-instance-profile` -> activated at node (`active-vpn-instance-profiles`, may override, adds per-AF router-id) -> referenced by access (`vpn-instance-profile` leafref); values lower win. Dual-stack address-family values take precedence over ipv4/ipv6 duplicates.
- Multi-domain motivation (§6.2): RD/RT must be coordinated across controllers, hence explicit RD/RT in the model. Multicast (§6.3) assumes MP-BGP MVPN with P2MP MPLS LSPs.
- Arcana placement: the console (service orchestrator) would *emit* L3NM; the missing piece is the network orchestration that turns one `vpn-service` into per-host cblink operations on interfaces, FIBs, BIRD, ipfw/dummynet, IPsec/wg, dhcpd/rtadvd. A `vpn-node` maps to **one FIB (or one vnet jail) on one Arcana host**; a `vpn-network-access` to **one interface (vlan/epair/physical) placed in that FIB with an address**.

## 5. Features / if-feature and what Arcana would advertise

Module feature `msdp`: **do not advertise**.

vpn-common features referenced by L3NM (`{...}?` in the trees): `external-connectivity` (external-connectivity container, profile list) — advertise; `rtg-bgp` (local-as leaves) — advertise; `multicast` (all multicast containers) — advertise only on hosts with net/pimd installed, and only for IPv4; `igmp`, `pim` — same; `mld` — no; `ipv4`, `ipv6` (ip-connection, static prefixes) — advertise; `bearer-reference` — advertise; `lag-interface` — advertise; `bfd` (oam/bfd, static bfd-enable) — advertise; `rtg-ospf-sham-link` — no; `encryption` — advertise (layer3 only; reject layer2 at apply time); `inbound-bw`, `outbound-bw` — advertise; `qos` — advertise; `carriers-carrier` — no. Not feature-gated but unusable: isis container (no feature guard in L3NM; `rtg-isis` only guards the identity in vpn-common, so not advertising `rtg-isis` makes `isis-routing` illegal — good), `rtg-vrrp` (advertise only if carp mapping accepted), `rtg-rip` — advertise.

## 7. Open questions / decisions

1. **VRF realisation: FIB vs vnet jail.** FIB (`setfib`, `ifconfig fib`, `net.fibs` at boot, per-FIB BIRD instance — what Arcana's SD-WAN already does) is light but leaky (shared sockets/addresses unless `net.add_addr_allfibs=0`, loopback visible everywhere, daemons like dhcrelay/pimd/ntpd need `setfib`); a vnet jail per `vpn-node` gives real isolation (own lo, own sysctls, own BIRD/pimd/dhcpd/ipfw), epair/vlan moved in with `ifconfig vnet` (invidia/vnet.c), at the cost of more processes and jail lifecycle coupling. Mixed: FIB for simple VPNs, jail when multicast/DHCP/NAT are needed.
2. **Standards-faithful RD/RT (BGP VPN SAFI) vs overlay-only.** Without kernel MPLS, RFC 4364 cannot be implemented; options: (a) carry RD/RT as bookkeeping and implement membership with per-VPN tunnels + per-FIB BGP sessions (today's model, O(VPN×PE²) sessions); (b) one BGP session per PE pair carrying all VPN routes as `vpn4`/`vpn6` in BIRD 3 with the `l3vpn` protocol and *fake* labels, and use a VXLAN VNI per VPN as the real encapsulation with the next hop resolved to the PE's VTEP — essentially EVPN type-5-like behaviour hand-built; needs confirming that bird3 on FreeBSD builds/works with `mpls` domains without kernel support (BIRD's MPLS kernel sync is Linux-only, but label allocation inside BIRD may still work). (c) Replace BGP VPN with a controller-computed route distribution (the console pushes static routes per FIB) — simplest, no RT semantics, poor convergence. This decision determines whether `vpn-targets`, `rd-choice`, `vpn-service-topology` are real or decorative.
3. **Inheritance resolution location.** Service-level profile -> node overrides -> access reference. Resolve in the console and push flat per-host data (agent stays simple, but the agent cannot validate against the model's precedence rules), or push the L3NM subtree for that host and let the agent resolve (agent needs the `vpn-instance-profile` merge logic, including dual-stack precedence over ipv4/ipv6).
4. **Default `priority-tagged` encapsulation** is unrealisable on FreeBSD. Either deviate (Arcana default `untagged-int`) and document the deviation, or require callers to set `type` explicitly (make it mandatory in the Arcana family).
5. **Unrealisable subtrees: omit, reject, or accept-and-ignore?** isis, sham-links, max-lsa, TCP-AO, ipv6-site-of-origin, warning-threshold, holddown, S-BFD, layer2 encryption, CsC, MSDP, MLD, bidir/anycast RP. YANG's answer is a `deviation` module (not-supported). cblink needs an equivalent (per-family `deviations:` list) so clients can discover what will be rejected before sending.
6. **VRRP -> CARP.** Accept `vrrp-routing` and implement with carp(4) (interoperates only among Arcana/BSD hosts), or add an Arcana identity `carp` and refuse `vrrp-routing`. Affects whether CE-side redundancy with third-party CEs is claimed.
7. **Key chains.** The BGP/OSPF/RIP/BFD authentication and the customer encryption profile all reference RFC 8177 key chains. Arcana has no key-chain object; needed: a `key-chain` family (name, keys with id, lifetimes, algorithm) mapped to BIRD `password` lists, setkey tcp-md5 SAs and swanctl secrets. Also decide secret handling (keys are config in YANG; Arcana may want write-only attributes).
8. **DHCP server choice per FIB.** `provider-dhcp` server/relay per access requires a DHCP daemon that can bind per interface and per FIB. Confirm what `luxuria/sddhcp.c` drives (kea vs isc-dhcp vs dnsmasq) and whether one instance per FIB or per jail is needed; DHCPv6 and relay add isc-dhcp44-relay/kea-dhcp6.
9. **Multicast scope.** net/pimd covers static RP/BSR, ASM/SSM, IPv4 only; everything else is unmappable. Decide whether to advertise `multicast` at all in the first iteration.
10. **QoS fidelity.** dummynet can honour bandwidth, per-class rate limits (as % of bandwidth -> computed bps) and ordering of classification; it cannot honour ~10 of the packet-field matches. Decide whether the Arcana family exposes the full RFC 8519-derived match set (with runtime rejection) or a trimmed one (with a documented deviation).
11. **Status semantics.** `admin-testing` and `admin-pre-deployment` need defined agent behaviour (e.g. testing = configured but excluded from SD-WAN steering and alarms; pre-deployment = validated but not applied, which requires a dry-run/validate op per family).
12. **Operations shape.** RFC uses RESTCONF POST on `/vpn-services`, `/vpn-service=X`, `/vpn-node=Y`. For cblink: either one `l3vpn-ntw` family with `set-service`, `set-node`, `set-access`, `del-*`, `get`/`dump` ops keyed by (vpn-id, vpn-node-id, id), or a generic datastore-style edit op carrying a path + subtree (closer to NETCONF edit-config, harder to generate C for).
