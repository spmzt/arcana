# RFC 7018 — Auto-Discovery VPN Problem Statement and Requirements

IETF IPsecME, Informational, September 2013. Source: `scratchpad/rfc/rfc7018.txt` (read in
full).

## 1. Purpose

RFC 7018 states the problem of letting a large number of IPsec gateways and endpoints
communicate directly (point-to-point SAs) with minimal configuration, where manual
configuration of every tunnel is infeasible, peer addresses change, and peers sit behind
NAT. It defines terms (ADVPN, endpoint, gateway, hub, spoke, star / full-mesh / dynamic
full-mesh topologies, allied and federated environments), motivates the work with three
use cases (endpoint-to-endpoint, gateway-to-gateway, endpoint-to-gateway), explains why
exhaustive configuration, static star topologies and proprietary solutions are
inadequate, and lists sixteen numbered requirements that any Auto-Discovery VPN solution
must satisfy. It defines no protocol (the IPsecME solutions that followed remained
drafts). For Arcana it is the requirements list for the SD-WAN tunnel layer: how the
console as a directory can let edges discover and build WireGuard/IPsec tunnels without
hand configuration, and what hub-and-spoke versus dynamic mesh must provide.

## 2. Terminology, use cases and requirements, completely

### 2.1 Terminology (Section 1.1)

- **ADVPN**: a VPN solution enabling a large number of systems to communicate directly,
  with minimal configuration and operator intervention, using IPsec.
- **Endpoint**: implements IPsec for its own traffic, not a gateway. **Gateway**:
  implements IPsec to protect traffic flowing through it.
- **Point-to-Point**: communication without active participation (encryption or
  decryption) by other parties.
- **Hub**: the central point of a star or dynamic full-mesh topology (or one of several in
  a full mesh); forwards traffic between encrypted links; no cleartext devices attached.
  **Spoke**: the endpoint or gateway that forwards traffic from cleartext devices into
  the ADVPN.
- **ADVPN Peer**: any member (gateway, endpoint, hub, spoke).
- **Star Topology**: direct connectivity only hub to spoke; spoke-to-spoke via the hub.
  **Full-Mesh**: direct connectivity between every spoke. **Dynamic Full-Mesh**: hub-and-
  spoke base with spoke-to-spoke connections created and removed on demand.
- **Allied and Federated Environments**: multiple organizations with close associations
  needing to connect.
- **SA**: per RFC 4301.

Context (Section 1): RFC 4301 §4.4 databases (SPD, SAD, PAD) need extensive per-tunnel
configuration; IKE implementations must know every peer's identity, credentials and the
addresses behind them; a simplified mechanism for dynamically establishing point-to-point
tunnels is needed. Both tunnel mode (gateways) and host-to-host transport mode are in
scope. Participants may be one administrative domain or several with an established trust
relationship; no trust relationship is out of scope.

### 2.2 Use cases (Section 2)

1. **Endpoint-to-Endpoint VPN**: two endpoints want a direct point-to-point SA, e.g. a
   direct secure voice/video call between nearby users instead of tromboning through
   remote gateways (latency, remote bandwidth, cost); must work when both are behind NAT
   and keep working as endpoints roam (out from behind a NAT, between NATs). In a star
   topology, spokes communicating directly need authentication that prevents
   impersonation by another spoke.
2. **Gateway-to-Gateway VPN**: enterprise star topologies trombone rich media through
   the hub; full mesh uses capacity best but needs considerable configuration; hence
   dynamically created and torn down spoke-to-spoke tunnels with minimal per-gateway
   configuration; must work across administrative domains with a trust relationship
   (collaborating organizations keeping independent control); gateways with dynamic IP
   addresses; routing implications: selectors may suffice, or additional tunneling (GRE)
   and routing protocols (OSPF) run over the IPsec tunnels and their configuration impact
   must be considered; L3VPNs over IPsec tunnels; gateways need authentication preventing
   impersonation.
3. **Endpoint-to-Gateway VPN**: a mobile endpoint should use the most efficient gateway
   as it roams, discovering and connecting to the current best gateway seamlessly without
   bringing down the connection.

### 2.3 Inadequacy of existing solutions (Section 3)

- **Exhaustive configuration**: every gateway/endpoint preconfigured with everything
  needed to pick the optimal peer and establish an SA; does not scale to hundreds of
  thousands of nodes, multiple domains and rapid change; limited by the smallest node.
- **Star topology**: hubs and spokes; spokes never connect to spokes; complicated by
  dynamic spoke addresses (dynamic DNS), desire for no configuration on the hub as
  spokes come and go; high load on hubs (a packet encrypted/decrypted several times),
  bottleneck bandwidth to the hub, wasteful when spokes are adjacent (two users in one
  building on fast Wi-Fi). "The challenge is to build large-scale IPsec-protected
  networks that can dynamically change with minimal administrative overhead."
- **Proprietary approaches**: no interoperability, lock-in, unusable across
  organizations.

### 2.4 Requirements (Section 4.1), verbatim in substance

1. For any topology (star, full mesh, dynamic full mesh), adding, removing or changing a
   gateway or endpoint minimizes configuration changes: adding or removing a spoke MUST
   NOT require configuration changes to hubs other than the one it connects to, SHOULD
   NOT require changes to that hub, and MUST NOT require changes in other spokes.
   Proposals are compared by how many nodes must be reconfigured and how much, plus the
   amount of static configuration. (Use cases 1, 2; Section 3.1.)
2. ADVPN peers MUST allow IPsec tunnels with other members without any configuration
   changes even when peer addresses change every time a device comes up: SPD entries or
   other configuration based on peer IP addresses must be updated automatically, avoided
   or otherwise handled.
3. Additional tunneling protocols (GRE) or routing protocols (OSPF) run over the IPsec
   tunnels: gateways MUST allow their operation over spoke-to-spoke tunnels with minimal
   or no configuration impact; the solution SHOULD NOT increase the configuration those
   protocols need.
4. In full-mesh and dynamic full-mesh topologies spokes MUST allow direct communication
   with other spokes; in star topology direct spoke-to-spoke communication MUST be
   disallowed. (Use cases 1, 2; Section 3.2.)
5. ADVPN peers MUST NOT have a way to get the long-term authentication credentials of any
   other peer; compromise of an endpoint MUST NOT affect the security of communications
   between other peers; compromise of a gateway SHOULD NOT affect communications between
   peers not associated with that gateway. (Spokes are compromised fairly often.)
6. Gateways SHOULD allow seamless handoff of sessions for roaming endpoints, even across
   policy boundaries, with minimal data traffic impact; roaming may change the
   endpoint-to-gateway relationship; external firewalls and NAT boxes are not part of the
   solution. (Use case 1.)
7. Gateways SHOULD allow easy handoff of a session to another gateway for latency,
   bandwidth, load balancing, availability or other policy factors; applies to hubs and
   spokes, including moving gateways (vehicle networks). (Use case 3.)
8. Gateways and endpoints MUST be able to participate even behind NAT boxes; some may not
   be fully reachable; a hub behind NAT is especially hard; two spokes behind separate
   NATs SHOULD be supported with workarounds (port forwarding, detecting uncooperative
   NATs and using a hub). Graceful fallback to hub-and-spoke as needed. (Use cases 1, 2.)
9. Changes such as establishing a new IPsec SA SHOULD be reportable and manageable; a MIB
   or other management technique is out of scope. (Manageability, especially use case 2.)
10. Endpoints and gateways from different organizations SHOULD be able to connect (allied
    and federated environments).
11. The administrator SHOULD be able to configure a star, full-mesh or partial full-mesh
    topology, based on which tunnels are allowed to be set up.
12. The solution SHOULD scale for multicast traffic (rich media, use case 2).
13. The solution SHOULD allow easy monitoring, logging and reporting of the dynamic
    changes for troubleshooting.
14. L3VPNs over IPsec tunnels (Provider-Edge-based VPNs): an ADVPN MUST support L3VPNs as
    applications protected by the IPsec tunnels.
15. The solution SHOULD allow enforcement of per-peer QoS in both star and full-mesh
    topologies.
16. The solution SHOULD take care of not letting the hub be a single point of failure.

### 2.5 Security considerations (Section 5)

The solution may dynamically update RFC 4301 databases (SPD, PAD), which RFC 4301 assumed
static and human-configured; allowing the protocol to alter security policy must be
thought out carefully. Example attack: traffic stealing, where an SPD entry says traffic
to 192.0.2.10 (www.example.com) is protected through peer Gw-Mallory, letting Mallory
impersonate or proxy the site; updates to the database require a clear trust model. Hubs
as single points of failure can take down the whole system, a security issue.

## 3. How Arcana maps onto each element, and what it would need

### 3.1 Arcana today against the use cases and terms

| RFC 7018 element | Arcana today |
|---|---|
| Gateway | an SD-WAN edge (a FreeBSD host or vnet jail running `arcana-agent`) with UNIs behind it; tunnels of kind gre, gif, geneve, wg or uswe, optionally under strongSwan IKEv2 (transport mode for gre/gif/wg carriers) or manually keyed ESP (uswe, Mplify 119-3) |
| Endpoint | SASE-3 remote users: WireGuard peers on an edge, one key per identity, address from a reserved prefix |
| Hub / spoke / topology | the SD-WAN document's virtual topologies per SWVC; tunnels provisioned pairwise by the console between every pair of edges a service connects (full mesh) or to a control-plane host (119-5 route reflector: control-plane hub, data still meshed); local Internet breakout or remote breakout via a tunnel (a data hub for Internet traffic) |
| Directory / controller | the console: it keeps every edge's public keys (wg, strongSwan ECDSA pubkey, uswe X25519 pairs), allocates inner addresses, writes `peer:ID` jobs with the far end's key and address, and reads back each end's key once both exist ("the far end's key is read once both ends have one") |
| Dynamic addresses | WireGuard learns a roaming peer's endpoint from its handshake; strongSwan can accept `%any`; uswe SAs are bound to addresses by setkey and the console learns a UCS End Point's DHCP/SLAAC address "once a plan" |
| NAT | WireGuard over UDP with keepalives; IKEv2 NAT-T available in strongSwan; uswe uses UDP-encapsulated ESP (R41 to R50) |
| Routing over tunnels | BIRD per service: iBGP between edges over the tunnels, OSPF/BGP/static at UNIs, BFD on tunnels; GRE/GIF carriers for routed IPsec |
| L3VPN | a FIB per service (subscriber domain), service domain FIB for tunnel addresses, breakout domain FIB (119-2); RFC 4364 VPN routes not implemented (no MPLS) |
| QoS | dummynet pipes and weighted queues per limiter/flow; DSCP on probes and tunnels |
| Monitoring | probes, BFD, `sdwan-tunnel` events, faults with Mplify 119 types, audit trail, `/api/sdwan/apply` history |
| Credentials | every private key is generated on its host and never leaves it (wg, strongSwan ECDSA, uswe X25519, the host's TLS key); the console holds only public halves, plus the CA key |

### 3.3 Proposal: auto-discovery VPN for Arcana with the console as directory

1. **Peer directory as data, not jobs.** Model a per-service *peer directory* (YANG):
   for each edge its identity (certificate name / ACP address), current public endpoints
   (address:port per UCS, learned from the agent's `address-add` events and from the
   reflexive address the console or hub observes), public keys per tunnel kind (wg,
   uswe X25519 pair, strongSwan ECDSA), allowed inner prefixes (the service's UNI
   prefixes, signed off by the console), topology role (hub, spoke) and policy (which
   spokes may connect directly). The console publishes the directory to the edges
   (YANG-Push subscription over cblink, or GRASP flood over the ACP once it exists)
   instead of writing one `peer:ID` job per pair. Agents then build or update tunnels from
   the directory themselves: an address change in the directory re-installs the uswe SAs
   (requirement 2), a new spoke appears only in the hub's and its own directory view
   (requirement 1), and the SPD/PAD-like decisions (which prefixes behind which peer) come
   from a single trusted source (the Section 5 trust model).
2. **Topologies.** Star: edges get only hub entries; hubs get all; ipfw/routes forbid
   spoke-to-spoke (requirement 4). Full mesh: everyone gets everyone (today). **Dynamic
   full mesh**: start star; when telemetry shows spoke-to-spoke traffic above a threshold
   for a time (flow records from ng_netflow, rfc9232.md, or ipfw counters per far prefix
   on the hub), the console (or a steering ASA over the ACP, rfc9222.md) marks the pair
   "shortcut allowed" in the directory with a lifetime; both agents build a direct tunnel
   (wg or IKEv2) and BIRD/the route reflector or a more specific route prefers it; idle
   timeout tears it down. The hub never changes configuration for it (requirement 1).
3. **Identity and keys.** Use the domain certificate (rfc8994.md) for IKEv2 peer
   authentication (`auth = pubkey` with the CA, PAD = "any certificate from our CA whose
   SAN names an edge in this service", id = certificate SAN), so no per-peer credential
   distribution is needed and no peer can learn another's long-term key (requirement 5).
   WireGuard keys stay per edge and are published through the directory, signed by the
   console (the directory itself travels inside mTLS/ACP). For uswe (manual SAs), the
   X25519 halves travel the same way; rekey negotiation peer-to-peer over the ACP removes
   the console from the hot path.
4. **Routing-based VPN, not selector-based.** Keep `if_ipsec`/gre/wg interfaces with
   routes from BIRD (iBGP to the route reflector of 119-5) so SPD entries are `::/0`-style
   per interface and never depend on peer addresses or prefixes (requirements 2 and 3);
   the route reflector is the control-plane hub and makes per-tunnel BGP sessions
   unnecessary for on-demand tunnels.
5. **NAT (requirement 8).** All tunnel kinds UDP-encapsulated (wg native; IKEv2 NAT-T
   and UDP-encapsulated ESP; uswe already UDP). The hub/console records each agent's
   observed source address and port (the PROXY protocol header or the peer address of the
   cblink connection, or an explicit STUN-like `reflexive` reply from the hub agent) and
   publishes it as the spoke's reflexive endpoint; spokes try direct (both reflexive
   endpoints, simultaneous open with keepalives); if no handshake within T, fall back to
   hub relay and mark the pair "relay" (uncooperative NAT). A hub must have a public
   address; the console host is one.
6. **Remote endpoints (use cases 1 and 3, requirements 6 and 7).** SASE-3 identities get
   a directory entry listing several edges (gateways) ordered by policy; the client
   configuration carries all of them (wg supports one peer per interface; use one
   interface per gateway or a client helper that switches endpoints); the console moves
   an identity between edges by changing allowed-ips and the client follows (handoff with
   re-handshake, not seamless, which satisfies SHOULD partially). Endpoint-to-endpoint
   between two remote users (use case 1) can be a wg shortcut via the same reflexive-
   address mechanism with keys published by the console.
7. **Hub resilience (requirement 16).** Two hubs per service (control-plane host and
   backup), two consoles (rfc7426.md) or at least a read-only standby that keeps serving
   the directory; data plane already survives.
8. **Reporting (requirements 9, 13).** Events `sdwan-tunnel` (exists), `sdwan-peer`
   (directory change applied), `sdwan-shortcut` (dynamic tunnel up/down with reason and
   lifetime), faults for rekey and NAT fallback; the audit trail records directory
   changes; the Paths tab shows static vs dynamic tunnels.
9. **QoS (requirement 15).** Optional per-tunnel dummynet pipe (bandwidth to each peer)
   generated from the directory beside the per-flow limiters.
10. **Standards hooks.** Use RFC 9061's I2NSF IPsec YANG (ike and ikeless cases) as the
    agent-side model for SAD/SPD/PAD programming of both IKEv2 and manual `uswe` SAs; the
    ikeless case is precisely "a controller distributes SA material to NSFs", i.e. the
    console as directory. Mention in the docs that IETF never standardized an ADVPN
    protocol (the IPsecME drafts expired), so Arcana's directory protocol is its own,
    carried by cblink/YANG; interoperability with other vendors stays with Mplify 119
    (USWE: manually keyed SAs with keys exchanged through the manager, which is the
    same directory idea).

## 4. Cannot be mapped / not applicable

- **Federated multi-vendor ADVPN (requirement 10)**: no standard protocol exists; Arcana
  can only interoperate at the IPsec/BGP level (Mplify 119) and would need cross-signed
  CAs or a shared directory format with another operator's console. Not planned beyond
  119.
- **Multicast scaling (requirement 12)**: no multicast routing in Arcana (BIRD has no
  PIM; FreeBSD's pim(4)/mrouted exist but are not integrated). Not applicable now.
- **Hub behind an uncooperative NAT (requirement 8, hard case)**: the RFC itself calls it
  especially difficult; Arcana requires a reachable hub.
- **Seamless mid-session handoff across gateways (requirement 6/7, SHOULD)**: WireGuard
  and IPsec sessions re-handshake; true seamlessness needs MOBIKE (RFC 4555, which
  strongSwan supports for IKEv2 clients) or a mobility layer; only partial.
- **Transport-mode host-to-host ADVPN between arbitrary servers**: Arcana's endpoints
  are edges and remote users; host-to-host transport mode SAs between fleet hosts would
  be the ACP's job (rfc8994.md), not the SD-WAN directory's.

## 5. Checklist Arcana could be measured against

1. Adding or removing an edge changes configuration only on that edge and its hub(s);
   other spokes learn of it, if at all, through the directory without re-provisioning.
2. A peer whose public address changes (DHCP, NAT rebinding, reboot) regains all its
   tunnels without any configuration change on any node.
3. Tunnel SPD/policies do not embed peer addresses or far prefixes; routing (BIRD/route
   reflector) decides what goes into which tunnel.
4. Routing and encapsulation protocols over tunnels (gre/gif, BGP, OSPF, BFD) need no
   extra configuration per dynamic tunnel.
5. The administrator chooses star, full mesh or partial/dynamic mesh per service; star
   forbids spoke-to-spoke in the data plane.
6. No node can obtain another node's long-term private key; the directory holds only
   public material; the CA key is protected (offline or HSM, sub-CA for enrolment).
7. Compromise of an edge is contained to its tunnels: revocation removes it from the
   directory and from every peer within a bounded time.
8. Peers behind NAT participate; two spokes behind separate NATs either shortcut via
   reflexive endpoints or fall back to the hub automatically and visibly.
9. Remote endpoints (users) can be moved between gateways by policy and reconnect
   without administrator action.
10. Every SA/tunnel establishment, rekey, teardown and fallback is an event with cause,
    peers and time; dynamic tunnels are distinguishable from provisioned ones.
11. Per-service L3VPN semantics (FIB per service, prefixes behind each peer) are kept
    over dynamic tunnels.
12. Per-peer QoS can be enforced on hub and spokes.
13. Loss of the console or of a hub does not stop data-plane forwarding or existing
    tunnels; a second directory/hub can take over within a defined time.
14. Directory updates are authenticated, authorized and audited so that no peer can
    inject a prefix-to-peer binding (traffic stealing).
15. Monitoring shows the current topology (static and dynamic tunnels) per service.

## 6. Open decisions and trade-offs

- **Directory push model**: the console computing everything (today: deterministic,
  explainable, one writer) vs agents building tunnels from a directory (requirement 1
  satisfied, fewer jobs, but two places where tunnel state is decided). A middle path:
  the console still plans, but the *peer directory* is the artifact it publishes, and
  agents reconcile against it.
- **Dynamic mesh trigger**: console-driven from flow telemetry (simple, central) vs
  edge-driven via GRASP negotiation over the ACP (works when the console is away, but
  needs the ACP and an ASA). Thresholds, lifetimes and hysteresis must avoid tunnel
  flapping.
- **Which tunnel kind for shortcuts**: WireGuard is the easiest (roaming, UDP, keys in
  the directory) but is outside Mplify 119's IPsec profile; IKEv2 with certificates is
  standard and uses the ACP identity. Possibly wg for Arcana-only services, uswe/IKEv2 for
  119-conformant ones.
- **Reflexive address discovery**: reuse the cblink connection's observed source (free,
  but the console may be behind a proxy) vs a tiny STUN-like exchange with the hub agent
  (accurate per UCS).
- **Hub placement**: the console host (always reachable, but a management box carrying
  user traffic) vs a designated edge per service (closer to the data, but another device
  to keep highly available).
- **How much of requirement 5 to push onto the console**: an offline CA with an online
  sub-CA for enrolment and a directory signed by a separate key would contain a console
  compromise; cost is operational complexity for a single-user system.
- **RFC 9061 adoption**: modelling SAs and policies with the I2NSF YANG gives a standard
  SBI for both IKE and manual cases, but FreeBSD's setkey/strongSwan mapping of every
  leaf (ESN, UDP encapsulation ports, reqid for if_ipsec) needs an augmentation; decide
  whether the standard module or an Arcana module is primary.
