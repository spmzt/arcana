# RFC 8528 — YANG Schema Mount

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8528.txt (March 2019, Standards Track, 1571 lines, read in full).

## Purpose
Mount a complete data model (any set of YANG modules, unmodified) at a container or list
node of a parent schema, so that e.g. `ietf-interfaces` appears both at the device top
level and inside each `logical-network-element` (RFC 8530) or `network-instance`
(RFC 8529). `uses` and `augment` cannot do this scalably. Mount points are labelled in the
parent module with the `yangmnt:mount-point` extension; what is mounted is told by state
data `/schema-mounts` (implementation time or run time), and each mount point instance
carries its own `ietf-yang-library` describing the mounted schema.

## Definitions (section 2)
mount point (container/list with `mount-point`); schema; top-level schema; mounted schema;
parent schema; schema mount. Design-time mounting is out of scope.

## Mount point (3.1)
- `yangmnt:mount-point <label>` only as a substatement of `container` or `list`; at most one
  per node; label is a YANG identifier; several mount points in a module MAY share a label
  (then one `/schema-mounts/mount-point` entry applies to all); a mount point in a grouping
  binds its label to the module *using* the grouping; MUST NOT be used in YANG 1.0 modules
  (mounted rpc/notifications need 1.1 action/notification-in-data semantics); mounted
  modules may be any YANG version. May be conditional with `if-feature`/`when` on the
  container/list. The extension does not define a data node.

## Data model (3.2) — tree verbatim
```
module: ietf-yang-schema-mount
  +--ro schema-mounts
     +--ro namespace* [prefix]
     |  +--ro prefix    yang:yang-identifier
     |  +--ro uri?      inet:uri
     +--ro mount-point* [module label]
        +--ro module                 yang:yang-identifier
        +--ro label                  yang:yang-identifier
        +--ro config?                boolean          (default true)
        +--ro (schema-ref)                            (mandatory)
           +--:(inline)
           |  +--ro inline!
           +--:(shared-schema)
              +--ro shared-schema!
                 +--ro parent-reference*   yang:xpath1.0
```

## Semantics (3.3, 3.4)
- A mount point without a `mount-point` entry has a void mounted schema: instances MUST NOT
  contain data beyond the parent schema's.
- `config false` on the mount point node or `config = false` in the entry makes the whole
  mounted schema read-only.
- Mounted schema is determined at run time: **every instance of the mount point in
  `<operational>` MUST contain a copy of YANG library data** describing the mounted schema
  exactly as a top-level schema would (non-NMDA servers MAY use 7895 `modules-state` under
  the mount; NMDA servers MUST use 8525).
- `inline`: instances MAY have different schemas (same content-id does not imply equality).
- `shared-schema`: all instances MUST have the same schema and the same YANG library
  content-id; may list `parent-reference` XPath expressions.
- Mounted schemas can themselves contain mount points (recursive), by implementing
  `ietf-yang-library` + `ietf-yang-schema-mount` inside the mounted schema.

## Mount jail and parent references (section 4)
- All paths in the mounted schema (leafref, instance-identifier, XPath in must/when, augment
  targets) are interpreted with the mount point as the root ("mount jail"); nothing outside
  is visible — except through `parent-reference` (shared-schema only): XPath 1.0 expressions
  evaluated with the mount point's node in the parent tree as context node, accessible tree =
  parent tree *without* mounted data, position=size=1, no variables, XPath core + 7950
  functions, prefixes from `/schema-mounts/namespace`. Each MUST evaluate to a node-set; the
  union of node-sets plus their ancestors is added to the accessible tree for XPath
  evaluation inside the mounted tree — **only for XPath**, not accessible via the protocol.
  Example (NI): `/if:interfaces/if:interface[ni:bind-network-instance-name = current()/../ni:name]`
  so that a mounted `ietf-routing` `outgoing-interface` leafref to `/if:interfaces/if:interface/if:name`
  validates against the interfaces bound to that NI.

## RPCs and notifications (section 5)
- An rpc defined in a mounted module is invoked **as an action of the mount point**:
  `POST /restconf/data/ietf-network-instance:network-instances/network-instance=rtrA/root/ietf-isis:clear-adjacency`.
- A top-level notification of a mounted module is emitted as if tied to the mount point.
- Mount points therefore SHOULD NOT have keyless-list ancestors (actions/notifications would
  not work).

## NMDA (6), NACM (7), implementation notes (8)
- NACM applies to mounted nodes with full paths:
  `/lne:logical-network-elements/lne:logical-network-element/lne:root/if:interfaces`.
- Shared management (one session sees parent + mounted) vs split management (a session per
  mount instance seeing only the mounted tree).

## Appendix A
Physical device YANG library includes ietf-datastores, iana-if-type, ietf-interfaces
(features arbitrary-names, pre-provisioning), ietf-ip, ietf-logical-network-element
(feature bind-lne-name), ietf-yang-library, ietf-yang-schema-mount. LNE mount point `root`
with `inline` (each LNE may differ); each LNE instance's `root` holds its own
`modules-state`/`yang-library` plus the interfaces bound to it (as system-controlled
interfaces inside the LNE). NI mount point `root` with `shared-schema` and the
parent-reference above.

## Relevance to Arcana (the central structural idea)
1. **vnet jails are LNEs.** A VNET jail has its own network stack: own interfaces, own
   addresses, own routing tables, own pf, own sockets. RFC 8530's
   `logical-network-element[name]/root` with `inline` schema mount is the exact model: the
   host's `ietf-interfaces` lists epair/if_bridge members with `lne:bind-lne-name = <jail>`
   (the host-side binding = `ifconfig epairXb vnet <jail>`), and under
   `.../root` the agent serves the jail's own `ietf-interfaces`, `ietf-ip`, `ietf-routing`,
   `ietf-network-instance` by running the same ioctl/sysctl/netlink code inside the jail
   (`jail_attach(2)` in a helper, or `jexec`, or `ifconfig -j`/`netstat -j`/`route -j`
   which FreeBSD 14+ support). Non-VNET jails are *not* LNEs (they share the host's stack
   with IP restrictions) and are better modelled as Arcana-specific `jail` list entries
   whose `ip4.addr`/`ip6.addr` are plain leaf-lists.
2. **FIBs are network instances.** `net.fibs` > 1 gives separate routing tables selected by
   `setfib(1)`/`SO_SETFIB`, with interfaces bound via `ifconfig <if> fib N`. RFC 8529's
   `network-instance[name]/root` with `shared-schema` mount of `ietf-routing` and a
   `parent-reference` on `/if:interfaces/if:interface[ni:bind-network-instance-name = …]`
   is exactly that: `bind-network-instance-name` on an interface ↔ its `fib` setting;
   mounted `ietf-routing` ↔ `netstat -rn -F N` / `route -n get -fib N` / rtsock with
   `SO_SETFIB` / netlink `RTA_TABLE`. FIB 0 is the default NI.
3. **Hosts in the fleet.** Nothing in the IETF models represents "a fleet of devices" under
   one RESTCONF root. The console can define `arcana-fleet:hosts/host[name]/root` with
   `yangmnt:mount-point root` and `inline` (each host may run a different agent revision,
   hence different YANG library) — then `/restconf/data/arcana-fleet:hosts/host=web1/root/ietf-interfaces:interfaces/interface=em0`
   is a conformant path, NACM rules can be written per host, YANG-Push subscriptions can
   target a host subtree, and the console's own `/yang-library` lists the fleet module while
   each host's library appears under its `root`. The console then proxies: strip the
   `hosts/host=X/root` prefix, forward the remainder to host X's agent as a cblink request,
   and the per-host `yang-library` is cached from the agent's `hello`.
4. For SIDs: a mounted schema's deltas are relative to the mount point? No — RFC 9254 says
   deltas are relative to the *parent schema node's SID in the same encoding*; under a mount
   point the mounted top-level nodes' parent is the mount point container, so the delta is
   `SID(ietf-interfaces:interfaces) − SID(lne:root)`, possibly a large positive or negative
   number (different modules, different ranges) — legal but ~3–5 bytes; or use tag 47 with
   absolute SIDs at mount roots as 9254 §4.5.1 suggests for anydata. Either works; the
   generator must know that children of a mount point are "foreign-rooted".
5. XPath evaluator must support the mount jail (root = mount point) and parent-reference
   node-set injection — modest extra work once an evaluator exists.
