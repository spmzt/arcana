# RFC 8519 — YANG Data Model for Network Access Control Lists (ACLs)

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8519.txt (read in full, 3363 lines).
Status: Standards Track, NETMOD WG, March 2019. Base model that RFC 9899 augments.

## 1. Purpose and where it sits

- Defines a device-level ("network element") data model for ACLs: a user-ordered list of
  Access Control Entries (ACEs), each a group of match criteria plus a group of actions.
  First matching ACE wins; no further ACEs are processed.
- It is a **device model** (per RFC 8309 taxonomy): it configures the forwarding behaviour of one
  device. It is not a service or network model. RFC 9899 Appendix A.3/A.8 later argue that the same
  ACL content should be reusable at network level and bound to several devices, which is the
  controller/console side of Arcana; RFC 8519 itself only knows about the device.
- The matching only takes effect when an ACL is attached to an *attachment point*. RFC 8519 defines
  only the **interface** attachment point (ingress and egress lists of ACLs per interface). Any other
  attachment (VRF, vty, QoS policy, routing protocol, "whole device") requires an augmentation.
- Three YANG 1.1 modules: `ietf-access-control-list` (the ACL "superclass": acls, acl, aces, ace,
  matches, actions, statistics, attachment-points), `ietf-packet-fields` (groupings of header match
  fields: eth, ip, ipv4, ipv6, tcp, udp, icmp, port-range-or-operator), and `ietf-ethertypes`
  (a placeholder typedef `ethertype`, a union of uint16 and an enumeration of IEEE Ethertypes).
- Vendor capability is advertised with `feature` statements in two sets: what headers the device can
  match (match-on-eth/ipv4/ipv6/tcp/udp/icmp) and which header combinations an ACL may mix
  (eth, ipv4, ipv6, mixed-eth-ipv4, mixed-eth-ipv6, mixed-eth-ipv4-ipv6); plus stats and attachment
  features.
- Transport assumed: NETCONF/RESTCONF with NACM. For Arcana this becomes a cblink family served by
  arcana-agent, with the console as the "network level" holder of ACL definitions.
- Appendix A shows the intended extension style: `augment` of `.../matches` with new `choice`s and of
  `.../actions` with new actions (count, policer, default-action), and compares with Linux nftables.

`ietf-packet-fields` and `ietf-ethertypes` define no data nodes (groupings and typedefs only), so the
RFC has no tree diagram for them. Their content, summarised exactly:

- typedef `operator`: enumeration `lte | gte | eq | neq`. "An operator is needed only if the lower-port
  is specified and the upper-port is not specified."
- grouping `port-range-or-operator`: `choice port-range-or-operator { case range { lower-port
  (mandatory, must '. <= ../upper-port'), upper-port (mandatory) } case operator { operator (default
  eq), port (mandatory) } }`.
- grouping `acl-ip-header-fields` (shared by ipv4 and ipv6): `dscp inet:dscp`, `ecn uint8 {0..3}`,
  `length uint16` (IPv4 Total Length / IPv6 Payload Length), `ttl uint8` (IPv6 Hop Limit),
  `protocol uint8` (IPv6: upper-layer protocol after extension headers).
- grouping `acl-ipv4-header-fields`: `ihl uint8 {5..60}`, `flags bits {reserved(0), fragment(1),
  more(2)}`, `offset uint16 {20..65535}`, `identification uint16`, `choice destination-network { case
  destination-ipv4-network { leaf destination-ipv4-network inet:ipv4-prefix } }`, `choice
  source-network { case source-ipv4-network { leaf source-ipv4-network inet:ipv4-prefix } }`.
- grouping `acl-ipv6-header-fields`: same two choices with `inet:ipv6-prefix`, plus `flow-label
  inet:ipv6-flow-label`.
- grouping `acl-eth-header-fields`: `destination-mac-address yang:mac-address`,
  `destination-mac-address-mask yang:mac-address`, `source-mac-address`, `source-mac-address-mask`,
  `ethertype eth:ethertype`.
- grouping `acl-tcp-header-fields`: `sequence-number uint32`, `acknowledgement-number uint32`,
  `data-offset uint8 {5..15}`, `reserved uint8`, `flags bits {cwr(1), ece(2), urg(3), ack(4), psh(5),
  rst(6), syn(7), fin(8)}` (note: bit positions 1..8, position 0 unused), `window-size uint16 units
  bytes`, `urgent-pointer uint16`, `options binary {length 1..40}`.
- grouping `acl-udp-header-fields`: `length uint16`.
- grouping `acl-icmp-header-fields`: `type uint8`, `code uint8`, `rest-of-header binary`.
- typedef `eth:ethertype`: `union { uint16; enumeration {ipv4=2048, arp=2054, wlan=2114, trill=8947,
  srp=8938, decnet=24579, rarp=32821, appletalk=32923, aarp=33011, vlan=33024, ipx=33079, qnx=33284,
  ipv6=34525, efc=34824, esp=34825, cobranet=34841, mpls-unicast=34887, mpls-multicast=34888,
  pppoe-discovery=34915, pppoe-session=34916, intel-ans=34925, jumbo-frames=34928, homeplug=34939,
  eap=34958, profinet=34962, hyperscsi=34970, aoe=34978, ethercat=34980, provider-bridging=34984,
  ethernet-powerlink=34987, goose=35000, gse=35001, sv=35002, lldp=35020, sercos=35021, wsmp=35036,
  homeplug-av-mme=35041, mrp=35043, macsec=35045, pbb=35047, cfm=35074, fcoe=35078, fcoe-ip=35092,
  roce=35093, tte=35101, hsr=35119} }`.

Identities in `ietf-access-control-list`:
- `forwarding-action` base; `accept`, `drop` (no ICMP error), `reject` (drop + ICMP error to source).
- `log-action` base; `log-syslog`, `log-none`.
- `acl-base` base; `ipv4-acl-type` {if-feature ipv4}, `ipv6-acl-type` {ipv6}, `eth-acl-type` {eth},
  `mixed-eth-ipv4-acl-type` (bases eth-acl-type AND ipv4-acl-type, if-feature mixed-eth-ipv4),
  `mixed-eth-ipv6-acl-type` (bases eth + ipv6), `mixed-eth-ipv4-ipv6-acl-type` (bases eth + ipv4 +
  ipv6). Multiple-base identities are what make `derived-from-or-self(/acls/acl/type,
  'acl:ipv4-acl-type')` true for a mixed ACL, which is how the `when` on the ipv4 match container is
  satisfied for mixed ACLs.

## 3. Node-by-node meaning and candidate FreeBSD realisation

Conventions below: "ipfw" means ipfw(8) rule syntax on FreeBSD 14/15; "pf" means pf.conf(5).
ipfw match options are ANDed; `not` negates the following option; `{ a or b }` is an or-block.
Arcana already drives ipfw (invidia/ipfw.c: numbered `add` lines, sets 0/1 swap for atomic apply,
tables created/flushed/swapped in sdwan.c) so ipfw is the primary target; pf is noted where it is the
only thing that can express a field.

### 3.1 Containers and lists

| Node | Meaning | FreeBSD realisation |
|---|---|---|
| `/acls` | Top container of all ACLs on the device. | The agent's view of the ipfw ruleset in the "ACL" band plus the attachment rules. Could also be a dedicated ipfw *set* range. |
| `/acls/acl[name]` (`name` string 1..64, "space and special characters are not allowed") | One ACL, an ordered list of ACEs. | A contiguous block of ipfw rule numbers reserved for the ACL (e.g. base = 10000 + 1000*i), ended by a `return` rule, and entered by `call <base>` from attachment rules. ipfw rules have no names: the agent keeps the `name -> base` table itself and writes the name into the rule comment (`ipfw add N ... // acl:<name> ace:<ace>`; comments are stored in the kernel and come back in `ipfw list`). Alternative: one ipfw *set* per ACL (`set N`), but there are only 32 sets and sets 0/1 are already used for Arcana's atomic apply. pf alternative: one anchor per ACL (`anchor "acl/<name>"`), which has native names and ordering. |
| `/acls/acl/type` (acl-type identityref) | Declares the header families the ACL may match; enforced by `when` on the match containers. | Validation only: with `eth-acl-type`/mixed types the rules must be loaded with `layer2` and `net.link.ether.ipfw=1` so that they run in the layer-2 pass; `ipv4-acl-type` -> rules use `ip4`/`all` protocols; `ipv6-acl-type` -> `ip6`. Mixed types are natural in ipfw (one rule may carry `MAC` and IP matches). |
| `/acls/acl/aces/ace[name]` (ordered-by user) | One rule: `matches` + `actions`; named. | One ipfw rule per ACE (or several when an ACE needs or-blocks or `count` helpers), rule numbers increasing in ACE order inside the ACL band. Reordering the user-ordered list = renumbering the band (atomic by building in set 1 and `set swap`, which Arcana already does). |
| `.../matches` | Criteria; empty container = match everything; one container per `l2`/`l3`/`l4` choice at most. | The match part of the rule. Empty = `ip from any to any`. |
| `.../actions` | `forwarding` (mandatory) and `logging` (default log-none). | The rule's action word (`allow`/`deny`/`reject`/`unreach`/`reset`) and the `log` keyword. |
| `.../statistics {acl-aggregate-stats}` (config false) | matched-packets / matched-octets across all attachment points. | `ipfw -a list` / `ipfw show` rule counters (pcnt/bcnt); `ipfw -c -a`, or `IP_FW_XGET` directly; zeroed with `ipfw zero N` (Arcana has verb zero). |
| `/acls/attachment-points/interface[interface-id] {interface-attachment}` | Interfaces that carry ACLs. `interface-id` is `if:interface-ref` (leafref to /if:interfaces/interface/name). | FreeBSD interface name (em0, vlan10, wg0, ipsec0, bridge0, epair0b...). `if:interface-ref` means the ACL family must reference the Arcana interface family's keys. |
| `.../ingress/acl-sets/acl-set[name]` (ordered-by user, leafref to /acls/acl/name) | Ordered list of ACLs applied to packets entering the interface. | One attachment rule per acl-set, in order: `ipfw add <att> call <base(acl)> ip from any to any in recv <if>` (ipfw `call`/`return`: subroutine semantics; call stack depth 16). If `call` is not wanted, `skipto <base>` with the ACL block falling through to a `skipto <next-att>`; `call`/`return` is cleaner because the same ACL block can be entered from several interfaces. For layer-2 ACL types the attachment rule needs `layer2` and the frames arrive via the ether_ipfw hook. pf: `anchor "acl/<name>" in on <if>`. |
| `.../egress/acl-sets/acl-set[name]` | Same, for packets leaving the interface. | `... out xmit <if>`. Note ipfw sees a forwarded packet twice (in on recv iface, out on xmit iface) so ingress/egress are exact. For locally generated packets only `out xmit` fires. |
| `.../acl-set/ace-statistics[name] {interface-stats}` (config false) | Per interface, per ACE counters. | ipfw counters are per rule, not per (rule, interface). To honour `interface-stats` the agent must instantiate the ACL block once per attachment (block per (acl, interface, direction)) so each copy has its own counters; otherwise only `acl-aggregate-stats` can be advertised. pf: per-rule counters inside an anchor loaded per interface, same trade-off. |

### 3.2 Match fields -> ipfw / pf

Legend: ok = exact; ~ = approximation; pf = only pf can; no = neither (goes to section 4).

| YANG leaf (container) | ipfw syntax | Notes / pf |
|---|---|---|
| eth/destination-mac-address (+ -mask) | `MAC <dst-mac>&<mask> any` or `MAC dst-mac/bits any` | ipfw `MAC dst src` with `&mask` (hex mask) or `/bits`; needs `layer2` rule and `net.link.ether.ipfw=1`. yang:mac-address mask (e.g. ff:ff:ff:00:00:00) maps 1:1 to `&ff:ff:ff:00:00:00`. pf (FreeBSD >= 13.1 `ether` rules): `ether pass in on em0 from 00:11:22:33:44:55 to any`; masks supported in FreeBSD 14 ether rules (`mac/mask`). |
| eth/source-mac-address (+ -mask) | `MAC any <src-mac>&<mask>` | as above. |
| eth/ethertype | `mac-type <n|name>` | ipfw accepts numeric (`0x86dd`) and names (ip, ip6, arp, vlan, ...). The `union(uint16, enum)` collapses to a number. pf: `ether proto 0x0800`. |
| ipv4/dscp, ipv6/dscp | `dscp <n|name>` | ipfw takes a list of numbers or names (cs0..cs7, af11..af43, ef, be, va). ok. pf: `dscp`/`tos`. |
| ipv4/ecn, ipv6/ecn | ~ `iptos congestion` only for CE (value 3 / bit 0x01 as ipfw sees TOS) | ipfw's `iptos` names (lowdelay, throughput, reliability, mincost, congestion) are the old TOS bits; ECT(0)/ECT(1)/CE cannot be matched as a 2-bit value. **pf**: `tos <byte>` matches the whole DS+ECN byte, so `tos 0x03` with the DSCP folded in is exact. |
| ipv4/length (Total Length) | `iplen <n>` (ranges/lists allowed) | ok. |
| ipv6/length (Payload Length) | `iplen <n+40>` | ipfw computes iplen for IPv6 as payload length + 40, so translate. ~ (exact after offset). |
| ipv4/ttl, ipv6/ttl (hop limit) | `ipttl <n>` | ok (ipfw applies ipttl to ip6_hlim). pf: no ttl match. |
| ipv4/protocol, ipv6/protocol | protocol word (`tcp`, `udp`, `icmp`, `icmp6`, `<number>`) or `proto <n>` | ok. For IPv6 ipfw walks extension headers to the upper-layer protocol, matching the RFC's definition. |
| ipv4/ihl | no | ipfw has only `ipoptions` (presence of specific options). `ihl > 5` ⇔ options present, so `ipoptions`-based approximation is possible only for "has options". |
| ipv4/flags (bits reserved/fragment/more) | `frag rf`, `frag df`, `frag mf` | FreeBSD 13+ `frag spec` with `df`, `mf`, `rf`, `offset`; several keywords in one `frag` spec require all listed bits. ok. pf: `fragment` only (any non-first fragment), no DF/RF bit match. |
| ipv4/offset (exact 13-bit offset value) | ~ `frag offset` (non-zero only) | exact value not matchable. no. |
| ipv4/identification | no | neither ipfw nor pf. |
| ipv4/destination-ipv4-network, source-ipv4-network | `to <prefix>`, `from <prefix>` | ok (`any`, `me`, lists, tables also exist). |
| ipv6/destination-ipv6-network, source-ipv6-network | `to <prefix6>`, `from <prefix6>` | ok (`me6`). |
| ipv6/flow-label | `flow-id <label>` | ok (list of labels allowed). |
| tcp/sequence-number | `tcpseq <n>` | ok. |
| tcp/acknowledgement-number | `tcpack <n>` | ok. |
| tcp/data-offset | no | ipfw has `tcpdatalen` (payload length), not header length. |
| tcp/reserved | no | |
| tcp/flags (bits cwr, ece, urg, ack, psh, rst, syn, fin) | `tcpflags [!]fin,[!]syn,[!]rst,[!]psh,[!]ack,[!]urg` | ipfw: listed flags must be set, `!flag` must be clear, others ignored. **cwr and ece are not in ipfw's vocabulary**; pf `flags` accepts `E` (ECE) and `W` (CWR): `flags S/SAEW`. The RFC 8519 `bits` type has no mask so "must be set" is the only sensible reading; RFC 9899 fixes this with flags-bitmask. |
| tcp/window-size | `tcpwin <n>` (ranges) | ok. |
| tcp/urgent-pointer | no | |
| tcp/options (binary 1..40) | ~ `tcpoptions mss,window,sack,ts,cc` | presence of option kinds only; no byte pattern. |
| tcp|udp/source-port, destination-port: case range (lower-port..upper-port) | `src-port lo-hi`, `dst-port lo-hi` (or in the address part: `from any lo-hi`) | ok. ipfw allows up to 30 ports/ranges in one list. |
| ... case operator eq port | `dst-port <p>` | ok. |
| ... neq port | `not dst-port <p>` | ok. |
| ... lte port | `dst-port 0-<p>` | ok. |
| ... gte port | `dst-port <p>-65535` | ok. |
| udp/length | ~ `iplen <len + IP header>` | UDP length is not matchable directly; for IPv4 without options iplen = udplen + 20; for IPv6 iplen = udplen + 40. ~ only when IHL is known (no options). |
| icmp/type | `icmptypes <t>` (IPv4) / `icmp6types <t>` (IPv6) | ok (lists allowed). Which keyword depends on the l3 choice (ipv4 vs ipv6) or on `protocol` 1 vs 58. |
| icmp/code | no in ipfw | **pf**: `icmp-type <t> code <c>` / `icmp6-type ... code`. |
| icmp/rest-of-header (binary) | no | |
| matches/egress-interface (if:interface-ref) | `xmit <if>` | ok; RFC says do not set when attached as egress ACL, or set equal to the attached interface. |
| matches/ingress-interface | `recv <if>` | ok (`via` matches either). |

### 3.3 Actions -> ipfw / pf

| YANG | ipfw | Notes |
|---|---|---|
| forwarding = accept | `allow` (synonyms accept, pass, permit) | Terminal. |
| forwarding = drop | `deny` (synonym drop) | Silent. |
| forwarding = reject | `reject` (= `unreach host`), `unreach6 <code>` for IPv6; for TCP `reset`/`reset6` is the usual "reject" | The RFC says "send an ICMP error message"; choose `unreach host`/`unreach6 addr` by default, and consider `reset` for TCP as a profile option. pf: `block return` / `block return-icmp(code)`. |
| logging = log-syslog | `log` [`logamount N`] with `net.inet.ip.fw.verbose=1`; FreeBSD 13+: `log logdst syslog` (also `ipfw0` and `rtsock`, which Arcana's gula/record.c already consumes) | ok. Rate limit via `net.inet.ip.fw.verbose_limit`/`logamount`. |
| logging = log-none (default) | nothing | ok. |

### 3.4 Statistics

`matched-packets`/`matched-octets` (yang:counter64) <- ipfw per-rule 64-bit counters (pcnt, bcnt) from
`ipfw -a list` or the raw `IP_FW_XGET` sockopt; `ipfw show` also prints the last-match timestamp
(not modelled). Aggregation across attachment points is automatic when one rule block is shared
through `call`; per-interface counts need per-attachment copies (see 3.1).

### 3.5 Attachment and ruleset layout (proposal)

```
# dispatch band (per interface, per direction, in acl-set order)
ipfw add 100 call 20000 ip from any to any in  recv em0   // att:em0/ingress/acl-set:edge-in
ipfw add 101 call 21000 ip from any to any in  recv em0   // att:em0/ingress/acl-set:guest
ipfw add 200 call 20000 ip from any to any out xmit em1   // att:em1/egress/acl-set:edge-in
# ACL "edge-in" block
ipfw add 20000 deny  log tcp  from 192.0.2.0/24 to 198.51.100.0/24 // acl:edge-in ace:rule1
ipfw add 20001 allow     udp  from any to 2001:db8::/32 53        // acl:edge-in ace:rule2
ipfw add 20999 return                                              // end of acl:edge-in
```
A packet matching no ACE returns to the dispatch band and continues to the next attachment rule and
finally to the rest of Arcana's ruleset; RFC 8519 does not define an implicit deny, so this is
conformant, but most vendors' ACLs end with an implicit deny (see Open decisions).

## 4. Cannot be mapped (with reasons)

| Node | Reason |
|---|---|
| ipv4/ecn, ipv6/ecn (as a 2-bit value) | ipfw has no ECN match; only pf `tos` (whole byte). |
| ipv4/ihl | No header-length match in ipfw or pf. |
| ipv4/offset (exact value 20..65535) | ipfw `frag offset` is only "offset != 0". |
| ipv4/identification | No match in ipfw/pf. |
| tcp/data-offset, tcp/reserved, tcp/urgent-pointer | No such match options. |
| tcp/options as a byte pattern | ipfw `tcpoptions` knows only option kinds mss, window, sack, ts, cc. |
| tcp/flags bits cwr, ece | ipfw `tcpflags` has six flags; pf has E/W, neither has AE (RFC 9899 adds it). |
| udp/length | Only indirectly via iplen; exact only when the IP header length is known. |
| icmp/code | ipfw cannot; pf can. |
| icmp/rest-of-header | No payload match (RFC 9899 `pattern` would need divert/ng_bpf, see rfc9899.md). |
| eth matches on a non-Ethernet interface | ipfw layer-2 hook exists only for Ethernet (ether_ipfw); tun/gif/wg/ipsec interfaces have no L2 header. |
| interface-stats without rule duplication | ipfw counters are per rule. |
| `name` as the identity of a rule | ipfw rules are identified by number; the name lives in the comment and in the agent's map. |
| ACL `type` enforcement at load time | ipfw does not know ACL types; the agent validates (`when derived-from-or-self`). |
| `reject` exact ICMP semantics | ipfw `reject`/`unreach` sends host-unreachable; the RFC does not say which code. |

## 6. YANG constructs used (each with the RFC's own example) and what the cblink YAML/CBOR schema needs

cblink today (cblink/docs/SPEC-FORMAT.md) has: u8..u64/s8..s64/bool/flag/text/bytes/float/nest
types, `enum`/`flags`/`const` definitions, `multi-attr` arrays, `required`, checks (min/max,
min-len/max-len/exact-len, min-count/max-count), do/dump/event/stream operations, mcast groups.
It has **no** identityref, union, leafref, choice, when/must, feature, default, ordered-by, composite
key, decimal64, date-and-time, pattern or config-false marking. Per construct:

| YANG construct | Example in RFC 8519 | What the strict YAML/CBOR schema must express |
|---|---|---|
| identityref (incl. multi-base identities) | `leaf forwarding { type identityref { base forwarding-action; } }`; `identity mixed-eth-ipv4-acl-type { base acl:eth-acl-type; base acl:ipv4-acl-type; }` | An open, namespaced enumeration: values are qualified names (`acl:accept`, `acl-enh:...`) that other modules extend. Encode on the wire as text `module:name` (or an SID/uint from a registry) and in the spec as `type: identityref` with `base:`; the schema must allow derivation (a value is valid if derived from the base) and multiple bases. |
| union | `typedef ethertype { type union { type uint16; type enumeration {...} } }` | A `union` kind: an attribute whose value may be one of several member types, tried in order; CBOR can carry uint or text in the same key, so the policy needs a per-attribute list of allowed kinds and per-member checks. |
| leafref | `leaf name { type leafref { path "/acls/acl/name"; } }`; `if:interface-ref` | A `ref:` check naming the target list key (another family's or the same family's): wire type is the target's type; validation needs state (handler) but the spec should declare the reference so generators and the console can resolve it. |
| choice/case (incl. implicit case from a container) | `choice l2 { container eth {...} }`, `choice l3 { container ipv4; container ipv6 }`, `choice port-range-or-operator { case range {...} case operator {...} }`, `choice destination-network { case destination-ipv4-network {...} }` (single case kept for future set references) | "At most one of these attributes" groups (mutual exclusion), optionally mandatory. Needs a `choice:` grouping of attribute names in the set with `mandatory` flag. |
| when | `container eth { when "derived-from-or-self(/acls/acl/type, 'acl:eth-acl-type')"; }` | Conditional presence depending on another node's value (possibly up the tree). A restricted expression language (equality / derived-from on a sibling or ancestor path) or handler code; the spec should at least record it for documentation. |
| must | `leaf lower-port { must '. <= ../upper-port' { error-message "..."; } }` | Cross-attribute constraints with an error message: needs a small constraint language (compare two attributes) or handler validation that returns extended-ack naming the attribute. |
| feature / if-feature (boolean expressions) | `feature mixed-eth-ipv4 { if-feature "match-on-eth and match-on-ipv4"; }`; `container eth { if-feature "match-on-eth"; }` | Capability flags advertised by the family (ctrl getfamily already lists ops/groups; add a features list), and per-attribute `if-feature:` so the console can grey out what a host does not do. |
| augment | Appendix A: `augment "/acl:acls/acl:acl/acl:aces/acl:ace/acl:matches" { choice protocol-payload-choice {...} }` | Extension of a set from another spec file: attribute ids must be allocated in a disjoint range per augmenting module (cblink: "numbers are forever"), or augments are flattened into the family at generation time with reserved id ranges per module. |
| default | `leaf logging { default "log-none"; }`, `leaf operator { default "eq"; }` | `default:` on an attribute: generator fills `has_x=false` with the default; the console shows it; NMDA "with-defaults" semantics for dumps. |
| mandatory | `leaf forwarding { mandatory true; }`, `lower-port/upper-port/port mandatory true` | Already `required` in cblink, but `mandatory` inside a choice case means "required if that case is chosen" — needs choice-aware required. |
| ordered-by user | `list ace { ordered-by user; }`, `list acl-set { ordered-by user; }` | Lists whose order is data: CBOR arrays preserve order (multi-attr of nest). The schema should mark `ordered: user` so dumps keep order and edits can insert before/after (netlink-style `insert`/`before` attributes or whole-list replace). |
| composite keys | none in RFC 8519 (single `key "name"` everywhere) — RFC 9061 has `key "start end"`. | `key:` list on a nest used as a list element; one or more attributes. |
| enumeration (with explicit values) | `typedef operator { enum lte; gte; eq; neq }`; ethertype enum with `value 2048` etc. | cblink `enum` definitions cover it (explicit values supported). |
| bits | `leaf flags { type bits { bit reserved {position 0;} bit fragment {position 1;} bit more {position 2;} } }`; TCP flags positions 1..8 | cblink `flags` definitions (bit numbers) cover it; note position 0 may be unused. |
| decimal64 | none here (RFC 9899 `rate-limit decimal64 fraction-digits 2`) | see rfc9899.md |
| yang:date-and-time | none here | see rfc9061.md/rfc9348.md (none there either) |
| inet:* / yang:* types | `inet:ipv4-prefix`, `inet:ipv6-prefix`, `inet:port-number`, `inet:dscp` (0..63), `inet:ipv6-flow-label` (0..1048575), `yang:mac-address`, `yang:counter64` | Typedef layer above cblink's base types: text with pattern (prefix, mac) or uint with range (port, dscp, flow-label); counters as u64 marked read-only/monotonic. A `typedef:` section or a shared types file is needed. |
| string length / pattern | `type string { length "1..64"; }` (name) | `min-len/max-len` exist; pattern does not (the RFC's "no spaces or special characters" is prose). |
| numeric range | `uint8 { range "0..3"; }` (ecn), `range "5..60"` (ihl), `uint16 { range "20..65535"; }` (offset) | `min`/`max` exist. |
| binary length | `type binary { length "1..40"; }` (tcp options) | `min-len/max-len` on bytes exist. |
| units | `leaf window-size { units "bytes"; }` | `units:` documentation field. |
| config false | `container statistics { config false; }`, `list ace-statistics { config false; }` | Attributes that appear only in replies/dumps/events, never accepted in requests: a `config: false` flag or simply absence from `request.attributes` (cblink already separates request/reply attribute lists, which models it). |
| grouping / uses | `uses pf:acl-eth-header-fields;` | Reusable attribute fragments across sets/families (cblink has none; an `include`/grouping mechanism avoids copy-paste of port-range-or-operator four times). |
| typedef | `typedef acl-type { type identityref { base acl-base; } }` | Named types. |
| rpc / action / notification | none in RFC 8519 | n/a |
| reference / description | everywhere | `doc:` exists. |

## 7. Open decisions and trade-offs

1. **ipfw vs pf as the ACL engine.** ipfw: Arcana already uses it (tables, nat, nat64, dummynet,
   divert to Suricata, logging to rtsock), has `call`/`return`, rule counters, fib/jail/uid matches,
   dummynet for 9899 rate-limit; cannot match ECN value, ICMP code, CWR/ECE, payload. pf: anchors
   give named, ordered ACLs for free, `tos`, `icmp code`, `flags E/W`, `ether` rules, tables with
   counters; but no dummynet-style shaping (ALTQ only), and running both filters means every packet
   is matched twice and two state models. Recommendation: ipfw primary, advertise the feature set
   accordingly; optionally a pf backend later with the same family.
2. **Name-to-number mapping.** ipfw has no names: choose bands (deterministic from an index kept by
   the agent) and persist the map; ipfw comments carry names for recovery after agent restart
   (`ipfw list` returns comments). Limits: rule numbers 1..65534, so the band size bounds ACEs per ACL
   and the number of ACLs.
3. **call/return vs skipto vs sets.** `call` lets one ACL block serve several attachments and keeps
   aggregate counters; but packets inside a called block that `skipto`/`tee` elsewhere lose the stack,
   and the call stack is 16 deep (nested ACL calls are not a thing here, so fine). Sets (32 max) are
   already used for atomic swaps.
4. **Implicit deny.** RFC 8519 defines none; nftables/Cisco semantics differ. Arcana can add an
   augment `default-action` per ACL (Appendix A.1 pattern) realised as the last rule of the block.
5. **Layer-2 pass.** Enabling net.link.ether.ipfw makes every Ethernet frame traverse the ruleset a
   second time; IP-only ACEs must be guarded (`not layer2`) or the ruleset must branch on `layer2`
   at the top. Only needed when an eth-type ACL exists.
6. **Per-interface statistics.** Either duplicate blocks per attachment (exact `interface-stats`,
   more rules) or advertise only `acl-aggregate-stats`.
7. **Mixing with the existing Arcana ipfw model.** The current family exposes raw ipfw words
   (`verb add`, `names`), SD-WAN rules, and sets 0/1 swaps. The ACL family should own a reserved
   band and be applied through the same set-swap transaction so a console "apply" is atomic across
   raw rules and ACLs.
8. **Statefulness.** The ACL model is stateless; FreeBSD operators expect `keep-state`/`check-state`.
   Offer it as an Arcana augment of `actions` (e.g. `stateful: true` -> `keep-state :acl-name`), not
   as default behaviour.
9. **reject semantics.** Choose `unreach host`/`unreach6 addr` vs `reset` for TCP; make it a
   per-ACL or per-ACE augment.
10. **Interface references.** `if:interface-ref` implies the interface family is the source of truth
    for names; for ACLs on interfaces that do not yet exist (cloned on demand), ipfw accepts unknown
    names in `recv`/`xmit`, so attachment can be configured ahead of creation (ipfw matches by name
    at run time) — decide whether the agent rejects or accepts dangling leafrefs.
