# RFC 8341 — Network Configuration Access Control Model (NACM)

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8341.txt (March 2018, STD 91, obsoletes 6536, 3251 lines, read in full).

## Purpose
Standard access control for NETCONF/RESTCONF: restricts which protocol operations
(rpc/action), which data nodes (CRUD) and which notifications a user (via groups) may
access. Three control points: protocol operation, datastore (data node), notification.
Also defines YANG extension statements `nacm:default-deny-write` and `nacm:default-deny-all`
that module authors put on sensitive nodes so they are protected before any rules exist.
Updated for YANG 1.1 actions and data-node notifications (read access to the ancestor
path + execute/read on the node) and for RESTCONF.

## Design objectives (section 2)
Simple; one rule set for operations, data and notifications; CRUDX permissions; groups
(local or from the transport, e.g. RADIUS; switchable); enforcement can be disabled
without deleting rules; machine-readable tagging of sensitive content.

## Model (section 3)
- Access operations: none, read, create, update, delete, execute ("write" = create +
  update + delete).
- Message processing: for each rpc — operation access check; for actions, read on every
  ancestor data node instance + execute on the action node; datastore accesses checked per
  node. For notifications — top-level: read on the notification type; data-node
  notification: read on ancestors + the notification node; denied → dropped silently for
  that subscription.
- Datastores: all conventional datastores and `<operational>` are NACM-controlled; new
  datastores define their CRUDX mapping; a read-only datastore needs only read.
- RESTCONF mapping (Table 1): OPTIONS → none; HEAD/GET → read (ancestors in the URI count
  as read); POST on datastore/data → create (URI nodes incl. the target are "none", the edit
  starts at the body's child); POST on operation → execute; PUT on data → create/update;
  PUT on datastore → update (copy-config); PATCH → update; DELETE → delete. For
  PUT/PATCH/DELETE the URI ancestors are "none".
- get/get-config: unauthorized nodes and their descendants are silently omitted; filters
  apply to the authorized subset.
- edit-config: effective operation "none" nodes (containers present only for naming) need no
  rights; create/delete/update rights are checked for nodes actually created/deleted/
  modified; unaltered or missing nodes in merge need nothing; **implicit side effects (when
  becoming false, other choice branches deleted) need no rights**; restricted contents MUST
  NOT leak in rpc-error.
- copy-config running→startup needs only exec; otherwise source read filtering + target
  create/update/delete checks. delete-config and kill-session denied by default regardless
  of exec-default. commit: check only the nodes actually different.
- Users (from the transport), groups (local `groups/group[name]/user-name*` + external
  groups if `enable-external-groups`), emergency recovery session bypasses everything.
- Global switches: `enable-nacm` (default true), `read-default` (permit),
  `write-default` (deny), `exec-default` (permit), `enable-external-groups` (true).
- Rule types: module rule (module-name only), protocol-operation rule (`rpc-name`),
  notification rule (`notification-name`), data-node rule (`path`, a
  `node-instance-identifier`: instance-identifier where key predicates are optional,
  `/` = whole datastore, matches the node and all descendants; XPath context has variable
  `$USER`).

## Enforcement procedures (3.4) — the exact algorithm
Initial operation: no NACM config → no write access except the recovery session; server-
initiated accesses (boot load) are not controlled. Rules in effect at message start apply
for the whole message. `access-denied` errors MUST NOT leak restricted data.

**RPC (3.4.4):** 1 enable-nacm false → permit; 2 recovery session → permit;
3 `<close-session>` → permit; 4 collect groups (+external); 5 none → step 10;
6 rule-lists in order, skip those whose `group` doesn't match; 7 rules in order, match =
(`module-name` is `*` or the rpc's module) ∧ (no rule-type, or protocol-operation with
`rpc-name` `*` or equal) ∧ (`access-operations` has exec or `*`); 8 first match →
action permit/deny; 10 rpc has `nacm:default-deny-all` → deny; 11 kill-session /
delete-config → deny; 12 exec-default. Error: `access-denied`, error-path = the operation.

**Data node (3.4.5):** 1–2 as above; 3–5 groups and rule-lists; 6 match = module-name ∧
(no rule-type, or data-node with `path` matching the node or an ancestor of it) ∧ the bit
for read/create/delete/update/exec (or `*`); 7 first match → permit/deny (read deny =
omit); 9 read: `default-deny-all` on the node → omit subtree; 10 write:
`default-deny-write` or `default-deny-all` → deny subtree; 11 read-default; 12
write-default; 13 exec-default (actions).

**Notification (3.4.6):** 1–2; 3 replayComplete/notificationComplete → permit; 4–6
groups/rule-lists; 7 match = module-name ∧ (no rule-type or notification with
`notification-name` `*`/equal) ∧ read bit; 8 permit/drop; 10 `default-deny-all` on the
notification → drop; 11 read-default. Data-node notifications also need read on the
ancestors (3.4.5). Authorization to receive the type implies its contents.

## Data model (3.5) verbatim
```
module: ietf-netconf-acm
  +--rw nacm                                  (nacm:default-deny-all)
     +--rw enable-nacm?              boolean                    default true
     +--rw read-default?             action-type                default permit
     +--rw write-default?            action-type                default deny
     +--rw exec-default?             action-type                default permit
     +--rw enable-external-groups?   boolean                    default true
     +--ro denied-operations         yang:zero-based-counter32  (mandatory)
     +--ro denied-data-writes        yang:zero-based-counter32  (mandatory)
     +--ro denied-notifications      yang:zero-based-counter32  (mandatory)
     +--rw groups
     |  +--rw group* [name]
     |     +--rw name         group-name-type      (length 1..max, pattern '[^\*].*')
     |     +--rw user-name*   user-name-type       (length 1..max)
     +--rw rule-list* [name]                       (ordered-by user)
        +--rw name     string                      (length 1..max)
        +--rw group*   union                       ('*' | group-name-type)
        +--rw rule* [name]                         (ordered-by user)
           +--rw name                 string
           +--rw module-name?         union        ('*' | string) default '*'
           +--rw (rule-type)?
           |  +--:(protocol-operation)
           |  |  +--rw rpc-name?            union  ('*' | string)
           |  +--:(notification)
           |  |  +--rw notification-name?   union  ('*' | string)
           |  +--:(data-node)
           |     +--rw path                 node-instance-identifier (mandatory)
           +--rw access-operations?   union        ('*' | bits create read update delete exec) default '*'
           +--rw action               action-type  permit|deny (mandatory)
           +--rw comment?             string
```
Module `ietf-netconf-acm@2018-02-14` (YANG 1.0!, prefix nacm). Extensions
`default-deny-write` (data definition statements) and `default-deny-all` (data
definitions, rpc, notification). Typedefs: user-name-type, matchall-string-type
(`pattern '\*'`), access-operations-type (bits create/read/update/delete/exec),
group-name-type, action-type, node-instance-identifier (yang:xpath1.0; predicates for
keys optional; `$USER` variable; no functions).

## Security considerations highlights
OPTIONS/PATCH MUST NOT vary responses on resource existence (probing); "fishing" via
edit errors; leafref aliasing of sensitive data; when/choice side effects can implicitly
change nodes the user may not write; lock operations as DoS; module designers ought to tag
sensitive nodes.

## Examples (appendix A)
Groups admin/limited/guest; module rules (`deny-ncm` on ietf-netconf-monitoring for guest,
`permit-all` for admin); protocol-operation rules (deny kill-session/delete-config);
data-node rules (`/n:nacm` deny for guest, `/acme:interfaces/acme:interface[acme:name='dummy']`
read update for limited+guest); notification rule (deny `sys-config-change`).

## Relevance to Arcana
1. Arcana today has a binary model: authenticated mTLS peer / 0600 socket = everything
   (`auth: true` on every op). NACM gives it a standard, YANG-configurable ACL for free:
   `arcana-agent` maps the client certificate's subject (or the Unix peer uid name) to a
   NACM username (RFC 7589 §7 algorithm as RESTCONF requires), groups `admin`,
   `read-only`, `console`; the console's single WebAuthn user maps likewise. Rules allow
   e.g. a monitoring client read-only on `<operational>`, or deny `exec` on
   `arcana-jails:jail/kill`.
2. The "implicit side effects need no rights" rule and the "edit begins at the target" rule
   must be reflected in how the generated server glue walks an edit: it needs the per-node
   effective operation (none/create/update/delete) computed by the edit-merge algorithm
   anyway (NETCONF edit-config semantics), so NACM is a hook at that point plus a read
   filter on output trees and notifications.
3. Data-node rule paths are `node-instance-identifier`s — the agent must parse the
   instance-identifier *string* form (not SID form) with optional predicates, and match
   "node or descendant". For CBOR the rule itself is config data (a string leaf) so it stays
   a string on the wire.
4. `ietf-netconf-acm` is YANG 1.0 — the parser must accept both versions (the differences
   are small: quoting, if-feature expressions, no action/anydata/notification-in-data).
5. SID range: IANA assigned 1250/50 for ietf-netconf-acm (RFC 9595 Table 4).
