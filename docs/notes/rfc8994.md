# RFC 8994 — An Autonomic Control Plane (ACP)

IETF ANIMA, Standards Track, May 2021. Source: `scratchpad/rfc/rfc8994.txt` (read in full,
Sections 1 to 13 and Appendix A). Dependencies read as far as 8994 relies on them:
RFC 8990 GRASP (`rfc8990.txt`, Sections 1 to 4 and the CDDL) and RFC 8995 BRSKI
(`rfc8995.txt`: Sections 1, 1.5, 2, 4, 5 intro and 5.1, 5.9, 9, Appendix A/B).

## 1. Purpose

RFC 8994 specifies a self-forming, self-managing, self-protecting IPv6 overlay, the
Autonomic Control Plane, that gives every node of a domain hop-by-hop authenticated and
encrypted connectivity independent of the data plane's configuration, addressing and
routing: a "virtual out-of-band network" built in-band. Nodes hold an ACP certificate
(an LDevID with an `acp-node-name` carrying the domain and the node's ULA address),
discover link-local neighbours with DULL GRASP, build IPsec (IKEv2) or DTLS secure
channels after a domain membership check, map the channels to virtual interfaces in an
ACP VRF, address loopbacks from a ULA /48 hashed from the domain name, route with a fixed
RPL profile, and run an ACP instance of GRASP for service discovery (EST servers for
certificate renewal, BRSKI registrars, anything else). It defines how non-ACP systems
(NMS, controllers) connect ("ACP connect"), how islands join across non-ACP L3 networks
(configured or tunneled remote neighbours), how registrars allocate addresses, how
operators diagnose, enable and disable it, and why the choices (GRASP, RPL, ULA, IPsec)
were made. Combined with BRSKI it forms the ANI; alone it serves classical centralized
(SDN-style, RFC 7426) management. For Arcana it is the specification of the management
network the console should have to every host even when the host's data plane is broken
by the very change the console made.

## 2. Terminology and architecture, completely

### 2.1 Terms (Section 2)

ACP; **ACP address** (IPv6 address of the node, stored in the acp-node-name); **ACP
address range/set** (addresses the node may assign, derived from the sub-scheme); **ACP
certificate** (an LDevID per RFC 5280 carrying acp-node-name; also "ANI certificate",
"AN certificate"); **ACP connect interface** (access for non-ACP nodes without a secure
channel); **ACP domain** (nodes with certificates that authenticate each other as
members); **ACP loopback interface** (in the ACP VRF, holds the ACP address); **ACP
network** (all nodes with access to the ACP, including via edge nodes); **ACP (ULA)
prefix(es)** (/48 prefixes; several with rsub; non-ULA on connect interfaces); **ACP
secure channel** (certificate-authenticated, integrity-protected, encrypted channel
between normally adjacent nodes, carrying ACP VRF traffic in-band but isolated); **ACP
secure channel protocol** (IKEv2/IPsec, DTLS); **ACP virtual interface** (interface in the
ACP VRF mapped to one or more secure channels); **acp-node-name field**; AN; **(AN) Domain
Name** (FQDN in the acp-node-name); **ANI** (ACP + BRSKI + GRASP; without further
autonomic functions it supports zero-touch bootstrap and stable connectivity for SDN,
RFC 8368); ANIMA; ASA; autonomic function; BRSKI; CA; CRL; **data plane** (everything
that is not the ACP VRF, including non-autonomous control and management); device;
**enrollment** (IDevID to LDevID + trust anchors); **EST** (RFC 7030); **GRASP** (needed
for neighbour discovery; the ACP is the "security and transport substrate" for the ACP
GRASP instance); **IDevID** (manufacturer certificate, not usable as ACP identity);
in-band; **Intent** (policy language of an AN); loopback interface; LDevID; management
(= OAM); **MASA**; MIC; **native interface** (exists without configuration: physical
interfaces); NOC; node; **Node-ID** (last 64 or 78 bits of the ACP address); OAM; OT;
**out-of-band network** and **virtual out-of-band network**; **root CA**; **RPL**
(RFC 6550); **registrar** (ACP/ANI/BRSKI: orchestrates enrollment with the ACP
certificate; non-ANI registrar mechanisms undefined; renewal/revocation may be done by
others; EST MUST be supported for renewal); **RPI** (RPL Packet Information, not used);
sUDI; **TA** (trust anchor); **UDI**; **ULA** (RFC 4193, Global ID prefix = first 48
bits); **(ACP) VRF** (a separate IPv6 forwarding and routing table with the ACP virtual
interfaces; "VRF-lite", no core-facing function); **(ACP) Zone** (nodes sharing a zone
field value).

### 2.2 Use cases and requirements (Sections 3, 4)

Use cases: (3.1) one infrastructure for all autonomic functions (single discovery,
security, instances); (3.2) secure bootstrap over an unconfigured network (no "rings
around the controller"; encrypted discovery of registrars via proxies; later stages of
configuration bootstrap too); (3.3) permanent reachability independent of the data plane
(misconfigured AAA, routing, shut interfaces; SDN controller changes that affect their
own reachability; a Virtual out-of-Band channel for management protocols; control
protocols survive transient data-plane faults; RFC 8368 details).

Requirements (informative): **ACP1** robust connectivity independent of configured
addressing, configuration and routing; **ACP2** separate address space from the data
plane; **ACP3** autonomically managed address space (ULA); **ACP4** generic: usable by all
functions and protocols of the ANI, not tied to an application or transport (hence IPv6
connectivity, not just GRASP); **ACP5** security: authenticated as from a trusted node,
very strongly recommended encrypted. Hop-by-hop because link-local addressing needs no
configuration; crossing non-ACP nodes is possible but depends on them.

### 2.3 Overview (Section 5, Figure 1)

When a node has an ACP certificate and is enabled: (1) create a VRF/virtual context;
(2) assign the ULA prefix learned from the acp-node-name to an ACP loopback interface in
the VRF; (3) build a candidate adjacency list: automatic for link-local adjacencies on
all native interfaces, one adjacency per interface, L2-switch methods where applicable;
(4) negotiate a secure tunnel per candidate with the candidate channel types; (5)
authenticate and authorize the peer by the domain membership check; (6) throttle retries
after failed authentication; (7) map each channel to an ACP virtual interface in the
VRF; (8) run a lightweight routing protocol announcing the loopback prefix; (9) done.
Nothing of this is reflected in configuration except explicit enabling; non-ACP NMS and
remote adjacencies across L3 need configuration.

```
          ACP Node 1                          ACP Node 2
       ...................               ...................
secure .                 .   secure      .                 .  secure
channel:  +-----------+  :   channel     :  +-----------+  : channel
..--------| ACP VRF   |---------------------| ACP VRF   |---------..
       : / \         / \   <--routing-->   / \         / \ :
       : \ /         \ /                   \ /         \ / :
..--------| loopback  |---------------------| loopback  |---------..
       :  | interface |  :               :  | interface |  :
       :  +-----------+  :               :  +-----------+  :
       :   Data Plane    :...............:   Data Plane    :
       :.................:    link       :.................:
```

### 2.4 Normative specification (Section 6)

**6.1 TLS**: wherever the ACP uses TLS (EST, CRLDP/OCSP over TLS, ACP GRASP, BRSKI on
ANI nodes): BCP 195 except TLS 1.2 REQUIRED and nothing older; TLS 1.3 SHOULD; MUST offer
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384 and TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384, MUST NOT
offer below 256-bit symmetric or 384-bit hash; TLS 1.3: TLS_AES_256_GCM_SHA384 MUST,
TLS_CHACHA20_POLY1305_SHA256 MAY; Supported Elliptic Curves with P-256 and P-384 MUST;
TLS 1.2 clients SHOULD send ec_point_format uncompressed.

**6.2 Domain, certificate, network**: group security; each node MUST have an LDevID (the
ACP certificate) and TA information; manual keying/shared secrets are not usable; raw
public keys cannot authenticate domain membership. Provisioning mechanism is out of scope
(Appendix A.2). *6.2.1 certificates*: RFC 5280 X.509v3; nodes MUST handle RSA and ECC;
MUST NOT accept RSA < 2048 or curves < 256-bit order; MUST support RSA 2048 and ECDSA
P-256, SHOULD P-384/P-521; MUST support RSA-SHA-256 and ECDSA signatures, SHOULD SHA-384/
512; an ACP certificate SHOULD use RSA if also used for other purposes, MAY use ECC if
only for ACP/ANI; ECC certs used for ECDH need keyUsage keyAgreement; other fields per
RFC 5280 / CA/Browser Forum; copying the IDevID serialNumber into the subject is useful
for diagnostics but leaks device type. *6.2.2 AcpNodeName*:

```
acp-node-name = local-part "@" acp-domain-name
local-part    = [ acp-address ] [ "+" rsub extensions ]
acp-address   = 32HEXDIG / "0"
rsub          = [ <subdomain> ]
extensions    = *( "+" extension )
routing-subdomain = [ rsub "." ] acp-domain-name
```

Example: address fd89:b714:f3db:0:200:0:6400:0, domain acp.example.com, rsub
area51.research gives `fd89b714f3db00000200000064000000+area51.research@acp.example.com`
and routing-subdomain `area51.research.acp.example.com`. MUST be carried as an X.509
subjectAltName otherName of type AcpNodeName (IA5String), OID id-on-AcpNodeName =
1.3.6.1.5.5.7.8.10 (ASN.1 module id-mod-anima-acpnodename-2020 = 97). Nodes MUST be able
to receive their address from the certificate (32HEXDIG), MUST authenticate peers with a
"0" address (address determined otherwise; can build secure channels) and with an
omitted address (domain member but no secure channels, e.g. NMS via ACP connect).
acp-domain-name SHOULD be an FQDN owned by the operator, lowercase-normalized for
comparison; it is only a hash seed and diagnostic name. Extensions MUST be ignored when
not understood. "++extension" when both address and rsub are omitted. *6.2.3 domain
membership check*: (1) proof of possession of the private key by the security
association protocol; (2) RFC 5280 path validation against one of the node's TAs
including lifetimes; (3) CRLDP/OCSP in the peer certificate MUST be honoured when
reachable, retried with the 6.7 backoff, and a channel MUST be closed when the peer is
later learned invalid, then retried periodically; (4) syntactically valid acp-node-name
with the same acp-domain-name; (5) for secure channels only: acp-address present
(32HEXDIG or "0"). Steps 1 to 4 authorize any connection between domain members
(e.g. ACP GRASP TLS); 1 to 5 authorize secure channels. rsub is not part of the check.
*6.2.3.1 time*: nodes with a trusted clock MUST check validity times; without one MAY
skip until time is known, SHOULD obtain time securely (NTP over the ACP), MAY use
insecure NTP over link-local from neighbours. *6.2.4 TAs*: provisioned with the
certificate by the registrar; renewal via EST MUST be supported; one or two self-signed
TA certs; path validation with zero or one intermediate CA MUST, two intermediates and
two TAs SHOULD (TA migration); the CA MUST sign acp-node-name only through trusted
registrars; private TA expected; one owner may run several ACP domains from one TA set.
*6.2.5 maintenance*: renewal of certificate and TA via EST MUST (MAY others); at least
one EST server across the ACP; remember the last EST server's locator, allow the
registrar to set it; the EST server MUST pass the membership check (rules 1 to 4) and
MUST carry id-kp-cmcRA EKU, which the client MUST check (protection against fake CA certs
on TA renewal); multiple ACP domains need separate EST certificates/addresses.
*6.2.5.1 SRV.est objective*: flooded with M_FLOOD, `["SRV.est", 4 (sync-only), 255,
objective-value]` plus O_IPv6_LOCATOR (ACP address, TCP, port); period default 60 s and
not smaller, ttl 3.5 periods (210000 ms); announce only when the CA is reachable.
*6.2.5.2 renewal*: try the remembered server, then GRASP-learned; start before 50% of
lifetime. *6.2.5.3 CRLs*: SHOULD support via HTTP from CRLDPs named in the certificate;
an IPv6 (ULA) CRLDP URL is reached via the ACP, a domain name via the data plane (no DNS
in the ACP); HTTPS MAY with membership-check authentication, possibly skipping CRL
checking so revoked nodes can learn their revocation. *6.2.5.4 lifetimes*: short
lifetimes allowed because renewal is automatic; a sub-CA with enough performance;
hours-long lifetimes can make revocation unnecessary (STAR, RFC 8739). *6.2.5.5
reenrollment*: an expired node becomes a reenrolling candidate keeping its TA and chain;
with BRSKI it first tries its expired ACP certificate (registrar MAY honour it and reuse
the acp-node-name), else IDevID; authenticate the registrar by the old TA before
accepting a voucher; alternate between both; never drop the old TA to avoid the
"duckling" state. *6.2.5.6 failing certificates*: detect revocation/expiry or repeated
connection failures where the peer passes the check, and switch to reenrolling.

**6.3 Adjacency table** (MUST): per adjacent node at least Node-ID, discovering
interface, link-local IPv6 address, certificate (with acp-node-name); supplemented by
configuration for non-adjacent peers; MAY cache validity/trust but every step MUST redo
the membership check.

**6.4 DULL GRASP neighbour discovery**: one DULL instance per L2 interface; native
interfaces SHOULD be auto-initialized so that only SLAAC, DULL GRASP and then secure
channel setup packets are accepted; MLDv2 join for ff02::13 (MLD-snooping switches);
discovery SHOULD NOT be on by default on non-native interfaces and MUST NOT run inside
the ACP; objective:

```
[M_FLOOD, session-id, h'fe80...', 210000,
  [["AN_ACP", 4, 1, "IKEv2"], [O_IPv6_LOCATOR, h'fe80...', IPPROTO_UDP, 15000]]
  [["AN_ACP", 4, 1, "DTLS" ], [O_IPv6_LOCATOR, h'fe80...', IPPROTO_UDP, 17000]]]
objective-value = method-name / [ method, *extension ]
method = method-name / [ method-name, *method-param ]
method-name = "IKEv2" / "DTLS" / id      ; id = text matching [A-Za-z@_$]([-.]*[A-Za-z0-9@_$])*
```

flags sync-only (4), loop-count 1, RECOMMENDED period 60 s, ttl 210000 ms, initiator
MUST be the sending interface's link-local address, locator MUST be O_IPv6_LOCATOR with
the same address, needed only when the protocol has no well-known port (DTLS always);
unknown method-params and extensions MUST be ignored; "IKEv2" not "IPsec"; no
certificate in DULL (fragmentation). Result stored in the adjacency table. BRSKI's
AN_Proxy may share the message.

**6.5 Candidate selection**: only same-domain nodes (all routing subdomains).

**6.6 Channel selection**: no unprotected negotiation; nodes MUST try all feasible
secure channel protocols (supported by both, as announced), sequentially or in parallel
as initiator, and MUST respond to all in parallel; once one authenticates, the peer with
the **higher Node-ID is the Decider**, the other the Follower; the Follower stops
initiating and accepts closes; the Decider converges on its preferred working protocol;
a "0"-address peer is Follower against a real address; the Decider SHOULD NOT send
payload until decided; the Follower MAY delay linking the channel up to 5 s; the 13-step
example (C1/C2); per-L2-interface context; neighbours with equal link-local addresses on
different interfaces MUST NOT be assumed identical; the Decider SHOULD NOT suppress
attempts on one interface because they failed on another.

**6.7 Verification**: any protocol MUST support certificate authentication with the
membership check; failures abort and log; reconnect attempts MUST be throttled,
RECOMMENDED exponential base-two backoff with IRT 10 s and MRT 640 s; responder failures
MUST NOT throttle the node's own initiator attempts.

**6.8 Secure channel protocols**: *6.8.1* no single MTI; consistent minimum strength
("no weakest link"); L2 mechanisms (MACsec) possible but unspecified; physical security
only via ACP connect. *6.8.2 common*: authenticate with the ACP certificate per 6.2.3;
MUST send the certificate directly (no hash/URL); MUST use forward secrecy; MUST provide
confidentiality with ≥ 256-bit-equivalent symmetric encryption (AES-256), NULL MUST NOT;
SHOULD be able to include the TA certificate for diagnostics, with a selector; MUST
terminate the channel immediately when any certificate in the peer's chain expires or is
revoked; drop legacy options when profiling new protocols. *6.8.3 IPsec*: announced as
"IKEv2"; narrow profile of RFC 8221 and RFC 8247. *6.8.3.1 native*: MUST tunnel mode,
IKEv2, IPv6 payload (ESP next header 41), link-local outer addresses, no manual keying,
TSi = TSr = (0, 0-65535, :: - ffff:...:ffff) because transit traffic is forwarded;
*8221*: no AH, ENCR_NULL MUST NOT, ENCR_AES_GCM_16 the only MTI, AES-CBC+HMAC-SHA2-256-128
and AES-CCM-8 MAY (SHOULD if faster), ChaCha20-Poly1305 SHOULD at equal performance, order
offers by performance, 256-bit AES keys only; *8247*: comply; certificate chain in the
"X.509 Certificate - Signature" payload; respond only with the ACP certificate on the
announced link-local address/port; ignore CERTREQ not naming our TA but still send our
chain (diagnostics); **ID_IPv6_ADDR MUST carry the ACP address** and match the
certificate's; **authentication method 14 (Digital Signature) MUST**; SHA2-512 MUST
(and SHA2-256); **DH group 19 (256-bit random ECP) MUST**. *6.8.3.2 IPsec with GRE*:
transport mode, next protocol 47, TS = own link-local addresses with proto 47; preferred
by IKEv2 over tunnel mode when both support it; IPv6 over GRE per RFC 7676. *6.8.4 DTLS*:
announced "DTLS" with a locally assigned UDP port; DTLS 1.2 MUST, older MUST NOT, BCP 195
otherwise; newer versions allowed if they negotiate down; IPv6 packets are the DTLS
payload; DTLS rekeying as any transport application. *6.8.5 profiles*: **baseline** =
native IPsec MUST, IPsec/GRE MAY; **constrained** = DTLS MUST when IPsec impossible;
gateways between both support both; documentation must state supported mechanisms and
profile.

**6.9 GRASP in the ACP**: the ACP MUST run a GRASP instance (service discovery via
M_DISCOVERY and M_FLOOD, hop-by-hop reliable flooding); no IP multicast routing in the
ACP (Appendix A.5); the ACP is GRASP's security and transport substrate: GRASP sends only
on ACP GRASP virtual interfaces, is told when they come and go, exists without
neighbours (ASAs on one node still discover each other; ASAs MUST operate and know when
there is no ACP); unicast GRASP uses the ACP address over **TLS** (6.1, membership check
for mutual auth; link-local addresses MUST NOT appear in objectives); link-local
multicast GRASP messages are replicated over **TCP connections to each link-local
neighbour** on the virtual interface; port **7017** for both; Figure 8 stacks ACP GRASP
instance / substrate (loopback TLS, subnet TCP) / ACP VRF with RPL and IPv6 forwarding /
IPsec-DTLS / data plane link-local. Discussion: TCP for flooding because lossy links would
otherwise force high retransmission rates; TLS for unicast against compromised inside
members (MITM), accepting double encryption.

**6.10 Context separation**: a dedicated VRF is one option; a logical container or VM
is preferred when the software allows; created automatically at bootstrap; protected
from data-plane configuration; not reachable from data-plane tables.

**6.11 Addressing**: loopback per node with a network-wide unique address (prefix);
links use link-local only; one routable prefix per node; ULA with L=1; no external
connectivity; permanent, not temporary, not privacy-sensitive; IPv6 only (simplicity,
no IPv4 need for AN or OAM). *6.11.2 base scheme*:

```
 8      40                     2                     78
+--+-------------------------+------+------------------------------+
|fd| hash(routing-subdomain) | Type |     (sub-scheme)             |
+--+-------------------------+------+------------------------------+
```

hash = first 40 bits of SHA-256 of the routing-subdomain (example 89b714f3db); rsub
MUST be chosen so hashes do not collide within an AN; nodes SHOULD NOT assume the hash in
operation; Type assigned by IANA (0 Zone/Manual, 1 Vlong, 2 to 3 reserved).

| Type | Name | F | Z | V-bits | Prefix announced |
|---|---|---|---|---|---|
| 0 | ACP-Zone | n/a | 0 | 1 | /127 |
| 0 | ACP-Manual | n/a | 1 | n/a | /64 |
| 1 | ACP-Vlong-8 | 0 | n/a | 8 | /120 |
| 1 | ACP-Vlong-16 | 1 | n/a | 16 | /112 |

*Zone (6.11.3)*: `| base 50 | Z=0 1 | Zone-ID 13 || Registrar-ID 48 | Node-Number 15 | V 1 |`;
Node-ID (64 bits) unique per domain; Registrar-ID unique per registrar, Node-Number
sequential; V=0 the ACP node base system, V=1 an optional "host" context with its own
transport endpoints; certificate address has V=0; the node's set covers any Zone-ID and
V; RECOMMENDED Zone-ID 0 unless doing incremental adoption (9.4); unrelated to RFC 4007
zones. *Manual (6.11.4)*: `| base 50 | Z=1 1 | Subnet-ID 13 || Interface Identifier 64 |`
for ACP connect subnets, assigned non-autonomically, SHOULD NOT appear in certificates;
nodes that cannot build secure channels omit the address and use ACP connect.
*Vlong (6.11.5)*: `| base 50 || Registrar-ID 46 | F 1 | Node-Number 23/15 | V 8/16 |`;
F=0 general-purpose nodes with < 256 virtual addresses (/120), F=1 edge nodes or
container-modular controllers needing many (/112); V bits assigned by the node, zero in
the certificate. *6.11.7 registrars*: PKI RAs that add acp-node-name; may be sub-CAs; any
mechanism allowed as long as the resulting certificates pass the check and the address
rules hold (a person with CLI counts); BRSKI the only defined protocol. MUST NOT allocate
colliding prefixes; MUST have one or more domain-unique **46-bit Registrar-IDs** (lower
46 bits of a known-unique EUI-48 may be used without signaling); with BRSKI the
acp-node-name goes to the pledge via EST CSR Attributes; policy chooses Zone vs Vlong and
prefix length (SHOULD default to Zone with Zone-ID 0; SHOULD allow choice by IDevID
serialNumber/PID); simple scheme: persist Registrar-ID and next Node-Numbers per
sub-scheme, never recycle; if lost, use a new Registrar-ID or discover used addresses;
on renewal/rekey the address MUST be kept (unless security or uniqueness issues) and
SHOULD be kept across registrars, expiry and failure.

**6.12 Routing: RPL** ("The routing protocol inside the ACP is RPL [RFC6550]"),
adjacencies across all ACP channels including all routing subdomains. Profile
(6.12.1): no RPI (hardware forwarding, overhead); **single RPL instance, RPLInstanceID
0**, one DODAG (best effort towards the primary NOC/root; traffic to other NOCs goes via
the root; acceptable for management traffic; root re-election on failure); scales
because leaf nodes keep little state; reconvergence by link up/down signalling, no ETX:
DIOs SHOULD be sent two or three times on losing the last parent, Detaching SHOULD be
preferred over Poisoning, SHOULD select at least three parents and send DAOs to all in
parallel, secure channel dead-peer detection (IKEv2 DPD) SHOULD trigger parent change
immediately; **MOP 2 (storing mode, no multicast) MUST**, MOP 3 MAY; DAO policy
proactive: K flag for DAO-ACK, retries 3 at 256 ms; metric hop count (diagnostic only);
**Objective Function OF0 (RFC 6552)**, rank_factor 5 for links ≤ 100 Mbps else 1; global
repair only on catastrophic events; local repair: No-Path DAO on link break, re-evaluate
parent on repair; no stretch, no data-path validation, no Trickle; multicast unused; RPL
security unused (ACP channels protect); P2P unused; every node announces its prefix
(/127, /112, /120) and MUST install a black hole route for unused parts of its assigned
space (longer prefixes on interfaces override; those are not announced); ACP connect
/64s announced; **administrative preference** (DODAGPreference): configured root 0b100,
ACP registrar 0b011 (default), ACP connect node 0b010, default 0b001; RPI not required
(storing mode, single instance); unknown destinations are only detectable at the root,
which SHOULD log them.

**6.13 General**: hop-by-hop encryption; no performance requirements (software-only
allowed); secure channels use link-local addresses and the link-local interface used for
the ACP must not be unconfigurable from the data plane (separate virtual interface,
separate MAC, Appendix A.9.2); **MTU MUST be derived locally** from link MTU minus
encapsulation, no PMTUD for channels, transport across the ACP MAY assume 1280; multiple
links SHOULD each carry a channel (Decider may prune); interfaces: *loopback* holds the
first address of the N-bit prefix (N = 128 - V bits), MUST NOT connect to other nodes
(reasons: addresses belong to interfaces, external interfaces are unstable, OAM services
expect one peer address, no per-subnet negotiation); *virtual interfaces*: point-to-point
per channel (dead peer SHOULD trigger RPL repair) or multi-access per underlying subnet
(replicate link-local multicast to every channel, unicast by forwarding table, dead peer
signals RPL); nodes MUST run SLAAC and ND on virtual interfaces; optimistic DAD
RECOMMENDED; link-local address MUST NOT depend on anything attackable from the data
plane (not the physical interface's link-local, not encapsulation parameters); link-layer
address fields SHOULD be ignored on receive, remember the channel; NBMA subnets MUST be
point-to-point virtual interfaces (flooding would fail); inter-domain channels better
point-to-point.

### 2.5 L2 switches (Section 7), non-ACP components (Section 8)

*7*: a flat LAN would create a full mesh of channels; ACP-capable switches run a
separate DULL GRASP instance per L2 port, extract ff02::13 packets at port level, MUST
never bridge ALL_GRASP_NEIGHBORS between ACP ports (MLD snooping must not either),
operate ACP on the L3 VLAN interface, multi-access virtual interfaces only per L2 port,
untagged GRASP only, STP interaction unresolved (ideally peer across blocked ports).

*8.1 ACP connect*: an interface-level configured workaround on an "ACP edge node" giving
trusted non-ACP nodes (NMS hosts, controllers) native unencrypted access to the whole
ACP; requires physical control; SHOULD use the Manual sub-scheme prefix, SHOULD NOT use
a prefix also routed outside; the prefix MUST be announced into RPL; NMS hosts MUST route
ACP prefixes via the connect interface (RFC 6724 longest match suffices with one ULA
prefix); the edge MUST RPF-filter (source must be from the connect subnet) unless
administratively changed; SHOULD restrict which nodes may enable ACP connect (registrar
policy, A.9.5); SHOULD be able to drop RPI headers. *8.1.2 software components*: the same
mechanism inside one device (NMS as container/VM on the ACP node) with a correct security
model: trusted orchestration gives only trusted software the ACP virtual subnet, and only
more trusted software both ACP and data plane. *8.1.3 autoconfiguration*: SLAAC on the
connect subnet, RFC 4191 RIOs announcing the aggregated ACP /48 prefixes and a default
route with lifetime 0; Vlong edges MAY carve connect prefixes from their /112 or /120.
*8.1.4 VRF select*: one interface for both ACP and data plane: the edge acts as two
routers with two link-local addresses and separate RAs; relies on RFC 6724 Rule 5.5 /
RFC 8028 on hosts; MAY. *8.1.5 GRASP across ACP connect*: allowed with equivalent
security; all GRASP on a combined interface belongs to the ACP domain and SHOULD use ACP
addresses.

*8.2 remote neighbours*: *configured* `connection = method "," local-addr "," remote-addr
["," pmtu]`, method any / IKEv2[:port] / DTLS[:port], addresses IPv4 or IPv6 global,
optional VRF, local "any" = source selection and listen on all, remote "any" = responder
only, a **hub** for spokes over the Internet; pmtu configurable; IKEv2 SHOULD support
NAT-T. *tunneled*: a preexisting IP-in-IP/GRE tunnel with "ACP enable" runs link-local
DULL and secure channels inside (double encapsulation, but no ACP changes, PMTUD from the
tunnel, firewall traversal); SHOULD allow restricting channel protocols on such tunnels
against downgrade; implementations SHOULD support at least GRE tunneled remote
neighbours. Both are less indestructible than L2-adjacent neighbours.

### 2.6 Operations (Section 9), benefits (10), security (11), IANA (12)

*9.1 diagnostics*: YANG models of GRASP/ACP/TLS/IPsec/certificates/time/VRF are necessary
but not sufficient; local, non-volatile logging; dependency-ordered checklists ("Is the
ACP operational?": enabling config, sane time, keying material, certificate validity/
revocation/CRL freshness/acp-node-name format, VRF created, interfaces enabled; "Why no
connection to a neighbour?": interface up and link-local, ACP enabled, DULL sent and
received (MLD snooping diagnostics: querier addresses), objective seen, neighbour MAC
known, last attempt, who closed, local reason: no common protocol, TA mismatch (show the
peer's TA), domain mismatch, revoked, expired, IKEv2/DTLS errors; "Is the ACP operating
across channels?": neighbours, RPL running, default route to root, routes per neighbour,
ACP GRASP running, SRV.est cached, BRSKI registrar cached, proxy operating); signaling the
TA in channel setup aids multi-tenant, expired-TA, merger and misconfigured-registrar
cases. *9.2 registrars*: interactions (reach pledges through proxies over the ACP, reach
the TA over the data plane, isolated ACP/data plane stacks, SZTP RFC 8572 as alternative,
vouchers from a MASA for secure-bootstrap devices), parameters (TA URL and credentials,
domain name, Registrar-ID defaulting to a MAC, next Node-IDs for recovery, admission
policies by serialNumber, address sub-scheme policy, voucher retrieval), limitations of
plain registrars (online TA needed; compromised registrar hard to clean up without
central tracking), **registrars with sub-CA** (enroll offline, revoke the sub-CA to purge
its nodes, short-lived leaf certificates without CRL), centralized Policy Management
System queried by registrars. *9.3 enabling and disabling*: enabling an interface means
permitting only ACP/BRSKI packets (SLAAC, ND, DULL, IKEv2/ESP or DTLS, BRSKI TCP/TLS) with
everything else filtered; **"admin down"** (physical layer kept, data plane filtered) vs
"physical down"; keep BRSKI pledge traffic even in admin down; new physical-down options
with "do not disconnect yourself" checks; fast state propagation via a DULL "admin-state"
objective and BFD instead of physical down; low-level link diagnostics disrupt the ACP,
negotiate self-terminating diagnostics; power considerations; interface-level "ACP/ANI
enable" automatic on native interfaces, explicit on non-native (tunnels: cost
configuration too, decide by purpose); node-level "ACP/ANI enable [up-if-only]" required
on brownfield nodes (software updates must not silently enable it; MASA attack risk if
ANI auto-enabled), auto on greenfield nodes which SHOULD put native interfaces in admin
down, terminate greenfield state on signs of physical possession (console, USB), and
SHOULD NOT run TOFU bootstrap protocols in parallel with BRSKI; undoing enable should be
constrained (certificate-carried policy). *9.4 partial adoption*: ACP zones per edge
network with Zone-IDs and registrars per zone, connected across a non-ACP core via L3VPN
of the ACP VRFs; GRASP across zones via a GRASP hub (application-level, in the NOC);
later merge without re-keying. *9.5 configuration summary*: no desirable ACP
configuration; exceptions: certificate provisioning without BRSKI, PKI functions, ACP
connect, enabling on brownfield nodes, remote neighbours; data-plane configuration over
the ACP is safer, configuring the ACP's own non-autonomic parts over the ACP needs care.

*10 benefits*: self-healing (new neighbours join, routing adapts, channels torn down on
expiry or revocation, partitions and mergers survive; central dependencies CRL/registrar/
CA; sub-CA registrars for resilience; merging TAs needs trusting the union; run over
admin-down interfaces or dependency-check admin actions); self-protection from outside
(no join without certificate, no injection, only configuration-level disruption through
the few enable options; protects legacy OAM protocols SNMP, NTP, PTP, DNS, DHCPv6,
syslog, RADIUS, Diameter, TACACS, IPFIX, NetFlow as a stopgap; link-local addressing makes
remote attacks from the data plane impossible) and from inside (management ports reachable
only from the ACP; end-to-end encryption on top); administrator view (minimal
configuration, full visibility, show/debug, NMS must discover and monitor it separately
from the data plane).

*11 security*: PKI chain of trust; registrars and EST servers are security-critical;
BRSKI/IDevID with TPM-class protection; EST considerations; malicious EST announcements
mitigated by id-kp-cmcRA; downgrade attacks on channel selection (A.9.9); private PKI
model; no source address spoofing prevention inside the ACP, so services need end-to-end
authentication (GRASP uses TLS); group security primarily against outside attackers;
mitigation of compromised members via revocation and short lifetimes; roles for
higher-trust functions (A.9.5); provisioning must consider connectivity impact; L2
bridged deployments need port security; DULL must check the locator equals the source.

*12 IANA*: id-mod-anima-acpnodename-2020 = 97; id-on-AcpNodeName = 10; GRASP objective
names AN_ACP, SRV.est; ACP Address Type registry (0 Zone/Manual, 1 Vlong, 2 to 3
unassigned, Standards Action).

### 2.7 Appendix A (informative but decision-relevant)

A.1 the sub-schemes spend 46/48 bits on Registrar-IDs for uncoordinated registrars; a
centralized PMS could save them in a future sub-scheme; the Manual scheme exists to keep
non-autonomic configuration out of autonomic space. A.2 BRSKI: registrar puts the
acp-node-name into the EST CSR Attributes; the CA must not alter it; hour-scale lifetimes
with reenrollment via the proxy can replace CRLs with a do-not-renew list; without BRSKI,
PKCS#7 provisioning, vendor NETCONF models or SZTP, which does not bootstrap across an
unconfigured network. A.3 discovery protocol: LLDP terminates on L2 ports (would stop at
non-ACP switches), mDNS cannot be terminated per port and is heavier, hence DULL GRASP.
**A.4 why RPL**: self-managing without areas, scales to 100 000+ nodes via default
routing, low state away from the root, unstructured address space (identifiers, mobile
nodes), modular Objective Functions, extensible, multi-topology possible, no path
optimisation needed for delay-insensitive feedback loops. A.5 no IP multicast (ASM
autoconfiguration too complex); SSM possible for future ASAs; LSP IGPs could flood
objectives but not M_DISCOVERY; DODAG-based flooding a future optimisation. A.6 one
domain = one membership check; rsub for separate /48s that may merge later; different
domain names for ACPs that must not connect; one CA may serve several domains; same name
with different CAs do not merge. A.7 Intent: circular dependencies; cross-domain
membership would need Intent to add TAs/domain names; a reduced ACP could carry Intent
first. **A.8 adopting ACP concepts elsewhere**: any /48 prefix instead of a hashed ULA
(registrar configuration); address field may be omitted if another unique ID exists,
then another Decider/Follower rule is needed; the ACP need not be a separate VRF where
everything is fully automated (ACP as the data plane plus BRSKI plus RFC 8992); CoAP/DTLS
instead of TCP/TLS for GRASP in constrained networks via the same negotiation; **"RPL ...
explicitly does not optimize for shortest paths and fastest convergence. Variations of the
ACP may want to use a different routing protocol or introduce more advanced RPL
profiles"**, with the variation chosen by certificate parameters that change rarely or are
provisioned before activation (BRSKI follow-up signaling); secure channel protocols are
easily added; hop-by-hop channels could be replaced by end-to-end security plus other
infrastructure protection, and future OAM should always be end-to-end secured. A.9
future: auto-aggregation of routes and automatic Zone-IDs via GRASP; separate MAC or
Ethertype for ACP packets; **YANG model for the ACP including adjacency table and GRASP
(A.9.3)**; RPL enhancements for dual NOC (Figure 17) via IP-in-IP/RPI or (Src,Dst)
routes, flooding along the DODAG; role assignments in the certificate (ACP connect
permission, registrar permission, NOC role limiting OAM TLS connections); autonomic L3
transit (hub-and-spoke tunneling to a cloud/central ACP, peer-to-peer over L3VPN);
diagnostics via LLDP or a DULL diagnostics objective, IDevID exposure trade-off, richer
secured diagnostics; compromised nodes (certificate-only credentials, no local password
configuration, lock-down of ACP configuration, remote credential revocation, GRASP-flooded
CRL updates); downgrade detection by a post-channel GRASP negotiation comparing announced
and chosen protocols.

### 2.8 GRASP (RFC 8990) as far as the ACP depends on it

- Terms: discovery, negotiation, state synchronization (negotiation without change
  requests), technical objective (name + value; discovery/synchronization/negotiation
  contexts), initiator/responder/counterpart roles, GRASP instance, GRASP core, GRASP
  interface. Deployment: one instance per node in the ACP, API to ASAs (RFC 8991), ASAs
  unprivileged, single addressing realm (no NAT), must tolerate socket failures and
  renumbering, no non-volatile storage dependence, no version number (M_INVALID for
  extensibility).
- Security substrate (2.5.1): every use MUST specify a security and transport substrate
  enforcing a mutually trusted group (the GRASP domain) with member authentication,
  integrity and removal; in the ANI it is the ACP (encryption mandated). **DULL
  (2.5.2)**: an insecure instance for link-local discovery only: M_DISCOVERY and M_FLOOD
  with loop count 1, other unsolicited types MUST NOT, discard loop count ≠ 1, discard
  objectives not part of the insecure service, never relay, responses with link-local
  addresses and no Divert, discard non-link-local sources; prefer flooding over
  discovery to minimize traffic.
- Transport (2.5.3): CBOR directly over the transport; discovery/flooding are link-local
  multicast hop-by-hop, SHOULD be reliable (TCP); over UDP no fragmentation, ≤ 1280-byte
  packets; all other messages unicast over a reliable transport (TCP by default); in the
  ACP: TCP for everything, link-local flooding replicated over TCP connections to each
  neighbour, UDP multicast only for the DULL instance; listen port 7017.
- Procedures: discovery (multicast M_DISCOVERY, unicast M_RESPONSE over TCP to the
  sending port, Divert to off-link responders, relaying with loop-count decrement, rate
  limits, session cache, timeout 100 ms × loop count, exponential backoff, response
  cache with ttl); negotiation (M_REQ_NEG, M_NEGOTIATE steps, M_WAIT, M_END with
  O_ACCEPT/O_DECLINE, timeout GRASP_DEF_TIMEOUT, dry run, one objective per thread,
  no transactional integrity); synchronization (M_REQ_SYN/M_SYNCH); flooding (M_FLOOD to
  ff02::13 with loop count, relayed on other interfaces with the same session id and
  initiator, rate-limited, cached ≥ 2 × timeout, repeated periodically, flooded values
  SHOULD NOT contain unencrypted private data); rapid mode (objective inside M_DISCOVERY)
  off by default.
- Constants (2.6): ALL_GRASP_NEIGHBORS ff02::13 / 224.0.0.119; GRASP_LISTEN_PORT 7017;
  GRASP_DEF_TIMEOUT 60000 ms; GRASP_DEF_LOOPCT 6; GRASP_DEF_MAX_SIZE 2048 bytes.
  Session ID: up to 32 bits, PRNG, tagged with the initiator address.
- Messages (2.8, CDDL §4): `[MESSAGE_TYPE, session-id, ?initiator, *option]`; M_NOOP 0,
  M_DISCOVERY 1, M_RESPONSE 2, M_REQ_NEG 3, M_REQ_SYN 4, M_NEGOTIATE 5, M_END 6, M_WAIT 7,
  M_SYNCH 8, M_FLOOD 9, M_INVALID 99; options O_DIVERT 100, O_ACCEPT 101, O_DECLINE 102
  (+reason), O_IPv6_LOCATOR 103 `[103, bytes16, proto, port]`, O_IPv4_LOCATOR 104,
  O_FQDN_LOCATOR 105, O_URI_LOCATOR 106; objective `[name, flags, loop-count, ?value]`,
  flags F_DISC 0, F_NEG 1, F_SYNCH 2, F_NEG_DRY 3; names without colon are IANA-registered,
  private names contain a colon with a globally unique prefix (PEN, FQDN or email);
  EX0..EX9 experimental.
- Security (3): full protection required; authentication by the external certificate
  mechanism; roles out of scope; confidentiality required (topology leaks); link-local
  multicast is in the clear and forgeable on-link; DoS mitigations by rate limits;
  bootstrap discovery is inevitably insecure; FQDN/URI locators are not assumed inside
  the secure environment.

### 2.9 BRSKI (RFC 8995) as far as the ACP depends on it

- Purpose: zero-touch bootstrap of pledges with a factory IDevID (IEEE 802.1AR) into a
  domain: registrar authenticates and authorizes the pledge, the pledge authenticates and
  authorizes the registrar through a **voucher** (RFC 8366) signed by the manufacturer's
  MASA; then EST enrollment of an LDevID. Prior approaches (TOFU, resurrecting duckling,
  pre-staging, call-home) rejected as not zero-touch or privacy/liability-laden.
- ANI requirements (1.5): BRSKI MUST for ANI devices; proxy discovery via DULL GRASP
  M_FLOOD; voucher status telemetry MUST; EST automation extensions MUST; registrar ASA
  supports all; all ANI devices SHOULD be proxies.
- Architecture (2): pledge, Join Proxy (circuit proxy, TLS not terminated), Domain
  Registrar (BRSKI-EST server, BRSKI-MASA client, RA/possibly CA), MASA with ownership
  tracking/audit log, PKI. Pledge states: discover, identify (IDevID in TLS with a
  provisionally accepted server certificate), request join (voucher-request with nonce),
  imprint (verify voucher, send voucher status telemetry), enroll (EST), enrolled;
  factory reset returns to discover. IDevID subject carries serialNumber; MASA URI
  extension id-pe-masa-url (1.3.6.1.5.5.7.1.32). No real-time clock needed (nonce
  freshness). Cloud registrar at a well-known URI when no local one. Protocol flow
  (Figure 4): GRASP M_FLOOD → TLS via proxy → provisional accept → voucher-request →
  registrar contacts MASA (pledge ID, domain ID, nonce) → voucher → pledge imprints →
  telemetry → audit-log check → EST enrollment.
- Proxying (4): the proxy floods `["AN_Proxy", 4, 1, ""]` with an O_IPv6_LOCATOR of its
  link-local address, TCP, a chosen port, ttl 180000; pledges obtain a link-local address
  (SLAAC, temporary addresses encouraged), listen for AN_Proxy, try every proxy with
  independent exponential backoff up to one hour, concurrent connections preferred (anti-
  Slowloris), unique nonce per attempt; registrars flood `["AN_join_registrar", 4, 255,
  "EST-TLS"]` with their ACP address locator inside the ACP every 60 s; registrars MUST
  accept HTTPS/EST on announced TCP ports and support the circuit proxy; mDNS/DNS-SD and
  IPv4/DHCP alternatives in Appendices A and B.
- Protocol details (5): BRSKI-EST under `/.well-known/brski` plus EST URIs; JSON for new
  operations; TLS 1.2 or newer required (1.3 encouraged); persistent connections; pledge
  treats all data as untrusted until the voucher validates; registrar authenticates the
  pledge by IDevID (per-manufacturer TA database), authorizes by policy (serial numbers,
  acceptlist of manufacturers), fetches voucher from MASA over HTTPS with its own
  credentials, verifies audit log, forwards voucher; pledge sends voucher status
  telemetry; **EST integration (5.9)**: pledge SHOULD fetch CA certificates, MUST request
  CSR Attributes and the registrar MUST validate the CSR against them; **in ACP networks
  the CSR Attributes MUST include the acp-node-name fields of RFC 8994 §6.2.2**; MUST
  request a client certificate; MUST POST enrollment status to `/.well-known/brski/
  enrollstatus` (version, status, reason, reason-context), re-establishing TLS with the
  new credentials on success.
- Applicability to the ACP (9): designed for professionally managed ISP/enterprise
  networks; proximity assertion via link-local to the proxy and ULA to the registrar;
  manufacturers MUST provide at least one one-touch mechanism without MASA availability
  (7.2); operational requirements: MASA online at the IDevID URL with escrowed signing
  key and audit log; domain owner operates an EST/registrar announced via GRASP, maybe an
  internal CA, acceptlist of manufacturers, EST servers for renewal, HSM/secret splitting
  for the CA key, uses the ACP for management; devices ship with MASA trust anchors and
  IDevIDs, find proxies via GRASP, enroll via EST, form ACPs with IPsec over link-local,
  then act as proxies themselves, renew before expiry.
- Reduced security modes (7): nonceless vouchers, trusting owners on first use at the
  MASA, pledge and registrar security reductions, updating voucher trust anchors.

In short: Arcana has a domain CA and a registrar, but **no ACP**. Management reaches a
host only while the host's data plane and the console's path to it work, which is the

exactly this).

### 3.2 Concrete proposal: an Arcana ACP on FreeBSD

**A. Certificates and registrar (6.2, 6.11.7, 9.2).**
1. Make the console's CA the ACP TA and the console the ACP registrar with sub-CA
   semantics (9.2.4): when an operator CA is used, let the console hold an intermediate
   CA certificate (`ca_key` becomes the sub-CA key) so leaf certificates can be short
   lived and revocation is by not renewing.
2. Issue host certificates with: SAN DNS:host (keep), SAN otherName AcpNodeName
   `<32hex>+<rsub>@<acp-domain-name>` (OID 1.3.6.1.5.5.7.8.10, IA5String), EKU
   `serverAuth` **and** `clientAuth` (hosts become initiators of channels and TLS clients
   of EST/GRASP), ECDSA P-256 (allowed: ACP-only use; add `keyAgreement` if ECDH with the
   certificate key is wanted), SHA-256 signature. The console's certificate gets an
   AcpNodeName with an address too (it is an ACP node) and `id-kp-cmcRA` for its EST
   role. Validate RSA 2048 chains as well (OpenSSL does).
3. Settings: `acp-domain-name` (default `acp.<console host's domain>`), optional `rsub`
   per site, a persisted 46-bit `Registrar-ID` (lower 46 bits of the console host's
   primary MAC or random once), persisted next Node-Numbers per sub-scheme, never
   recycled. ULA prefix = `fd` + first 40 bits of SHA-256(routing-subdomain).
4. Sub-scheme policy: Zone (Type 0, Zone-ID 0, /127) for plain hosts; **Vlong-8**
   (/120) for hosts that run vnet jails or many services so that V bits can address
   jails and ASAs (6.11.5 "individual software components"); Vlong-16 (/112) for the
   console host and route-reflector hosts (edge nodes with many clients). Store the
   choice per host in the server list.
5. Keep the token enrolment as the registrar mechanism (6.11.7.1 allows "any
   mechanism"), but harden it toward BRSKI's properties: put the CA certificate's
   SHA-256 fingerprint into the enrol command the console prints (TOFU of the console's
   HTTPS certificate is otherwise possible), carry the acp-node-name to the host in the
   response (the CSR Attributes role of BRSKI 5.9.2; the console ignores the CSR subject
   already), store the certificate chain and TA, and record the enrolment in the audit
   trail (BRSKI's enrollstatus telemetry analogue).
6. Renewal: an EST server (RFC 7030 `/.well-known/est/{cacerts,csrattrs,simplereenroll}`)
   in the console, reachable over the ACP at its ULA, announced with `SRV.est` M_FLOOD
   every 60 s (ttl 210 s); the agent renews before 50% of lifetime using its current
   certificate for TLS client auth, keeps the acp-node-name, and falls back to
   reenrolment with a new token if the certificate has failed (6.2.5.5/6). Lifetimes:
   weeks for leaves, years for the sub-CA; CRL at an HTTP CRLDP on the console's ULA for
   emergencies (cblink already loads CRLs). Enrolment over the ACP through a **join
   proxy**: an enrolled host floods `AN_Proxy` on its interfaces and circuit-proxies TCP
   to the console's EST/enrol endpoint over the ACP, so a new host without data-plane
   reachability to the console can enrol (BRSKI §4 adapted to the token).

**B. Discovery and channels (6.3 to 6.8).**
7. A userland daemon of our own (`arcana-acp` or inside `arcana-grasp`, see rfc9222.md),
   C, libcbor, OpenSSL: one DULL GRASP instance per enabled interface sending
   `["AN_ACP", 4, 1, "IKEv2"]` (and optionally `"DTLS"` with a port) in M_FLOOD to
   ff02::13:7017 every 60 s from the interface's link-local address, joining the group
   with `IPV6_JOIN_GROUP` (MLDv2); maintains the adjacency table (Node-ID, interface,
   link-local, certificate) and exposes it through a cblink `acp` dump and YANG state
   (A.9.3). Native interfaces auto-enabled; tunnels and vnet epairs only when the
   console says so (9.3.4) with an RPL/IGP cost.
8. Secure channels, baseline profile: **IPsec/IKEv2 by strongSwan** (already a plugin,
   swanctl conf.d files owned by Arcana): per neighbour a connection with
   `local_addrs/remote_addrs` = link-local, `local { auth = pubkey, certs = acp.pem,
   id = <ACP address as ID_IPv6_ADDR> }`, remote id = peer ACP address from the adjacency
   table, `proposals = aes256gcm16-sha512-ecp256` (ESP `aes256gcm16`, IKE PRF/integrity
   SHA-512 allowed, DH group 19 = ecp256), tunnel mode, `local_ts = remote_ts = ::/0`,
   `send_cert = always` (certificate sent directly, 6.8.2), `dpd_delay` for dead peer
   detection (6.12.1.1.2), rekey by strongSwan, terminate on certificate expiry (6.8.2:
   a swanctl `--terminate` from the daemon when validity ends), **if_ipsec(4)** interface
   with a reqid per neighbour as the ACP virtual interface (policies on the interface,
   strongSwan `policies = no`, as `luxuria/ipsec.c` already does for data tunnels).
   Alternative when gre(4) virtual interfaces are preferred: transport-mode IPsec with
   TS proto 47 and `gre` over IPv6 link-local (6.8.3.2). Decider/Follower by comparing
   Node-IDs after the first successful IKE_AUTH; backoff IRT 10 s / MRT 640 s on
   initiator failures only. DTLS (constrained profile) would need a tun(4)-based
   userland DTLS 1.2 tunnel: possible later, not required since IPsec is MTI for the
   baseline profile. **WireGuard is not an ACP secure channel protocol**: its
   authentication is by raw key, not the ACP certificate (6.8.2 MUST), so it may only be
   a private `method-name` for Arcana-only domains after binding the WG key to the
   certificate inside a cert-authenticated exchange; not recommended.
9. Context separation (6.10): either a dedicated FIB (`setfib`; the if_ipsec interfaces,
   the ACP loopback `lo1` with the ULA and the GRASP/agent sockets bound to that FIB with
   `SO_SETFIB`, plus ipfw rules forbidding the ACP ULA range on data-plane interfaces),
   or, preferred by the RFC's "logical container" ranking, a **vnet jail `acp`** holding
   the if_ipsec/gre interfaces, `lo1`, the ACP GRASP instance and the agent's ACP-facing
   cblink listener, with the privileged agent reached over an AF_UNIX socket exposed into
   the jail. FreeBSD FIBs share the interface and socket namespace, so the jail gives the
   real separation; cost: strongSwan or if_ipsec in a vnet jail must be verified on the
   target release (IPsec is VNET-aware).
10. Addressing (6.11, 6.13.5): `lo1` with the first address of the assigned prefix
    (/128), a black hole route for the rest of the /120 or /112 (`route add -blackhole`),
    SLAAC/ND on the virtual interfaces with a link-local address derived from a stable
    local identifier (not the physical interface's link-local, 6.13.5.2), optimistic DAD;
    MTU = link MTU minus ESP/IPv6 overhead, set on the if_ipsec interface; transports
    across the ACP assume 1280.
11. Remote neighbours (8.2): hosts across the Internet (the normal case for SD-WAN edges)
    get **configured remote ACP neighbours**: `IKEv2, any, <console host public address>`
    on every edge (the console host as **hub**, `remote-addr any`, NAT-T enabled) and
    additional edge-to-edge entries where the document already provisions a tunnel; or
    **tunneled remote neighbours** by enabling ACP on the existing SD-WAN tunnel
    interfaces (double encapsulation, but zero new mechanism; restrict channel protocols
    on them against downgrade). This is A.9.6's hub-and-spoke "autonomic L3 transit" and
    connects to rfc7018.md's directory model.

**C. Routing (6.12).**
12. **No FreeBSD RPL implementation exists** (base has none; ports have none; Linux
    implementations such as unstrung or Contiki's are tied to their stacks). Two
    options, both to be stated in the documentation:
    - *Conformant*: implement the ACP RPL profile ourselves in the ACP daemon: ICMPv6
      type 155 DIO/DIS/DAO/DAO-ACK, one instance (ID 0), storing mode MOP 2, OF0 with
      rank_factor 5/1 by link speed, proactive DAO with K flag and 3 retries at 256 ms,
      DIO repetition 2 to 3 times on parent loss, Detaching over Poisoning, ≥ 3 parents,
      No-Path DAO on link break, dead-peer trigger from IKE DPD, administrative
      preference 0b011 for the console host (registrar) so it becomes the DODAG root,
      routes installed via netlink into the ACP FIB/jail, black hole route, unknown
      destination logging at the root. No RPI, no RPL security, no multicast: a few
      thousand lines of C, and it interoperates with any other RFC 8994 node.
    - *Variation per A.8*: run BIRD (already a plugin) in the ACP context with **Babel
      (RFC 8966)** or OSPFv3 over the virtual interfaces, `kernel table <acp fib>`. This
      is explicitly allowed only as an ACP *variation*, not as RFC 8994 conformance
      ("the routing protocol inside the ACP is RPL" is normative); it depends on a
      package (BIRD) for the management plane's survival, and it does not give the
      root-oriented state economy. Record the choice in the certificate's extensions
      field (A.8 suggests certificate parameters for variations) so mixed domains cannot
      form by accident.
    Recommendation: start with the BIRD/Babel variation to get an ACP working fast on
    the lab, keep the RPL profile as the conformance target once the daemon exists, since
    Babel's link-local-only, prefix-announcing, P2P-friendly model maps one-to-one onto
    the RPL profile's externally visible behaviour (one prefix per node, no transit
    prefixes on links).

**D. GRASP in the ACP (6.9) and services.**
13. The ACP GRASP instance: TCP 7017 on the virtual interfaces' link-local addresses for
    M_DISCOVERY/M_FLOOD replication, TLS (TLS 1.3 with TLS_AES_256_GCM_SHA384, mutual
    certificates with the membership check rules 1 to 4) on the ULA for unicast; objectives
    `SRV.est` (console), `AN_join_registrar`-like `arcana:console` locator, and the ASA
    objectives of rfc9222.md. The console learns each host's ACP address from the
    certificate it issued (no discovery needed) and connects cblink **over the ACP ULA**
    first, data plane second: that is the virtual out-of-band channel. cblink's TLS 1.3
    already meets 6.1.
14. NMS access (8.1): the console process runs on an ACP node (its own host's agent);
    give the console host's `acp` jail or FIB a second virtual subnet (8.1.2 "software
    components") or run arcana-console with `setfib` for its agent connections; RPF on the edge is
    the jail's ipfw. A non-Arcana NMS could be attached via an ACP connect interface
    with a Manual-scheme /64 (Z=1, Subnet-ID) and RFC 4191 RIOs from rtadvd.

**E. Operations (9) and telemetry.**
15. `acp` YANG module and cblink ops: adjacency table, channels with protocol/state/last
    error/peer TA, routing table of the ACP, GRASP caches (SRV.est, console locator),
    certificate validity and renewal state, enable flags per interface; faults of type
    `acp` (neighbour lost, certificate failing, no EST server, no default route) raised as
    `sdwan-fault`-style events; the 9.1 dependency-ordered checklist as a console view.
16. **Admin down**: redefine the interface `down` job for ACP-enabled interfaces as
    "data plane filtered by ipfw, physical layer up" (9.3.2) with a `physical-down`
    option that refuses to run over the interface it would cut (the ipfw safe mode
    pattern); "ACP enable [up-if-only]" as a host setting from the console, default on
    for enrolled hosts (brownfield: explicit, which the enrol step is).
17. Time: certificate checks need time; the NTP step runs over the ACP too (6.2.3.1);
    hosts without a trusted clock may use link-local NTP from a neighbour.
18. Lab verification: two vnet jails on epairs (L2 adjacency: DULL, IKEv2, if_ipsec,
    lo1, Babel/RPL, GRASP flood of SRV.est, console cblink over ULA while the data-plane
    route is removed), then three with the console host as hub over a "WAN" jail
    (configured remote neighbours, NAT-T through an ipfw nat jail), then ACP on top of a
    `wg` SD-WAN tunnel (tunneled remote neighbour).

## 4. Cannot be mapped / not applicable

- **BRSKI, IDevID, MASA, vouchers**: general-purpose FreeBSD hosts have no manufacturer
  802.1AR identity or MASA; TPM-backed identities would be a project of their own. The
  token is a "one-touch" registrar mechanism, which 6.11.7.1 permits; conformance claims
  must say "ACP without ANI/BRSKI".
- **RPL as specified**, until implemented: the Babel/OSPFv3 variation is non-conformant by
  design (A.8) and interoperates only with Arcana nodes.
- **L2 switch per-port DULL (7)**: a FreeBSD host bridging with if_bridge(4) cannot
  terminate ff02::13 per member port without kernel work (ng_bridge + ng_ether could
  intercept per hook but that is a research item). Hosts are L3 nodes for the ACP.
- **MACsec and hardware-accelerated IPsec considerations**: FreeBSD has no MACsec; IPsec
  offload is NIC-dependent and irrelevant to the profile.
- **Constrained profile (DTLS-only nodes), CoAP/DTLS GRASP**: no constrained nodes in the
  fleet; DTLS channels stay optional.
- **Multi-access virtual interfaces (6.13.5.2.2)**: with if_ipsec per peer the natural
  model is point-to-point; multi-access would need our own replication logic; P2P is
  allowed and simpler.
- **Mergers of independently grown ACPs, multiple TAs**: single fleet, single CA; keep
  `rsub` free for the day two consoles merge.
- **Hardware admin-down semantics, power considerations of long-haul optics**: software
  hosts; only the ipfw-based admin down applies.

## 5. Checklist Arcana could be measured against

1. Every host and the console hold an X.509v3 certificate from the domain TA with a
   subjectAltName otherName AcpNodeName (`<32hex>[+rsub]@<acp-domain-name>`), EKUs for
   both client and server roles, ECDSA P-256 or RSA ≥ 2048, SHA-256 or better.
2. Nodes validate peers with the five-rule domain membership check (key possession,
   RFC 5280 path to the TA with lifetimes, CRL/OCSP when reachable with closure on later
   discovery, same lowercase acp-domain-name, address present for channels).
3. Nodes with a trusted clock check validity times; nodes without obtain time (NTP over
   the ACP or link-local) before relying on them.
4. Certificates and TAs are renewed via EST over the ACP before 50% of lifetime; at least
   one EST server exists and floods `SRV.est` every 60 s with ttl 210 s and carries
   id-kp-cmcRA; the last server is remembered.
5. The registrar (console) owns a unique 46-bit Registrar-ID, allocates non-colliding
   prefixes from the Zone (default, Zone-ID 0) or Vlong sub-schemes, persists next
   Node-Numbers, never recycles, and preserves a node's address across renewal and
   re-enrolment.
6. The ULA /48 is `fd` + 40-bit SHA-256 of the routing-subdomain; the node's address set
   is derived from the sub-scheme; the loopback holds the first address; a black hole
   route covers the rest; the prefix (/127, /120 or /112) is announced into routing.
7. Each node keeps an adjacency table (Node-ID, interface, link-local address,
   certificate) fed by DULL GRASP and configuration.
8. DULL GRASP runs per enabled interface: M_FLOOD `AN_ACP` with sync-only flags, loop
   count 1, period 60 s, ttl 210 s, initiator = sending link-local, O_IPv6_LOCATOR equal
   to the source, MLDv2 membership of ff02::13, UDP 7017; never inside the ACP.
9. ACP is auto-enabled on native interfaces only; non-native (tunnel) interfaces are
   enabled explicitly with a routing cost; an interface in "down" behaves as admin down
   (physical up, data plane filtered) unless `up-if-only`.
10. All feasible announced channel protocols are attempted; Decider = higher Node-ID;
    Follower passive; initiator failures back off 10 s to 640 s exponentially; responder
    failures never throttle the initiator.
11. Secure channels authenticate with the ACP certificate sent directly, use forward
    secrecy, ≥ 256-bit AEAD, no NULL, and close immediately on peer certificate expiry or
    revocation; the TA may be signalled for diagnostics.
12. IPsec channels: IKEv2, tunnel mode over link-local, TS any, ESP next header 41,
    AES-256-GCM-16 mandatory (no AH, no NULL, no 128-bit keys), DH group 19, digital
    signature authentication method 14 with SHA-512 supported, ID_IPv6_ADDR = ACP
    address matching the certificate; or transport mode with GRE (proto 47) by agreement.
13. The implementation documents its secure channel mechanisms and profile (baseline:
    native IPsec MUST, GRE MAY; constrained: DTLS 1.2).
14. The ACP has its own forwarding and routing context (FIB or vnet jail) created
    automatically, not reachable from data-plane tables, not removable by data-plane
    configuration.
15. Secure channels map to virtual interfaces in that context with SLAAC/ND and
    link-local addresses independent of the data plane; NBMA links are point-to-point.
16. Routing inside the ACP runs the RFC 8994 RPL profile (instance 0, storing mode, OF0,
    rank factor by link speed, proactive DAO with ACK, repair on link events, root
    preference registrar 0b011), or the documentation states the variation (Babel/OSPFv3
    via BIRD) and its non-conformance.
17. An ACP GRASP instance runs: TCP 7017 link-local flooding over per-neighbour
    connections, TLS (1.2 minimum, 1.3 preferred, 256-bit suites, P-256/P-384) with the
    membership check for unicast on the ACP address; no link-local addresses in
    objectives; ASAs survive the absence of an ACP.
18. MTU of channels derived from link MTU minus overhead; no PMTUD on channels.
19. Non-ACP management hosts attach via ACP connect (Manual sub-scheme, RPF filtering,
    RIOs) or as software components with a trusted internal subnet; the console reaches
    agents over the ACP first.
20. Remote neighbours across non-ACP L3 are supported as configured (method, local,
    remote, pmtu; hub with remote any; NAT-T) and as tunneled (GRE at least) neighbours,
    with the option to restrict channel protocols on tunnels.
21. Diagnostics answer the 9.1 questions locally and non-volatilely: enablement, time,
    keying material, certificate validity and CRL freshness, context created, interfaces
    enabled, DULL sent/received, objective seen, neighbour MAC, last attempt and failure
    reason (TA, domain, revocation, expiry, protocol), channels, routing, default route,
    GRASP running, SRV.est cached.
22. The ACP appears in no running configuration except enable switches and the
    non-autonomic exceptions (certificate provisioning, ACP connect, remote neighbours).
23. Management-plane services on hosts listen on the ACP only where possible; services
    across the ACP use end-to-end authentication (TLS with domain certificates) because
    source addresses are spoofable inside.
24. Compromised nodes are removed by revocation or non-renewal; registrar and EST
    components are hardened like a CA; roles (console, registrar, edge) are expressed in
    certificates.
25. A YANG model of the ACP state (adjacency table, channels, GRASP caches, routes) is
    exposed through the management interface.

## 6. Open decisions and trade-offs

- **RPL implementation vs BIRD/Babel variation.** Conformance and independence from a
  package versus time to a working management overlay. A staged plan (Babel first, RPL
  later, both selectable by a certificate extension) keeps both doors open; mixing them in
  one domain must be prevented.
- **FIB vs vnet jail as the ACP context.** The jail is the RFC's preferred "logical
  container" and prevents data-plane configuration from touching the ACP, but moves
  strongSwan/if_ipsec and the agent's listener into a jail and complicates the AF_UNIX
  path; the FIB is simpler but shares interfaces and sockets with the data plane.
- **strongSwan (package) vs a native IKEv2.** The ACP's survival would depend on a
  package; FreeBSD base has no IKE daemon. Alternatives: racoon (ports, IKEv1 only, not
  allowed), iked from OpenBSD (ports: `security/openiked`; IKEv2, certificate auth,
  supports if_ipsec via reqid? to verify), or a minimal IKEv2 of our own (large). The
  DTLS channel in our own daemon avoids any IKE dependency but needs a tun(4) tunnel and
  the constrained profile is not interoperable with baseline-only peers.
- **Token enrolment vs BRSKI-like zero-touch.** Without IDevIDs there is no voucher; the
  question is how much TOFU to accept: fingerprint-in-command and join proxies reduce it;
  a TPM-backed per-host identity later would enable a BRSKI-shaped flow with the console
  as MASA.
- **Short-lived certificates vs CRLs.** Short lifetimes (days) with EST renewal are
  simpler and self-healing but make a console outage lethal after the lifetime; a CRLDP
  on the console's ULA plus longer lifetimes is more forgiving. Combine: medium lifetime
  (30 days), renewal at 50%, CRL for emergencies.
- **Hub-and-spoke over the Internet vs ACP over SD-WAN tunnels.** Configured remote
  neighbours to the console host are independent of the SD-WAN data plane (the point of
  the ACP) but add an IPsec association per edge to the console host; tunneled neighbours
  reuse what exists but fall with the tunnel they ride.
- **Who is the DODAG root / hub.** The console host by preference 0b011; a second hub
  (standby console or a route reflector host) for resilience, which the single-DODAG RPL
  profile handles by re-election, not by optimal routing.
- **Vlong V bits for jails**: addressing each vnet jail from the host's /120 is elegant
  (jails become ACP-reachable without their own channels) but requires routing inside
  the host between the ACP context and jail epairs; alternatively each jail is its own
  ACP node with its own certificate.
- **How much of the existing data-plane IPsec to reuse**: raw-key strongSwan connections
  for data tunnels can stay; the ACP's connections must be certificate-authenticated. Two
  authentication models in one daemon are fine but the conf.d ownership must be clear.
