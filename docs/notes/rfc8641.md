# RFC 8641 — Subscription to YANG Notifications for Datastore Updates (YANG-Push)

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8641.txt (September 2019, Standards Track, 3251 lines, read in full).

## Purpose
Replaces polling with subscriptions to a *datastore* (not an event stream): a subscriber
selects nodes (subtree or XPath filter) in a datastore (any `ds:datastore` identity) and
receives either periodic snapshots (`push-update`) or on-change deltas
(`push-change-update`, YANG Patch encoded). Augments RFC 8639's RPCs, subscription list,
filters and state-change notifications; adds `resync-subscription`.

## Concepts (sections 2–3)
- datastore node update, update record, update trigger, selection filter, periodic vs
  on-change subscription.
- Periodic: `period` (centiseconds) + optional `anchor-time` (updates at anchor + n·period;
  if absent, anchor = time of the first update).
- On-change (feature `on-change`): `dampening-period` (min interval between update
  records for the subscription as a whole; at the end of the period the *current* values of
  all changed objects are sent — churn that returns to the original value is still
  reported as a no-op change), `excluded-change` (leaf-list of change-type: create, delete,
  insert, move, replace), `sync-on-start` (default true: an initial `push-update` snapshot;
  false: only deltas, no resync possible).
- Negotiation: a declined RPC SHOULD carry hints (`period-hint`, `filter-failure-hint`,
  `object-count-estimate/limit`, `kilobytes-estimate/limit`) in yang-data
  `establish-subscription-datastore-error-info` / `modify-subscription-datastore-error-info`
  / `resync-subscription-error` (the tree diagrams in Figure 9 call them
  `establish-subscription-error-datastore` etc.; the module uses the `-datastore-error-info`
  names).
- On-change may be unsupported for some objects (counters); a publisher MAY accept the
  subscription and silently omit those objects, or reject (`on-change-unsupported`).
  Which objects are on-change-capable should be discoverable (future
  notification-capabilities draft, now RFC 9196).
- Update record construction for on-change: set A (before / start of dampening), set B
  (after / end of dampening), both after filtering and access control; build a YANG Patch
  (RFC 8072) A → B; cancelled-out changes are still included as the last change (a
  `create` of an existing node or a `replace` with the same value is *valid* in YANG-Push,
  unlike RFC 8072); send if non-empty. Create→delete during dampening reports `delete`;
  delete→create reports `create`.
- Reliability: a publisher MUST notify receivers when it cannot keep the terms:
  `incomplete-update` flag on `push-update`/`push-change-update`; MAY suspend
  (`subscription-suspended`), MUST suspend if it cannot create an update record at all;
  on resume SHOULD send a complete patch, or a full `push-update` if sync-on-start, else
  `incomplete-update` on the next delta. Update records MUST NOT be resequenced. Loss of
  transport terminates (dynamic) or suspends (configured). Publishers SHOULD decline
  requests they are unlikely to fulfil.
- Encodings: periodic update = what a retrieval with the same filter would return;
  on-change = YANG Patch operations: `create` (new objects, except entries of
  user-ordered lists), `delete`, `replace` (value change), `insert` (new entry in a
  user-ordered list), `move` (reorder). `patch-id` SHOULD be a counter from 0,
  reset on every `push-update` resync and after 4294967295.
- Selection filters: `datastore-subtree-filter` (RFC 6241 §6, feature sn:subtree) or
  `datastore-xpath-filter` (node-set result; non-node-set = selects nothing; context node =
  root of the target datastore; prefixes = module names; feature sn:xpath). A publisher
  MUST support at least one. Only one filter per subscription.
- Receiver authorization (3.9): each push MUST have NACM read access applied; unauthorized
  nodes silently omitted; empty periodic result → an empty `push-update` MUST still be sent;
  empty on-change → MUST NOT send; filtered changes MUST NOT affect dampening; a selection
  that can never match → `unchanging-selection` may reject/terminate; lost access SHOULD
  appear as a patch `delete`.
- YANG library: the receiver is expected to know the publisher's YANG library; module
  changes come through `yang-library-change`/`yang-library-update`.

## Trees (section 4) verbatim
Augmentations to ietf-subscribed-notifications:
```
module: ietf-subscribed-notifications
  +--rw filters
  |  +--rw yp:selection-filter* [filter-id]
  |     +--rw yp:filter-id                   string
  |     +--rw (yp:filter-spec)?
  |        +--:(yp:datastore-subtree-filter)
  |        |  +--rw yp:datastore-subtree-filter?   <anydata> {sn:subtree}?
  |        +--:(yp:datastore-xpath-filter)
  |           +--rw yp:datastore-xpath-filter?     yang:xpath1.0 {sn:xpath}?
  +--rw subscriptions
     +--rw subscription* [id]
        +--rw (target)
        |  +--:(stream) ...
        |  +--:(yp:datastore)
        |     +--rw yp:datastore                     identityref   (base ds:datastore, mandatory)
        |     +--rw (yp:selection-filter)?
        |        +--:(yp:by-reference)
        |        |  +--rw yp:selection-filter-ref          selection-filter-ref
        |        +--:(yp:within-subscription)
        |           +--rw (yp:filter-spec)?
        |              +--:(yp:datastore-subtree-filter)
        |              |  +--rw yp:datastore-subtree-filter?   <anydata> {sn:subtree}?
        |              +--:(yp:datastore-xpath-filter)
        |                 +--rw yp:datastore-xpath-filter?     yang:xpath1.0 {sn:xpath}?
        +--rw (yp:update-trigger)
           +--:(yp:periodic)
           |  +--rw yp:periodic!
           |     +--rw yp:period         centiseconds   (mandatory)
           |     +--rw yp:anchor-time?   yang:date-and-time
           +--:(yp:on-change) {on-change}?
              +--rw yp:on-change!
                 +--rw yp:dampening-period?   centiseconds   (default 0)
                 +--rw yp:sync-on-start?      boolean        (default true)
                 +--rw yp:excluded-change*    change-type
```
The same `(yp:datastore)` case and `(yp:update-trigger)` choice augment
`establish-subscription/input` (full update-policy), `modify-subscription/input`
(update-policy-modifiable: period/anchor-time, dampening-period only — sync-on-start and
excluded-change are not modifiable), `subscription-started` and `subscription-modified`.

New in ietf-yang-push:
```
rpcs:
  +---x resync-subscription {on-change}?
     +---w input +---w id    sn:subscription-id
yang-data: resync-subscription-error, establish-subscription-datastore-error-info,
           modify-subscription-datastore-error-info
  +--ro reason?                identityref
  +--ro period-hint?           centiseconds
  +--ro filter-failure-hint?   string
  +--ro object-count-estimate? uint32
  +--ro object-count-limit?    uint32
  +--ro kilobytes-estimate?    uint32
  +--ro kilobytes-limit?       uint32
notifications:
  +---n push-update
  |  +--ro id?                   sn:subscription-id
  |  +--ro datastore-contents?   <anydata>
  |  +--ro incomplete-update?    empty
  +---n push-change-update {on-change}?
     +--ro id?                   sn:subscription-id
     +--ro datastore-changes
     |  +--ro yang-patch                    (uses ypatch:yang-patch, RFC 8072)
     |     +--ro patch-id    string
     |     +--ro comment?    string
     |     +--ro edit* [edit-id]
     |        +--ro edit-id      string
     |        +--ro operation    enumeration   create|delete|insert|merge|move|replace|remove
     |        +--ro target       target-resource-offset   (api-path relative to the datastore)
     |        +--ro point?       target-resource-offset
     |        +--ro where?       enumeration   before|after|first|last
     |        +--ro value?       <anydata>
     +--ro incomplete-update?    empty
```
Identities (errors): `cant-exclude`, `datastore-not-subscribable` (also a terminated
reason), `no-such-subscription-resync`, `on-change-unsupported`,
`on-change-sync-unsupported`, `period-unsupported` (also suspended reason),
`update-too-big` (also suspended), `sync-too-big` (also suspended, also resync error),
`unchanging-selection` (also terminated reason). Typedefs: `change-type` enumeration,
`selection-filter-ref` (leafref `/sn:filters/yp:selection-filter/yp:filter-id`),
`centiseconds` (uint32). Module `ietf-yang-push@2019-09-09` (prefix yp) imports yang, sn,
ds, rc, ypatch (RFC 8072 `ietf-yang-patch`).

Example messages: periodic
`<push-update><id>1011</id><datastore-contents><interfaces>…<oper-status>up</oper-status>…</datastore-contents></push-update>`;
on-change `<push-change-update><id>89</id><datastore-changes><yang-patch><patch-id>0</patch-id><edit><edit-id>edit1</edit-id><operation>replace</operation><target>/ietf-interfaces:interfaces</target><value>…</value></edit></yang-patch></datastore-changes></push-change-update>`.

## What this means for Arcana
1. **The console polls today** (jobs once a second, stats, lists). YANG-Push replaces that:
   periodic subscriptions to `<operational>` for stats (`period 100` = 1 s) and on-change
   subscriptions for jail state, service state, job trace, interface oper-status, routes.
   The agent must therefore keep an in-memory operational tree (or a cached snapshot)
   to diff against — kqueue/devd/rtsock/netlink events give the triggers (interface and
   route changes via `PF_ROUTE`/netlink multicast; jail creation via `jail_get`
   polling or devd `JAIL` events? there is no jail event source in base, so periodic
   polling inside the agent; services via `service status` polling; jobs via the queue
   itself).
2. **On-change requires YANG Patch (RFC 8072) encoding** — one more module
   (`ietf-yang-patch`) and its `target-resource-offset` = api-path strings even in CBOR
   (the `target` leaf is a string type, so in YANG-CBOR it stays a text api-path, not an
   instance-identifier; this is a known inefficiency; CORECONF has no YANG-Push binding yet).
   The `value` anydata is encoded per 9254 §4.5 with deltas relative to the anydata node —
   so inside `value` either the root SID is absolute (tag 47) or the value's top-level
   deltas are computed against SID(`value`): the generator must handle anydata roots.
3. The cblink transport binding: `push-update`/`push-change-update` are ordinary
   notifications; sending them on a per-subscription cblink push stream gives ordered,
   flow-controlled delivery; the stream's credit exhaustion is exactly `update-too-big` /
   `unsupportable-volume` → `subscription-suspended`, and reopening with
   `resync-subscription` → `push-update`. The console translates them to SSE
   `{"ietf-restconf:notification": {"eventTime": …, "ietf-yang-push:push-update": {...}}}`
   for the browser (RESTCONF-notif binding).
4. Validation side: `datastore-xpath-filter` needs the XPath evaluator returning node-sets
   over the operational tree; subtree filters are structural and cheap — start with
   subtree, add XPath when the evaluator exists for must/when anyway.
5. NACM read access per push record is required; with Arcana's single-user model this
   reduces to "console is admin", but the hook must exist in the generated server glue.
