# RFC 8791 — YANG Data Structure Extensions (sx:structure)

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8791.txt (June 2020, Standards Track, updates 8340, 700 lines, read in full).

## Purpose
Defines abstract data structures in YANG that are *not* datastore contents: protocol
message parts, file formats, error payloads. Replaces RFC 8040's `rc:yang-data` (limited to
a single top-level container) with `sx:structure` (any data-def content, may be nested
elsewhere, can be augmented from other modules with `sx:augment-structure`). Used by
RFC 9595 (`sid-file`), CORECONF (`error`), and is the natural tool for cblink's own
framework messages (hello, error, credit...).

## Module ietf-yang-structure-ext@2020-06-17 (prefix sx)
- `extension structure { argument name { yin-element true; } }`
  - Only as a top-level statement (module/submodule).
  - Substatements: `*must-stmt [status] [description] [reference] *(typedef/grouping)
    *data-def-stmt`.
  - Shares the identifier namespace with sibling data nodes, rpcs, notifications (7950
    §6.2.1 bullet 7): a structure cannot have the same name as a top-level data node.
  - **Encoded exactly like an `anydata` node**: the structure's name is encoded as a
    container, children as its children. JSON: `"example-errors:my-error": {"error-number": 131}`.
    CBOR (RFC 9254 §5): `{ SID(structure): { delta: value, ... } }`.
  - The module name/namespace of the defining module applies to the children.
  - XPath document element = the extension statement itself; children of the document root
    are the data-def substatements. Context for must, when, path, min/max-elements,
    mandatory, unique, ordered-by, instance-identifier.
  - Constraints relaxed: `list` need not have a `key`; `config` is ignored.
  - Does NOT define a media type; a specification using it MUST specify the encoding.
- `extension augment-structure { argument path { yin-element true; } }`
  - Top-level only; path = absolute-schema-nodeid whose first node names the structure.
  - Substatements: `[status] [description] [reference] 1*(data-def-stmt / case-stmt)`.
  - Context node derived like `augment`; same relaxations (keyless lists, config ignored).
  - Needed because a plain `augment` cannot target a structure (tools need not understand
    the extension).
- Tree diagrams (updates RFC 8340): new sections `structure <name>:` and
  `augment-structure <path>:`, nodes without flags (no rw/ro).

## Examples
```
module: example-module
  structure address-book:
    +-- address* [last first]
       +-- last      string
       +-- first     string
       +-- street?   string
       +-- city?     string
       +-- state?    string
module: example-module-aug
  augment-structure /exm:address-book/exm:address:
    +-- county?    string
    +-- zipcode?   string
```
JSON: `"example-module:address-book": {"address": [{"city": "Bedrock", "example-module-aug:zipcode": "70777", "first": "Fred", "last": "Flintstone", "street": "301 Cobblestone Way"}, ...]}`.
A.5: a structure used as `<error-info>` content inside an rpc-error.

## Relevance to cblink
1. **All of cblink's framework-level payloads can be modelled as structures** in a module
   `cblink` (or `ietf-`-style `cblink-framework`): `structure hello { limits {...}; impl }`,
   `structure error { code, message, path (instance-identifier), missing (SID) , cookie }`,
   `structure credit { increment }`, `structure close { code, message }`, `structure family-info
   {...}` (if a family concept survives), `structure subscription {...}`. They get SIDs like
   any other item, are encoded per RFC 9254 §5 as `{SID: {…}}` and the framework keys stop
   being ad hoc negative integers.
2. Error reporting: reuse `ietf-coreconf`'s `sx:structure error` (SID 1024, with
   error-tag/error-app-tag identities 1001..1023) directly or define `cblink:error` with an
   `augment-structure` adding errno/cookie. Reusing ietf-coreconf's gives standard identities
   for free.
3. RPC-ish messages that are not datastore operations (e.g. the generated
   `P_<stream>_data` payloads of a cblink stream) are structures too: a stream's payload set
   becomes `sx:structure <name>-data`.
4. Generator: cblink-gen must recognise the `sx:structure` and `sx:augment-structure`
   extension statements (and RFC 8040's `rc:yang-data` for `ietf-restconf`) — they are
   `unknown-statement`s in the YANG grammar but with data-def bodies; the parser must treat
   their bodies as schema nodes.
