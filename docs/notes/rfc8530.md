# RFC 8530 — YANG Model for Logical Network Elements (ietf-logical-network-element)

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8530.txt (March 2019; 2289 compact lines, read in full).

## Purpose
An LNE is an independently managed virtual network device hosted by a parent device
("guest"/"host" analogy to VMs): own interfaces (possibly renamed), own YANG library, own
management servers, own routing tables, no name clashes with the host or other LNEs. The
module lists LNEs, assigns host interfaces to them (`bind-lne-name` augment of
`ietf-interfaces`) and exposes each LNE's whole data tree under a schema mount point `root`
when the host is allowed to manage it (`managed` true). Companion of RFC 8529 (NIs inside
an LNE). Vendor terms: logical system, logical router, virtual switch/chassis/fabric.

## Module ietf-logical-network-element@2019-01-25 (prefix lne)
Imports if, yangmnt. `name` string (key); `managed` boolean default true ("may not be
modifiable in all implementations"); `description`; container `root` with
`yangmnt:mount-point "root"` — "SHALL always contain a YANG library and interfaces
instance"; when `managed` is false any access below root SHALL fail with error-tag
`access-denied`, error-app-tag `lne-not-managed`. Augment `bind-lne-name` leafref; failure
→ `operation-failed` / `lne-assignment-failed` + error-info; asynchronous failure →
`bind-lne-name-failed` notification (`name` and `bind-lne-name` both mandatory).

## Rules (section 3)
- Creating a list entry instantiates an LNE; deleting destroys it (7950 §7.8.6).
- On successful interface assignment the implementation MUST create a system-created
  interface inside the LNE (name is a local matter; may be identical or mapped), exposed via
  the LNE's `ietf-interfaces`.
- LNE view (3.2): managed through its own servers with its root as device root; the
  LNE's YANG library lists its modules; only LNE resources appear; indistinguishable from a
  physical device.
- Host view (3.3): `managed` true ⇒ LNE info SHALL be accessible from the host context via
  `root` with paths modified per RFC 8528; if the schema-mount entry has `config true` it
  SHALL also be modifiable from the host; the same information MUST be presented in both
  views. `inline` or `shared-schema` are both allowed; `inline` is expected when `managed`
  is always false; with `shared-schema` the YANG library under each `root` MUST match the
  schema-mount definition. Beyond yang-library and interfaces, any module may be present.
- Security: `managed` deserves attention in multi-tenant setups (tenant may not want the
  host operator to see inside); `bind-lne-name` changes are like physically pulling a card.

## FreeBSD mapping: VNET jails as LNEs
A VNET jail (`vnet` parameter, `VIMAGE` kernel, default in GENERIC since 12.0) has its own
complete network stack: interfaces, addresses, routing tables (all FIBs), ARP/ND caches,
sockets, pf/ipfw instance, sysctl `net.*` values — exactly an LNE. Interfaces are moved into
it with `ifconfig <if> vnet <jail>` (`SIOCSIFVNET`, `ifr_jid`) and back with `-vnet`
(`SIOCSIFRVNET`); jail.conf `vnet.interface = "epair0b"` does it at start; `exec.prestart`
creates epairs/bridges. Non-VNET jails share the host stack (restricted to `ip4.addr`
aliases) and are **not** LNEs.

Naming (3.1): FreeBSD keeps the interface name across the vnet move (epair0b is epair0b
inside) unless renamed with `ifconfig name`; jail.conf `vnet.interface` only accepts the
existing name. The RFC's `cust1:eth1` host naming convention is optional.

Error mapping: `lne-not-managed` → cblink CODE EACCES with error-app-tag; `lne-assignment-
failed` → EIO/ENXIO with MSG.

Event sources: jail creation/removal — the kernel tells it: kqueue(2)'s `EVFILT_JAIL`
(FreeBSD 15), `NOTE_JAIL_CHILD` on a prison with the new child's jid, `NOTE_JAIL_REMOVE`
when one goes; the agent watches the host's prison and each jail for both
(`ira/jailwatch.c`, events of kind `jail-state`), so nested jails are told too. No
jail.conf hooks are needed (devd has no jail events; polling `jail_get` would miss a
quick restart). Interface moves: rtsock
`RTM_IFANNOUNCE` with `IFAN_DEPARTURE` in the host and `IFAN_ARRIVAL` in the jail's vnet
(a rtsock inside the jail is needed to see the arrival).

## Relevance to the cblink/YANG design
- Arcana's `jail` family (list/action/create) becomes: `arcana-jails:jails/jail[name]`
  (all jail params as leaves, generated from `jail(8)` parameter list) **plus**, for VNET
  jails, an `ietf-logical-network-element` entry whose `root` mounts the network modules.
  Rather than duplicate the list, augment `lne:logical-network-element` with
  `arcana-jails:jail-ref` or make `arcana-jails:jail` the LNE (`yangmnt:mount-point "root"`
  directly on the jail list entry — RFC 8528 allows any list to carry a mount point; using
  the IETF LNE module is the interoperable choice).
- Two mount points in one agent: `lne:root` (per VNET jail, shared-schema) and `ni:vrf-root`
  (per FIB, shared-schema), nested (NIs inside LNE root). Generator must support nested
  mounts and generate the mounted schema's `yang-library` instance per mount.
- On the wire: a request for `/lne:logical-network-elements/logical-network-element[name='j1']/root/if:interfaces`
  in CBOR is an instance-identifier `[SID(root), "j1"]`-rooted FETCH; the agent dispatches
  by attaching to the jail. cblink `PATH` framework attribute today is an array path —
  maps exactly onto a SID instance-identifier.
