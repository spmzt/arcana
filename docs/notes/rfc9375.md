# RFC 9375 — A YANG Data Model for Network and VPN Service Performance Monitoring

Source read in full: `scratchpad/rfc/rfc9375.txt` (2005 lines, April 2023,
Standards Track, OPSAWG). Supporting texts read: RFC 8345 §4 (model
structure, design decisions: unidirectional links, presence containers for
network types, require-instance false, URI ids, NMDA origin) and the
`ietf-network` / `ietf-network-topology` trees; RFC 8346 §4–§6 (the L3
unicast topology module, as the pattern of a network-type augmentation
with `when`, `choice`, `leaf-list`, notifications); RFC 9181 identities
(service-type, vpn-topology, role, protocol-type) and `vpn-id`; RFC 8776
for nothing here (not imported). Measurement protocols are discussed from
the RFCs 9375 cites (OWAMP 4656, TWAMP 5357, STAMP 8762, Y.1731, IOAM 9197,
BGP-LS 8571, MPLS LM/DM 6374) and from RFC 9341/9342 (Alternate Marking)
which 9375 does **not** cite.

---

## 1. Purpose and where it sits

- Defines `ietf-network-vpn-pm` (prefix `nvp`), a **pure augmentation** of
  RFC 8345's `ietf-network` and `ietf-network-topology`. It adds *no*
  top-level container, *no* RPC, *no* notification, *no* feature: it hangs
  PM configuration (percentiles, measurement interval, which VPN PM method)
  and PM state (loss/delay/jitter statistics per link, octet/packet counters
  per termination point, route/MAC counts per node) onto an existing
  topology instance.
- Position (§3, Figure 1): between the **Service Orchestrator** and the
  **Network Controller**, beside the network service models (L3NM RFC 9182,
  L2NM RFC 9291). The controller first builds topology visibility (RFC 8345
  networks, SAPs, L3NM/L2NM), then *derives* network or VPN PM data "by
  aggregating (and filtering) lower-level data collected via monitoring
  counters of the devices". So the model describes what a **controller
  exposes northbound**; devices supply raw measurements by OWAMP/TWAMP/STAMP/
  MPLS LM-DM/IOAM, TED (BGP-LS) or LMAP.
- Two layers in one list: when a `network` entry has the `service` presence
  container under `network-types`, its PM is **VPN-service PM** (abstract
  links between PEs = tunnels or inter-access-interface connections); when
  absent, it is **underlay network PM** (topology links, ports).
- Retrieval: YANG-Push subscriptions (RFC 8641 periodic / on-change / replay,
  RFC 8632 alarms for thresholds) or on-demand NETCONF/RESTCONF GET filtered
  by link-id (§3.1–3.2).
- All link metrics are **one-way** and **unidirectional** (RFC 8345 links
  are unidirectional; a bidirectional tunnel is two links).
- **In Arcana terms**: the console is the Network Controller; each SD-WAN
  service is one `network` with `service` present (plus one underlay
  network for the edges' UCS/FIB-0 view); the console's Paths tab is the
  consumer. The agent is the measurement source (ICMP probes today, a STAMP
  reflector/sender tomorrow) and the counter source (if_data). The cblink
  family would carry the *per-edge* slice: per tunnel-end link statistics,
  per interface TP statistics, per FIB route counts — in exactly the shapes
  of the groupings so the console only aggregates.

Note the tree hides four details visible only in the YANG: (1) `role` is
augmented `when '../nw:network-types/nvp:service'`; (2) `vpn-pm-type` is a
*separate* augment of `/nt:link/perf-mon` with the same `when`; (3)
`vpn-network-access` is a separate augment of `pm-statistics` with
`when '../../../nw:network-types/nvp:service'`; (4) `vpn-tunnel-type` is
`config false` inside the `config true` presence container `vpn-tunnel`
(the client enables tunnel PM; the system reports the tunnel type).

### 2.4 The RFC 8345 base being augmented (verbatim, RFC 8345 §4.1–4.2)

```
   module: ietf-network
     +--rw networks
        +--rw network* [network-id]
           +--rw network-id            network-id
           +--rw network-types
           +--rw supporting-network* [network-ref]
           |  +--rw network-ref    -> /networks/network/network-id
           +--rw node* [node-id]
              +--rw node-id            node-id
              +--rw supporting-node* [network-ref node-ref]
                 +--rw network-ref
                 |       -> ../../../supporting-network/network-ref
                 +--rw node-ref       -> /networks/network/node/node-id

   module: ietf-network-topology
     augment /nw:networks/nw:network:
       +--rw link* [link-id]
          +--rw link-id            link-id
          +--rw source
          |  +--rw source-node?   -> ../../../nw:node/node-id
          |  +--rw source-tp?     leafref
          +--rw destination
          |  +--rw dest-node?   -> ../../../nw:node/node-id
          |  +--rw dest-tp?     leafref
          +--rw supporting-link* [network-ref link-ref]
             +--rw network-ref
             |       -> ../../../nw:supporting-network/network-ref
             +--rw link-ref       leafref
     augment /nw:networks/nw:network/nw:node:
       +--rw termination-point* [tp-id]
          +--rw tp-id                           tp-id
          +--rw supporting-termination-point*
                  [network-ref node-ref tp-ref]
             +--rw network-ref
             |       -> ../../../nw:supporting-node/network-ref
             +--rw node-ref
             |       -> ../../../nw:supporting-node/node-ref
             +--rw tp-ref         leafref
```

`network-id`, `node-id`, `link-id`, `tp-id` are all `inet:uri`. Every
leafref in RFC 8345 carries `require-instance false` (§4.4.3) so an overlay
may dangle while the underlay churns; a dangling object is dropped from
`<operational>` but kept in `<intended>`. Links are point-to-point and
unidirectional (§4.4.5); multihoming/aggregation = several links plus a
higher-layer link supported by them (§4.4.6). The companion RFC 8346
(`ietf-l3-unicast-topology`, prefix `l3t`) shows the canonical pattern:
presence container `l3-unicast-topology!` under `network-types`, `when`
guards on every augment, node attributes (`name inet:domain-name`,
`flag*` identityref leaf-list, `router-id* rt-types:router-id`,
`prefix* [prefix] {prefix inet:ip-prefix, metric uint32, flag*}`), link
attributes (`name`, `flag*`, `metric1/metric2 uint64`), TP
`choice termination-point-type { case ip {ip-address* inet:ip-address}
case unnumbered {unnumbered-id uint32} case interface-name {interface-name
string} }`, and four notifications (`l3-node-event`, `l3-link-event`,
`l3-prefix-event`, `termination-point-event`) each carrying
`l3-event-type enumeration {add, remove, update}` plus the object's
reference and attributes.

### 2.5 Identities, typedefs and groupings in the module

| Kind | Name | Definition |
|---|---|---|
| identity | `node-type` → `pe`, `p`, `asbr` | PE: edge with customer-facing function; P: core router without customer interfaces; ASBR (RFC 4364). |
| identity | `pm-source-type` → `pm-source-bgpls` (RFC 8571), `pm-source-owamp` (RFC 4656), `pm-source-twamp` (RFC 5357), `pm-source-stamp` (RFC 8762), `pm-source-y-1731` (ITU-T Y.1731), `pm-source-ioam` (RFC 9197) | "The OAM tool used to collect the PM data." **These six are the only base values.** There is no identity for ICMP echo/ping, Alternate Marking (RFC 9341/9342), IPFIX, MPLS LM/DM (RFC 6374, though cited in §3), or plain "bgp". Any of those must be a new identity with `base nvp:pm-source-type` in an augmenting module. |
| identity | `pm-type` → `pm-type-network-link`, `pm-type-vpn-inter-access`, `pm-type-vpn-tunnel` | Key of the `pm` list. |
| typedef | `percentage` | `decimal64 { fraction-digits 5; range "0..100"; }` |
| typedef | `percentile` | `decimal64 { fraction-digits 3; range "0..100"; }` — "95.000 → 95 % of samples ≤ value" |
| grouping | `entry-summary` | config-false container with ipv4-num / ipv6-num / mac-num |
| grouping | `link-loss-statistics` | container loss-statistics {packet-loss-count counter64, loss-ratio percentage} |
| grouping | `link-delay-statistics` | container delay-statistics {unit-value identityref base lime:time-unit-type default lime:milliseconds; min/max/low/intermediate/high gauge64} |
| grouping | `link-jitter-statistics` | same shape for IPDV (RFC 3393) |
| grouping | `tp-svc-telemetry` | last-updated date-and-time (config false) + 13 counter64 leaves |
| from RFC 9181 | `vpn-common:vpn-id` = `string`; `service-type` → l3vpn, vpls, vpws, vpws-evpn, pbb-evpn, mpls-evpn, vxlan-evpn; `vpn-topology` → any-to-any, hub-spoke, hub-spoke-disjoint, custom; `role` → any-to-any-role, spoke-role, hub-role, custom-role; `protocol-type` → ip-in-ip {ip-in-ipv4, ip-in-ipv6}, gre {gre-v4, gre-v6}, vxlan-trans, geneve, ldp, mpls-in-udp, sr {sr-mpls, srv6, sr-mpls-over-ip}, rsvp-te, bgp-lu, unknown | Note: no `sd-wan` service type, no `wireguard`/`ipsec` protocol type. |
| from RFC 8532 | `lime:time-unit-type` → hours, minutes, seconds, milliseconds, microseconds, nanoseconds | unit of delay/jitter values |

Editorial nits worth knowing when implementing: §4.4 prose says the default
high percentile is the **90th**, the module says `default "95.000"` (the
module is normative); Appendix A.2's JSON uses the prefix
`"ietf-network-pm:perf-mon"` which is not the module's name
(`ietf-network-vpn-pm`); A.1 subscribes with `"period": "500"` (YANG-Push
periods are centiseconds → 5 s).

## 3. Every container/list/significant leaf: meaning and candidate Arcana realisation

Arcana vocabulary as in rfc9731.md. FreeBSD counter names are the
`struct if_data` fields returned by `getifaddrs(3)` (AF_LINK `ifa_data`) or
`sysctl NET_RT_IFLIST`, also printed by `netstat -ibdW --libxo json`.

### 3.1 Network level — `network-types/service!`

| Node | Meaning | Arcana realisation | Gap |
|---|---|---|---|
| `service` presence container | Present → this `network` entry is a VPN service topology to be monitored; absent → underlay network PM. | One `network` per **SD-WAN service** (service present) + one **underlay** network per routing domain of interest (UCS/FIB 0: edges as nodes, WAN uplinks as TPs, the probed edge-to-edge underlay paths as links). Console builds both from the document. | Agent: none (it does not hold networks); but every agent reply must say *which service/network* a measurement belongs to (service id on every tunnel/link record). |
| `service-type` identityref base `vpn-common:service-type`, **mandatory** | L3VPN, VPLS, VPWS, EVPN variants. | SD-WAN is an L3 service with its own data plane; closest standard value `vpn-common:l3vpn`. Better: define `arcana:sd-wan { base vpn-common:service-type; }`. | Decision needed (see §7). |
| `vpn-id` vpn-common:vpn-id (string) | Correlates with the L3NM/L2NM service instance. | The service document's id. | — |
| `vpn-service-topology` identityref base `vpn-common:vpn-topology` | any-to-any / hub-spoke / hub-spoke-disjoint / custom. | MEF 70.2 service topology in the document (full mesh = any-to-any; hub-and-spoke; disjoint spokes). | — |

### 3.2 Node level

| Node | Meaning | Arcana realisation | Gap |
|---|---|---|---|
| `node-type` identityref base `node-type` (pe / p / asbr) | So that PM "between any two nodes that each have a specific node type" can be reported. | Edge host = `pe`. The control-plane host (BIRD route reflector) carries no data plane; model it as `p` if it is in the underlay network at all. A breakout host = `asbr` is a stretch (it is the boundary to the Internet). | Host facts (`hello`) could carry a `node-type`/role so the console does not infer it. |
| `entry-summary` (config false) | Route/MAC table sizes. | **Per FIB on the edge**: `total-active-routes` = count of the routing table of that FIB (`netstat -rn -F <fib> --libxo json`, or rtsock `NET_RT_DUMP` with the fib, counting RTF_UP entries per family). `maximum-routes`: FreeBSD has no per-FIB route limit; leave absent or report 0 = unlimited (semantics undefined by the RFC: "maximum number of IPv4 routes for the VPN or network" — presumably a configured limit; omit). | Agent's `network` reply already lists routes; add a cheap `route-count {fib, ipv4, ipv6}` reply rather than dumping. |
| `entry-summary/mac-num` | MAC table size (L2VPN). | Only if a service is L2 (geneve/vxlan into `bridge(4)`): `ifconfig bridgeN addr` count = total, `ifconfig bridgeN maxaddr` (default 2000) = maximum. For today's L3 SD-WAN: absent. | — |
| `role` identityref base `vpn-common:role`, default `any-to-any-role`, `when service` | The node's role in the VPN topology. | Hub / spoke edge in a hub-spoke service; any-to-any otherwise. Known to the console from the document. | — |

### 3.3 Link level — `perf-mon` (config part)

| Node | Meaning | Arcana realisation | Gap |
|---|---|---|---|
| `nt:link` itself (unidirectional, [link-id], source{node,tp} → destination{node,tp}) | For a service network: the abstract PE–PE link (tunnel or inter-access connection). For the underlay: the topology link. | **Two links per Arcana tunnel** (A→B and B→A), source-tp = the tunnel interface (or UNI) on A, dest-tp on B. For the underlay network: the WAN path between edge A's uplink and edge B's uplink (what the probe actually traverses). | Agent must name its tunnel ends with stable TP ids (ifindex/ifname + host) and the far end (remote address) so the console can build both links. |
| `low-percentile` / `intermediate-percentile` / `high-percentile` percentile, defaults 10.000 / 50.000 / 95.000 | Which percentiles the client wants reported; 0.000 = not interested; all three 0 → only min/max. | A **per-probe-target configuration** the console sends (today `sdwan-probes` has `report`/`tca` but no percentiles). Agent keeps all per-probe RTT samples of the current measurement interval (e.g. 60 s / 100 ms = 600 values, or 3600 at 1 s eval) and computes the three percentiles at interval end (nearest-rank on a sorted array is enough; or a running t-digest/HDR histogram if intervals get long). | **Agent lacks percentile statistics entirely**: samples today are mean one-way delay, ipdv, loss, min, max. Needs raw retention + sort per interval. |
| `measurement-interval` uint32 range 1..max, units seconds, default 60 | The interval over which one `pm` entry's statistics are computed. | Maps onto a *new* probe parameter distinct from `interval` (100 ms between echoes) and `eval` (1000 ms sample): the reporting interval over which min/max/percentiles/loss are aggregated. Default 60 s. The 1 s samples can continue to feed the Paths chart. | Add `measurement-interval` to probe config; agent emits one `pm` record per interval with start/end time. |

### 3.4 Link level — `perf-mon/pm*` [pm-type] (state)

| Node | Meaning | Arcana realisation | Gap |
|---|---|---|---|
| `pm` list keyed by `pm-type` identityref (network-link / vpn-inter-access / vpn-tunnel) | One statistics bundle per PM method on the link. A link may have several (e.g. tunnel PM and inter-access PM). | For a service-network tunnel link: `pm-type-vpn-tunnel` (Arcana's probes run *inside* the tunnel: the ICMP target is the far tunnel address). For the underlay link: `pm-type-network-link` (probe the far edge's WAN address directly, a probe class Arcana does not run yet but could: same engine, different target and fib 0). `pm-type-vpn-inter-access` would mean UNI-to-UNI through the subscriber FIB — possible by probing the far UNI address in the service FIB. | A list keyed by an *identityref* must be expressible (see §6). |
| `pm-attributes/start-time`, `end-time` yang:date-and-time | When this measurement window started/ended. | Interval boundaries from the agent's clock (CLOCK_REALTIME, RFC 3339 with offset; Mplify 119 makes NTP a mandatory step, so wall-clock is trusted). | Agent timestamps are epoch numbers today; needs a date-and-time encoding decision. |
| `pm-source` identityref base `pm-source-type` | Which OAM tool produced the numbers. | **Today: none fits** — ICMP echo is not among bgpls/owamp/twamp/stamp/y-1731/ioam. Options: (a) define `arcana:pm-source-icmp-echo`; (b) implement **STAMP** (RFC 8762) in the agent and report `pm-source-stamp` legitimately. BFD-derived loss/liveness (Mplify 119) is also not a pm-source. | See §7 for the STAMP proposal. |
| `one-way-pm-statistics/loss-statistics` {packet-loss-count counter64, loss-ratio percentage} | Lost packets and percentage over the interval, one direction. | ICMP: lost = sent − answered in the interval; it cannot tell the direction of loss → report the same figure on both unidirectional links with a documented caveat, or only on the link whose source runs the probe. STAMP: the reflector returns the sender's sequence number and its own; far-end loss = gaps in reflector sequence, near-end loss = missing replies minus far-end loss (RFC 8762 §4.3 / RFC 8972 direct-measurement TLV). `loss-ratio` is a decimal64 with 5 fraction digits (e.g. `0.01667`), not a fraction. | Agent reports a fraction ("loss a fraction"); convert to percent ×100 with 5 decimals. |
| `delay-statistics` {unit-value identityref base lime:time-unit-type default milliseconds; min, max, low/intermediate/high percentile: gauge64} | One-way delay summary. **No mean/average leaf.** Units are an identityref, values integers → use `lime:microseconds` for sub-ms resolution. | Arcana measures RTT and halves it ("one-way delay (ms, half the mean round trip)"). Keep that for ICMP (document it via pm-source), report in microseconds. With STAMP + synchronized clocks (RFC 8762 timestamps in NTP or PTP format; FreeBSD `SO_TS_CLOCK` for RX kernel timestamps; TX timestamps in user space) true one-way delay per direction is available. | Agent lacks: percentiles; integer microsecond values (currently float ms); choice of unit. |

| Node | Meaning | Arcana realisation |
|---|---|---|
| `inter-vpn-access-interface/inter-vpn-access-interface` empty leaf | Enables PM of the logical point-to-point VPN connection between two VPN access interfaces (includes PE–PE). ### 3.7 What the model needs that the agent lacks (summary)

1. **Percentile statistics** (three configurable percentiles) of one-way
   delay and IPDV per measurement interval → retain raw per-probe values.
2. **Measurement intervals with start/end timestamps** (date-and-time), as
   distinct from probe spacing and 1 s samples; default 60 s.
3. **Integer values with explicit units** (gauge64 + unit identity),
   **loss as decimal percentage** (5 fraction digits), **loss count** as
   counter64.
4. A **pm-source** that exists in the registry: implement STAMP, or define
   an Arcana identity for ICMP echo (and one for BFD-derived liveness).
5. **Per-class (DSCP) statistics**: several probe sessions per tunnel.
6. **Per-direction** loss/delay: ICMP cannot; STAMP (with RFC 8972 TLVs)
   and Alternate Marking can.
7. **Typed interface counters** per TP (13 leaves) instead of netstat JSON;
   per-FIB **route counts**; optional bridge MAC counts.
8. **Underlay-link PM** (`pm-type-network-link`): probing the far edge's
   WAN address outside the tunnel, so underlay and overlay can be compared.
9. **Link identities**: stable TP ids and far-end ids so the console can
   build two unidirectional links per tunnel with `supporting-link` into the
   underlay network.
10. **Push**: YANG-Push periodic/on-change ≙ cblink `server-to-client`
    streams of `pm` records and the `events` multicast for threshold
    crossings (RFC 8632 alarms ≙ Arcana `sdwan-fault`/TCA events).

### 3.8 How the metrics relate to TWAMP / STAMP / Alternate Marking (and the others)

| pm-source | What it measures | Clock needs | Fit for Arcana / FreeBSD |
|---|---|---|---|
| OWAMP (RFC 4656) | One-way delay, IPDV, loss per direction with a control protocol (TCP) and test sessions (UDP), timestamps NTP format. | Synchronized clocks (NTP/PTP) for delay; none for loss. | Heavy (control protocol, modes); not worth implementing. |
| TWAMP (RFC 5357) / TWAMP Light | Two-way: sender timestamps T1, reflector stamps T2/T3, sender T4 → RTT = (T4−T1)−(T3−T2); one-way = T2−T1 if synced; loss by sequence numbers; reflector processing time removed. TWAMP Light drops the control protocol. | Sync only for one-way. | Feasible; superseded by STAMP. |
| **STAMP (RFC 8762, TLVs RFC 8972)** | Same four timestamps as TWAMP Light, UDP port 862 by default, fixed 44-byte (unauthenticated) packets, sequence numbers both ways, reflector in stateless or stateful mode, optional HMAC authentication; RFC 8972 adds TLVs (padding, location, timestamp info incl. clock-sync source/method, class-of-service with DSCP/ECN echo, direct measurement = transmit/receive counters for **loss per direction**, access report, follow-up). | Sync for one-way delay (NTP ok for ms accuracy); none for RTT/loss. | **Best fit**: a session-reflector in `arcana-agent` is ~200 lines (UDP socket per FIB, reply with T2/T3, copy sequence), a session-sender replaces the ICMP engine with the same scheduling (interval, size, dscp, count, timeout). Kernel RX timestamps via `SO_TIMESTAMP`/`SO_TS_CLOCK`; TX timestamp just before `sendto`. Yields: one-way delay per direction (with NTP, which Mplify 119 already requires), IPDV per direction, loss per direction, RTT, and `pm-source-stamp`. Unauthenticated mode inside the IPsec/wg tunnel is fine; authenticated mode uses HMAC-SHA-256. Also the natural "ping" replacement MEF 70.2 §11.4 tolerates. |
| Y.1731 (ETH-DM/ETH-LM/SLM) | Ethernet OAM frames: two-way/one-way delay, frame loss by counters. | — | L2 only; no FreeBSD support; not applicable. |
| IOAM (RFC 9197) | In-band trace/edge-to-edge data fields in real packets. | — | No FreeBSD data-plane support. |
| BGP-LS (RFC 8571) | Carries IGP TE metric extensions (RFC 7471/8570: unidirectional link delay min/max/avg, delay variation, loss, residual/available/utilized bw) learned by the IGP. | — | BIRD does not implement BGP-LS; OSPF-TE extensions not in BIRD. Not applicable, though the *metric set* (RFC 7471) is exactly what Arcana measures and could be fed into OSPF/BGP costs. |
| MPLS LM/DM (RFC 6374) | Loss by counters, delay by timestamps over MPLS/G-ACh. | — | No MPLS on FreeBSD. |
| **Alternate Marking (RFC 9341 base, RFC 9342 clustered)** — *not* in RFC 9375's identity list | Passive: mark real traffic with a 1-bit colour alternating every period (e.g. a DSCP bit, or the IPv6 AltMark option RFC 9343); count packets per colour at both ends → exact loss per period; timestamp the first packet of each block → delay. | Loosely synced clocks (period ≫ skew). | Possible on FreeBSD with ipfw: `count` rules per colour per tunnel (or per-table counters) at both edges, colour flipped by the agent each period on the sender side (ipfw `dscp` set in the tunnel's egress rules); the console subtracts. Measures the *actual* traffic, not probes; cannot measure when idle. Would need `arcana:pm-source-alt-marking` with base `pm-source-type`. |
| IPFIX (RFC 7011), "bgp", "ipfix" (named in the task) | Flow export; not a delay/loss source. | — | Not in RFC 9375; counters only. |

So: RFC 9375 only *labels* the source and carries one-way summaries; the
measurement semantics (which timestamps, which direction) come from the
cited protocol. Arcana's ICMP engine gives RTT-derived values with no
standard label; STAMP is the smallest step to a standard label and real
per-direction numbers.

## 4. Cannot be mapped (with reasons)

| Node / concept | Why not |
|---|---|
| `inbound-broadcast` / `outbound-broadcast` as distinct from multicast | FreeBSD `if_data` has only `ifi_imcasts`/`ifi_omcasts` covering both; the split would need per-driver or ipfw counting. |
| `entry-summary/*/maximum-routes` | FreeBSD has no configured per-FIB route maximum; the leaf's meaning ("maximum number of routes for the VPN") presumes a limit. Omit. |
| `mac-num` for L3 services | No MAC table in an L3 SD-WAN service; only if an L2 (bridge/vxlan) service exists. |
| `node-type asbr`, `p` | Arcana has no ASBRs or pure-core routers; everything is an edge or the controller. The identities exist but will rarely be used. |
| `pm-source-*` for ICMP echo and BFD | Not in the base identity set; requires Arcana identities. A strict implementation must not report `pm-source-twamp`/`-stamp` for ICMP. |
| `service-type` for SD-WAN | RFC 9181 has no SD-WAN identity; `l3vpn` is a misnomer for an overlay with its own tunnels. Needs an Arcana identity (or the IETF's future one). |
| `vpn-tunnel-type` for wg/ipsec | RFC 9181 `protocol-type` has no WireGuard/IPsec identity. Needs Arcana identities. |
| Per-direction loss / one-way delay from ICMP echo | ICMP only measures RTT and total loss; one-way values are RTT/2 (an assumption of symmetry). Strictly, Arcana should either report both directions' links with the same halved value and an ICMP pm-source, or move to STAMP. |
| The RFC 8345 `supporting-link` / `supporting-node` hierarchy between a service link and underlay links | Needs the underlay path (which WAN link, which provider) — Arcana knows the first hop (the uplink/FIB) but not the Internet path; `supporting-link` can only name the local uplink TP. |
| On-change YANG-Push semantics for counters | Counters change continuously; only periodic push makes sense (the RFC says so). Arcana streams are periodic by construction. |
| Mean/average delay | The model has no mean leaf (min/max/percentiles only); Arcana's current mean is not representable — the 50th percentile is the standard surrogate. |
| `loss-ratio` precision as a 0..100 decimal64(5) | Representable, but the schema must carry decimal64 (scaled integer) rather than `float`, or the value loses its declared precision. |

## 5. Features, and which Arcana could advertise

RFC 9375 defines **no YANG features** (`grep feature` → none) and imports
none that appear in its tree. Everything is unconditionally supported once
the module is advertised. The only "optional" behaviours are expressed by
data: the three percentiles set to 0.000, the `service` presence container,
the `vpn-tunnel` presence container, the empty `inter-vpn-access-interface`
leaf.

What Arcana could therefore *advertise* is the module itself plus the
augmenting identities it defines. If the cblink family models features, a
sensible Arcana-side feature set (in an `arcana-pm` augmenting module) is:

- `percentiles` — the agent computes low/intermediate/high percentiles
  (after raw sample retention is implemented).
- `per-class-pm` — several DSCP probe sessions per link.
- `stamp` — pm-source-stamp available (reflector + sender).
- `alt-marking` — passive loss by ipfw colour counters.
- `underlay-link-pm` — `pm-type-network-link` probes outside the tunnel.
- `tp-counters` — the 13 counters per TP; `vpn-network-access` counters.
- `route-summary` — per-FIB route counts.

## 7. Open decisions and trade-offs

1. **ICMP echo vs STAMP.** Keeping ICMP: zero data-plane change, no clock
   dependency, but no standard `pm-source`, no per-direction values, and
   one-way = RTT/2 by assumption. Moving to STAMP: a reflector in the agent
   on each tunnel address (and UNI/WAN address for the other pm-types),
   standard label, per-direction loss (RFC 8972 direct-measurement TLV),
   true one-way delay with NTP (already a Mplify 119 step), DSCP/ECN echo
   TLV for per-class checks, and a path toward interoperating with
   third-party STAMP reflectors. Cost: ~1 kLOC, UDP 862 open on tunnel
   addresses (inside the tunnel, so acceptable), a `stamp` feature. MEF
   70.2 §11.4 tolerates ping; Mplify 119 keeps BFD for faults — so STAMP
   replaces only the performance engine. Recommendation: STAMP sender +
   reflector, ICMP kept as a fallback with `arcana:pm-source-icmp-echo`.
2. **Where percentiles are computed.** On the agent per measurement
   interval (RFC shape, cheap at 600–3600 samples/interval, stays accurate)
   vs. on the console from 1 s samples (no agent change, but percentiles of
   means are not percentiles). Recommendation: agent; keep the 1 s samples
   as the chart stream.
3. **Measurement interval alignment.** RFC default 60 s; Arcana's TCA
   damping counts "intervals in a row". Decide whether TCA evaluation uses
   the 1 s sample (fast failover) or the PM interval (standard); likely
   both: faults from BFD/1 s samples, PM records every 60 s.
4. **Units.** `lime:milliseconds` default loses sub-ms resolution on LAN
   paths; use `lime:microseconds` everywhere Arcana reports (allowed by the
   model, the unit leaf says so).
5. **Network list layout.** One `network` per service + one underlay
   network (FIB 0 of the edges) with `supporting-network`, or additionally
   one per Mplify 119 routing domain (UCS, SD-WAN Service, Subscriber,
   Breakout)? The PM module only needs service networks and the underlay;
   routing domains are better served by RFC 8346 L3 topologies, one per
   FIB, which is also where per-FIB `prefix*` (routes) and `router-id`
   belong.
6. **Two links per tunnel.** The RFC's unidirectional links double every
   tunnel; with ICMP both links carry the same numbers. Either accept the
   duplication (strict) or report only the link whose source is the
   measuring edge and let the console mirror. STAMP removes the dilemma.
7. **Identifier scheme.** RFC 8345 ids are URIs. Proposal:
   `arcana:host/<hostname>` (node), `arcana:host/<hostname>/if/<ifname>`
   (tp), `arcana:svc/<service>/tunnel/<id>/<a>-<b>` (link),
   `arcana:svc/<service>` and `arcana:underlay` (networks). Agent emits
   the host/if parts; the console composes the rest.
8. **How much lives in the cblink family.** Minimal: typed per-interface
   counter records (`tp-svc-telemetry` shape), per-tunnel `pm` records
   (`pm-attributes` shape with pm-type, pm-source, class-id, interval
   times), per-FIB route counts, probe/STAMP config carrying percentiles and
   measurement-interval. Maximal: the agent holds the service network
   objects (nodes/links) itself. The minimal set is enough for the console
   to serve RFC 9375 northbound and keeps the agent free of topology.
9. **Decimal64 on the wire.** CBOR has tag 4 decimal fractions (libcbor
   supports tags); alternatively `s64` + `fraction-digits` in the schema.
   The latter is simpler in C and preserves YANG's canonical precision;
   JSON conversion at the console prints the dot.
10. **Alternate Marking as a passive source.** Attractive for SD-WAN
    (measures real traffic per tunnel and class with ipfw counters only),
    but needs colour bits in the tunnel header (DSCP bit or IPv6 AltMark
    option) that must survive the underlay, synchronized period flips and
    counter reads on both edges, and a new identity. Defer; design the
    `pm-source` attribute so it can be added.
11. **Threshold crossing alerts.** RFC 9375 relies on RFC 8632 alarms;
    Arcana has `sdwan-fault` events with severity and 24 h retention.
    Decide whether to model TCAs after `ietf-alarms` (resource = link
    URI, alarm-type-id = `arcana:tca-delay`, severity, is-cleared,
    time-created) so faults and PM share identifiers.
