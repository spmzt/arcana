# RFC 9342 — Clustered Alternate-Marking Method (with RFC 9341, Alternate-Marking base)

Sources read in full: `rfc/rfc9341.txt` (Alternate-Marking Method, December 2022, Standards
Track, obsoletes RFC 8321) and `rfc/rfc9342.txt` (Clustered Alternate-Marking Method, December
2022, Standards Track, obsoletes RFC 8889). Both are *methodology* documents: how the counters
and timestamps are transported is out of scope; the marking field is chosen per encapsulation
(e.g. RFC 9343 defines the IPv6 AltMark Hop-by-Hop/Destination option, not read here).

## 1. Purpose

RFC 9341 defines the Alternate-Marking Method: a hybrid (RFC 7799 "Hybrid Type I") performance
measurement that colours the packets of a production flow alternately (two colours A/B,
switched on a fixed timer) so that every measurement point along the path can count the
packets of the same block and compare counts for packet loss, and, with a second marking,
timestamp selected packets for one-way delay and delay variation; no probe packets are
injected. RFC 9342 extends it from point-to-point flows to multipoint-to-multipoint unicast
flows (including anycast and ECMP) by defining a "monitoring network" graph of measurement
points, a two-step algorithm that partitions it into **clusters** (smallest subnetworks where
packets in = packets out), the per-cluster packet-loss formula, multipoint delay via mean
delay or hash-based packet selection, and a closed-loop "network zooming" approach an SDN
controller can drive: monitor coarsely, and when loss or delay appears, refine the flow filter
or activate more measurement points until the fault is localised. For Arcana it is the passive
loss/delay measurement on real SD-WAN traffic, driven by the console over ipfw rule counters.

## 2. Content

### 2.1 RFC 9341 — the base method
- Motivation: counting packets at two points only works if both refer to the same set of
  packets; colouring creates blocks without delimiter packets or sequence numbers.
- **Packet-loss measurement (§3.1)**: traffic split into blocks by colour; block creation by a
  **fixed timer is REQUIRED**; switching after a fixed number of packets is optional and out
  of scope. Each measurement point keeps two counters per flow and interface (C(A), C(B));
  loss in block = upstream count − downstream count of the same colour. Read counters not
  immediately after a colour switch (reordering) — wait L/2.
- Strategies: **flow-based** (REQUIRED; only the selected flow is coloured; path must be known
  or every path monitored — untraversed interfaces simply count zero) and **link-based** (all
  traffic on a link recoloured per hop, two counters per class).
- End-to-end monitoring needs only the first and last hop; hop-by-hop needs every node.
- **One-way delay (§3.2)**: two-way delay = sum of the two one-way delays; NTP or PTP
  timestamps.
  - *Single-Marking*: timestamp the first packet of each block at both ends; valid only without
    loss/reordering of that packet (undetectable error). More samples: every N-th packet.
  - *Mean delay (§3.2.1.1)*: average of all arrival timestamps in a block at each node;
    difference = mean delay; robust to reordering, one value per block, no min/max/percentiles,
    error accumulates.
  - *Double-Marking (§3.2.2)*: a second marking bit selects packets inside a block (one per
    block is the robust choice; or several spaced ≥ mean delay apart) whose timestamps are
    compared per packet → min/max/median/percentiles; lost double-marked packets are
    recognisable because their number per block is known. Prefer 99.9th percentile over range
    (RFC 5481).
- **Delay variation (§3.3)**: RFC 3393 inter-arrival jitter from consecutive one-way delays
  (single marking: first packets of blocks; double marking: the marked packets).
- **Functions (§4)**: marking (choose where and how; multiple marking nodes allowed if they
  switch coherently; mark as close to the source as possible), counting/timestamping (two
  counters per flow per monitored interface), data collection and correlation (centralised
  NMS push or poll, or a protocol-based exchange — e.g. extending TWAMP/OWAMP; a **Block
  Number (BN)** MAY be attached to each count/timestamp to correlate; requires time sync).
- **Synchronisation and timing (§5)**: all nodes synced within ±A/2 (difference ≤ A);
  guard band **d = A + D_avg + 3·D_stddev**; available counting interval = L − 2d > 0, i.e.
  **d < L/2** (fundamental rule); counters read and double-marked packets chosen inside that
  interval. Longer L tolerates worse sync but measures less often.
- **Fragmentation (§6)**: mark all fragments if the encapsulation allows; nodes fragmenting
  inside the domain SHOULD keep the mark on one fragment only; measurement points SHOULD
  ignore unmarked fragments and count marked ones as whole packets.
- **Deployment (§7)**: one flag available → loss as §3.1, delay by single marking (mean delay
  MAY); two flags → loss as §3.1, delay by double marking (single MAY also). Factors: number
  of flags, marking period (temporal sampling, constrained by §5), kind of statistics wanted,
  computational load. Marked vs unmarked traffic is recognised by the presence of the marking
  extension. **MUST only be applied in a controlled domain (RFC 8799)**; external marked
  packets must be filtered or cleared at the boundary.
- RFC 6390 template (§8): method measures loss (RFC 7680), delay (RFC 7679), jitter (RFC 3393);
  units = exact packets lost; singletons; parameters = flow/link, period, methods.
- Security (§10): passive, no new packets; marking must not alter QoS; eavesdropping yields only
  the bits; harm to measurement by mark tampering or injected traffic → controlled domain,
  filter at borders; covert channel possible but low rate; delay attacks on double-marked
  packets; time-protocol attacks (RFC 7384); reporting channels MUST be secured.

### 2.2 RFC 9342 — clustered / multipoint
- Scope: multipoint-to-multipoint unicast, anycast (special case if routing is stable), ECMP
  (point-to-multipoint); not BUM/multicast (RFC 9341 link-by-link handles those). Reduces
  counters: n measurement points × m flows × 2 colours otherwise.
- Terms: **monitoring network** (graph of measurement points and the links between them,
  per flow or whole topology; no node both source and destination), **cluster** (smallest
  non-trivial subnetwork with packets-in = packets-out absent loss), **multipoint metrics**.
  Relation to RFC 5644: extends one-to-group to group-to-group, spatial metrics to clusters.
- **Flow classification (§3)**: identification fields (L3/L4, any subset, possibly outer
  encapsulation or non-header conditions) determine the path pattern: 5-tuple → point-to-point
  (or point-to-point multipath with load balancing); single source address →
  point-to-multipoint; single destination → multipoint-to-point; general → multipoint-to-
  multipoint.
- **Network packet loss (§4.2)**, assuming stable routing and measurement points at every
  ingress/egress: `PL = (PI1 + … + PIn) − (PO1 + … + POm)` per marking period and per flow;
  intermediate points only split the measurement.
- **Clustering (§5)**: a cluster contains all arcs leaving its input nodes and all arcs
  entering its output nodes. In a completely monitored network each device is a cluster and
  each link is two clusters. Two-interface routers may be simplified to one measurement point.
  Clusters may be defined from topology so they apply to all flows; invariant under
  translation/encapsulation.
- **Partition algorithm (§5.1)**, per direction (a node cannot be both source and destination):
  1. **Group** the (unidirectional) links that have the same starting node.
  2. **Join** groups that share at least one ending node (iterate until no change).
  Each resulting set of links plus its endpoint nodes is a cluster. Example (Appendix A):
  links R1→R2, R1→R3, R1→R10, R2→R4, R2→R5, R3→R5, R3→R9, R4→R6, R4→R7, R5→R8 → groups
  {R1-*}, {R2-R4,R2-R5}, {R3-R5,R3-R9}, {R4-R6,R4-R7}, {R5-R8}; groups 2 and 3 share R5 →
  clusters C1={R1→R2,R1→R3,R1→R10}, C2={R2→R4,R2→R5,R3→R5,R3→R9}, C3={R4→R6,R4→R7},
  C4={R5→R8}. Two-node clusters localise loss to a link; larger ones only to the cluster.
  Multiple sources MUST mark coherently and be synchronised (§8). Counters per period also
  give packet rate per cluster → CIR/EIR per cluster. Combinations of clusters keep the
  loss property. Recursive alternative in [IEEE-ACM-TON-MPNPM].
- **Multipoint loss (§6)**: the §4.2 formula applied per cluster or combination.
- **Multipoint delay (§7)**:
  - multipoint-path basis: *mean delay* generalised — difference of the packet-count-weighted
    averages of mean timestamps of output and input node sets; two-way = sum of directions.
  - single-packet basis: single marking (first/last packet) does **not** work (cannot tell
    which path the first packet took); double marking works only statistically (one packet per
    block follows one path per period; with multiple sources select one source per period);
    more than one picked packet per period on all paths → neither method applicable.
  - **Hash-based selection (§7.2.2)**: RFC 5474/5475 hashing combined with single marking
    ("Mixed Hashed Marking"): blocks anchor the hashed samples (a lost sample affects only its
    block); dynamic hash length keeps the sample count per period bounded regardless of rate;
    the solution for per-packet delay in multipoint paths.
- **Timing (§8)**: egress nodes receive marked packets from several ingresses in random order;
  the reference measurement interval is that of the marking node most aligned with the start
  (Figure 2); the extra gap between sources is folded into A; same guard band
  `d = A + D_avg + 3·D_stddev`, `L − 2d > 0` verified for each measurement point; a normal
  delay distribution is assumed (reformulate otherwise).
- **Deployment (§9)**: one flag → loss by clusters, delay by mean delay (no single-marking
  first/last packet); two flags → loss by clusters, delay SHOULD be per packet by double
  marking (mean delay MAY); one flag + hashing → loss by clusters, delay MUST use hashing.
  Controlled domain only.
- **Closed-loop PM (§10)**: an SDN controller/NMS knowing the topology starts coarse, and on
  loss or high delay reconfigures filters to partition into clusters/combinations down to a
  point-to-point flow ("network zooming": change the traffic filter, or activate more
  measurement points — with a transient to wait after reconfiguration), optionally hashing for
  delay of a specific source; per period packet rate and bandwidth are known so rate limits
  can be checked; marking periods of 1 s or less are used by some implementations; the
  controller can keep history; the method also serves **traffic visualisation** (which
  cluster/path a flow crosses).

### 2.3 Marking fields usable (what the RFCs say and what exists)
- The RFCs leave the field to the encapsulation ("specific flags in the packet header",
  "a dedicated, reserved marking field in a protocol extension"). Candidates on IP:
  - **DSCP bits**: usable in a controlled domain by dedicating codepoints (e.g. two codepoints
    of the same PHB class that differ in one bit — Pool 2/3 `xxxx11`/`xxxx01` local-use
    codepoints per RFC 2474 — so the PHB is unchanged); risk: remarking by intermediate QoS,
    and it steals DSCP space the SD-WAN policy uses.
  - **IPv6 Flow Label**: 20 bits, end-to-end, normally untouched; one or two bits could carry
    the colours (non-standard; RFC 6437 says routers must not modify it, which is a plus for
    survivability but setting it on behalf of a flow breaks its ECMP hash stability).
  - **IPv6 AltMark Hop-by-Hop/Destination option (RFC 9343)**: the standard carrier (L and D
    flag bits + FlowMonID); needs the sender/encapsulator to insert an extension header.
  - Tunnel headers Arcana controls: **GRE Key** (gre(4) `grekey`, a 32-bit field the far end
    checks — only if both ends switch coherently, i.e. not for marking), Geneve options (not
    settable by the FreeBSD driver), WireGuard/IPsec (encrypted, nothing to mark outside).

## 3. How Arcana could realise it on FreeBSD

The SD-WAN edge already has: ipfw rules per flow in a dedicated set, DSCP set per flow/tunnel
(`setdscp`), ipfw per-rule packet/byte counters (`ipfw -S show`, read into the `sdwan` read),
dummynet, netgraph via `ngctl`, the `ipfw:::rule-matched` DTrace probe (the sampler in
gula/record.c), time via ntpd (an SD-WAN step), events and streams over cblink, and a console
that knows the topology of every service (edges, tunnels, UNIs).

1. **Marking at the ingress edge with ipfw** (flow-based strategy, REQUIRED by 9341): for each
   monitored flow (the SD-WAN application flow, already matched by the classification rules)
   add a rule that sets the colour: `ipfw add N setdscp <A|B> <match>` followed by the normal
   steering. Colour switch on the fixed timer L (e.g. 10 s, configurable): the agent flips the
   rule in place (`ipfw set swap`-style: keep two prepared rulesets or simply `ipfw add` the new
   colour rule with a lower number and delete the old one; both are single syscalls, so the
   switch is atomic enough relative to L). Use a DSCP pair in the same class (e.g. the policy's
   DSCP with the lowest bit as colour where the class allows, or a reserved local-use pair
   mapped back at the egress) — DSCP policy knob in the console. Alternatively mark with
   **`ipfw tag`** (an mbuf tag, host-local) for link-based counting on the same host only.
2. **Counting at each measurement point with ipfw counters**: two `count` rules per flow per
   interface (`count dscp A …`, `count dscp B …`), on the ingress edge's egress tunnel
   (`out xmit tunX`) and on the egress edge's tunnel ingress (`in recv tunX`) and at the UNI
   egress; counters read with `ipfw -S show` (or the libipfw/sockopt `IP_FW3` getter the agent
   already uses) at L/2 after each switch, i.e. inside the available counting interval; the
   agent attaches the **Block Number** (floor(time/L) from the NTP-synced clock) and the
   colour to each reading and streams `am-count` records (flow, interface, colour, BN,
   packets, bytes) to the console. Guard band check: the agent knows A (ntpd's `maxerror`
   from `ntp_gettime(2)`), D_avg and D_stddev (from the STAMP/ICMP probes of the tunnel) and
   refuses an L with L − 2d ≤ 0.
   Counter accuracy caveat: `ipfw -S show` counts are read per rule and are atomic per rule,
   not across rules — fine because the inactive colour's counter is steady.
3. **Correlation in the console** (centralised NMS, polling or push over cblink streams):
   per (flow, BN, colour) compute loss between any two measurement points, per link (two-node
   clusters: the tunnels) and end-to-end (UNI ingress → UNI egress). For a service with several
   edges and tunnels build the **monitoring network** from the SD-WAN document (edges = nodes,
   tunnels and UNIs = arcs, per direction) and run the §5.1 two-step partition; show loss per
   cluster on the Paths tab; "zoom" by activating counting rules on more interfaces or
   narrowing the flow filter (5-tuple) — the console already recompiles `sdwan-rules`.
4. **Delay**: single marking's "first packet of a block" needs per-packet timestamps the ipfw
   counters do not give. Options on FreeBSD: (a) **mean delay** from a netgraph tap: `ipfw
   ngtee <cookie>` on the marked flow → `ng_ipfw` → `ng_bpf` filtered to the double-marked
   packets → `ng_socket` into the agent, which timestamps with `SO_TIMESTAMP`; (b) **double
   marking with ipfw**: a second DSCP bit or `ipfw ... log logdst bpf` on a rule matching one
   packet per block (ipfw has no "every N-th"/"first in period" match; use `ipfw ... limit`?
   no — use a `probability` match? `prob` gives random sampling, not one-per-block; the
   realistic path is the **hash-based selection of RFC 9342 §7.2.2**: an `ng_bpf` program or
   a `pcap` filter that selects packets whose hash of invariant fields falls in a range — the
   bpf tap (`logdst bpf` per rule, FreeBSD 16, already used by capture.c) gives each selected
   packet with a kernel timestamp at both edges; the console pairs them by (BN, hash) and gets
   per-packet one-way delay, min/max/percentiles, and IPDV; dynamic hash range keeps the
   sample count bounded. This is "one flag + hash-based selection" of §9, the recommended
   deployment for Arcana. Requires the packet to be identical at both edges (it is, inside the
   tunnel: hash the inner IP id/ports/payload bytes before NAT; exclude DSCP/TTL from the hash).
5. **Timing**: ntpd already a managed step; A from `ntp_gettime`; L default 10 s (d is tens
   of ms on a WAN, so L − 2d ≫ 0; 1 s possible on good links); readings at L/2 after switch.
6. **Boundary filtering** (controlled domain): at every UNI ingress, `setdscp` to the policy
   value already overwrites any external colour; at the breakout egress the colour is reset.
7. **Model/contract**: an `alt-marking` part of the PM YANG shape: per flow `marking {period
   L, colours {A,B} as DSCP, double-marking/hash {range}}`, per measurement point `counters*
   [flow, interface, direction]` streamed with `block-number`; results exported as RFC 9375
   `perf-mon` with `pm-source` = a local identity derived from `pm-source-type` (no
   `pm-source-alt-mark` identity exists in RFC 9375; define `arcana:pm-source-alternate-
   marking`), `pm-type-vpn-tunnel` for tunnels and a cluster-level link in the monitoring
   network for clusters. Combine with STAMP's Direct Measurement TLV to carry the counts
   in-band between the two ends (RFC 9341 §4.3's "extend TWAMP/OWAMP" option).

## 4. Cannot be mapped / not applicable
- **RFC 9343 IPv6 AltMark option**: ipfw cannot insert a Hop-by-Hop/Destination option; no
  FreeBSD kernel path to add extension headers to forwarded packets → not without kernel work.
- **Link-based strategy across hosts**: recolouring per hop on every FreeBSD link would need
  every transit device to be Arcana-managed; only edges are. Flow-based end-to-end and per
  tunnel is what fits.
- **Per-packet timestamps from ipfw counters**: counters give counts only; delay needs a tap
  (bpf/netgraph) — i.e. the method's "timestamp the first packet of the block" is replaced by
  hash-selected samples.
- **Marking inside encrypted tunnels seen by the underlay**: once in IPsec/wg the colour is
  invisible to the UCS; measurement points are only the two edges (end-to-end per tunnel).
  Outer-header DSCP copy (IPsec `dscpinherit`, already in the family) would expose the colour
  but intermediate ISP devices are not measurement points anyway.
- **Multicast/BUM**: out of 9342's scope; Arcana's SD-WAN is unicast.
- **Fragment handling inside the kernel**: ipfw `reass` can reassemble before counting, which
  side-steps §6; otherwise unmarked non-first fragments (DSCP is on every fragment of an IPv4
  packet, so actually every fragment is marked — count with `frag !offset` to count first
  fragments only).
- **Hardware counters/timestamps**: none; all software (fine at SD-WAN edge rates).

## 5. Checklist of requirements / tests
1. Fixed-timer blocks (L configurable; default 10 s); colour switch coherent across all marking
   edges of a service (NTP-synced; switch at BN boundaries, not at arbitrary local times).
2. Flow-based marking with ipfw `setdscp`; the colour pair documented and reserved in the
   SD-WAN DSCP policy; UNI ingress overwrites external marks (controlled domain).
3. Two counters per flow per monitored interface and direction (`count dscp A/B in recv`,
   `out xmit`), created with the SD-WAN rules.
4. Counters read at L/2 after the switch, tagged with Block Number and colour, delivered over
   cblink (stream or event) with the agent's clock error A.
5. Guard-band rule enforced: d = A + D_avg + 3·D_stddev < L/2, D from the tunnel's probes;
   the console refuses/raises when violated.
6. Console computes per-block loss per tunnel (two-node cluster), end-to-end per flow, and
   per cluster from the §5.1 partition of the service's monitoring network; shows packet rate
   per cluster.
7. Partition algorithm implemented exactly as §5.1 (group by start node; join on shared end
   node; per direction) with the Appendix A graph as a unit test (expect 4 clusters).
8. Hash-based sample selection on a bpf tap at both edges; per-packet one-way delay only with
   synced clocks; min/max/percentiles and RFC 3393 IPDV per block; sample count bounded by a
   dynamic hash range.
9. Mean delay per block as the fallback (one flag, no tap).
10. Fragments: count first fragments only or reassemble first; document the choice.
11. Network zooming: the console can enable more counting points or narrow the flow filter and
    waits a configurable transient before trusting the next block.
12. Security: marked packets from outside the domain cleared at ingress; counter reports over
    mTLS; marking does not change the PHB class.
13. Lab test (two vnet jails + epair + dummynet `plr 0.01`): loss per block measured equals
    dummynet's drops ± 0; with `delay 50` the hash-selected one-way delay is ≈ 50 ms when
    both jails share the host clock (A ≈ 0).
14. Lab test for 9342: three edges (hub + two spokes), a flow from both spokes to the hub;
    monitoring network partition yields the expected clusters; loss injected on one tunnel is
    localised to that cluster.

## 6. Open decisions and trade-offs
- **Which bits to colour with**: DSCP (works today with ipfw, risks remarking and collides with
  QoS classes) vs IPv6 flow label (clean but IPv6-only and non-standard) vs waiting for a
  kernel AltMark option (standard, not available). Recommendation: DSCP pair in the same PHB
  class, policy-controlled, IPv4+IPv6.
- **Block length L**: short (1 s) gives timely loss detection but demands tight sync and
  frequent counter reads (CPU on the agent, bandwidth to the console); long (60 s) is cheap
  but slow. Make it per service; default 10 s.
- **Counting scope**: per application flow (what MEF policies name) vs per tunnel aggregate
  (fewer counters, no per-app attribution). 9342's zooming suggests: aggregate per tunnel by
  default, per flow on demand.
- **Delay by hash tap vs STAMP only**: the tap adds kernel copies of sampled packets and agent
  work; STAMP already gives delay actively. Alternate marking's unique value is *loss of real
  traffic*; delay by hashing is optional (keep for "is the active probe representative?").
- **Where correlation lives**: console (central, matches 9342's SDN-controller framing) vs
  edges exchanging counts in-band via STAMP Direct Measurement TLV (works without the console,
  for local failover decisions). Do both: console for clusters, in-band for the per-tunnel
  loss that steering uses.
- **Counter read mechanism**: `ipfw -S show` text parsing (exists) vs the `IP_FW3` sockopt
  (`IP_FW_XGET`) in-process for a precise read instant; the latter is better for the L/2
  timing.
