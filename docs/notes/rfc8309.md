## 1. Purpose and place in the layered picture

- Terminology RFC. Defines what a *service model* is, splits it into **customer service model** (customer <-> operator interface, e.g. L3SM RFC 8299, L2SM RFC 8466) and **service delivery model** (operator-internal, "network service YANG module" per RFC 8199, e.g. L3NM RFC 9182), and distinguishes both from **network configuration models** (orchestrator -> controller) and **device configuration models** (controller -> network element).
- Layering (Fig. 3): Customer --(a) customer service model--> Service Orchestrator --service delivery model--> Network Orchestrator --network configuration model--> Controller --device configuration model--> Network Element. Interface (a) is the only one that is technology-agnostic; everything south of it knows topology, technology and operator policy.
- A customer service model is **never sent to a device**; it describes the service as experienced, not how it is realised. Commercial terms and SLAs are out of scope (operators augment).
- Service models must be *extensible* (augment) for operator-specific features and policy; common data (customer postal address) should live in its own module and be reused.
- Says nothing about encoding/transport: NETCONF/RESTCONF XML/JSON are the IETF defaults but "co-located software components might use an internal API". This is the licence for Arcana to carry YANG-shaped data over cblink/CBOR.
- Manageability: operational state is *not* part of a customer service model but operators may add it by extension; a feedback loop reporting degradation is expected; the orchestrator must know other commitments before committing resources.
- Security: the customer/operator interface is commercial; must be authenticated, authorised and encrypted; abstraction protects the operator from exposing topology.
- Arcana placement: the web console (arcana-console) / PWA is the **customer + service orchestrator** face; arcana-agent on each FreeBSD host is simultaneously **controller and network element** (one host = one PE). The future "SDN" piece is the network orchestrator that turns an L3NM into per-host cblink operations.

## 3. Concepts and candidate Arcana realisation

| Concept (RFC 8309) | Meaning | Arcana / FreeBSD realisation |
|---|---|---|
| Customer | buys connectivity; may be internal (IP network as customer of optical) | Tenant in the console; also "an Arcana fleet as customer of another fleet" (inter-fleet NNI, see RFC 9408 App. C) |
| Network Operator | owns the network | The fleet owner; the console + agents |
| Service | connectivity between sites / Internet, possibly a tunnel; plus guarantees | Today: SD-WAN "service" (MEF 70.2) in `invidia/sdwan.c`; future: an L3NM `vpn-service` |
| Customer Service Model (a) | technology-agnostic request | **Not in scope for the agent.** Belongs in the console (service orchestrator). Candidate: L3SM subset or MEF 70.2 SD-WAN service as today |
| Service Delivery Model | network-centric, operator-only | L3NM (RFC 9182) + SAP (RFC 9408) spoken between console and a (new) fleet-level orchestrator, or directly console -> agents if the console *is* the network orchestrator |
| Network Configuration Model | orchestrator -> controller | Collapses with the device model in Arcana: the console speaks cblink families to each agent |
| Device Configuration Model | controller -> element | cblink families on arcana-agent (interfaces, routes/FIB, ipfw, BIRD, IPsec, wg, jails, ...). The "device YANG" equivalents are ietf-interfaces/ietf-ip/ietf-routing/ietf-acl/ietf-nat |
| Service interface (b) | northbound of network orchestrator, network-centric | cblink itself, or a future "arcana-l3nm" family on the console |
| Technology reaching the customer site (encapsulation, CE-PE protocols, OAM) | the only tech allowed in a customer model | VLAN (vlan(4)), BGP/OSPF via BIRD, BFD via BIRD, DHCP/SLAAC (dhcpd/rtadvd), ICMP probes (Arcana SD-WAN probes) |
| Policy | only customer-influenceable policy belongs in the service model | SD-WAN steering policy (ipfw tables), bandwidth (dummynet) stay; vendor policy stays in agent/profile ids |
| SLA / commercial terms | out of scope, operator augments | Arcana's MEF 70.2 performance objectives + probes live as an *augment*, not in the IETF models |
| Operational state of a service | not in customer model; may be exported by extension | L3NM/SAP do carry admin/oper status; Arcana events + usage sampling feed them |
| Feedback loop / resource awareness | orchestrator must check commitments before committing | Arcana needs a fleet-wide allocator (FIB numbers, VNIs, RD/RT, VLAN ids) before the agent is told |

None.

## 6. YANG constructs

None used. The RFC does establish that *augment* is the extension mechanism for operator-specific features, SLAs, policy and operational state — so whatever cblink grows must have an augmentation story (section 6 of rfc9181.md).

## 7. Open questions / decisions

1. **Where does the service orchestrator live?** (a) in the console (customer model = console forms / MEF 70.2 SD-WAN service as today; delivery model = L3NM emitted to agents), or (b) a new `arcanad` fleet daemon that owns L3NM/SAP and allocates shared resources. Trade-off: (a) is less code but the console is unprivileged and stateless-ish; (b) gives a single point for RD/RT/VNI/FIB allocation and multi-domain NNI but adds a component.
2. **Collapse controller and device?** Arcana agents already act as both. Keeping L3NM strictly at the fleet level and mapping to *existing* device-like cblink families (interfaces, routes, bird, ipfw) preserves the layering of Fig. 3; alternatively give each agent an `l3vpn-ntw`-shaped family and let the agent do the decomposition (simpler orchestrator, fatter agent, but then the agent must understand RTs it cannot enforce without MPLS).
3. **Customer service model:** adopt L3SM (RFC 8299, 10k lines, heavily MPLS-provider flavoured) or keep MEF 70.2 as the customer face and treat L3NM as the only IETF model? The RFC explicitly allows non-YANG customer models.
4. **Transport:** RFC says encoding is deployment-specific. Decision: cblink/CBOR with YANG-derived schema (needs the construct list in rfc9181.md §6) vs. adding a RESTCONF/JSON (RFC 7951) or CORECONF/YANG-CBOR (RFC 9254) northbound to the console for interop with third-party orchestrators.
