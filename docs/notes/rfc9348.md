# RFC 9348 — A YANG Data Model for IP Traffic Flow Security (IP-TFS)

Sources: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc9348.txt (read in full,
1325 lines) and rfc9347.txt (AGGFRAG mode for ESP and its use for IP-TFS; read in full, 1614 lines,
for the data-plane requirements).
Status: both Standards Track, IPSECME WG, January 2023.

## 1. Purpose and where it sits

- RFC 9348 defines `ietf-ipsec-iptfs`, a module that **augments the RFC 9061 IKE and IKE-less
  models** with the configuration and operational state of IP Traffic Flow Security: the AGGFRAG
  tunnel mode of ESP (RFC 9347) that sends fixed-size outer packets at a constant (or
  congestion-controlled) rate, aggregating and fragmenting inner IP packets to hide size and timing
  (Traffic Flow Confidentiality, RFC 4303 §2.7 done efficiently).
- It is a **device model** augmentation: config under each SPD entry's `ipsec-sa-cfg` (what to
  negotiate/apply to SAs created from that policy), read-only copies under the IKE `child-sa-info`
  and the IKE-less `sad-entry` (what the SA actually runs), and per-SA statistics (plain IPsec
  tx/rx counters behind `ipsec-stats`, IP-TFS inner/outer packet counters behind `iptfs-stats`).
- IP-TFS behaviour is **source controlled**: all configuration is at the sending side; each
  direction is independent (an SA pair may run IP-TFS one way only), so counters may be 0 for the
  idle direction.
- This version configures the simple fixed-size/fixed-rate mode (plus congestion control); the
  model is "structured to allow for different types of operation through future augmentation".
- RFC 9347 data plane in short: ESP Next Header 144 (AGGFRAG_PAYLOAD); 4-octet header (sub-type 0,
  non-CC: Sub-Type, Reserved, BlockOffset) or 24-octet header (sub-type 1, CC: adds P/E flags,
  LossEventRate, RTT 22 bits, Echo Delay 21 bits, Transmit Delay 21 bits, TVal, TEcho); DataBlocks
  are IPv4 (type nibble 4, length from Total Length), IPv6 (6, Payload Length + 40) or Pad (0, to
  the end); fragments of an inner packet go in consecutive ESP sequence numbers (all-pad payloads may
  interleave), sequence numbers MUST increase by exactly 1; receiver keeps a reorder window (default
  suggestion 3), a lost-packet timer, reassembly state; CC mode runs a TFRC (RFC 5348) loop fed by
  the CC header; ECN CE counts as loss (E bit), outer ECN set to Not-ECT (RFC 6040 compatibility
  mode); DF never mapped; DS field not copied by default; IKEv2 negotiates with notify USE_AGGFRAG
  (16442) carrying flags C (CC required) and D (don't fragment: receiver cannot reassemble); AGGFRAG
  SAs are exclusive (no mixed payloads); PMTU via PLMTUD using CC payloads with the P bit as probes.

**FreeBSD status:** the FreeBSD kernel (netipsec: xform_esp.c, ipsec.c, ipsec_output.c, key.c) has
**no AGGFRAG/IP-TFS support**: no handling of ESP next header 144, no aggregation/fragmentation
engine, no fixed-rate pacer, no reorder/reassembly on input, no CC header processing, no PF_KEY
extension to configure any of it, and strongSwan's `kernel-pfkey` backend cannot request it
(strongSwan's IP-TFS support, where it exists, targets Linux XFRM iptfs, Linux 6.14+). Arcana's code
base has no reference to AGGFRAG/IP-TFS. Everything in this module is therefore **unmappable today**;
section 3 states what each node would require.

## 3. Node-by-node meaning and what FreeBSD would need

| Node | Meaning (RFC 9348/9347 refs) | FreeBSD requirement / candidate realisation |
|---|---|---|
| traffic-flow-security (container, config under spd-entry/.../ipsec-sa-cfg; ro under child-sa-info and sad-entry) | Enables AGGFRAG mode on SAs created from this policy. Presence = IP-TFS on (no explicit enable leaf). | A per-SA flag in the SAD (new `SADB_X_SAFLAGS_IPTFS` or a new PF_KEY extension `SADB_X_EXT_IPTFS` carrying the parameters below); `setkey add ... -iptfs ...`; for IKE, charon must send/accept USE_AGGFRAG (16442) and pass the result to the kernel via kernel-pfkey — strongSwan has no FreeBSD path for this. |
| congestion-control boolean default true | true: CC sub-type 1 payloads, TFRC rate adaptation, CC info exchanged at least once per RTT, no-feedback timeout halves the rate; false: fixed rate (non-CC mode MUST only be used under full administrative control of the path; circuit breakers RECOMMENDED). | Kernel: TFRC implementation (RFC 5348 / RFC 4342 style) per SA; receiver-side loss-event-rate computation; sender RTT estimation from TVal/TEcho/Echo Delay/Transmit Delay; a paired SA back to the sender (empty AGGFRAG payloads on a non-AGGFRAG return SA). Also the `C` flag in USE_AGGFRAG. |
| packet-size/use-path-mtu-discovery boolean default true | Discover the outer size by PMTUD/PLMTUD (RFC 8899, probes = CC payloads with P bit); explicit size only adjusted downward when set. | Kernel: PLMTUD probing state machine per SA using CC payloads; FreeBSD has PMTUD for the tunnel (`net.inet.ipsec` + tcp_hc/route MTU) but nothing per-SA probe-based. |
| packet-size/outer-packet-size uint16 bytes | Fixed size of the outer IP+ESP packet. | Kernel: pad/fragment to exactly this size (Appendix A of 9347: 1404-octet ESP space example). |
| (tunnel-rate) l2-fixed-rate / l3-fixed-rate yang:gauge64 bits/second | Nominal bandwidth, counting L2 framing (Ethernet 38 octets/pkt incl. preamble/IPG) or L3 bytes; rate / packet size = send interval; CC may adjust. | Kernel: a per-SA pacer (callout/high-resolution timer firing every size*8/rate seconds, sending a packet even when only padding is available). Gauge64 is unusual for config (it is a *gauge* type used as a rate). |
| dont-fragment boolean default false | Do not fragment inner packets across outer packets; inner packets larger than the outer payload are dropped (9347 §2.2.4/6.1.4 `D` flag semantics: what the sender of the notify can receive). | Kernel: tx behaviour switch; IKE: the D flag in USE_AGGFRAG. With fragmentation disabled the tunnel behaves like RFC 4301 wrt ICMP Too Big and EMTU. |
| max-aggregation-time decimal64 (fraction-digits 6) milliseconds | Longest an inner packet may be held waiting for the outer packet to fill; longer -> dropped rather than queued. | Kernel: per-SA aggregation queue with a deadline per inner packet, nanosecond resolution (`units ms`, 6 fraction digits = 1 ns). |
| window-size uint16 0..65535 | Receiver reorder window in packets (0 = no reordering); 9347 suggests 3 as a default and allows dynamic adjustment; may be reduced to the smaller of replay and reorder windows. | Kernel: receive-side reorder buffer keyed by ESP sequence number (ESN-aware), distinct from the anti-replay window. |
| send-immediately boolean default false | Receiver forwards complete inner packets as soon as they arrive, without waiting for lost/misordered outer packets (lower delay, more out-of-order inner delivery). | Kernel: receive processing mode switch (9347 §2.5 two methods). |
| lost-packet-timer-interval decimal64 (6) milliseconds | How long the receiver waits for a missing outer packet before declaring it lost; RECOMMENDED to use; absent timer means delay up to window-size * send interval. | Kernel: per-SA timer in the reorder engine. |
| ipsec-stats {ipsec-stats} tx-pkts, tx-octets, tx-drop-pkts, rx-pkts, rx-octets, rx-drop-pkts | Per-SA plain IPsec packet/byte/drop counters (tx = outbound SA, rx = inbound SA). | **Partially realisable today without IP-TFS**: FreeBSD keeps per-SA `sadb_lifetime_current.bytes` and `.allocations` (packets) via SADB_DUMP/`setkey -D`; since an SA is unidirectional, an outbound SA gives tx-pkts/tx-octets and an inbound SA gives rx-pkts/rx-octets. Per-SA drops are not kept (only global `netstat -sp esp`/`-sp ipsec` counters: esps_hdrops, esps_badilen, esps_replay, esps_badauth, esps_noxform, esps_qfull...). So `ipsec-stats` can be advertised with tx/rx pkts/octets exact and drop counters either omitted or reported as global. Also `ipsec(4)` interface counters (`netstat -i`) when SAs serve an ipsec interface. |
| iptfs-inner-pkt-stats {iptfs-stats} tx-pkts, tx-octets, rx-pkts, rx-octets, rx-incomplete-pkts | Inner packet counters (whole packets; incomplete = fragments never completed). | Kernel: counters in the AGGFRAG engine. none today. |
| iptfs-outer-pkt-stats {iptfs-stats} tx-all-pad-pkts/-octets, tx-extra-pad-pkts/-octets, rx-all-pad-pkts/-octets, rx-extra-pad-pkts/-octets, rx-errored-pkts, rx-missed-pkts | Outer packet padding and error counters (all-pad = no data; extra-pad = data + padding, 9347 §2.2.3/2.2.3.1; missed = sequence gaps). | Kernel counters. none today. |

Where the engine would live in FreeBSD, if implemented: the natural ingress point is the output
path of `ipsec(4)` interfaces (if_ipsec.c) or `ipsec_output.c` for policy-based tunnels: the
aggregation queue + pacer per outbound SA (`struct secasvar` gains an iptfs state pointer);
`xform_esp.c` esp_output builds AGGFRAG payloads (next header 144) instead of the inner IP header
next-protocol, esp_input dispatches on 144 to the reassembly/reorder engine before `ipsec_input`
delivery; PF_KEY gains an extension to carry the eight parameters and to report state; sysctls for
defaults; counters in `struct espstat` or per SA. IKE side: charon needs USE_AGGFRAG support and
kernel-pfkey glue (upstream work, not Arcana's). A userland data plane (divert/netmap) could prototype
the sender side but cannot be the ESP endpoint without the kernel's SA state.

## 4. Cannot be mapped (with reasons)

| Node | Reason |
|---|---|
| traffic-flow-security and every leaf in it (congestion-control, packet-size/*, l2-/l3-fixed-rate, dont-fragment, max-aggregation-time, window-size, send-immediately, lost-packet-timer-interval), both config and operational | No AGGFRAG/IP-TFS in the FreeBSD kernel, no PF_KEY knobs, no strongSwan support on FreeBSD. |
| iptfs-inner-pkt-stats, iptfs-outer-pkt-stats | No engine, no counters. |
| ipsec-stats/tx-drop-pkts, rx-drop-pkts per SA | FreeBSD ESP drop counters are global. |
| USE_AGGFRAG negotiation (IKE case) | charon on FreeBSD cannot negotiate it meaningfully without a kernel. |

What is mappable: `ipsec-stats` tx/rx pkts and octets (per-SA lifetime counters), as an
augment of the RFC 9061 `sad-entry`/`child-sa-info` state — Arcana can implement that part and
advertise `ipsec-stats` with the drop-counter caveat.

## 7. Open decisions and trade-offs

1. **Model it or not.** Including the `traffic-flow-security` nests in the cblink IPsec family keeps
   the family a faithful mirror of RFC 9061+9348 and lets a future kernel implementation land
   without a family version bump; but every FreeBSD host would reject writes, and the console must
   hide it behind a capability. Alternative: define the attribute ids now (numbers are forever) but
   do not generate handlers until there is a data plane.
2. **Kernel implementation scope.** A FreeBSD AGGFRAG implementation is a substantial netipsec
   project (sender pacer + aggregator, receiver reorder/reassembly, CC/TFRC, PLMTUD, PF_KEY
   extension, counters, ESN interplay, exclusive-SA rule, ICMP/PMTU behaviour per 9347 §2.2.6-2.2.7)
   plus strongSwan kernel-pfkey and USE_AGGFRAG support upstream. Decide whether Arcana's SDN plan
   funds it (TFC is a real SD-WAN differentiator) or declares IP-TFS out of scope and documents it.
3. **Non-CC mode safety.** If implemented, the non-congestion-controlled mode needs the operator
   attestations and circuit breakers RFC 9347 §2.4.1-2.4.2.1 call for; the model has no leaf for a
   circuit breaker, so Arcana would augment (loss rate threshold + duration).
4. **ipsec-stats now.** Implement the `ipsec-stats` augment on the RFC 9061 SAD state immediately
   (cheap, useful for the console), decide how to present drops (omit vs global).
5. **Decimal64 representation** is shared with RFC 9899 `rate-limit`: pick one encoding rule for the
   whole cblink schema (scaled integers with `fraction-digits` in the spec is the simplest for C and
   CBOR; the console converts).
6. **Where IP-TFS parameters would attach in Arcana's route-based design.** Arcana's tunnels are
   ipsec(4) interfaces with a reqid; IP-TFS per policy (RFC) vs per interface (Arcana) — if ever
   implemented, the ipsec(4) interface is the obvious place for the pacer and the parameters
   (`ifconfig ipsec0 iptfs rate 1G size 1400 ...`), which would make the family's `spd-entry` level
   placement a translation.
