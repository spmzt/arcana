# RFC 10053 — A Framework for Computing-Aware Traffic Steering (CATS)

Read in full: 1452 lines, fetched from https://www.rfc-editor.org/rfc/rfc10053.txt (HTTP 200).
Informational, October 2026. Li (ed.), Du, Boucadair (ed.), Contreras, Drake. Companion: RFC 10054 (CATS problem statement, use cases, requirements).
Local copy: `scratchpad/rfc/rfc10053.txt`. (The number resolves at rfc-editor.org; it is a published RFC, not a draft; no datatracker fallback was needed.)

## 1. Purpose

RFC 10053 defines the functional framework for Computing-Aware Traffic Steering: steering a
client's service request to the most suitable *service contact instance* among several
sites, using both network metrics and computing metrics, instead of the routing-closest
instance. It fixes the identifiers (CS-ID for a service, CSCI-ID for a contact instance),
the components (service sites/instances/contact instances, C-SMA service metric agent,
C-NMA network metric agent, C-PS path selector, C-TC traffic classifier, Ingress/Egress
CATS-Forwarders, underlay), the planes (management, control, data), the workflow (service
announcement, metrics distribution, service access processing with overlay encapsulation
between forwarders, service contact instance affinity), operational matters (provisioning,
OAM, deployment models distributed/centralised/hybrid, metric normalisation and
aggregation, verification, operational impact), security (metric churn as attack vector,
authentication/integrity between components, service authentication) and privacy
(no fingerprinting by on-path nodes, encrypt path information). Single-provider scope.

## 2. Architecture and terminology (complete)

### 2.1 Terminology (§2)
- **Client**: endpoint connecting to the provider network.
- **Flow**: packets in a time interval identified by header fields (5-tuple; must also work without ports: fragments, ESP).
- **CATS**: a TE approach (RFC 9522) accounting for dynamic compute/storage resources and network state to optimise service-specific forwarding toward a service contact instance.
- **Metric**: quantitative input to selection; network metric or computing metric ([CATS-METRICS] draft for the latter).
- **Service**: offering orchestrated from networking/compute/storage resources; provider controls resources and logic; may be processes, virtual/physical instances, one or many nodes/sites, chained; same service in many locations = many service instances.
- **Computing service**: service built from computing resources.
- **CS-ID**: identifier of a service, used by clients; identifies all instances regardless of location; independent of which contact instance serves; sufficiently unique within the CATS system (need not be global).
- **Service instance**: running resources following a service logic; many per service; runs in a service site.
- **Service site**: location (node or set of nodes) hosting instances.
- **Service contact instance**: client-facing function receiving requests for a service; may front one or more instances (e.g. a load balancer); steering beyond it is hidden; reachable via at least one Egress CATS-Forwarder; several per service at same/different sites.
- **CSCI-ID**: identifier of a contact instance; structure unspecified (e.g. a unicast IP address).
- **Service request**: request to access a service, in a service-specific protocol, sent to the CS-ID without knowledge of CATS-Forwarders.
- **CATS-Forwarder**: steers service traffic to a contact instance per C-PS decisions; Ingress (steers along the CATS path to an Egress) and Egress (end of path, connects to the site).
- **C-PS**: selects paths/sites/instances to meet service requests using service and network status.
- **C-SMA**: collects service capabilities/status, reports to C-PS.
- **C-NMA**: collects network capabilities/status, reports to C-PS.
- **C-TC**: determines which packets belong to a flow for a service request; coordinates with the Ingress CATS-Forwarder to place them on the C-PS path.

### 2.2 Framework (§3)
- **Assumptions (§3.1)**: a service may have several instances in several sites, all under one CS-ID, each reachable via one or more contact instances.
- **Identifiers (§3.2)**: CS-ID (requests spread over contact instances by initiator location, instance availability/load, congestion); CSCI-ID (e.g. unicast IP).
- **Planes (§3.3, Fig. 1)**: Management (monitor/configure/maintain CATS devices), Control (schedule services from compute+network info; decide forwarding; communicate decisions), Data (classify, steer onto paths, forward to contact instances). Planes consist of components (C-PS, C-NMA in control; forwarders, C-TC in data).
- **Components (§3.4, Fig. 2)**: service sites/instances/contact instances (§3.4.1; CS-ID sufficiently unique; clients see only contact instances; Egress forwarders provide access); **C-SMA** (§3.4.2; co-located with or adjacent to a contact instance, hosted by or adjacent to an Egress forwarder; one or more); **C-NMA** (§3.4.3; standalone or hosted by forwarders/C-PS; leverages RFC 7471/8570/8571 TE metric extensions; one or more); **C-PS** (§3.4.4; uses C-SMA/C-NMA information encoded as metrics plus CS-IDs/CSCI-IDs to select Egress forwarders, possibly contact instances, and the best paths/tunnels considering congestion; integrated in a forwarder or standalone in a PCE/SDN controller); **C-TC** (§3.4.5; associates packets with service requests using CS-IDs or their resolution to locators; ensures all packets of a request go to the same contact instance; CS-IDs may be visible via TLS SNI but not with ECH (RFC 9849) — prefer explicit non-volatile signals (RFC 8558); classified packets are encapsulated; typically in forwarders); **CATS-Forwarders** (§3.4.6; multi-homed sites; if C-PS chose a contact instance and C-TC marked CSCI-ID info, Egress forwards accordingly; if only CS-ID marked, Egress selects a contact instance using its knowledge and observed load; without policy Egress must keep a request on one contact instance; per-instance vs aggregated per-site metrics; aggregated preferred for scale, relies on Egress to pick; Egress may aggregate across sites and choose the best site itself); **Underlay** (§3.4.7; IP/MPLS, not CATS-aware; CATS paths distributed among forwarders only; P routers untouched).

### 2.3 Workflow (§4)
- **Service announcement (§4.1)**: provider assigns CS-ID (may be a network identifier such as an IP address); CS-ID→locator mapping may come from name resolution (DNS), none mandated.
- **Metrics distribution (§4.2)**: C-SMA collects computing capabilities/metrics per CS-ID, aggregates per contact instance or keeps separate, advertises CS-ID+metrics to C-PSes; metrics include compute and service-specific (e.g. number of clients); may change very frequently — distribution frequency is protocol work; options: interval-based, threshold-triggered, policy-based, normalised metrics. C-NMA collects network metrics via existing measurement/routing protocols (extensions may be needed, e.g. link latency), distributes to C-PSes; distributed/centralised/hybrid; routing protocols can dampen state changes (PRC in OSPFv3); C-NMAs configured for update timing like C-SMAs.
- **Service access processing (§4.3)**: C-PS selects paths to Egress forwarders by both metric kinds; C-PS collocated with Ingress or centralised; no algorithm specified — service request or local policy feeds the selection logic (metrics in, contact instance out), enabling service-specific selection; requests are packets of SIP, HTTP, IPv6, SRv6, RTSP carrying CS-ID and parameters; matching C-TC entry → Ingress encapsulates and forwards to the selected Egress; Egress decapsulates and delivers to the contact instance.
- **Affinity (§4.4)**: packets of a flow for a request always to the same contact instance and along the same path (misordering, latency variation); implementation must keep selection and steering consistent per flow, same Egress; configurable per service at deployment or per request; flow definitions vary (RTP audio+video two 5-tuples); protocols for affinity to C-TCs must support flexible, application-independent flow identification; per-service configurable affinity info (identification type/means, timeout); no mechanism defined here.

### 2.4 Operational considerations (§5)
- **Provisioning (§5.1)**: incremental (not all PEs); tasks: give C-PS the locators of Ingress forwarders/C-TCs (or discover); connect C-PS to C-NMAs/C-SMAs; allocate CS-ID/CSCI-ID and bind to contact instances; give C-PS per-service optimisation metrics and policy; configure forwarder encapsulation capabilities and mutual-authentication credentials; reset C-TC classification tables; initial classification rules per capabilities; traffic counters at forwarders for Ingress/Egress correlation. Means: NETCONF, IPFIX, RESTCONF, YANG notifications (extensions out of scope).
- **Supervision/OAM (§5.2)**: expose C-TC classification capabilities; expose forwarder encapsulation capabilities; retrieve active classification tables, steering rules, C-PS policies, forwarder counters; OAM tools to check classification/steering/forwarding and for performance measurement.
- **Deployment (§5.3)**: distributed (metrics among devices via distributed protocols; C-PS in Ingress), centralised (metrics to a central element, e.g. PCE, which computes — possibly pre-computes — paths and syncs with Ingress), hybrid (static capability info distributed, frequently changing utilisation collected centrally; scheduling in controller, Ingress, or both; controller must pass collected path info to Ingress-side C-PS). Single provider only. Appendix A examples.
- **Metrics (§5.4)**: per-instance vs per-site aggregation scalability; normalise (unitless scores) and/or aggregate; placement: normalisation at contact instances (C-SMAs on forwarders are resource-limited), aggregation at C-SMA or contact instances; the same functions must be enabled everywhere (multi-vendor fairness) → a set must be standardised; expose a configuration parameter to activate them.
- **Verification (§5.5)**: log error events; support reachability assessment and path tracing.
- **Impact (§5.6)**: new function to manage cooperation between network and compute elements (e.g. an orchestrator connecting C-SMA and C-NMA); added complexity if not reused.

### 2.5 Security (§6) and privacy (§7)
Frequent compute changes in a routing protocol threaten stability and can be exploited (rapid spawn/delete); solutions must support aggregation, dampening, threshold-triggered updates. Metric information is sensitive (network/compute intelligence, weak spots) and may be tampered with (misdirection to an attacker's instance): authentication and integrity between C-SMA/C-NMA and C-PS and between C-PS and Ingress forwarders; C-SMAs must authenticate the services they report for. Privacy: prevent on-path underlay nodes from fingerprinting/tracking clients; no personal data beyond the client's packet; request↔site binding sensitive when correlatable → encrypt; encrypt C-PS path information in distribution (layer unspecified). Single provider.

### 2.6 Appendix A deployment examples
Distributed: C-SMA co-located with Egress Forwarder 2 advertises (CS-ID 1, CSCI-ID 1/2) metrics; C-SMA at site 3 advertises CS-ID 1/CSCI-ID 3 and CS-ID 2; C-SMA may send to the Egress which redistributes to Ingress, or directly; C-PS in Ingress Forwarder 1 combines with C-NMA metrics; per-site aggregated metrics use a per-site CSCI-ID. Centralised: all C-SMA and C-NMA metrics to a central C-PS which sends paths to Forwarder 1. Hybrid: some metrics (1,2,3) to the central C-PS, others (4,5) directly to the Ingress; Ingress may compute paths for subsequent packets.

## 3. How Arcana could realise each element on FreeBSD

Arcana already has every raw ingredient: agents measure jails and services (`stats`, `services`, `processes`), probes measure tunnels (`sdwan-probes`/`sdwan`), ipfw classifies at UNIs (`sdwan-rules`), steering tables hold ordered candidates with local failover (`sdwan-steer`), tunnels are the overlay, BIRD distributes routes per service, and the console is the central controller. CATS is largely a *policy loop and a data model* on top.

| CATS element | Arcana realisation on FreeBSD |
|---|---|
| Service, service instance, service site | Service = console object with a CS-ID; instance = a jail (or a host service) running the application; site = an Arcana host (or group) behind an edge. |
| Service contact instance | The jail's listening address (or a load balancer jail: nginx/haproxy/Squid, which may fan out to backend instances — RFC §3.4.6's LB case); reachable via the edge = Egress CATS-Forwarder. |
| CS-ID | An IP address (anycast-style: the same prefix/host address announced from every site into the service FIB) or a DNS name resolving to it. The RFC allows "CS-ID may be a network identifier such as an IP address". Alternative: a well-known VIP per service held in an ipfw table. |
| CSCI-ID | The unicast address of the instance jail (or per-site VIP when aggregating per site, per Appendix A.1). |
| Ingress CATS-Forwarder | The edge host at the client's UNI: ipfw classification + `setfib` + steering into a tunnel (overlay encapsulation gre/gif/geneve/wg/IPsec) toward the chosen Egress. |
| Egress CATS-Forwarder | The edge in front of the site: decapsulates, forwards to the contact instance; if only CS-ID is marked, it chooses the local instance (ipfw `fwd` to a chosen jail address per table entry, or routes the CS-ID VIP to one jail). |
| C-TC (classifier) | ipfw rules at the UNI: `lookup dst-ip <cs-id table>` / `dst-port` / `proto` → affinity state (`keep-state`/`record-state` with `limit`), DSCP mark (`setdscp`), FIB, and `fwd <tunnel next-hop>` or a per-service-FIB route. L7 CS-ID (HTTP Host/TLS SNI): not in ipfw; Squid in `sni` mode (`sdwan-proxy`) can act as an L7 C-TC for HTTP(S); ECH defeats SNI as the RFC warns. Non-port flows (ESP, fragments): ipfw `flow` tables keyed on addresses/proto only. |
| C-SMA | The agent: `stats` (CPU, memory, rctl usage per jail), `services` (service state), `processes`, plus a per-instance hook (an HTTP/exec health probe job) for service-specific metrics (connections, queue depth); reports as cblink reads/events to the console. For non-Arcana sites: an exporter jail speaking the same JSON. Normalisation (unitless 0–100 score) done in the agent per §5.4 recommendation (the agent is co-located with the contact instance, not with the forwarder) — configurable function. |
| C-NMA | The agent's probes (`sdwan`: delay, ipdv, loss per tunnel, TCA), BFD state (`network kind=bird`), interface counters/utilisation (`network kind=interfaces`), dummynet queue occupancy. Reported to the console (centralised) and usable locally. |
| C-PS, centralised model | Console: per service, a selection function over (network metric per Ingress→Egress tunnel, compute metric per contact instance), with policy (weights, thresholds, hysteresis); output: ordered candidate lists per Ingress written into `sdwan-steer` (`entries`: table, prefix = CS-ID, candidates = [tunnel id, via]). Paths may be pre-computed (RFC §5.3). |
| C-PS, distributed model | Agent-local: `sdwan-steer` already picks "the first candidate whose far end the probes do not say is down" — extend the agent to re-rank candidates by local probe metrics and by compute scores received via the control plane (BGP: see next row). |
| Distributed metrics via routing (§4.2) | Each site's BIRD instance announces the CS-ID prefix with a BGP attribute encoding the normalised compute score (MED, or an extended community) into the service's iBGP (route reflector, 119-5); BIRD filters at the Ingress set route preference from the attribute; dampening by BIRD `import keep filtered`/route flap damping alternatives (BIRD has no RFD; dampen at the source: threshold-triggered re-announce only). This is the RFC's "metrics carried in a routing protocol" model with its stability caveat (§6). |
| Hybrid model | Static capability (which sites host which CS-ID) via BGP announcements; dynamic load via console → `sdwan-steer`. Matches RFC §5.3 hybrid exactly and today's split (console policy + agent failover). |
| Overlay encapsulation between forwarders | Existing tunnels per service FIB; the underlay (FIB 0, carriers) is untouched (RFC §3.4.7). |
| Service access processing (§4.3) | Ingress: classify → encapsulate → tunnel to Egress; Egress: decapsulate (tunnel interface in service FIB) → route/`fwd` to contact instance. |
| Affinity (§4.4) | ipfw dynamic rules: the first packet of a flow matches the steering rule with `keep-state`, later packets hit `check-state` and replay the parent action (`fwd`/`setfib`) → same Egress and path for the flow's lifetime (state timeouts = affinity timeout, per-service via `set-limit`/`dyn_*` sysctls or per-rule `:name` state sets). Multi-5-tuple affinity (RTP audio+video) = `flow` table keyed by (src-ip, dst-ip) only, or L7 proxy. Steering table changes affect only new flows if the rules are state-first. |
| Egress-side instance choice (§3.4.6) | Egress edge: ipfw `fwd` entries (CS-ID → chosen jail) updated by the agent from local compute metrics (C-SMA co-located), `keep-state` for request affinity; or a load-balancer jail. |
| Service announcement (§4.1) | Console allocates CS-ID (address) and CSCI-IDs; publishes DNS records via `sdwan-dns` (unbound local-data) per service. |
| Provisioning (§5.1) | All via cblink: forwarder locators (edges), C-PS↔agent connectivity (cblink itself), ID allocation (console), per-service optimisation policy (console config), encapsulation capability (`kernel`/`network`), classification reset/initial rules (`sdwan-rules` set swap), counters (ipfw per-rule counters; `ng_netflow` IPFIX export for Ingress/Egress correlation — FreeBSD's netgraph exports NetFlow v5/v9/IPFIX). |
| Supervision/OAM (§5.2) | `network kind=ipfw` returns rules/tables (classification table), steering tables from the kept `sdwan-steer`, C-PS policies from the console, counters; `traceroute`, `capture`, probes for path checks. |
| Metric normalisation/aggregation (§5.4) | Normalise in the agent next to the instance; aggregate per site in the agent or the console; one configurable function set; expose the toggle in the service model. |
| Verification (§5.5) | Events log (`events`, `history`), `traceroute` per FIB, probe traces. |
| Security (§6) | mTLS cblink between agents (C-SMA/C-NMA) and console (C-PS) and between console and Ingress; service authentication: the agent only reports jails it manages (identity by jail name + console-assigned CS-ID binding); dampening/thresholds/aggregation in the console policy; BGP path authenticated (TCP MD5/TCP-AO not in FreeBSD base — MD5 yes). |
| Privacy (§7) | Tunnels encrypted (IPsec/WG) hide client↔site binding from on-path underlay; steering tables travel over mTLS; no client identifiers added beyond the packet. |
| Management plane (§3.3) | Console UI/API; YANG: a small `arcana-cats` module (services, CS-ID, instances, policies, metrics) on top of ietf-routing/ietf-interfaces; IPFIX for counters. |

## 4. Cannot be mapped (and why)

1. **SRv6/MPLS-encoded CATS paths and in-header CS-ID/CSCI-ID metadata (§4.3 mentions SRv6)** — no SR/MPLS; steering is by tunnel choice and ipfw `fwd`, not by programmable path headers. Fine for single-tunnel overlay paths; multi-segment explicit paths are expressed hop by hop (FIB routes on Arcana transit hosts).
2. **L7 CS-ID classification in the forwarding path** — ipfw sees L3/L4 only; TLS SNI/HTTP Host requires the Squid proxy (adds a hop, breaks end-to-end TLS unless SNI-only), and ECH hides SNI entirely; non-volatile explicit signals (RFC 8558) are an application-side choice outside Arcana.
3. **Standardised normalisation/aggregation functions ([CATS-METRICS] still a draft)** — Arcana must pick its own; multi-vendor fairness (§5.4) is unachievable until the draft lands; mark the functions as Arcana-specific.
4. **Routing-protocol distribution of compute metrics with proper damping** — BIRD lacks route flap damping; carrying volatile metrics in MED/communities risks churn (RFC §6); only threshold-triggered announcements at the source mitigate it. The centralised model avoids this.
5. **Flow identification without ports for all cases (§2 "Flow")** — ipfw dynamic state is keyed on the 5-tuple; for ESP/fragments use address-only `flow` tables; IPsec-tunnelled client traffic inside the overlay cannot be classified per inner flow.
6. **Exact per-request (not per-flow) affinity for multi-connection protocols (SIP+RTP)** — needs application awareness (proxy) or address-pair affinity; the RFC itself defines no mechanism.
7. **Per-site metric aggregation at the Egress forwarder "when packets arrive" (§3.4.6 last paragraph)** — Egress-time dynamic choice per packet with state is possible via ipfw `fwd`+`keep-state`, but weighted/ratio-based spreading across instances is not an ipfw primitive (no weighted `fwd`/`nat` round robin); use a load-balancer jail or `ipfw nat` with multiple `redirect_addr`? — `libalias` has no weighted pools; so: proxy jail.
8. **IOAM/path tracing beyond `traceroute`** — none in kernel.
9. **Multi-provider CATS** — out of the RFC's scope and ours.
10. **TCP-AO for BGP sessions** — not in FreeBSD; TCP MD5 only.

## 5. Requirements and recommendations checklist

1. Identify each service by a CS-ID sufficiently unique across the CATS system and independent of the serving contact instance (§3.2, §3.4.1).
2. Identify contact instances by CSCI-IDs (e.g. unicast IP) (§3.2).
3. Provide C-SMA(s) co-located/adjacent to contact instances or Egress forwarders to collect compute/service metrics per CS-ID, optionally aggregated per contact instance or site (§3.4.2, §4.2).
4. Provide C-NMA(s) collecting network state, leveraging existing TE metric mechanisms (§3.4.3).
5. Provide C-PS(es), integrated or standalone (PCE/SDN), selecting Egress forwarders/contact instances and paths from both metric kinds and CS-IDs/CSCI-IDs (§3.4.4).
6. Provide C-TC(s) classifying service requests by CS-ID (or resolved locators) and keeping all packets of a request on the same contact instance; prefer explicit non-volatile signals over SNI (§3.4.5).
7. Ingress forwarders steer along C-PS paths with encapsulation; Egress forwarders deliver, choosing an instance when only CS-ID is marked, and must keep a request on one contact instance absent policy (§3.4.6).
8. Do not require CATS awareness in the underlay (§3.4.7).
9. Announce services by binding CS-IDs to identifiers (DNS or other) (§4.1).
10. Distribute metrics with controlled frequency: interval, threshold, policy, or normalised metrics; configure C-NMAs similarly (§4.2).
11. Keep selection logic pluggable per service/policy (metrics in, contact instance out) (§4.3).
12. Guarantee service contact instance affinity and same-path forwarding per flow; flexible, application-independent flow identification; per-service affinity configuration (type, timeout) (§4.4).
13. Provisioning: forwarder/C-TC locators to C-PS; C-PS↔C-NMA/C-SMA connectivity; ID allocation and binding; per-service metrics and optimisation policy; encapsulation and mutual-authentication credentials; classification table reset and initial rules; traffic counters at forwarders (§5.1).
14. OAM: expose classification and encapsulation capabilities; retrieve classification tables, steering rules, C-PS policies, counters; tools for behaviour checks and performance measurement (§5.2).
15. Support incremental deployment (not all PEs) (§5.1).
16. Choose distributed, centralised or hybrid deployment deliberately (§5.3).
17. Normalise and/or aggregate metrics; place normalisation at contact instances (or C-SMA), aggregation at C-SMA/contact instances; use identical functions everywhere; expose a configuration parameter to activate them (§5.4).
18. Log error events; support reachability assessment and path tracing (§5.5).
19. Provide a function coordinating network and compute elements (orchestrator) (§5.6).
20. Security: guard against metric churn (aggregation, dampening, thresholds); authenticate and integrity-protect C-SMA/C-NMA↔C-PS and C-PS↔Ingress; C-SMAs authenticate the services they report for (§6).
21. Privacy: prevent on-path fingerprinting/tracking; expose no extra personal data; encrypt request↔site bindings when correlatable; encrypt distributed path information (§7).

## 6. Open decisions and trade-offs for Arcana

1. **Deployment model**: centralised (console C-PS writes `sdwan-steer`; simple, consistent, slower, console is a dependency) vs hybrid (console sets candidates and weights; agents re-rank locally from probes and BGP-carried compute scores; faster, risk of inconsistent choices between Ingresses). Recommendation: hybrid, with the console as the only writer of candidate sets and agents choosing among them.
2. **CS-ID representation**: anycast address announced from every site (natural for BGP-based hybrid; conflicts with per-instance CSCI-ID visibility) vs VIP + ipfw table + `fwd` (full control, more rules). Also whether DNS (unbound) publishes CS-IDs.
3. **Compute-metric transport**: cblink only (console-mediated), or additionally BGP attributes via the per-service RR; the latter couples routing stability to load churn (RFC §6) and needs damping we must build at the source.
4. **Normalisation function**: define Arcana's unitless score (e.g. weighted CPU/memory/connections/health) now, versioned, and expose the toggle; migrate to [CATS-METRICS] when published.
5. **Affinity mechanism**: ipfw dynamic state per flow (cheap, kernel-enforced, but state tables scale with flows and fail over with loss of state) vs address-pair tables (coarser, stateless) vs L7 proxy (precise, costly). Per-service choice, default dynamic state.
6. **Egress-side instance choice**: ipfw `fwd` per CS-ID (one instance at a time per Egress, switched by the agent) vs a load-balancer jail per site (weighted spreading, health checks, but a hop and a process). Likely both: `fwd` for small sites, LB jail when more than N instances.
7. **Update cadence and hysteresis**: probe `eval` (1 s) and compute sampling intervals vs steering stability; define dampening in the console policy (min dwell time, hysteresis bands) to avoid oscillation.
8. **Classification of encrypted/ECH traffic**: accept L3/L4 CS-ID only (VIP/port) as the supported path; document that SNI classification is best effort and ECH defeats it.
9. **Counters and correlation**: adopt `ng_netflow` IPFIX export per service FIB at Ingress and Egress for request accounting, or rely on ipfw per-rule counters (cheaper, coarser).
10. **YANG surface**: model CATS objects (service, CS-ID, sites, contact instances, policy, metric functions) as an Arcana module layered on the slice/SD-WAN service model, since the IETF has no CATS YANG yet; keep names aligned with RFC 10053 terms for later alignment.
11. **Security posture for metric sources**: whether non-Arcana exporters (sites not running the agent) are allowed as C-SMAs, and how they authenticate (console-issued certificates via the same CA).
