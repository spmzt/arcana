## 1. Purpose and place in the layered picture

- Operator-perspective framework for using YANG models end to end: **service models** (customer-oriented, 1:1 "pipe"/hose/funnel scope, bidirectional capacity and OWD guarantees), **network models** (operator-oriented, e.g. L3NM: instance name, access interface, protocol type, capacity, RD/RT) and **device models** (interface add, BGP peer, tunnel id, QoS). It defines the term *network model* reused by RFC 9182 and RFC 9408 ("describes a network-level abstraction ... devices and their subsystems and relevant protocols ... across multiple devices").
- Three functional tiers: Orchestrator (service modeling + service orchestration), Controller (network modeling + network orchestration), Device (device modeling). All three are the same operator's. Explicitly: "the architecture does not preclude deployments where the Controller is embedded on a device" — that is Arcana's agent.
- Life cycle (Fig. 4): service level = exposure, creation/modification, assurance, optimization, diagnosis, decommission; network level = specific service creation/modification/assurance/optimization/diagnosis (via multi-layer/multi-domain **service mapping**); device level = **service fulfillment** = intended config provision -> config validation -> performance monitoring -> fault diagnostic, with aggregation upward.
- Key mechanisms named: **service mapping** (L3SM -> RD/RT/VRF in L3NM; L3SM -> TE tunnel/VN), **service decomposition** (network model -> set of device models: BGP, QoS, NI, IP, interfaces), **schema mount** (RFC 8528) to compose device models, **YANG library** (RFC 8525) to learn what a lower layer supports, **NMDA** (RFC 8342) intended vs operational datastores for config validation, **YANG-Push** (RFC 8641) + **ECA policy** for event-based telemetry, **OAM** RPC models (RFC 8531/8532/8533) for diagnosis, alarms (RFC 8632).
- Section 5.1 is the canonical L3VPN flow (Fig. 5/6): customer L3SM -> orchestrator service mapping -> L3NM -> controller service decomposition -> BGP/QoS/Interface/NI/IP device models on PE1/PE2; target adds UNI topology (became RFC 9408 SAP), L3NM notifications and L3NM capabilities flowing up.
- Security: NACM; the "confused deputy" when translating between layers; upper layers must monitor to detect misbehaving lower layers; network models may expose whether encryption is enabled (the `encryption` feature of vpn-common).
- Appendix A inventories the models per layer; useful as the catalogue to align cblink families against (section 3 below).

## 3. Framework elements and candidate Arcana realisation

### 3.1 Tiers

| RFC 8969 element | Arcana today | Target |
|---|---|---|
| Orchestrator: service modeling | Console forms; SD-WAN service (MEF 70.2) | Console owns the customer model; emits L3NM + SAP |
| Orchestrator: service orchestration (service mapping, decomposition across domains) | none | New fleet-level logic (console or `arcanad`): allocate FIB numbers, VNIs, RD/RT, VLAN ids, tunnel endpoints, BIRD instance names |
| Controller: network modeling/orchestration | none; console talks to each agent directly | Either the same fleet-level logic, or one agent elected "controller" per domain |
| Device: device modeling | cblink families on arcana-agent (invidia/*, luxuria/*, ira/*) | Keep; reshape families to mirror ietf-interfaces / ietf-ip / ietf-routing / ietf-acl / ietf-nat / ietf-bgp semantics so decomposition is mechanical |
| "Controller embedded on a device" | this is exactly arcana-agent (root, drives ifconfig/route/ipfw/birdc/swanctl) | keep |

### 3.2 Life cycle (Fig. 4) mapped

| Phase | Arcana realisation |
|---|---|
| Service exposure / catalog | Console: list of service types the fleet can deliver = SAP `sap-network/service-type` (RFC 9408) + feature advertisement per agent (cblink `ctrl getfamily` + a capabilities op) |
| Service creation/modification | Console -> L3NM instance -> per-agent cblink `do` ops (idempotent, versioned). Diff-based modification requires the agent to expose intended config (rc.conf/jail.conf/bird.conf fragments Arcana already writes) |
| Service assurance | gula/probe.c (ICMP probes per tunnel/FIB), gula/stats.c usage sampling, gula/faults.c -> feed `oper-status` + `last-change` of L3NM/SAP; MEF 70.2 objectives as augment |
| Service optimization | SD-WAN policy steering (ipfw tables, dummynet) re-pushed by console on probe results; equivalent to "new VPN policies populated into the network" |
| Service diagnosis (OAM RPCs, RFC 8531/8532/8533) | cblink `do` ops: ping/traceroute per FIB (`setfib N ping`), `birdc show protocols`, BFD session state; a "connectionless OAM" family would be the natural home |
| Service decommission | Delete L3NM `vpn-service` -> teardown ops; needs ordered teardown (routes, BIRD protocol, tunnels, VLANs, FIB release) and reference counting of shared SAPs |
| Intended config provision | sysrc / jail.conf / bird.conf / swanctl.conf writes (persisted) = *intended*; `ifconfig`/`route` live = *applied* |
| Config validation (NMDA intended vs operational) | Arcana already separates persisted vs live for interfaces/rc.conf; a per-family "dump operational" vs "dump intended" distinction (cblink has only one `dump`) is needed |
| Performance monitoring (datastore subscription) | cblink streams (server-to-client push) and mcast-group events ≈ YANG-Push on-change/periodic |
| Fault diagnostic | gula/faults.c, dmesg/syslog events; RFC 8632 alarm semantics (raise/clear, severity) could shape the events family |
| ECA policy on device (Fig. 8) | Agent-local rules (e.g. "probe loss > x% -> swap ipfw table") = closed loop without console; today Arcana's SD-WAN steering decisions live where? If in the agent, this is ECA |

## 4. Cannot be mapped

- MPLS/SR/RSVP-TE tunnel models and TE topology: no FreeBSD data plane. Transport in Arcana is IP tunnels (gif/gre/vxlan/geneve/wg/ipsec) which RFC 9181 covers via `protocol-type`.
- Schema mount / YANG library: cblink has no module composition or capability advertisement beyond `ctrl getfamily` (name, version). Needs a features/capabilities op.
- NMDA intended/operational split: cblink families have one `dump`; a datastore selector attribute would be required.

## 5. Features

None.

## 6. YANG constructs

None directly, but the framework relies on: `augment` (telemetry augmenting VN/TE), schema mount (RFC 8528), YANG-Push subscriptions (RFC 8641) ≈ cblink streams, notifications ≈ cblink `event`, RPC ≈ cblink `do` (OAM, path computation). Policy models (ECA) would need `when`/conditions.

## 7. Open questions / decisions

1. **Closed loop location:** service assurance and optimization at the fleet (console) level vs ECA in the agent. Agent-local ECA (probe -> ipfw table swap) survives console outages; fleet-level sees cross-site state.
2. **Datastores:** add an `intended`/`operational` discriminator to every dump (e.g. a common `datastore` attribute or two ops per family) or keep Arcana's "persisted vs live" ad hoc per family.
3. **Capabilities:** advertise per-agent features (vpn-common features, BIRD version, presence of pimd, kernel MROUTING) through a cblink capabilities family so the orchestrator can do service feasibility (RFC 9408 §1, RFC 8969 §3.2).
4. **Diagnosis RPCs:** create one OAM family (ping/traceroute/bfd-state/bgp-state per FIB) modelled after RFC 8532/8533 rather than per-subsystem ad hoc ops.
5. **Multi-domain:** will Arcana ever orchestrate across two fleets (NNI)? If yes, L3NM `underlay-transport` and SAP NNI roles must be kept; if no, drop them from the family to keep it small.
