# RFC 8525 — YANG Library

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc8525.txt (March 2019, Standards Track, obsoletes 7895, 1795 lines, read in full).

## Purpose
Operational-state module `ietf-yang-library` through which a server advertises the YANG
modules (with revision, namespace, features, deviations, submodules, location URLs), the
datastores it supports and the schema (module-set union) of each datastore. NMDA-aware
(each datastore may have a different schema); legacy `/modules-state` (RFC 7895) kept as
deprecated and SHOULD still be populated for old clients. Mandatory for RESTCONF servers
(RFC 8040 §10) and for NETCONF 1.1 module advertisement (RFC 7950 §5.6.4). Also the
mechanism schema mount (RFC 8528) uses inside each mount point.

## Objectives (section 2)
Per module: name, revision, submodules, features, deviations. Per datastore: identity and
schema. Design criteria: cacheable (content-id); dynamic datastores may implement modules
not in conventional datastores; a module may be omitted from `<operational>`; **one revision
per module across all datastores**; multiple revisions only as import-only; usable under
schema mount.

## Data model (section 3) — tree verbatim
```
module: ietf-yang-library
  +--ro yang-library
     +--ro module-set* [name]
     |  +--ro name                  string
     |  +--ro module* [name]
     |  |  +--ro name         yang:yang-identifier
     |  |  +--ro revision?    revision-identifier
     |  |  +--ro namespace    inet:uri
     |  |  +--ro location*    inet:uri
     |  |  +--ro submodule* [name]
     |  |  |  +--ro name        yang:yang-identifier
     |  |  |  +--ro revision?   revision-identifier
     |  |  |  +--ro location*   inet:uri
     |  |  +--ro feature*     yang:yang-identifier
     |  |  +--ro deviation*   -> ../../module/name
     |  +--ro import-only-module* [name revision]
     |     +--ro name         yang:yang-identifier
     |     +--ro revision     union            (revision-identifier | "" )
     |     +--ro namespace    inet:uri
     |     +--ro location*    inet:uri
     |     +--ro submodule* [name]
     |        +--ro name        yang:yang-identifier
     |        +--ro revision?   revision-identifier
     |        +--ro location*   inet:uri
     +--ro schema* [name]
     |  +--ro name          string
     |  +--ro module-set*   -> ../../module-set/name
     +--ro datastore* [name]
     |  +--ro name      ds:datastore-ref
     |  +--ro schema    -> ../../schema/name
     +--ro content-id    string

  notifications:
    +---n yang-library-update
       +--ro content-id    -> /yang-library/content-id
```
- module-set: an arbitrary grouping; no semantics attached; need not be referentially
  complete. `module` = implemented modules (7950 §5.6.5) with features and deviation
  modules (a deviation module MUST NOT deviate itself); `import-only-module` = modules used
  only for imports (several revisions allowed).
- schema: a union of module-sets; MUST be valid and referentially complete; a non-import-only
  module in several sets MUST have identical revision/features/deviations.
- datastore: one entry per supported datastore (`ds:datastore-ref` identity); entries with
  the same schema SHOULD reference the same schema entry.
- content-id: MUST change whenever anything else in `/yang-library` changes; no requirement
  that the same content gives the same id; triggers `yang-library-update`.
- Deprecated legacy: `/modules-state { module-set-id; module*[name revision] { name,
  revision, schema (uri), namespace, feature*, deviation*[name revision], conformance-type
  implement|import, submodule*[name revision] } }` and notification `yang-library-change`.
- Typedef `revision-identifier` = `\d{4}-\d{2}-\d{2}`.

## Examples (appendices B, C)
Basic server: module-set `config-modules` (ietf-interfaces 2018-02-20, ietf-ip 2018-02-22,
import-only yang/inet types) and `state-modules` (ietf-hardware + iana-hardware import);
schemas `config-schema` = {config-modules}, `state-schema` = {config-modules, state-modules};
datastores startup/running → config-schema, operational → state-schema.
Advanced server: ietf-routing with features `multiple-ribs`, `router-id` only in
`<operational>` (so router-id is readable but not configurable), a dynamic datastore
`ex-ds-eph:ds-ephemeral` with its own schema, datastore-specific deviations in the
operational schema.

## Relevance to Arcana / cblink
1. The YANG library is the **discovery protocol** that replaces cblink's `ctrl getfamily`
   (family name → id, ops, groups): the agent exposes `/yang-library` listing its modules
   (ietf-interfaces, ietf-ip, ietf-routing, ietf-network-instance,
   ietf-logical-network-element, ietf-yang-schema-mount, arcana-jails, arcana-services, …),
   features (e.g. `if-mib`, `arbitrary-names`, `pre-provisioning`, `ipv4-non-contiguous-netmasks`,
   `multiple-ribs`, `router-id`, `bind-network-instance-name`, `bind-lne-name`), deviations
   (e.g. a FreeBSD deviation module removing nodes FreeBSD cannot provide), and the
   datastores (running, operational, maybe an `arcana:live` dynamic one). The console caches
   it by `content-id` and refreshes on `yang-library-update`.
2. **SIDs and the YANG library.** RFC 9595 §1 notes that for CORECONF "the transport of
   YANG module SIDs might be unnecessary" but a *constrained YANG library*
   (draft-ietf-core-yang-library) exists: it adds SID-range information per module so a
   client can map SIDs. For Arcana the console and agent are built from the same `.sid`
   files, but a conformant design should still publish, per module, the `.sid` file
   location (the `location` leaf-list may point to the module and, by convention, to its
   `.sid`) or an Arcana augmentation `arcana:sid-file` on `module`. Without a SID-level
   check a mismatch between console and agent SID tables is silent — the `content-id` MUST
   therefore include the SID file versions, and the cblink `hello` should carry it.
3. Under schema mount (per-host or per-jail mount points) each mount point instance MUST
   contain its own `ietf-yang-library` instance; for `shared-schema` all instances have
   the same content-id.
4. Size: for a dozen modules this is ~2–4 KiB of CBOR; cacheable; fits a single cblink
   frame.
