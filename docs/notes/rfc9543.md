# RFC 9543 — A Framework for Network Slices in Networks Built from IETF Technologies

Read in full: 2421 lines, fetched from https://www.rfc-editor.org/rfc/rfc9543.txt (HTTP 200).
Informational, March 2024. Farrel, Drake (eds.), Rokui, Homma, Makhijani, Contreras, Tantsura.
Local copy: `scratchpad/rfc/rfc9543.txt`.

## 1. Purpose

RFC 9543 defines the term "IETF Network Slice" (to be cited by other documents as
"RFC 9543 Network Slice") and the general framework for requesting and operating one. A
slice is connectivity between a set of Service Demarcation Points (SDPs) *plus* a set of
commitments on network resources (bandwidth, latency, jitter, loss, availability), over a
shared underlay built from IETF technologies. The document separates the *service* the
customer asks for (technology-agnostic: SDPs, connectivity constructs, SLOs/SLEs) from the
*realisation* in the provider network (technology-specific: partitioning resources with
VPN, TE, queuing, etc.). It names the components (Orchestrator, Network Slice Controller
(NSC), Network Controller), the interfaces between them, the vocabulary of objectives
(SLI/SLO/SLE/SLA), the realisation pipeline (underlay → Filtered Topology → Network
Resource Partition (NRP) → slice), isolation, composition, monitoring, security and
privacy. It is deliberately not prescriptive about technologies; it hands realisation to
RFC 9732 (enhanced VPNs), ACTN (RFC 8453), SFC (RFC 7665) and future YANG models
(the network-slice service model draft).

## 2. Architecture and terminology (complete)

### 2.1 Core terminology (§3)

| Term | Definition (as the RFC gives it) |
|---|---|
| Customer | Requester of a slice service; may be an enterprise, an operator, a person, an application, or another division of the same operator; may request SLO monitoring. |
| Provider | The organisation that delivers the service and controls the resources of the network that is sliced (physical or itself virtual). |
| Customer Edge (CE) | Customer device attached to the provider: routers, switches, firewalls, RAN/Core nodes, load balancers, header-enrichment proxies, PEPs. May be provider-managed. |
| Provider Edge (PE) | Provider device a CE attaches to; CE↔PE is many-to-many. |
| Attachment Circuit (AC) | Technology-specific channel CE↔PE. Customer and provider agree which L2/L3 header/payload field values identify to which {slice service, connectivity construct, SLOs/SLEs} a packet belongs. Policing/shaping per connectivity construct on the AC, in both directions; excess traffic is dropped by default unless an out-of-profile policy is agreed. The AC may be inside or outside the service (§5.2). |
| Service Demarcation Point (SDP) | Where the service is delivered to the customer: a CE, a PE, a device, a software component or an abstract virtual function. Unique identifier within a slice service (IP, MAC); same identifier may be reused across services. May be abstracted as a Service Attachment Point (SAP, RFC 9408). |
| Connectivity Construct | A set of SDPs plus a communication type (P2P, P2MP, A2A). Constructs may be grouped administratively. |
| IETF Network Slice Service | The function delivered to the customer; technology-agnostic. |
| IETF Network Slice | The realisation in the provider's network by partitioning resources and applying tools and techniques (§4.1, §7). |
| SLI | A quantifiable measure (throughput in bit/s, latency in ms). |
| SLO | A target or range for an SLI ("SLI <= target", "lower <= SLI <= upper"); customer can verify by measurement. |
| SLE | An unmeasurable (by the customer) request: diversity, isolation, geography, security. May become an SLO once verifiable. |
| SLA | The explicit or implicit contract: set of SLOs and SLEs per connectivity construct per sending SDP to the set of receiving SDPs, with tolerances, commercial terms and consequences. |
| NSC | Network Slice Controller. |
| Orchestrator | Composes services/resources; talks to the NSC; may sit on the customer side or the provider side. |
| Network Controller | Infrastructure controller offering resources to the NSC; may be an existing technology-specific controller. |
| Ancillary CE | An extra sender/receiver inside or attached to the provider network that is not a customer site (IPTV/DNS server, hub, service function); resolvable address or placeholder resolved at realisation time; it is an SDP. |
| Filtered Topology | Operator-selected subset of underlay nodes/links by capability (security, geography, colour) used as candidate underlay for NRPs. Optional. |
| NRP | A subset of the buffer/queuing/scheduling resources and associated policies on each of a connected set of links in the underlay. Possibly the whole underlay (one NRP). Dedicated or shared topology. |

### 2.2 The slice and its service (§4)

- Slices are created to meet bandwidth, latency, latency variation and other requirements; creation is initiated by a management system/application in response to an actual or logical service request; once created they are monitored, modified, deleted.
- The underlay must be able to change device configuration on demand (in-band signalling or controllers).
- Slices may be combined hierarchically (a slice sliced again) or sequentially (slices of several networks stitched end to end, e.g. 3GPP TN slices).
- Service = set of SDPs + one or more connectivity constructs between subsets of SDPs + SLOs/SLEs *per sending SDP per construct*. A provider may limit a service to one construct (then several services are needed for several constructs) — a free deployment choice.
- "Carrier's carrier" is allowed: a customer resells slices.
- Per SDP the parties agree which end of the AC is the SDP, hence whether the AC is subject to the SLOs/SLEs.

#### Connectivity constructs (§4.2.1)
- **P2P**: one sender, one receiver; like a private wire/tunnel; SLOs apply at the sender (implicitly at the receiver).
- **P2MP**: one sender, many receivers; like a P2MP tunnel or multi-access VLAN segment; one SLO/SLE set at the sender.
- **A2A**: any sender to any set of receivers; implies routing by the provider; may carry unicast, multicast or broadcast; the provider may limit A2A to unicast; realisation (multicast in the core, ingress replication, hub-and-spoke) is out of scope. SLOs apply per sending SDP regardless of receivers; a sender "may be disappointed" if a receiver is oversubscribed; use P2P for pairwise specifics.
- A sending SDP may be in several constructs with different SLOs/SLEs in each.

#### Mapping traffic flows (§4.2.2)
- Unicast → P2P (direct) or A2A (provider routes); P2MP for unicast is unusual.
- Bidirectional unicast = two P2P constructs; an additional SLE may demand fate sharing.
- Multicast → set of P2P, one P2MP, a mix, or A2A; replication location is the operator's choice and invisible to the customer.
- MP2P = multiple P2P; egress may receive from all ingresses at once; the provider cannot coordinate policing across distinct sources, so the customer must size SLOs with the receiver's capacity in mind.
- MP2MP = set of P2MP, or A2A with multicast, or hub-and-spoke where the hub is an SDP or an ancillary CE.
- The senders' SLOs define the receivers' load; constructs need not map 1:1 to tunnels.
- Multi-homed CE: single-active (one AC) or all-active (traffic distributed across ACs).

### 2.3 System characteristics (§5)

#### Common SLOs (§5.1.1.1), "directly measurable objectives"
1. Guaranteed Minimum Bandwidth (bit/s, unidirectional, at any time).
2. Guaranteed Maximum Latency (one-way, RFC 7679, excluding application latency).
3. Maximum Permissible Delay Variation (PDV per RFC 3393).
4. Maximum Permissible Packet Loss Ratio (RFC 7680).
5. Availability (uptime / (uptime + downtime), uptime meaning all SLOs met; stated with the measurement period and the maximum single downtime).

Other SLOs (§5.1.1.2): MTU, traffic type (IPv4, IPv6, Ethernet, unstructured), application-aware behaviours (via network functions). Future YANG models may define them precisely.

#### Common SLEs (§5.1.2.1), "indirectly measurable objectives"
- **Security**: encryption or security techniques between SDPs (e.g. only MACsec links; ESP for TS 33.210, HIPAA, PCI).
- **Geographic restrictions**: avoid a country, etc.
- **Maximal occupancy level**: number of flows admitted and optionally countable resource units (IP/MAC addresses); must say whether per service, per subset or per construct.
- **Isolation**: unaffected by other services' bursts (see §8).
- **Diversity**: different constructs on different underlay resources.
SLEs apply per construct and direction but are commonly applied to all constructs of a service.

#### SDP placement (§5.2, Figure 1), four scopes
1. Inside the CE (CE provider-operated): slice may use CE buffers/queues.
2. Up to the CE including the AC but no CE resources: slicing the AC needs tagging (VLAN) or policing at the AC ends.
3. Customer-facing port on the PE: port-based VPN style; each port or virtual port (VLAN tag) identifies the slice/SDP.
4. Inside the PE: the PE classifies AC traffic by IP addresses, protocol, ports, etc.
Choice is the operator's; may be asymmetric per SDP. Mapping to a specific construct, when an SDP sources several, uses the same mechanisms. SDP characteristics: ingress/egress point; unique id in the customer context; provider associates provider-scope identifiers (IP, VLAN tag, MPLS label, interface/port, node id); mapped to endpoints of services/tunnels/paths during realisation; the NSC uses the provider-scope identifiers.

#### Composition (§5.3)
Hierarchical (recursive; multi-layer vertical) and sequential (stitched; data planes may differ). Decomposed slices are independently realised and managed.

### 2.4 Framework (§6)

- Stakeholders: Orchestrator, NSC, Network Controller, plus customer and provider (§6.1).
- Intents (§6.2): the customer says *what*, not *how*; limited or no visibility into topology, even inside one administrative domain (security, layering, scalability). Abstraction per RFC 7926. Mechanisms for the Service Interface: PCEP/GMPLS UNI (binary TLV), NETCONF/RESTCONF (XML/JSON), gRPC/gNMI (protobuf); YANG for modelling. Existing models may need augmentation; feasibility checks before requests may be needed.
- **NSC functions (§6.3)**:
  1. Expose a technology-agnostic Service Interface for create/modify/delete carrying SDPs, SLO parameters (and monitoring thresholds), input selection (filtering), policies, selected SLEs with parameters; plus monitoring.
  2. Determine an abstract topology connecting the SDPs meeting the criteria; retain the mapping abstract→underlay for monitoring.
  3. Mapping Functions: agnostic requests → technology-specific config; filtering/selection info → underlay entities that classify traffic to construct/slice; treatment → underlay entities meeting SLOs/SLEs.
  4. Collect telemetry (OAM results, statistics, states) for all elements of the abstract topology.
  5. Evaluate performance against SLOs and expose it to the customer; notifications when thresholds are reached.
- Interfaces (§6.3.1, Fig. 2/3): **Service Interface** (customer system ↔ NSC; technology-agnostic; config, policies, operational state, status/performance), **Network Configuration Interface** (NSC ↔ Network Controllers; technology-specific; built on existing IETF network models), plus the Network Controllers' **Device Configuration Interface**; the three correspond to Service Model / Network Service Model / Device Model of RFC 8309. The customer system may equal O-RAN's SMO.
- Service Interface data model must include at least: SDP and connectivity information, SLO/SLE specification, status information (§6.3.1.1).

### 2.5 Realisation (§7)

Figure 4 pipeline, bottom up: **Underlay (physical or virtual) network** → provisioned by Network Controllers (RFC 8309) → optional **Topology Filter** producing **Filtered Topologies** (preselect links/nodes by security, geography, colour; offline or dynamic) → **Resource Partitioning** producing **NRPs** → **Grouping/Mapping** of connectivity constructs onto NRPs → slices as seen by the customer.

Rules stated:
- An NRP is a subset of buffer/queuing/scheduling resources and policies on each of a connected set of links; amount and granularity are operator policy; dedicated or shared topology; any existing or new technology.
- One or more constructs from one or more slices map to an NRP; **a construct maps to exactly one NRP** (many-to-one); all traffic of the construct is in that NRP; **all PEs connected by a construct must be present in its NRP**.
- An NRP may be chosen for its SLO/SLE support, construct support, or administrative reasons; one NRP per construct is allowed (scaling implications); all constructs of a slice may share one unshared NRP.
- NRPs may use work-conserving or non-work-conserving schedulers (RFC 3290 §2) — technology specific.
- Steps may be in any order and iterative; the underlay may be extended.

Procedures (§7.2): (1) NSC exposes capabilities; (2) customer may ask feasibility — yes/no, with hints on what would be possible; (3) customer requests; NSC answers created/not, with hints; (4) NSC maps request to capabilities, applies provider policy, creates or supplements the NRP. The service definition never changes with the realisation technology.

Applicability: ACTN VNs over a TE underlay (§7.3, [ACTN-NS]); enhanced VPNs (§7.4, now RFC 9732); IP/MPLS marking with labels/SIDs and *aggregation* of constructs under one marking to scale (§7.5, no solution cited); SFC (§7.6): expose ancillary CEs, capture SFC requirements with performance metrics, run SF placement, generate classification rules (same as or distinct from slice identification rules) and SFC forwarding policies, provision Classifiers and SFFs; data plane NSH (RFC 8300), MPLS NSH (RFC 8596), NSH+SR (RFC 9491).

### 2.6 Isolation (§8)
Requirement side: an SLE; the customer cannot generally verify it. Realisation side: resource partitioning from dedicated allocation to sharing with safeguards; traffic separation by L3VPN/L2VPN/EVPN; interference avoidance by capacity planning, dedicated resources, policing/shaping, prioritisation; service continuity by backup paths and dedicated resources for selected slices.

### 2.7 Management, security, privacy (§9–§11)
Instrumentation and dynamic reconfiguration; conformance to customer security constraints expressed as SLEs; strong NSC authentication to every network it spans; both interfaces secured with authentication, authorisation and auditing; it must not be possible to attack a slice by loading other slices (delay attacks on latency-bound services, compute contention for virtual functions); reduce exposure of realisation information; customers needing confidentiality should bring their own IPsec; privacy: one customer must not discover another or see sites outside its slice.

### 2.8 Appendix examples
A.1 MP2P as three P2P constructs; A.2 SFC with ancillary CEs (known ACE, several ACEs, or a placeholder "ServiceFunction" resolved by the operator); A.3 hub-and-spoke under customer control (hub as ancillary CE; P2P mesh via hub or P2MP via hub replication); A.4 L3VPN as one A2A construct realised as P2P mesh / hub-and-spoke; A.5 hierarchical (NSC of operator requests a slice from a carrier's NSC; virtual link); A.6 horizontal (NNIs appear as SDPs of each network's slice; a Coordinator binds them).

## 3. How Arcana could realise each element on FreeBSD

Arcana today (MEF 70.2 phases 1–6, per `docs/PLAN-119-SASE.md` and the `sdwan-*` operations in `share/arcana/arcana.yaml`): a FIB per service on each edge; gre/gif/geneve/wg tunnels, IPsec where asked; ICMP probes (delay, ipdv, loss, TCA); ipfw classification/steering with local failover (`sdwan-rules`, `sdwan-steer`); breakout, NAT, dummynet bandwidth; BIRD per service (`sdwan-bird`), iBGP between edges. That is already an RFC 9543 realisation in miniature; the mapping below says which role each existing piece plays and what is missing.

| RFC 9543 element | Arcana realisation on FreeBSD |
|---|---|
| Customer / Orchestrator | A console tenant/role; the console's JSON API (or a future YANG/RESTCONF northbound) is the Service Interface. |
| NSC | The console ("orchestrator" in NAMING.md), which compiles a service document into per-edge configuration. |
| Network Controller + Device Configuration Interface | The same console process acting per host, and `arcana-agent` over cblink. The cblink family *is* the device model; the YANG redesign should make it a device model in RFC 8309 terms (ietf-interfaces/ietf-ip/ietf-routing + Arcana modules for ipfw, dummynet, tunnels, BIRD). |
| Slice Service | The SD-WAN service (MEF 70.2 SWVC) object in the console: SDPs = UNIs, constructs, SLOs/SLEs = the service's performance policy. |
| Slice (realisation) | On each edge: the service FIB (`setfib`), the tunnels of that service, the ipfw set with tables (`sdwan-rules`), the dummynet objects (`pipe/queue/sched config`), the BIRD instance. |
| SDP | A UNI on an edge host. Placement 3 (customer-facing port) = the UNI interface or a VLAN subinterface (`if_vlan`) identifying the slice; placement 4 (inside PE) = ipfw rules classifying by 5-tuple/DSCP into the slice (`setfib N`, `queue N`). Placement 1 is available when the CE is itself an Arcana host or a vnet jail. Provider-scope identifiers: interface name, VLAN id, FIB number, ipfw table name, tunnel id. |
| AC | The UNI's physical or VLAN interface. Policing/shaping per construct both ways: ipfw `pipe` (shaper) or netgraph `ng_car` (token-bucket policer: CIR/CBS/EBS, colour-aware) attached via `ipfw ... netgraph` / `ngtee`; `in recv ifX` and `out xmit ifX` select direction. Excess dropped by default = dummynet queue overflow or ng_car red action. |
| P2P construct | A classifier (ipfw table entry: src prefix at SDP A → dst prefix at SDP B) steering into one tunnel (A→B) with a dedicated dummynet queue on the tunnel's egress; reverse direction is a second construct. |
| P2MP construct | No overlay multicast in the kernel path today. Hard caps: `pipe N config bw X` for policing/out-of-profile. Admission control arithmetic in the console: sum of commitments <= link rate. |
| Guaranteed maximum latency SLO | Only *measured* end to end (probes); *bounded* only for the queueing component on Arcana-owned hops: a `prio` scheduler (`sched N config type prio`, `queue ... pri P`) or a high WF2Q+ weight plus small queue sizes (`queue ... slots S` / `bytes B`) and AQM (`codel`, `pie`, `fq_codel`, `fq_pie` scheduler types or queue options). The transit underlay (Internet) is not ours. |
| Max delay variation SLO | Measured by probes (`ipdv`); influenced by the same priority/AQM configuration. |
| Max loss ratio SLO | Measured by probes; controlled by queue sizing and AQM; `plr` on a pipe is deliberate loss, never used for a slice. |
| Availability SLO | Computed by the console from the probe/BFD state history (`state`, `since` in the `sdwan` read; `sdwan-tunnel` events) per construct, over the SLA window, with the maximum single downtime. |
| MTU SLO / traffic type | Tunnel kind and MTU per service (gre/gif/wg = IP only; geneve/vxlan = Ethernet); `ifconfig mtu`; path MTU checked by probes with `size`. |
| Security SLE | Tunnels under IPsec (strongSwan IKEv2 today; manual SAs planned in 119-3) or WireGuard; "only encrypted links" = the console's Filtered Topology admits only encrypted tunnels for that slice. MACsec: not in FreeBSD. |
| Geographic SLE | Edge hosts and WAN links tagged with location/provider in the console; the Filtered Topology excludes tagged links. Beyond our hops the Internet path is unknown; cannot be promised. |
| Maximal occupancy SLE | ipfw `limit {src-addr|dst-addr|...} N` (dynamic-state count per key), `set-limit` for dynamic rules, table size limits, DHCP pool size (`sdwan-dhcp`), BIRD `import limit`/`receive limit` for prefixes. |
| Isolation SLE | Separate FIB (data plane), separate BIRD instance (control plane), separate ipfw set/tables (policy), dedicated dummynet queues on every Arcana link (resource), separate tunnels (path); console-side admission control; optional dedicated WAN interface per slice tier. See "cannot" for its limits. |
| Diversity SLE | The console picks disjoint WAN interfaces/tunnels (different underlay providers) for two constructs; steering candidate lists (`sdwan-steer`) kept disjoint. SRLG knowledge only as far as our edges. |
| Filtered Topology | Console-side graph of hosts, interfaces, tunnels with attributes (encrypted, provider, region, rate, measured delay); a slice tier selects a subset. |
| NRP | A named set of dummynet scheduler+queue objects (same numbering) on every link of a Filtered Topology, plus the tunnel set; constructs of several slices share one NRP by sharing the same queue; `(tunnel, DSCP)` or VLAN acts as the NRP identifier across Arcana links (see §4). |
| Construct→NRP many-to-one; all PEs present | Console invariant checks: each construct references one NRP; every edge of the construct has that NRP's queues configured and a tunnel in the NRP's set. |
| Telemetry | `sdwan` read (probes), `network kind=ipfw` (`rules` counters, `qos` queues/pipes), `network kind=interfaces` counters, `network kind=bird` (BFD, BGP), events (`sdwan-tunnel`, TCA), per-rule byte/packet counters as per-construct SLIs; netgraph `ng_netflow` → IPFIX for flow accounting. |
| Feasibility query (step 2) | Console computes: bandwidth admission on known links; measured delay/loss history of candidate tunnels vs the requested SLO; returns yes/no with "what would fit" (lower rate, other edges). |
| Capability exposure (step 1) | Agent `hello`/`kernel`/`network` tell which modules (dummynet, netgraph nodes, wg, ipsec, geneve) exist; console publishes supported SLO/SLE set. |
| Hierarchical composition | A slice whose "underlay" is another Arcana slice: vnet jails as CEs inside edges, or a second console consuming the first's service as a virtual link. Possible with the existing jail/vnet plumbing. |
| Sequential composition / NNI as SDP | A border edge host whose "UNI" is an NNI to another domain's edge; needs a Coordinator above two consoles. Not built; the SDP model allows it. |
| SFC / ancillary CEs | Service functions as jails in the service FIB (already: unbound via `sdwan-dns`, Squid via `sdwan-proxy`, Suricata via `sdwan-ids` with `divert`); classification by ipfw; forwarding by `fwd`/`divert`/`netgraph`. No NSH; chaining is by routing/`fwd` hops, not a service path header. |
| Hub-and-spoke under customer control | The hub as a jail or edge host with routes in the service FIB; P2P constructs to the hub. Trivial in the FIB model. |
| Security considerations | cblink over mTLS, per-host certificates from the console CA (`arcana-enrol`); console WebAuthn; audit of jobs (`history`, `events`); no customer visibility of other services (console authorisation per tenant). |

Marking choices available in the kernel for identifying slice/construct traffic on Arcana links (RFC §7.5 wants a packet marking): DSCP (6 bits; `setdscp` action, `dscp` match), IPv6 flow label (20 bits; `flow-id` match; set only by the sending host's stack), VLAN id/PCP per Ethernet link (`if_vlan`, PCP fixed per VLAN interface), the tunnel itself (one tunnel per NRP), `ipfw tag` (host-local mbuf tag, lost on the wire). No MPLS label, no SRv6 SID, no NRP IPv6 option.

## 4. Cannot be mapped (and why)

1. **Packet-marked NRP/slice identifiers in the IP/MPLS sense (§7.5)** — MPLS labels, SR SIDs, resource-aware segments, the IPv6 NRP/VTN-ID option: FreeBSD has no MPLS or SRv6 forwarding and ipfw cannot act on hop-by-hop options; adding either is kernel work Arcana does not do (decision 119-4). Only DSCP, VLAN, flow label (host-set, unenforced) and "a tunnel per NRP" remain; DSCP gives at most 64 classes, so NRP count per link is bounded.
2. **Guaranteed maximum latency / PDV as an *enforced* SLO across the underlay** — the Internet or carrier path between edges is not ours; we can only measure and steer. Even on our own hops dummynet is a software scheduler in a general-purpose kernel (timer granularity, interrupt jitter, no worst-case per-hop calculus); we can shape and prioritise, not prove a bound.
3. **Non-work-conserving time-based scheduling** (TSN 802.1Qbv/Qch, FlexE channels, CBS of 802.1Qav): no kernel support; dummynet `pipe bw` is a rate shaper, the only non-work-conserving element available.
4. **ALTQ (CBQ/HFSC/PRIQ/FAIRQ/CODEL)** — needs a custom kernel (`options ALTQ*`, not in GENERIC) and attaches to pf, not ipfw; Arcana is ipfw-based and does not ship kernels. Not used.
5. **MACsec as a Security SLE** — not in FreeBSD.
6. **P2MP tunnels / multicast in the core with resource reservation** — no mLDP/P2MP-TE; IP multicast routing needs `ip_mroute.ko` + pimd (port) and gives no reservation; realised as ingress replication or L2 netgraph fan-out instead.
7. **Geographic SLE beyond Arcana hops** — the underlay provider's routing is invisible; promises are limited to which of our edges/links are used.
8. **Isolation SLE as a hard guarantee** — NIC queues, CPU, interrupt processing and the shared tunnel path are not partitioned per slice; dummynet isolates bandwidth share, not host CPU or the carrier's queues. Per-slice dedicated interfaces help; per-slice NIC rings/RSS from user space are not configurable.
9. **Fate-sharing SLE for bidirectional P2P** — the two directions may be steered independently by the two edges; fate sharing is a console policy (same tunnel both ways), not something the data plane enforces.
10. **SFC with NSH (RFC 8300/8596/9491)** — no NSH in kernel; chaining only by routing hops/`fwd`/`divert`.
11. **ACTN TE underlay (§7.3)** — no RSVP-TE/PCEP; ACTN VN concepts are only partly reusable (the console's abstract topology).
12. **One-way latency per RFC 7679** — probes are ICMP round trips halved; true one-way needs synchronised clocks (PTP: ports only, software timestamps) and a TWAMP/STAMP reflector (not in base; would be a small user-space daemon of ours). See the DetNet notes.
13. **Customer-verifiable isolation / in-network SLI for transit** — no IOAM in kernel.

## 5. Requirements and recommendations checklist

(Informational RFC; these are the framework's stated obligations and "must/should" level statements for an NSC and a realisation.)

1. Separate the service (what) from the realisation (how); the service definition must not change when the realisation technology changes (§4, §7.2).
2. Express a service as SDPs + connectivity constructs (P2P/P2MP/A2A) + SLOs/SLEs per sending SDP per construct (§4.2).
3. Every SDP has a unique identifier within the service; the provider binds provider-scope identifiers (addresses, VLAN, interface, node) to it (§3.2, §5.2).
4. Agree per SDP where the demarcation is (CE, AC, PE port, inside PE) and so whether the AC is subject to the SLOs (§4.2, §5.2).
5. Customer and provider agree which header fields map a packet to {service, construct, SLO/SLE} on the AC (§3.2).
6. Police/shape per construct on the AC in both directions; drop excess by default unless an out-of-profile policy exists (§3.2).
7. Support at least the common SLOs: min bandwidth, max latency, max PDV, max loss ratio, availability (with period and max single outage) (§5.1.1.1).
8. Support SLE selection and parameters where agreed: security, geography, max occupancy (state its scope), isolation, diversity (§5.1.2).
9. The Service Interface must be technology-agnostic and carry at least SDP/connectivity info, SLO/SLE spec and status (§6.3.1.1); customers get no underlay topology (§6.2).
10. The NSC must: expose capabilities; answer feasibility queries with yes/no and hints; create/modify/delete; determine and retain the abstract topology and its mapping; map filtering info and treatment to underlay entities; collect telemetry; evaluate SLOs and notify on thresholds (§6.3, §7.2).
11. Use the three-model structure of RFC 8309 (service / network / device) for the interfaces (§6.3.1).
12. A connectivity construct maps to exactly one NRP; all PEs of the construct are in that NRP (§7.1).
13. NRPs may use work-conserving and/or non-work-conserving schedulers as the SLOs require (§7.1).
14. Filtered Topologies are optional; slices may be hosted directly on the underlay (§7.1).
15. Where many slices exist, aggregate constructs under common markings/behaviours to scale (§7.5).
16. Realise isolation by partitioning (dedicated or safeguarded sharing), traffic separation (VPN), interference avoidance (planning, policing, shaping, prioritisation) and continuity (backup paths) (§8.2).
17. Instrument the realisation; support dynamic reconfiguration (§9).
18. Strong authentication of the NSC toward every network; authentication, authorisation and auditing on both interfaces (§10).
19. Make it impossible to degrade a slice by loading another (policing, planning); limit exposure of realisation details (§10).
20. Customers must encrypt themselves if they need confidentiality; the provider does not guarantee it (§10).
21. Privacy: no customer learns of another, no site visible outside its slice (§11).
22. Ancillary CEs (service functions, hubs, servers) are SDPs; placeholders are resolved at realisation (§4.2.3, §7.6).

## 6. Open decisions and trade-offs for Arcana

1. **Northbound model**: adopt the TEAS network-slice service YANG (draft-ietf-teas-ietf-network-slice-nbi-yang, cited by RFC 9732) as the console's Service Interface and map MEF 70.2 onto it (SWVC ↔ slice service, UNI ↔ SDP/SAP per RFC 9408, policy performance criteria ↔ SLOs, encryption/breakout rules ↔ SLEs), or keep MEF 70.2 vocabulary and offer the slice model as a view. The RFC supports both; one source of truth is needed.
2. **1:1 or N:1 slice:construct**: the RFC lets us limit a service to one construct. Arcana's A2A FIB model already gives N:1 cheaply; P2P constructs with pairwise SLOs multiply dummynet queues per tunnel (65535 queue numbers per host, but console bookkeeping grows).
3. **Default SDP placement**: VLAN-per-slice on the UNI (placement 3, simple, customer-visible tag) vs 5-tuple classification (placement 4, flexible, more rules). Suggest 3 by default, 4 as an option per UNI.
4. **NRP granularity**: one NRP per slice (strongest isolation, most state) vs a few tiers (e.g. three WF2Q+ schedulers per link shared by many slices, as RFC 9732 §4.4 recommends for scale). DSCP's 64 codepoints and ipfw's 32 sets (0–31; `sdwan-rules` uses one) push toward tiers.
5. **"Guaranteed minimum bandwidth" semantics**: WF2Q+ queue weight (work-conserving; borrows idle capacity; guarantee only holds if the scheduler's `bw` equals the real link/tunnel rate) vs a `pipe` hard cap (predictable, wastes capacity). Tunnel rates are not known: measure (probes with `size`, interface counters) or declare per WAN link.
6. **DSCP trust at the UNI**: trust the customer's marking, remark per construct (`setdscp`), or map into the tunnel outer header only (gre/gif copy inner TOS; wg sets DSCP per its own policy). Affects whether transit providers see our class.
7. **One-way metrics**: keep ICMP RTT/2 or build a STAMP (RFC 8762) reflector/sender in the agent (user space, raw UDP, allowed) plus PTP/NTP discipline; without hardware timestamps accuracy is ~tens of µs at best — enough for ms-level SLOs, not for DetNet.
8. **Availability window**: define measurement period and max single outage in the service document; decide if BFD (119-1) or probes drive "downtime".
9. **Isolation tiers**: "shared" (queue weight), "dedicated queue + tunnel", "dedicated WAN interface" — expose as SLE levels and price/limit them, since hard isolation is not achievable.
10. **Hierarchical slicing via vnet jails**: whether an edge may host customer CEs as jails (SDP placement 1) — powerful, but blurs the trust boundary the architecture doc defends.
11. **Multi-domain**: a Coordinator over several consoles (A.6) is a later product decision; design the SDP/NNI data model so it is not precluded.
12. **Feasibility arithmetic**: how conservative admission control is (sum of CIRs vs measured utilisation vs statistical multiplexing); reject rather than silently accept (RFC 8578 §11.3.1 agrees).
