# RFC 7951 — JSON Encoding of Data Modeled with YANG

Source: /tmp/claude-0/-home-user-arcana/c5b51962-0391-52a9-87d4-18bb94158d90/scratchpad/rfc/rfc7951.txt (August 2016, Standards Track, 1123 lines, read in full).

## Purpose
Defines how YANG data trees (config, state, rpc/action input/output, notifications) are
encoded as JSON text, following I-JSON (RFC 7493) as closely as possible. It is the
encoding RESTCONF uses for `application/yang-data+json` and the format Arcana's console
north-bound API must speak to be "YANG-conformant JSON". All rules except anydata also apply
to YANG 1.0.

## Rules

### Names and namespaces (section 4)
- `member-name = [identifier ":"] identifier`; the prefix is the **module name** (never the
  YANG prefix); submodule items use the main module's name.
- Namespace-qualified form MUST be used for every member of the top-level object and whenever
  the node's module differs from its parent's; simple form MUST be used otherwise.
  (`{"example-foomod:top": {"foo": 54, "example-barmod:bar": true}}`.)
- The same qualified-name form is used inside identityref and instance-identifier values.

### Data nodes (section 5) — top-level structure is always an object; UTF-8
| Node | JSON |
|---|---|
| leaf | name/value; value is string, number, `true`/`false`, or `[null]` per type |
| container | name/object |
| leaf-list | name/array of scalars; ordered-by MUST be observed |
| list | name/array of objects; entries' member order is arbitrary (keys need not come first, unlike XML); ordered-by MUST be observed |
| anydata | name/object; content MUST be valid I-JSON, member names per the ABNF, arrays either all unique scalars (leaf-list) or all objects (list), `null` only inside `[null]` |
| anyxml | name/any I-JSON value |
| metadata | members whose name starts with `@` (RFC 7952) — out of scope here |

### Types (section 6)
| YANG type | JSON |
|---|---|
| int8/16/32, uint8/16/32 | JSON number |
| **int64, uint64, decimal64** | **JSON string** with the YANG lexical form (`"123"`, `"2.57"`) — I-JSON says numbers outside IEEE double range must be strings |
| string | JSON string |
| boolean | `true` / `false` literals |
| enumeration | JSON string = enum name |
| bits | JSON string = space-separated set bit names |
| binary | JSON string, base64 (RFC 4648 §4; NOT base64url, the one deviation from I-JSON) |
| leafref | as the referenced leaf's type |
| identityref | JSON string = identity name, module-qualified when defined in a different module than the leaf (`"iana-if-type:ethernetCsmacd"`); simple or qualified otherwise |
| empty | `[null]` (an array with one null — chosen so that languages treating null members as absent still see it) |
| union | encoded per the member type; **JSON type information participates in member resolution**: `"bar": 13.5` for union{uint16,string} is an error (number not uint16), `"bar": "1"` is a string |
| instance-identifier | JSON string, XML-like path but with module-name qualification rules: leftmost name always qualified; later names qualified only when the module changes; same in predicates. `/ietf-interfaces:interfaces/interface[name='eth0']/ietf-ip:ipv4/ip` |

### I-JSON compliance (section 7)
UTF-8; member names unique within an object; member order never relied on; all YANG numbers
exchangeable reliably (64-bit as strings). Only deviation: base64 instead of base64url.

### Security (section 8)
Receivers SHOULD reject messages not complying with these rules.

## Appendix A example (ietf-interfaces + ex-vlan) — the shape the console must produce
```
{"ietf-interfaces:interfaces": {"interface": [
   {"name": "eth0", "type": "iana-if-type:ethernetCsmacd", "enabled": false},
   {"name": "eth1", "type": "iana-if-type:ethernetCsmacd", "enabled": true, "ex-vlan:vlan-tagging": true},
   {"name": "eth1.10", "type": "iana-if-type:l2vlan", "enabled": true, "ex-vlan:base-interface": "eth1", "ex-vlan:vlan-id": 10},
   {"name": "lo1", "type": "iana-if-type:softwareLoopback", "enabled": true}]},
 "ietf-interfaces:interfaces-state": {"interface": [
   {"name": "eth0", "type": "iana-if-type:ethernetCsmacd", "admin-status": "down", "oper-status": "down",
    "if-index": 2, "phys-address": "00:01:02:03:04:05",
    "statistics": {"discontinuity-time": "2013-04-01T03:00:00+00:00"}}, ...]}}
```

## CBOR ↔ JSON translation table (what the console must do between cblink and the browser)
| | YANG-CBOR (9254, id=sid) | YANG-JSON (7951) |
|---|---|---|
| key | SID delta (int) | module-qualified or simple name — needs SID → schema node → (module, name) and the parent's module to decide qualification |
| int64/uint64 | CBOR int | decimal string |
| decimal64 | tag 4 [exp, mantissa] | decimal string with `.` and `fraction-digits` digits (canonical: no trailing zeros, at least one digit each side) |
| enumeration | int value | name string (needs the enum table) |
| bits | byte string / skip array | space-separated names ordered by position |
| binary | byte string | base64 |
| identityref | SID (uint) | `module:name` (qualified when module ≠ leaf's module) |
| empty | null | `[null]` |
| instance-identifier | SID or [SID, keys…] | XPath-like string with module names; needs the schema to rebuild the path and to know which ancestor list each key belongs to, and the key types to render the predicate values (`[name='eth0']`, `[.='v']`, `[3]`) |
| union | tagged members (43–46) | per member; JSON type participates |
| list | array of maps | array of objects |
| leaf-list | array | array |
| anyxml | any CBOR | any I-JSON (lossy for byte strings/tags: JSON has no bytes → base64 by convention) |
Every row needs the compiled schema on the console side; the translation cannot be done by
a schema-less CBOR→JSON converter. This is the core argument for the console linking the
same generated schema tables as the agent.
